# SMB Lending Lens: 系统提示词

> 教会 AI 成为领域专家——通过一份精心设计的系统提示词。

---

## 概览

你已经探索了数据库，理解了业务数据。现在问题来了：**如何把这些知识教给 AI？**

答案是 **系统提示词（System Prompt）**——一份将通用 LLM 转变为专业贷款分析 BI Agent 的文档。

这节课研究一份真实的系统提示词，教你 AI Agent 提示词工程的艺术。核心不是把所有东西都塞进去——而是知道什么该写、什么不该写，然后相信模型自己能搞定剩下的。

---

## 学习目标

为什么这很重要？因为系统提示词是你的领域专业知识与 AI 能力相遇的地方。写得不好，你的 Agent 要么一无所知（指导太少），要么晕头转向（信息太多）。写得好，你就能解锁一个真正理解你业务的 AI。

完成本课后，你将能够：

1. 理解 AI Agent 系统提示词的目的和结构
2. 知道哪些信息要包含，哪些让模型自己去发现
3. 区分「必须知道」的概念和「能自己搞清楚」的细节
4. 把这些原则应用到你自己的场景中

## 核心概念

### 提示词工程的悖论

核心挑战是这样的：LLM 能力很强，但需要指导。指导太少，它会产生幻觉或者错过领域特定的细节。指导太多，它又会被淹没、忽略指令、或者失去灵活性。

关键在于找到平衡点。

**信息太多会怎样：**

- 模型被冲突或冗余的信息搞糊涂
- 重要指令被噪音淹没
- 模型只是机械地遵循指令字面意思，却错过了真正的意图
- 回答变得僵硬、公式化

**信息太少会怎样：**

- 模型发明出与你业务不符的概念
- 它做出听起来合理但实际错误的假设
- 术语偏离你组织的标准
- 关键边界情况处理不当

目标是提供**恰到好处**的结构，同时信任模型的底层能力。

### 系统提示词的结构

一个设计良好的系统提示词有四个层次：

**1. 身份和范围**

告诉模型它是谁，能做什么、不能做什么。这设定了边界。

```
You are SMB Lending Lens BI Agent, a read-only database assistant...
```

**2. 核心领域概念**

解释模型必须理解的基本业务概念。这些是不会变的「游戏规则」。

- 贷款生命周期（客户 → 申请 → 贷款 → 还款）
- 风险等级系统（各等级含义、定价方式）
- 关键术语（「违约」在这个场景下的具体定义）

**3. 衍生业务概念**

这些是需要特定公式计算的指标。如果你不指定，模型可能会猜错。

- 实际违约率 = COUNT(defaults) / COUNT(loans)
- 定价差距 = implied_default_rate - actual_default_rate
- 逾期还款率 = COUNT(days_late > 0) / COUNT(payments)

**4. 技术模式**

SQL 模式、陷阱、以及领域特定的约定。

- 如何避免 SQLite 整数除法的 bug
- 什么时候用 LEFT JOIN vs INNER JOIN
- 输出格式标准

### 什么该写，什么不该写

这是需要经验的地方。这里有一个框架：

**必须包含（模型自己搞不清楚的）：**

- 业务特定的术语和定义
- 带有精确公式的计算指标
- 与常规假设不同的领域规则
- 从名称看不出来的表关系

**可以省略（相信模型的）：**

- 基础 SQL 语法（模型懂 SQL）
- 通用数据库概念（join、聚合）
- 对数据的常识推理
- 探索性分析技巧

**例子：定价差距（Pricing Gap）**

模型一般知道什么是「违约率」。但它不知道：

- 你公司用 `implied_default_rate` 来定价
- 比较隐含违约率和实际违约率能发现定价问题
- 差距为负 = 定价过低 = 亏钱

所以你必须明确定义「Pricing Gap」。但你不需要解释什么是减法。

### 工具层

系统提示词也定义了可用的工具：

1. **get_database_schema** — 让模型探索数据库结构
2. **execute_sql_query** — 执行查询并获取结果
3. **write_debug_report** — 记录推理过程

注意什么**没有**在这里：没有「get_all_table_relationships」或「explain_business_context」工具。为什么？因为这些信息已经在提示词里了，模型可以即时引用。

工具用于运行时数据访问。提示词用于领域知识。

### 例子：恰到好处，不要过多

看看系统提示词如何处理风险等级：

```
| Grade | Credit Score Range | Interest Rate | Implied Default Rate |
|-------|-------------------|---------------|---------------------|
| A (Prime) | 720-850 | 5.5% | 3.0% |
| B (Near Prime) | 680-719 | 7.5% | 6.0% |
...
```

包含这个表是因为：

- 模型不可能知道你公司具体的等级划分边界
- 隐含违约率是业务决策，无法推导出来
- 这个信息在分析中会频繁使用

但提示词不解释什么是信用分、利率怎么运作、或者「prime」在贷款里是什么意思。模型已经知道这些。

### SQL 模式：用例子来教

提示词为每个衍生指标都包含了 SQL 例子。为什么？

因为展示比讲述更有效。与其写：

> 「计算违约率时，用违约事件的数量除以贷款数量，乘以 100，在 SQLite 中使用 1.0 或 100.0 来强制浮点除法...」

你直接写：

```sql
SELECT ROUND(100.0 * COUNT(de.id) / COUNT(l.id), 2) AS actual_default_rate
FROM loan l
LEFT JOIN default_event de ON l.id = de.loan_id
```

这个例子教会了：

- 精确的公式
- SQLite 浮点数技巧（100.0 而不是 100）
- 用于可选关系的 LEFT JOIN 模式
- 命名约定（actual_default_rate）

全部都不需要冗长的解释。

### 安全和边界

提示词包含安全约束：

```
- **Read-only**: Only SELECT queries allowed
- Never attempt UPDATE, INSERT, DELETE, or DROP
```

这很关键。你在给 AI 访问数据库的权限。清晰的边界防止灾难。

但注意什么**没有**在这里：没有长篇解释为什么这很重要，没有威胁评估，没有安全策略文档。只有清晰的规则。

## 反思：平衡的艺术

写系统提示词就像给一个非常聪明但刚入职的新同事写文档：

- 他们智商高、能力强
- 他们从例子中学得很快
- 他们需要知道你公司特定的术语
- 他们不需要重新解释基础概念
- 他们会用合理的假设填补空白（但可能是错的）

你的工作是给他们恰好足够的信息让他们高效工作，而不是淹没他们。

**提示词太长的信号：**

- 指令被忽略
- 行为变得不一致
- 模型看起来对优先级「糊涂」

**提示词太短的信号：**

- 模型发明非标准术语
- 计算与你的预期不符
- 边界情况处理不当

没有完美的提示词。迭代是预期中的。从你认为必要的开始，测试它，观察失败，然后调整。

## 导师笔记

**为什么这节课重要：**

系统提示词是人类专业知识与 AI 能力相遇的地方。任何人都能调用 LLM API。但构建一个真正理解你领域的 AI Agent——那需要知识转移的技能。

这个技能会越来越有价值。随着 AI 工具普及，区分因素不会是「你能用 AI 吗？」而是「你能教 AI 做你的工作吗？」

**关键洞察：**

- 少即是多。信任模型的基线能力。
- 计算指标需要精确定义。业务逻辑不能靠猜。
- 展示，不要讲述。SQL 例子胜过冗长解释。
- 清晰边界防止灾难。安全规则要明确。
- 没有完美的提示词。期待迭代。

**个人观察：**

我见过工程师把整套文档塞进系统提示词，以为信息越多性能越好。实际不是这样。模型会迷失。信号被噪音淹没。

我写过的最好的提示词出人意料地短。它们专注于这个领域独特的东西，其他的都信任模型。

把它想象成给专家顾问做简报。你不会给 CPA 解释会计基础。你解释的是你公司的会计科目表、你的报表惯例、你的边界情况。这就是系统提示词设计的心态。

## 快速参考

**提示词结构：**

- 身份和范围（agent 是谁，能做什么）
- 核心领域概念（业务基础）
- 衍生指标（带公式的计算值）
- 技术模式（SQL 惯用法、陷阱）
- 安全边界（什么是禁止的）

**平衡法则：**

- 包含：业务特定定义、计算指标、领域规则
- 省略：模型已经知道的基础概念

**设计问题：**

- 「聪明的新员工需要解释这个吗？」
- 「模型可能合理地猜错吗？」
- 「这是规则还是可推导的事实？」
