# 看懂界面文案的那条管线

## 1. 目标

**先搞清楚这一篇在整条线上的位置, 否则它读起来像是莫名其妙开始讲一个配置文件格式.**

回到第 2 篇那个承诺: 一到两小时把这个 app 整个换成另一个行业的 app. 界面上有几百句话全是
这个行业特有的, 换领域时它们都得重写. 这一篇回答的就是: 它们该住在哪儿, 才让那次重写是
可控的.

答案是一条硬规矩: **组件里一个字的业务文案都不许写, 全部集中在一个文件里.** 散着就意味着
换领域要全仓库搜一遍再逐处判断, 而那件事人做会漏, 让 AI 做更会漏, 并且**漏了不报错**.

重心不是记住文件在哪, 是看懂一次**有代价的取舍**. 这份文案本可以写成 TypeScript, 那样编译器
会免费帮你查字段名和图标名; 换成 TOML 就等于把这个安全网扔了. 扔掉换来的是一个数据集的全部
产出集中在一个目录里, 换领域时改的是一个目录而不是散落全仓库的字符串.

**关键在于扔掉的东西被一件件补回来了**, 而不是就这么算了. 所以这一篇的练习 2 要你亲手去
触发那两个补回来的检查, 看它们真的拦得住, 也看它们报错报得有多具体.

还有一条要记住: 这一层的坑**几乎全是静默的**. 空标题, 错图标, 错位的 key, 印了两遍的欢迎语,
没有一个会让程序崩. 所以改完文案两条命令都要跑, 只跑一条是最常见的漏.

---

## 2. 要做的事情

1. 读完 README, 重点是概览里那张散着和集中的对比表, 三段路径, 两个构建期检查, 和组件里
   不许拼句子那一节.
2. 打开 `data/site.toml` 从头扫到尾, 认一遍它分成哪几节, 每节对应界面上的哪一块.
3. 打开 `lib/site/schema.ts`, 找到那份必填 key 清单, 数一数有多少条.
4. 打开 `lib/site/load.ts`, 找到那两个会抛异常的检查, 各读一遍它们报错时说了什么.
5. 对 README 练习 1 里那六样东西各判断一次该进文案文件还是该写死在组件里, 然后去仓库里
   对答案.
6. 开一个叫 `09-copy-lives-in-one-file` 的 branch, 下面几步都在它上面做.
7. 改一句正常的文案: 把 agent 页输入框的提示语改成别的句子, 起开发服务器确认它真的变了.
8. 把 `[brand]` 那节的 `footerName` 整行注释掉, 跑 `mise run build-web`, 读那条报错.
9. 恢复那一行, 再把某张能力卡的 `icon` 改成一个不存在的名字, 再跑一次构建, 读那条报错.
10. 全部恢复, 跑 `mise run cli-check-content` 和 `mise run build-web` 两条, 确认都过.

**预计用时:** 60 到 85 分钟

## 3. 检查清单

- [ ] **这一篇在干什么**: 你能说清它是在为换掉整个业务领域做准备, 并解释文案散着的时候
      让 AI 去改会坏在哪里.
- [ ] **三段路径说得清**: 你能说出解析, 校验, 渲染三段各由谁做, 各交出什么, 以及哪一个产物
      是唯一穿过 server 和 client 边界的.
- [ ] **取舍讲得出**: 你能说清这份文案为什么是 TOML 而不是 TypeScript, 代价是什么, 收益是
      什么, 以及为什么这笔交易划算.
- [ ] **两个检查各拦过一次**: 你亲手制造过一次缺 key 和一次错图标名, 见过两条报错, 然后
      恢复了.
- [ ] **报错的信息量**: 你能说出图标名那条报错除了坏名字还给了你什么, 以及这为什么重要.
- [ ] **两条命令的分工**: 你能说清 `check-content` 和 `build-web` 各查什么, 为什么两条都要跑.
- [ ] **拼句子的症状**: 你能说清把一句话拆在文案文件和组件里会坏成什么样, 以及为什么测试
      全绿也发现不了.
- [ ] **归属判得对**: 那六样东西你都判断过归谁, 并和仓库里的实际位置对过答案; 你也能说出
      TOML 里普通字段为什么必须写在数组表之前.
- [ ] **工作区干净**: 练习改的每一处都恢复了, `git status` 没有留下改动.
