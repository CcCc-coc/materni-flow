# 看懂界面文案的那条管线

## 1. 目标

上一篇里页面反复在做一个动作, 读盘拿文案. 这一篇讲那条路径的全貌, 以及一条听起来像洁癖但
分量很重的规矩: **组件里一个字的业务文案都不许写.**

这一篇的重心不是记住文件在哪, 是看懂一次**有代价的取舍**. 这份文案本可以写成 TypeScript,
那样编译器会免费帮你查字段名和图标名; 换成 TOML 就等于把这个安全网扔了. 扔掉换来的是一个
数据集的全部产出集中在一个目录里, 换领域时改的是一个目录而不是散落全仓库的字符串.

**关键在于扔掉的东西被一件件补回来了**, 而不是就这么算了. 所以这一篇的练习 1 要你亲手去
触发那两个补回来的检查, 看它们真的拦得住, 也看它们报错报得有多具体.

还有一条要记住: 这一层的坑**几乎全是静默的**. 空标题, 错图标, 错位的 key, 印了两遍的欢迎语,
没有一个会让程序崩. 所以改完文案两条命令都要跑, 只跑一条是最常见的漏.

---

## 2. 要做的事情

1. 读完 README, 重点是三段路径那张表, 两个构建期检查, 和组件里不许拼句子那一节.
2. 打开 `data/site.toml` 从头扫到尾, 认一遍它分成哪几节, 每节对应界面上的哪一块.
3. 打开 `lib/site/schema.ts`, 找到那份必填 key 清单, 数一数有多少条.
4. 打开 `lib/site/load.ts`, 找到那两个会抛异常的检查, 各读一遍它们报错时说了什么.
5. 改一句正常的文案: 把 agent 页输入框的提示语改成别的句子, 起开发服务器确认它真的变了.
6. 把 `[brand]` 那节的 `footerName` 整行注释掉, 跑 `mise run build-web`, 读那条报错.
7. 恢复那一行, 再把某张能力卡的 `icon` 改成一个不存在的名字, 再跑一次构建, 读那条报错.
8. 全部恢复, 跑 `mise run check-content` 和 `mise run build-web` 两条, 确认都过.
9. 对 README 练习 2 里那六样东西各判断一次该进文案文件还是该写死在组件里, 然后去仓库里
   对答案.

**预计用时:** 60 到 85 分钟

---

## 3. 检查清单

- [ ] **三段路径说得清**: 你能说出解析, 校验, 渲染三段各由谁做, 各交出什么, 以及哪一个产物
      是唯一穿过 server 和 client 边界的.
- [ ] **取舍讲得出**: 你能说清这份文案为什么是 TOML 而不是 TypeScript, 代价是什么, 收益是
      什么, 以及为什么这笔交易划算.
- [ ] **两个检查各拦过一次**: 你亲手制造过一次缺 key 和一次错图标名, 见过两条报错, 然后
      恢复了.
- [ ] **报错的信息量**: 你能说出图标名那条报错除了坏名字还给了你什么, 以及这为什么重要.
- [ ] **两条命令的分工**: 你能说清 `check-content` 和 `build-web` 各查什么, 为什么两条都要跑.
- [ ] **拼句子的症状**: 你能说清把一句话拆在文案文件和组件里会坏成什么样, 以及为什么测试
      全绿也发现不了.
- [ ] **数组表的坑**: 你能说出 TOML 里普通字段为什么必须写在数组表之前, 写反了会怎样.
- [ ] **归属判得对**: 那六样东西你都判断过归谁, 并和仓库里的实际位置对过答案.
- [ ] **工作区干净**: 练习改的每一处都恢复了, `git status` 没有留下改动.
