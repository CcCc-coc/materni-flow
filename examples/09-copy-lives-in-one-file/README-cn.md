# 界面上每一句话都住在一个文件里

> 前端一个字的业务文案都不许内联. 这条规矩听起来像洁癖, 但它是那个一到两小时换掉整个业务
> 领域的承诺里, 分量最重的一条.

## 1. 概览

上一篇里页面反复在做一个动作: 读盘拿文案, 然后当 props 传下去. 这一篇讲那条路径的全貌.

界面上你看到的每一个字, 从导航栏的名字到底部的版权行, 从四张能力卡的标题到输入框的提示语,
全都在 `data/site.toml` 这一个文件里. 组件只负责摆放, 不负责拼句子.

这一篇讲三件事: ** 这条路径是怎么走的, 为什么选了一个会丢掉编译器检查的格式, 以及丢掉的那些
检查由谁补上.**

---

## 2. 学习目标

先算一笔账, 因为这条规矩的代价和收益都很具体.

**代价**: 这份文案是 TOML 格式的. 如果写成 TypeScript, 编译器会免费帮你查字段名和图标名,
写错当场标红. TOML 没有这个待遇.

**收益**: 一个数据集的全部产出集中在 `data/` 一个目录里. 换业务领域时, 你改的是一个目录,
而不是一堆散落在二十个组件里的字符串.

这笔交易划算, 判据是**两边分别在什么时候帮到你**: 编译期检查是在你**写的时候** 帮你一次,
目录集中是在**每一次换数据集和每一次 review** 时帮你. 后者发生的次数多得多.

但代价要真的被补上, 不能就这么丢掉. 所以这一篇有一半在讲那两个补回来的检查.

学完这个 Task, 你将能够:

1. 描述一句文案从磁盘到浏览器的三段路径, 说出每一段交出什么
2. 解释为什么这份文案是 TOML 而不是 TypeScript, 以及这个选择的代价是什么
3. 说出两个构建期检查各拦住什么, 不拦的话会静默地坏成什么样
4. 说清组件里为什么不许拼半句话, 并举出破坏它之后的具体症状
5. 认出 TOML 数组表那个不报错只错位的坑

## 4. 你将学到什么

一条三段式的内容管线, 加两个你会亲手触发一次的构建期检查.

带走的那句话是: **一句话拆在两个文件里, 就没有任何一个地方能看出它读起来是什么样.**

---

## 5. 三段路径

一句文案从磁盘走到浏览器要过三步, 每一步交出的东西都有名字.

| 段 | 谁做的 | 交出什么 | 说明 |
| :--- | :--- | :--- | :--- |
| 解析 | `lib/site/load.ts` 的 `loadSite()` | 一个未经检查的普通对象 | 把人写的 TOML 文件读进来变成 JavaScript 对象. 它**碰文件系统, 所以是 server only**, 而且结果按进程缓存, 同一次构建里问第二次不会再读盘 |
| 校验 | 同一个函数里的两个检查 | 一个可以放心用的配置对象 | TOML 换掉 TypeScript 之后补回来的那道关. 两个检查都**直接抛异常**, 所以构建真的会被拦住 |
| 渲染 | server component 把它当 props 传下去 | 烘死在产物里的静态 HTML | 两个页面都是构建期静态生成的, 所以产物里是写死的字符串, 请求时不读盘 |

这条路径的要点全在中间那个产物上: **它是唯一穿过 server 和 client 边界的东西.** 浏览器里
显示的每一个字都来自它, 而它在构建结束的那一刻就冻住了.

推论: **客户端组件不许自己去读配置.** 不是因为麻烦, 是因为读文案那个函数碰文件系统, 而
浏览器里根本没有文件系统.

---

## 6. 为什么是 TOML 而不是 TypeScript

这份文案曾经是一个 TypeScript 文件, 换成 TOML 是一个**有代价的选择**, 值得把两边都说清楚.

| | 写成 `.ts` | 写成 `.toml` |
| :--- | :--- | :--- |
| 编译器查字段名和图标名 | **免费给你** | 没有 |
| 数据集的产出在哪 | 散在前端代码树里 | **集中在 `data/` 一个目录** |
| 换数据集是什么形状 | 一个跨目录的 diff | **一个目录替换** |
| 谁来写这份文件 | 得懂一点 TypeScript | 会写配置文件就行 |

关键在第二行和第三行. 这份文案**属于数据集, 不属于前端**. 把它留在前端代码树里, 一次换数据
集就变成散落全仓库的改动, 没有人能一眼确认改全了没有. 而把一个数据集的全部产出 (文案, 说明,
提示词, 数据) 收进同一个目录, 换数据集就退化成一次目录替换. 这和第 6 篇里擦教学痕迹退化成
删目录是同一个思路.

编译器不查, 就由加载时来查. 那正是下一节.

## 7. 两个构建期检查

它们都在 `lib/site/load.ts` 里, 都会抛异常, 所以 `mise run build-web` 真的会被拦住.

### 检查一: 必填 key 不能少

`lib/site/schema.ts` 里有一个叫 `REQUIRED_SITE_KEYS` 的清单, 用点号路径列出了这份文件必须
declare 的每一个 key, 从 `brand.displayName` 一直到 `chat.messages.waitForResponse`, 二十
多条. 加载时逐个查, 少一个就报出**缺的 key 名和文件路径**.

**不查的后果是静默的**: TOML 不被类型检查, 所以缺一个 key 的结果是组件收到一个空值, 然后
在线上渲染成一个空标题. 页面不报错, 只是有一块地方什么都没有.

### 检查二: 图标名必须存在

`lib/icons.ts` 里显式列出了这份文案能用的全部图标名. 四张能力卡各自点名一个图标, 加载时逐个
比对, 拼错就报出**坏名字和全部合法名字**.

**不查的后果同样是静默的**: 拼错的图标会渲染成一个中性的兜底图形. 卡片看着好好的, 就是配错
了图, 没有人会注意到.

### 两个都只有构建才查得到

**`mise run check-content` 查不到这两样.** 那条命令读的是 `data/` 里的散文, 这两个检查读的
是同一批文件经过前端加载器的样子. 两者查的东西不重叠.

所以改完文案**两条命令都要跑**:

```bash
mise run check-content
mise run build-web
```

只跑前一条是最常见的漏, 于是一个拼错的图标名安静地上了线.

## 8. 组件里不许拼句子

文案文件里每一条都是**一句完整的话**, 组件原样打印它:

这一条是一句完整的话, 横幅原样打印它:

```toml
welcomeMessage = "I'm here to help you with SMB lending analytics."
```

不要把它写成半句, 再让组件补上另外半句:

```jsx
// 不要这样
I'm here to help you with{" "}<span>{site.chat.messages.welcomeMessage}</span>.
```

**一句话拆在两个文件里, 就没有任何一个地方能看出它读起来是什么样.** 改 TOML 的人看不到框架,
改组件的人看不到值, 两边各自都对, 拼起来是
`I'm here to help you with I'm here to help you with ...`.

这类错误**不报错, 不失败, 测试全绿**, 只有真的打开页面读那一行的人才会发现. 这个仓库真的
出过一次, 代价是聊天页的欢迎语在屏幕上印了两遍.

同一条规矩还有一个推论: **换数据集的人只该动 `data/`.** 一旦句子的一半住在组件里, 换领域
就必须去改 TypeScript, 而那正是这套设计承诺不需要发生的事.

### 哪些字不算文案

有几处的文字确实写死在组件里, 而且**应该写死**, 判据还是那条老规矩: 换个业务领域, 它要不
要改?

| 文字 | 在哪 | 为什么不进文案文件 |
| :--- | :--- | :--- |
| 导航条上的 Home 和 Start Chat | `Navigation.tsx` | 这个 app 有几个页面是脚手架的事实, 不是数据集的 |
| 头像方块里那两个字母 | `AssistantAvatar.tsx` | 要塞进一个很小的方块, 而数据集可以给 agent 起一个很长的名字 |
| 思考中和加载中 | `message.tsx` 与两个 `loading.tsx` | 描述的是运行状态, 不是业务 |
| 关闭这类无障碍标签 | 多处 | 给读屏软件用的标签, 不是展示文案 |

## 9. TOML 有一个坑

这一条不写下来一定会踩.

**一旦开始一个数组表, 后面每一个不带节名的 key 都属于该数组的最后一个元素.** 所以每一节的
普通字段必须写在数组表**之前**.

对的写法, 普通字段全在数组表之前:

```toml
[chat]
agent = "Lending Lens"
inputPlaceholder = "Ask about the loan book..."

[[chat.suggestedActions]]
title = "..."
```

错的写法, 而且不报错:

```toml
[chat]
[[chat.suggestedActions]]
title = "..."
agent = "Lending Lens"     # 这一行现在属于上面那个按钮, 不属于 chat
```

写反了不报错, 只会**静默错位**: 那个 key 跑到了别的地方, 而它原来该在的位置变成了缺失, 于是
你收到的是必填 key 检查的报错, 而报出来的 key 名和你刚改的地方看起来毫无关系.

文案文件顶部的注释专门写了这一条, 因为它是这个格式最容易咬人的地方.

## 10. 那份长说明为什么原样返回

`data/` 下面还有一个文件: `business-context.md`, 首页那个说明覆盖层的正文.

读它的函数只做一件加工: **剥掉 HTML 注释**. 除此之外原样返回, 一个字都不解析.

**故意不解析**, 因为它由 chat 页那个同一个 Markdown 渲染器来渲染. 所以在这个文件里写一个
mermaid 围栏, 覆盖层里就真的会画出一张图, 而这一层加载代码完全不知道图这个概念存在.

**为什么要剥注释**: 那个 Markdown 渲染器没装解释 HTML 的插件, 所以它不会把 HTML 注释当注释,
而是原样打印出来. 一句写给下一个作者的备注, 会变成访客读到的一段正文. 在这里剥掉而不是禁止
在文件里写注释, 是为了让作者的批注能留在有用的地方.

那 12 条 kickstart 按钮各自带的那个 `render` 字段这一篇不展开, 它属于一份三方契约的一部分,
第 29 篇 (渲染契约) 会一次讲完.

## 11. 练习

### 练习 1: 让那两个检查各拦你一次

**目标:** 亲眼确认丢掉的编译器检查真的被补回来了.

**怎么做:**

1. 先改一句正常的文案: 打开 `data/site.toml`, 把 `[chat]` 那节的 `inputPlaceholder` 改成别的
   句子, 起开发服务器打开 agent 页确认它变了
2. 把 `[brand]` 那节的 `footerName` 那一整行注释掉, 跑 `mise run build-web`, 读报错
3. 恢复那一行, 把某张能力卡的 `icon` 改成一个不存在的名字比如 `Banana`, 再跑一次构建, 读报错
4. 全部恢复, 跑 `mise run check-content` 和 `mise run build-web` 两条确认都绿

**你会观察到:**

第 2 步报出的是缺失的 key 名和文件路径. 第 3 步报出的是坏名字, **以及全部合法名字的清单**,
所以你不用去翻源码就知道该填什么. 另外注意第 4 步里 `check-content` 对这两种错误一声不吭,
只有构建拦得住.

> **关键洞见:** 一个检查值不值钱, 看它报错的时候给了你多少信息. 报一句配置有误, 和报出坏
> 名字加全部合法名字, 是两种完全不同的东西.

### 练习 2: 判断这几句话该住在哪儿

**目标:** 把换个业务领域它要不要改这条判据用在文案上.

**怎么做:**

对下面六样东西, 各回答一句该进 `data/site.toml` 还是该写死在组件里:

1. 首页那个大标题
2. 导航条右上角那个按钮上的 Start Chat
3. agent 自称的名字
4. agent 正在思考时显示的那个词
5. 四张能力卡上那些概念名
6. 关闭按钮给读屏软件用的那个标签

然后去 `data/site.toml` 和 `components/` 里找到它们真实的位置, 对答案.

**你会观察到:**

第 2 个和第 3 个最容易搞混. 两个都是按钮或标题上的短语, 但一个描述的是这个 app 有几个页面
(脚手架的事实), 另一个是数据集给这个 agent 起的名字 (换领域就要改).

> **关键洞见:** 判断一个字符串归谁, 不看它出现在界面的哪个位置, 看换一个业务领域它要不要跟
> 着变.

## 13. 导师寄语

**为什么这一篇讲的是取舍而不是规矩:**

界面文案集中管理这件事, 说出来谁都同意. 难的是当它开始有代价的时候还愿不愿意守: 编译器不
帮你查了, 加一个字段要多打开一个文件, 有时候在组件里直接写一句话确实更快.

这个仓库的做法不是喊口号, 是**把丢掉的东西一件件补回来**. 编译器不查字段, 就在加载时查;
不查图标名, 就在加载时查; 而且报错要报得足够具体, 具体到你不用去翻源码.

这是一个通用的判断方式: 当你要放弃某个安全网去换别的东西时, 先说清楚放弃的是什么, 再说清楚
拿什么补上. 只说收益不说代价的设计, 迟早会在某个安静的地方咬人.

**关键洞见:**

- 编译期检查是在写的时候帮你一次, 结构上的集中是在每一次替换和 review 时帮你
- 报错的信息量决定了一个检查的价值. 报出全部合法取值和只报一句配置有误, 差得很远
- 这一层的坑几乎全是静默的: 空标题, 错图标, 错位的 key, 印了两遍的欢迎语. 没有一个会崩

**下一步:**

文案有了, 接下来是它被摆成什么样. 第 10 篇 (首页) 讲首页那三层结构怎么把一个完全不懂这行的
陌生人, 带到能提出第一个问题的位置.

## 14. 速查

**改完文案跑这两条, 缺一不可:**

```bash
mise run check-content
mise run build-web
```

**关键文件:**

- `data/site.toml`: 界面上说的每一句话
- `data/business-context.md`: 首页那个说明覆盖层的正文
- `lib/site/load.ts`: 读盘加两个构建期检查
