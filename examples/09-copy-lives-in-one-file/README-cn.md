# 界面上每一句话都住在一个文件里

> 前端一个字的业务文案都不许内联. 这条规矩听起来像洁癖, 但它是那个一到两小时换掉整个业务
> 领域的承诺里, 分量最重的一条.

## 1. 概览

先把这一篇放回它该在的位置, 否则你会觉得我们莫名其妙开始讲一个配置文件格式.

回到第 2 篇那个承诺: **一到两小时, 把这个 app 整个换成另一个行业的 app.** 今天它是中小企业
放贷的风险分析, 明天可以是供应链的库存分析. 那不是一句口号, 是这门课的终点.

**这一篇就是那个承诺的第一块砖.**

问题很具体: 界面上有几百句话, 全是这个行业特有的. 要换领域, 这几百句话都得重写. 那么它们
应该住在哪儿?

**如果它们散在几十个组件里**, 换领域就变成: 全仓库搜一遍, 逐处判断哪句该改哪句不该, 然后
祈祷没漏. 这件事人做会漏, 让 AI 做更会漏, 而且**漏了不报错**, 只是新页面上还留着上一个行业
的半句话.

**如果它们全部集中在一个文件里**, 换领域就变成: 打开那个文件, 从头到尾重写一遍. 有没有漏,
读一遍就知道.

所以这个项目定了一条硬规矩:
**界面上一个字的业务文案都不许写在组件里, 全部住在 [`data/site.toml`](../../data/site.toml).**
这一篇讲这条规矩怎么落地, 以及它的代价由谁来付.

### 这条规矩在有 AI 之后变得更重要

这一点值得单独说, 因为它是第 4 篇那个理念在内容这一侧的兑现.

你派给 AI 的任务是**把界面上所有提到贷款的地方换成提到订单**. 两种仓库里, 这句话的实际
含义完全不同:

| 仓库长什么样 | AI 实际要做什么 | 结果 |
| :--- | :--- | :--- |
| 文案散在几十个组件里 | 全仓库搜, 逐处判断该不该改, 还要小心别把变量名和注释一起改了 | 每次都会漏几处, 而且没有任何东西会提醒 |
| 文案集中在一个文件里 | 打开那一个文件重写 | 改动落点只有一个文件, 一眼就能验收 |

**同一个模型, 同一句话, 差别全在仓库这一侧.** 这就是第 4 篇说的那件事: 你想让 AI 干得准,
最有效的投资不是打磨提示词, 是把该集中的东西集中起来.

### 卡住了怎么办

这一篇每一步都可能出错: 改完文案页面没变, 或者构建直接失败.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/09-copy-lives-in-one-file/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/09-copy-lives-in-one-file/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

上面那条规矩说出来谁都同意. 难的是**它有代价, 而且代价出现得比收益早**.

这份文案是 TOML 格式的, 也就是一个纯文本配置文件. 它本来可以写成 TypeScript, 那样编译器会
免费帮你查字段名和图标名, 写错当场标红. 换成 TOML 就等于把这个安全网扔了.

那为什么还要换?

| | 写成 `.ts` | 写成 `.toml` |
| :--- | :--- | :--- |
| 编译器查字段名和图标名 | **免费给你** | 没有 |
| 这份文案住在哪 | 前端代码树里, 和组件混在一起 | **和这个数据集的其它产出一起, 在 [`data/`](../../data)** |
| 换数据集是什么形状 | 一个跨目录的 diff | **一个目录替换** |
| 谁写得了这份文件 | 得懂一点 TypeScript | 会写配置文件就行 |

关键在中间两行. 这份文案**属于数据集, 不属于前端**. 把一个数据集的全部产出 (界面文案, 长
说明, agent 的提示词, 数据本身) 收进同一个目录, 换数据集就退化成一次目录替换. 这和第 7 篇
里擦教学痕迹退化成删几个目录, 是同一个思路.

**但扔掉的安全网必须补回来, 不能就这么算了.** 所以这一篇有一半篇幅在讲那两个补回来的检查,
而你会亲手让它们各拦你一次.

学完这个 Task, 你将能够:

1. 说清界面文案为什么必须集中, 以及这件事和让 AI 改得准之间的关系
2. 描述一句文案从磁盘到浏览器的三段路径, 说出每一段交出什么
3. 解释这份文案为什么是 TOML 而不是 TypeScript, 代价是什么, 拿什么补上
4. 说出两个构建期检查各拦住什么, 不拦的话会静默地坏成什么样
5. 判断一个界面上的字符串该进文案文件还是该写死在组件里

## 4. 你将学到什么

一条三段式的内容管线, 两个你会亲手触发一次的构建期检查, 和一条判断字符串归属的判据.

带走的那个理念是: **不变的部分不碰, 会变的部分集中到一处.** 这是这个项目能被 AI 准确改动
的全部秘密, 也是后面每一层都会重复的做法.

带走的那句话是: **一句话拆在两个文件里, 就没有任何一个地方能看出它读起来是什么样.**

## 5. 三段路径

你在那个文案文件里敲下一句话, 它最后出现在别人的浏览器里. 中间它要走三步.

用一个不太严谨但很好记的比方: **这三步像把一件东西从仓库搬上货架.**

| 这一步 | 用大白话说 | 谁做的 | 做完交出什么 |
| :--- | :--- | :--- | :--- |
| **解析** | 从仓库里把货取出来 | [`lib/site/load.ts`](../../lib/site/load.ts) 的 `loadSite()` | 一个还没检查过的普通对象 |
| **校验** | 验一遍货对不对 | 同一个函数里的两个检查 | 一个可以放心用的配置对象 |
| **渲染** | 摆到货架上 | server component 把它当 props 传下去 | 烘死在产物里的静态 HTML |

三步各自还有一点值得知道的:

**解析这一步碰文件系统**, 所以它只能在服务器上跑, 浏览器里跑不了 —— 浏览器根本没有文件
系统这个东西. 而且结果按进程缓存, 同一次构建里问第二次不会再读一遍盘.

**校验那两个检查都是直接抛异常的**, 不是打印一句警告. 所以构建真的会被拦住, 而不是带着
问题继续往下走. 这是 TOML 换掉 TypeScript 之后特意补回来的那道关, 下一节展开.

**渲染那一步是在构建期做的**, 不是用户打开页面的时候. 所以线上产物里躺着的已经是写死的
字符串了, 请求进来根本不读盘.

### 这条路径的重点在中间那个产物上

三步讲完, 真正要带走的是这一句:

> **那个校验完的配置对象, 是唯一穿过服务器和浏览器这条边界的东西.**

浏览器里显示的每一个字都来自它, 而它在构建结束的那一刻就冻住了.

由此推出一条纪律: **在浏览器里跑的组件, 不许自己去读配置.** 不是因为麻烦, 是因为读文案
那个函数要碰文件系统, 而浏览器里没有文件系统 —— 真写了, 它会在构建或者运行时炸给你看.

## 6. 编译器不查, 就由加载时来查

第 2 节那张表说了这笔交易划算, 但只说了一半. 另一半是: **划算的前提是丢掉的东西被补回来.**

判据是**两边分别在什么时候帮到你**. 编译期检查是在你**写的时候** 帮你一次; 目录集中是在
**每一次换数据集和每一次 review** 时帮你. 后者发生的次数多得多, 所以这笔交易成立.

但那不代表可以不管字段写错这件事. 一个缺了 key 的文案文件不会报错, 它会让组件收到一个空值,
然后在**线上** 渲染成一个空标题. 这比编译期报错糟糕得多.

所以那两个检查被搬到了加载的时候, 就在读这份文件的那个函数里, 而且**都直接抛异常**, 所以
`mise run build-web` 真的会被拦住. 下一节讲它们各查什么.

## 7. 两个构建期检查

它们都在 [`lib/site/load.ts`](../../lib/site/load.ts) 里, 都会抛异常, 所以 `mise run build-web` 真的会被拦住.

### 检查一: 必填 key 不能少

[`lib/site/schema.ts`](../../lib/site/schema.ts) 里有一个叫 `REQUIRED_SITE_KEYS` 的清单, 用点号路径列出了这份文件必须
declare 的每一个 key, 从 `brand.displayName` 一直到 `chat.messages.waitForResponse`, 二十
多条. 加载时逐个查, 少一个就报出**缺的 key 名和文件路径**.

**不查的后果是静默的**: TOML 不被类型检查, 所以缺一个 key 的结果是组件收到一个空值, 然后
在线上渲染成一个空标题. 页面不报错, 只是有一块地方什么都没有.

### 检查二: 图标名必须存在

[`lib/icons.ts`](../../lib/icons.ts) 里显式列出了这份文案能用的全部图标名. 四张能力卡各自点名一个图标, 加载时逐个
比对, 拼错就报出**坏名字和全部合法名字**.

**不查的后果同样是静默的**: 拼错的图标会渲染成一个中性的兜底图形. 卡片看着好好的, 就是配错
了图, 没有人会注意到.

### 两个都只有构建才查得到

**`mise run cli-check-content` 查不到这两样.** 那条命令读的是 [`data/`](../../data) 里的散文, 这两个检查读的
是同一批文件经过前端加载器的样子. 两者查的东西不重叠.

所以改完文案**两条命令都要跑**:

```bash
mise run cli-check-content
mise run build-web
```

只跑前一条是最常见的漏, 于是一个拼错的图标名安静地上了线.

## 8. 组件里不许拼句子

文案文件里每一条都是**一句完整的话**, 组件原样打印它. 比如横幅那句:

```toml
welcomeMessage = "I'm here to help you with SMB lending analytics."
```

不要把它写成半句, 再让组件补上另外半句 (下面这段是**反例**):

```jsx
I'm here to help you with{" "}<span>{site.chat.messages.welcomeMessage}</span>.
```

**一句话拆在两个文件里, 就没有任何一个地方能看出它读起来是什么样.** 改 TOML 的人看不到框架,
改组件的人看不到值, 两边各自都对, 拼起来是
`I'm here to help you with I'm here to help you with ...`.

这类错误**不报错, 不失败, 测试全绿**, 只有真的打开页面读那一行的人才会发现. 这个仓库真的
出过一次, 代价是聊天页的欢迎语在屏幕上印了两遍.

同一条规矩还有一个推论: **换数据集的人只该动 [`data/`](../../data).** 一旦句子的一半住在组件里, 换领域
就必须去改 TypeScript, 而那正是这套设计承诺不需要发生的事.

### 哪些字不算文案

有几处的文字确实写死在组件里, 而且**应该写死**, 判据还是那条老规矩: 换个业务领域, 它要不
要改?

| 文字 | 在哪 | 为什么不进文案文件 |
| :--- | :--- | :--- |
| 导航条上的 Home 和 Start Chat | `Navigation.tsx` | 这个 app 有几个页面是脚手架的事实, 不是数据集的 |
| 头像方块里那两个字母 | `AssistantAvatar.tsx` | 要塞进一个很小的方块, 而数据集可以给 agent 起一个很长的名字 |
| 思考中和加载中 | `message.tsx` 与两个 `loading.tsx` | 描述的是运行状态, 不是业务 |
| 关闭这类无障碍标签 | 多处 | 给读屏软件用的标签, 不是展示文案 |

## 9. TOML 有一个坑

这一条不写下来一定会踩.

**一旦开始一个数组表, 后面每一个不带节名的 key 都属于该数组的最后一个元素.** 所以每一节的
普通字段必须写在数组表**之前**.

对的写法, 普通字段全在数组表之前:

```toml
[chat]
agent = "Lending Lens"
inputPlaceholder = "Ask about the loan book..."

[[chat.suggestedActions]]
title = "..."
```

错的写法, 而且不报错:

```toml
[chat]
[[chat.suggestedActions]]
title = "..."
agent = "Lending Lens"
```

最后那行 `agent` 现在属于上面那个按钮, 不属于 `chat`.

写反了不报错, 只会**静默错位**: 那个 key 跑到了别的地方, 而它原来该在的位置变成了缺失, 于是
你收到的是必填 key 检查的报错, 而报出来的 key 名和你刚改的地方看起来毫无关系.

文案文件顶部的注释专门写了这一条, 因为它是这个格式最容易咬人的地方.

## 10. 那份长说明为什么原样返回

[`data/`](../../data) 下面还有一个文件: `business-context.md`, 首页那个说明覆盖层的正文.

读它的函数只做一件加工: **剥掉 HTML 注释**. 除此之外原样返回, 一个字都不解析.

**故意不解析**, 因为它由 chat 页那个同一个 Markdown 渲染器来渲染. 所以在这个文件里写一个
mermaid 围栏, 覆盖层里就真的会画出一张图, 而这一层加载代码完全不知道图这个概念存在.

**为什么要剥注释**: 那个 Markdown 渲染器没装解释 HTML 的插件, 所以它不会把 HTML 注释当注释,
而是原样打印出来. 一句写给下一个作者的备注, 会变成访客读到的一段正文. 在这里剥掉而不是禁止
在文件里写注释, 是为了让作者的批注能留在有用的地方.

那 12 条 kickstart 按钮各自带的那个 `render` 字段这一篇不展开, 它属于一份三方契约的一部分,
第 34 篇 (渲染契约) 会一次讲完.

## 11. 练习

### 练习 1: 判断这几句话该住在哪儿

**目标:** 把换个业务领域它要不要改这条判据用在文案上.

**怎么做:**

对下面六样东西, 各回答一句该进 [`data/site.toml`](../../data/site.toml) 还是该写死在组件里:

1. 首页那个大标题
2. 导航条右上角那个按钮上的 Start Chat
3. agent 自称的名字
4. agent 正在思考时显示的那个词
5. 四张能力卡上那些概念名
6. 关闭按钮给读屏软件用的那个标签

然后去 [`data/site.toml`](../../data/site.toml) 和 [`components/`](../../components) 里找到它们真实的位置, 对答案.

**你会观察到:**

第 2 个和第 3 个最容易搞混. 两个都是按钮或标题上的短语, 但一个描述的是这个 app 有几个页面
(脚手架的事实), 另一个是数据集给这个 agent 起的名字 (换领域就要改).

> **关键洞见:** 判断一个字符串归谁, 不看它出现在界面的哪个位置, 看换一个业务领域它要不要跟
> 着变.

---

### 练习 2: 让那两个检查各拦你一次

**目标:** 亲眼确认丢掉的编译器检查真的被补回来了.

**怎么做:**

1. 先改一句正常的文案: 打开 [`data/site.toml`](../../data/site.toml), 把 `[chat]` 那节的 `inputPlaceholder` 改成别的
   句子, 起开发服务器打开 agent 页确认它变了
2. 把 `[brand]` 那节的 `footerName` 那一整行注释掉, 跑 `mise run build-web`, 读报错
3. 恢复那一行, 把某张能力卡的 `icon` 改成一个不存在的名字比如 `Banana`, 再跑一次构建, 读报错
4. 全部恢复, 跑 `mise run cli-check-content` 和 `mise run build-web` 两条确认都绿

**你会观察到:**

第 2 步报出的是缺失的 key 名和文件路径. 第 3 步报出的是坏名字, **以及全部合法名字的清单**,
所以你不用去翻源码就知道该填什么. 另外注意第 4 步里 `check-content` 对这两种错误一声不吭,
只有构建拦得住.

> **关键洞见:** 一个检查值不值钱, 看它报错的时候给了你多少信息. 报一句配置有误, 和报出坏
> 名字加全部合法名字, 是两种完全不同的东西.

| 和 AI 的关系 | 文案散着, AI 每次都会漏几处而且不报错; 文案集中, 改动落点只有一个文件 |
| 三段路径 | 解析成对象, 校验成可用配置, 当 props 传进客户端组件. 中间那个产物是唯一穿过边界的东西 |
| 为什么是 TOML | 用编译期检查换目录集中. 前者帮你一次, 后者在每次换数据集和每次 review 时帮你 |
| 必填 key 检查 | 少一个 key 就报出 key 名和文件路径. 不查的话组件收到空值, 线上渲染成空标题 |
| 图标名检查 | 拼错就报出坏名字和全部合法名字. 不查的话静默渲染成兜底图形, 没人会注意到 |
| 两条命令都要跑 | `check-content` 读散文, `build-web` 走前端加载器. 查的东西不重叠 |
| 组件里不许拼句子 | 一句话拆两个文件, 没有任何一处能看出它读起来是什么样, 而且测试全绿 |
| TOML 数组表的坑 | 数组表之后的裸 key 属于数组最后一个元素. 写反了静默错位 |
| 那份长说明 | 原样返回只剥 HTML 注释, 因为它走的是 chat 页同一个渲染器 |

## 13. 导师寄语

**为什么这一篇讲的是取舍而不是规矩:**

界面文案集中管理这件事, 说出来谁都同意. 难的是当它开始有代价的时候还愿不愿意守: 编译器不
帮你查了, 加一个字段要多打开一个文件, 有时候在组件里直接写一句话确实更快.

而每一次就这一次直接写在组件里, 都是在把未来那次换领域的时间从两小时往两天推. 代价不在
当下, 在很久以后的某一天, 这正是这类规矩最难守的原因.

这个仓库的做法不是喊口号, 是**把丢掉的东西一件件补回来**. 编译器不查字段, 就在加载时查;
不查图标名, 就在加载时查; 而且报错要报得足够具体, 具体到你不用去翻源码.

这是一个通用的判断方式: 当你要放弃某个安全网去换别的东西时, 先说清楚放弃的是什么, 再说清楚
拿什么补上. 只说收益不说代价的设计, 迟早会在某个安静的地方咬人.

**关键洞见:**

- 让 AI 改得准的办法不是把话说得更巧, 是先把该改的东西收进一个它跑不出去的范围
- 编译期检查是在写的时候帮你一次, 结构上的集中是在每一次替换和 review 时帮你
- 报错的信息量决定了一个检查的价值. 报出全部合法取值和只报一句配置有误, 差得很远
- 这一层的坑几乎全是静默的: 空标题, 错图标, 错位的 key, 印了两遍的欢迎语. 没有一个会崩

**下一步:**

文案有了, 接下来是它被摆成什么样. 第 10 篇 ([首页](../10-the-home-page/README-cn.md)) 讲首页那三层结构怎么把一个完全不懂这行的
陌生人, 带到能提出第一个问题的位置.

## 14. 速查

**改完文案跑这两条, 缺一不可:**

```bash
mise run cli-check-content
mise run build-web
```

**关键文件:**

- [`data/site.toml`](../../data/site.toml): 界面上说的每一句话
- [`data/business-context.md`](../../data/business-context.md): 首页那个说明覆盖层的正文
- [`lib/site/load.ts`](../../lib/site/load.ts): 读盘加两个构建期检查
- [`lib/site/schema.ts`](../../lib/site/schema.ts): 这份文件的形状, 和必填 key 清单
- [`lib/icons.ts`](../../lib/icons.ts): 文案里能点名的全部图标

**两条不许破的规矩:**

- 组件里不写业务文案, 也不拼半句话
- 每一节的普通字段写在数组表之前
