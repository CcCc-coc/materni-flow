# 一个数据集里到底装着什么

> 你以为数据集是一个数据库文件. 其实那个文件是最不重要的一样东西, 因为它是跑出来的.

## 1. 概览

第 4 篇 ([把它跑起来](../04-get-it-running/README-cn.md)) 停在一个半成品上: 首页能看能点,
agent 页一点就报错, 因为数据库里一行数据都没有.

接下来四篇把这一半补上, 顺序是这样的:

| 篇 | 干什么 |
| :--- | :--- |
| **17 (这一篇)** | 认识数据集这五个文件, 跑一次生成器, 在本地造出数据库 |
| 18 ([读懂这个库](../18-read-the-schema/README-cn.md)) | 十张表是怎么连起来的, 怎么看懂一张关系图 |
| 19 ([用业务问题学 SQL](../19-sql-by-business-question/README-cn.md)) | 拿真实业务问题当索引去读那二十个查询 |
| 20 ([把种子发布到 PostgreSQL](../20-seed-to-postgres/README-cn.md)) | 把本地数据发布上去, agent 从这一刻开始能用 |

这一篇要纠正一个几乎所有人都有的直觉.

**你以为的数据集**: 一个 `.sqlite` 文件, 或者一堆 CSV. 拿到就能用.

**这个项目里的数据集**: 四份人写的文档, 加一个生成器脚本. **数据库是跑出来的**, 所以它
根本不在 Git 里.

这个区别听起来只是工程细节, 其实它决定了第 35 篇 (造一个新数据集) 你要交出什么东西 ——
到那时候你要为自己那个行业做一个数据集, 而你要写的正是这五个文件, 不是一个数据库.

---

## 2. 学习目标

先回答一个很自然的疑问: **为什么要这么麻烦? 直接放一个数据库文件进仓库不好吗?**

不好, 而且理由有三层, 一层比一层重要.

### 第一层: 二进制文件不适合放进 Git

Git 擅长的是文本. 你改了一行代码, `git diff` 会告诉你改了哪一行.

而一个数据库是二进制的. 你重新生成一次, Git 只会告诉你这个文件变了, **变了什么它说不出来**.
更糟的是它每变一次就在仓库历史里留一份完整副本, 而这个库有十几万行, 三十兆. 几次之后仓库
就臃肿得没法看了, 而且**删不掉** —— Git 的历史是不会忘的.

### 第二层: 它是可再生的

这一层是判据本身: **一个东西如果能从别的东西确定性地生成出来, 它就不该被保存.**

生成器是确定性的 —— 同一份代码跑两遍, 拿到的行一模一样 (下面第 6 节讲它怎么做到的).
既然如此, 存那个结果就是在存一份冗余, 而冗余是会不同步的: 有人改了生成器忘了重新生成,
于是仓库里那个文件和生成它的代码对不上, 而**没有任何东西会报错**.

这条判据在别处也成立: 编译产物, 打包结果, 缓存, 都是同一类东西.

### 第三层: 真正重要的是那四份文档

这一层最容易被忽略, 但它是这个项目的核心主张.

**一个数据集的价值不在数据里, 在描述这门生意的那些文字里.** 数据只是这些描述的一个具体
实例. 你把 ER 文档和业务背景读懂了, 换一批随机种子重跑一遍, 那还是同一个数据集.

所以进 Git 的是**源头**, 而不是**结果**. 这跟你交作品集时的道理是一样的: 别人
想看的是你怎么想的, 不是你跑出来的那堆数字.

学完这个 Task, 你将能够:

1. 说出一个数据集由哪五个文件构成, 每一个各自回答什么问题
2. 解释为什么生成的数据库不进 Git, 并说出那条可再生就不保存的判据
3. 在自己机器上跑通生成器, 拿到本地那份数据库
4. 说清生成器为什么要钉死一个参考日期, 而不是用今天
5. 解释这个项目为什么去找那个数据库文件, 而不是把文件名写死在代码里

## 5. 五个文件

打开 [`dataset/`](../../dataset) 目录, 你会看到五个带编号的文件. **编号就是阅读顺序**,
从最粗到最细:

| 文件 | 用大白话说 | 它回答什么问题 | 多长 |
| :--- | :--- | :--- | :--- |
| `00-*_summary-cn.md` | 一段话简介 | 这个数据集是关于什么的 | 一段 |
| `01-*_business_context-cn.md` | 这门生意的说明书 | 这家公司靠什么赚钱, 这行的黑话都是什么意思 | 长 |
| `02-*_er_document-cn.md` | 表和表的关系图 | 有哪些表, 每张表有哪些列, 谁连着谁 | 长 |
| `03-*_sql_queries-cn.md` | 二十道业务题带答案 | 这行的人每天真正会问什么, 怎么用 SQL 答 | 很长 |
| `04-*_data_generator-cn.py` | 造数据的脚本 | 上面这些描述, 变成具体的行长什么样 | 几千行 |

外加一个 `requirements.txt`, 下面第 8 节说它为什么单独存在.

### 这个顺序不是随便排的

它是**从人到机器** 的顺序. 前两份是给人读的, 讲的是生意; 第三份开始转向数据; 第四份是二十
个具体查询, 已经是半技术的了; 最后那个是纯代码.

**换个角度看, 这也是你造一个新数据集时的写作顺序.** 你不可能先写生成器再想清楚这门生意是
什么 —— 那样写出来的数据一定是空的, 表结构合法但没有任何业务含义.

### 这四份文档后来去了哪里

值得提前说一句, 否则你会觉得这些文档写了没人看:

| 这份文档 | 后来喂给了谁 |
| :--- | :--- |
| 业务背景 | 一部分变成 [`data/business-context.md`](../../data/business-context.md), 就是首页那个长说明 |
| ER 文档 | 它描述的结构后来由程序从数据库里反射出来, 压缩成一段字符串喂给 agent (第 21 篇) |
| 二十个查询 | 精选之后变成 [`data/system-prompt.md`](../../data/system-prompt.md) 里的 SQL 例子 (第 24 篇) |
| 生成器 | 只在造数据时跑一次, 之后就不再参与 |

所以 [`dataset/`](../../dataset) 是**源头**, [`data/`](../../data) 是**给这个 app 用的成品**.
两者内容重叠但用途不同, 一个给人读, 一个给程序和模型读.

## 6. 跑一次生成器

命令只有一条:

```bash
.venv/bin/python .claude/skills/about-bi-agent-app-scaffold-cn/scripts/teaching_cli.py gen-data
```

它会先装生成器自己的依赖, 然后跑那个脚本, 几分钟之后在 [`dataset/`](../../dataset) 下面
留下一个 `.sqlite` 文件.

### 它做了两件你可能没预料到的事

**第一, 数据库已经在的话, 它什么都不做.**

它会打印一句已经有了, 保留原样, 然后直接退出. 因为生成要跑几分钟, 而绝大多数时候它已经在
那儿了 —— 每次都重新生成纯粹是浪费你的时间.

真要重来就加 `--force`.

**第二, `--force` 会先删掉 [`dataset/`](../../dataset) 里的每一个 `.sqlite`.**

这一条看起来有点粗暴, 它其实在防一个很具体的事故: **一个仓库只服务一个数据集.** 如果你
换过数据集, 上一个数据集的 `.sqlite` 还躺在那儿, 那这个目录里就有两个数据库文件了.

而这个项目找数据库的方式是去目录里找 (下面第 7 节讲), 找到两个它会**拒绝选**, 直接报错.
于是你刚刚辛辛苦苦重新生成的那个正确的库, 看起来像是坏的 —— 而真正的原因是一个你早就忘了
的旧文件.

所以 `--force` 先清场再生成. 这不是打扫卫生, 是让重新生成这个动作真的能把你带回一个干净
状态.

### 那个钉死的日期

打开生成器扫一眼, 你会发现一个叫参考日的常量, 值是一个写死的日期.

数据集里所有今天, 当前, 最近这类语义, 全都锚在这个日期上, **而不是锚在系统时间上**.

为什么? 因为如果用今天:

| | 用系统时间 | 钉死一个日期 |
| :--- | :--- | :--- |
| 今天跑和下个月跑 | 数据不一样 | **一模一样** |
| 文档里写的期望结果 | 过一阵就对不上了 | 永远对得上 |
| SQL 查询里的日期 | 每次要重新想 | 直接写那个字面量 |
| 别人复现你的问题 | 复现不出来 | 一定复现得出来 |

**这是一条通用的工程习惯**: 凡是会让同一份代码跑出不同结果的东西 —— 当前时间, 随机数,
机器名, 网络 —— 都是可复现性的敌人. 能钉死就钉死.

那二十个 SQL 查询里凡是需要今天的地方, 写的也都是那个日期的字面量, 不是取当前时间的函数.
同一个理由.

## 7. 文件名是找出来的, 不是写死的

这一节讲一个很小但很能说明这个项目性格的设计.

数据库文件叫什么名字? 它跟着数据集走 —— 换一个数据集, 文件名就变了.

那代码怎么找到它? 两种做法:

| 做法 | 后果 |
| :--- | :--- |
| 把文件名写在代码里 | 换数据集要改 [`agent_app/`](../../agent_app) 里的代码 |
| **去目录里按模式找** | 换数据集只动 [`dataset/`](../../dataset), 代码一行不改 |

这个项目选第二种, 因为它要兑现第 2 篇立下的那句承诺:
**换一个业务领域, [`agent_app/`](../../agent_app) 下面一行都不改.**
文件名属于数据集, 把它写进那个包就等于在包里留了一个数据集的痕迹.

### 找不到和找到好几个, 都要报错

这是这个设计里最值得学的一点. 那个查找函数有三种结局:

| 找到几个 | 怎么办 |
| :--- | :--- |
| 正好一个 | 用它 |
| 一个都没有 | **报错**, 并在错误信息里直接给出生成它的那条命令 |
| 好几个 | **报错**, 并说一个仓库只服务一个数据集, 把不用的删掉 |

第三种最要紧. 一个很自然的偷懒写法是找到多个就取第一个 —— 排序之后总有一个第一嘛.

**但那正是错的数据集被端上桌的方式.** 它不会报错, 它会安安静静地服务一个你以为已经换掉的
旧数据集, 而你要等到某个答案明显不对劲的时候才会发现.

> **这条判断你会在这个仓库里反复看到**: 在能跑但可能是错的, 和当场失败之间, 一律选后者.
> 第 13 篇 ([前后端分离](../13-wire-next-to-fastapi/README-cn.md)) 里端口钉死在 3000 是同
> 一条判断, 第 20 篇里那个空 schema 检查也是.

## 8. 生成器的依赖为什么单独放

[`dataset/`](../../dataset) 下面有一个 `requirements.txt`, 而这个项目的 Python 依赖明明
写在 [`pyproject.toml`](../../pyproject.toml) 里.

为什么要有两份?

因为它们属于两个不同的东西: **生成器的依赖不是这个 app 的依赖.** 造假数据需要一个造假数据
的库, 而这个 app 跑起来之后根本不需要它 —— 数据早就造好了, 躺在数据库里.

而这个区分带来的好处在删除的那一刻才显现: 教学层是**整块删掉** 的. 你删掉
[`dataset/`](../../dataset) 这个目录, 那份 `requirements.txt` 跟着一起走, 生成器的依赖也就
自然消失了.

如果当初把它们混进 [`pyproject.toml`](../../pyproject.toml), 那删除的时候你就得**逐行去挑**
哪几个包是教学用的 —— 而挑错一个是完全静默的, 要么多装一个没用的包, 要么删掉一个 app 真的
在用的.

这正是第 6 篇 ([教学层和生产层](../06-teaching-and-production/README-cn.md)) 那条边界在这里
的具体样子.

> **一个通用的问法**: 你想把两样东西放在一起时, 先问一句 —— **它们会一起被删掉吗?** 答案
> 是否, 就分开放.

## 9. 练习

### 练习 1: 跑一次, 然后故意制造一次找到好几个

**目标:** 拿到本地数据库, 并亲眼看一次那个拒绝选择的报错.

**怎么做:**

1. 开一个叫 `17-what-a-dataset-is` 的 branch
2. 跑一次 `gen-data`, 等它跑完, 记下它最后打印的文件名和大小
3. **再跑一次同样的命令**, 看它这次说了什么, 想清楚为什么
4. 现在制造那个事故: 把生成出来的那个文件复制一份, 改个名字, 比如
   `cp dataset/*.sqlite dataset/leftover.sqlite`
5. 跑 `.venv/bin/python scripts/test_04_print_database_schema.py`, 读那条报错
6. 把复制出来的那个删掉 (`rm dataset/leftover.sqlite`), 再跑一次确认恢复正常

**你会观察到:**

第 3 步它一秒就退出了, 什么都没做. 第 5 步的报错会把两个文件名都列出来, 并直接告诉你一个
仓库只服务一个数据集.

如果你这台机器上**本来就有一个上个数据集留下的 `.sqlite`**, 那你在第 2 步就会撞上这个报错,
不用等到第 4 步 —— 那就更好, 你看到的是真实事故而不是模拟的.

> **关键洞见:** 一个报错如果能顺便告诉你怎么修, 它的价值会翻好几倍. 你在第 5 步读到的那条
> 就是被人特意写成这样的, 不是碰巧.

### 练习 2: 判断这五个文件里, 换个行业要重写几份

**目标:** 把这一篇和第 2 篇那条换领域的主线接上.

**怎么做:**

1. 拿出你在第 2 篇 ([为什么是这个项目](../02-why-this-project/README-cn.md)) 里写的那份
   `tmp/my-target-domain.md`, 里面有你选的公司和那三个业务问题
2. 对着第 5 节那张表, 一个文件一个文件地回答: **换成你那个行业, 这份要不要重写?**
3. 对每一份, 再回答一句: 重写它需要你知道什么? 是这行的常识, 还是编程知识?
4. 最后看一眼你那三个业务问题, 想一想: 要让它们答得出来, `02-*` 那份 ER 文档里至少得有
   哪几张表?

**你会观察到:**

五份**全都要重写**, 一份都不能留. 但真正难的只有前两份, 因为它们要求你懂那门生意; 后面
三份是前两份的机械后果 —— 表结构由业务实体决定, 查询由业务问题决定, 生成器由表结构决定.

> **关键洞见:** 第 35 篇 (造一个新数据集) 你要交的就是这五个文件. 现在提前知道这件事, 你
> 读后面几篇的眼光会不一样: 你不是在学别人的数据集, 你是在看一份你迟早要自己写一遍的样板.

## 11. 导师寄语

**为什么这一篇值得认真读:**

大多数人接触数据集是从下载一个 CSV 开始的. 那个习惯会让你觉得数据集就是数据, 而拿到数据
就是全部.

这个项目想让你换一个视角: **数据是描述的产物, 不是描述本身.** 那四份文档才是真正的资产,
因为它们是人对一门生意的理解; 数据只是这份理解的一个具体实例, 跑一下就有.

这个视角会在第 35 篇兑现. 那时候你要为自己那个行业造一个数据集, 而你会发现难的从来不是写
生成器 —— 那是最机械的一步. 难的是把那门生意描述清楚到能生成出可信的数据.

**关键洞见:**

- 可再生的东西不保存, 保存的是生成它的东西
- 当前时间是可复现性的敌人. 能钉死就钉死
- 在能跑但可能是错的, 和当场失败之间, 一律选后者
- 两样东西该不该放在一起, 问它们会不会一起被删掉

**下一步:**

数据库现在躺在你的硬盘上了, 但你还不知道它里面长什么样. 第 18 篇
([读懂这个库](../18-read-the-schema/README-cn.md)) 会带你读那张关系图: 十张表分成哪几类,
外键是怎么把它们串起来的, 以及为什么灌数据的顺序不能乱来.

## 12. 速查

**造数据:**

```bash
CLI=.claude/skills/about-bi-agent-app-scaffold-cn/scripts/teaching_cli.py
.venv/bin/python $CLI gen-data           # 已经有了就什么都不做
.venv/bin/python $CLI gen-data --force   # 先删光所有 .sqlite 再重新造
```

**五个文件:**

| 编号 | 是什么 |
| :--- | :--- |
| 00 | 一段话简介 |
| 01 | 业务背景, 行业科普, 术语表 |
| 02 | ER 文档: 表, 列, 外键 |

**两条判据:**

- 能确定性生成出来的东西, 不保存
- 两样东西放不放在一起, 问它们会不会一起被删掉
