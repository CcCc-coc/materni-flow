# 最后一条消息不一定是答案

## 1. 目标

前四篇拆完了 agent 本身, 这一篇讲**它说完话之后**.

**核心是一件和直觉不符的事**: agent 跑完交回来的不是一句答案, 是**一整串消息** —— 想一步,
调个工具, 又想一步, 最后才说答案. 而你要从里面挖出思考和答案两样东西给界面用.

**最要紧的一句: 答案常常不在最后一条消息里.** 因为系统提示词让 agent 答完之后再调一次写调试
报告的工具, 于是它最后那条消息只剩一句思考. 无条件读最后一条, 拿到的是空字符串 —— 而空答案
在界面上是**一个思考块下面什么都没有**, 用户会以为卡死了.

这一篇的两个练习都不用调模型, 也不用起服务器: 那三组消息是照着真实形状手写的, 输出每次一样.

**练习 2 一定要做.** 你会亲手把那句判断去掉, 看答案变成空的 ——
而**脚本正常跑完, 没有任何报错, 退出码是 0**. 这类改动在代码审查里看起来只是简化了一下,
后果要到用户那边才显形.

---

## 2. 要做的事情

1. 读完 README, 重点是第 2 节那个空答案的后果, 和第 7 节为什么不改提示词.
2. 开一个叫 `26-explain-the-reasoning` 的 branch.
3. 跑 `01_parse_three_replies.py`, 三组输出都读一遍.
4. 对着第 2 组回答: 思考是从几条消息里攒起来的, 答案来自第几条.
5. 打开那个脚本, 读那三组手写消息, 确认第 2 组最后一条确实只有思考.
6. 打开 `agent_app/agent_response.py`, 在收集那一步里找到那句只有还剩东西才记成答案的判断.
7. 找到第三步那个改写函数, 看它为什么要求标签单独占一行, 想清楚这在防什么.
8. 找到那三步被绑成一个函数的地方, 读注释里给的理由.
9. 起开发服务器, 在 agent 页问一个问题, 答完后打开 `tmp/debug_report.md` 看那份报告.
10. 把第 6 步那句判断改成无条件记录, 再跑一次脚本, 只看第 2 组的 answer.
11. 确认全程没有任何报错, 脚本正常退出.
12. 改回去, 再跑一次确认恢复.

**预计用时:** 50 到 80 分钟

## 3. 检查清单

- [ ] **交回来的是什么**: 你能说清 agent 交回来的东西和一次普通模型调用有什么不同.
- [ ] **答案在第几条**: 你跑过脚本, 知道第 2 组的答案来自中间那条而不是最后一条, 也说得出
      为什么最后一条只剩思考.
- [ ] **那句判断找到了**: 你在代码里指得出挡住空答案的那一句.
- [ ] **亲手弄空过一次**: 你把那句判断改成无条件记录, 见过 answer 变空, 并确认全程零报错.
- [ ] **三步为什么绑一起**: 你能说清分开暴露的风险, 以及漏掉第三步的症状是什么.
- [ ] **改写标签的理由**: 你能说清模型为什么会把 `<thinking>` 的习惯用到 `<chart>` 上, 以及
      markdown 遇到未知标签会怎样.
- [ ] **为什么不改提示词**: 你能复述毫无歧义的转换用代码做这条判据, 并说清它和提示词是概率性
      的这件事怎么连起来.
- [ ] **空答案的兜底**: 你能说清为什么不让它空着, 理由要落在用户接下来能做什么上.
- [ ] **工作区干净**: 练习改的那句判断还原了.
