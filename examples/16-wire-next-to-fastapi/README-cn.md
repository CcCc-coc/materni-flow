# 前后端分离, 和这个项目是怎么接线的

> 你敲一条命令, 起来的是两个互不相干的程序. 浏览器却只认一个地址. 这一篇讲这件事为什么
> 是这样, 以及它带来了什么麻烦.

## 1. 概览

数据住在哪儿讲完了. 这一篇转向另一侧.

但在读后端代码之前, 得先补一个概念. 因为你已经在用它了, 只是没人跟你说过它叫什么:

**你敲的那条 `mise run dev`, 起来的是两个程序, 不是一个.**

这件事有个名字, 叫**前后端分离**. 它是过去十几年里网站开发方式最大的一次变化, 而且它决定了
这个项目的目录为什么长成那样, 为什么有 [`app/`](../../app) 和 [`api/`](../../api) 两套东西,
以及为什么你本地跑起来要等两个服务器都就绪.

这一篇前面大半在讲**这件事本身**, 因为它对后面每一篇都有用; 后面小半才回到这个项目, 看它
具体是怎么接的.

**这一篇不要求你会写后端.** 它要求你脑子里有一张图: 谁在哪儿, 谁跟谁说话, 说的是什么.

### 卡住了怎么办

这一篇每一步都可能出错: 两个服务器只起来一个, 端口被别的东西占着, 或者请求转发不过去.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/16-wire-next-to-fastapi/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/16-wire-next-to-fastapi/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

先说为什么这个概念值得单独花一篇.

你现在打开这个仓库, 会看到两套完全不同的东西: 一套 TypeScript, 一套 Python; 一个装依赖用
pnpm, 一个用 uv; 一边跑在 3000, 一边跑在 8000.

**如果你不知道前后端分离是什么, 这一切看起来就是随意的.** 为什么不写成一个程序? 为什么要
两种语言? 为什么本地要起两个进程而线上又不是?

知道了这个概念, 上面每一个问题都有答案, 而且是同一个答案.

**还有一个更实际的理由**: 这一层是这门课后面最容易浪费时间的地方. 端口被占, 服务器起不来,
或者更糟, 起来了但接到了别的项目的后端. 这几种情况的症状都很像程序坏了, 而实际上和代码
一点关系没有.

学完这个 Task, 你将能够:

1. 用自己的话解释什么是前后端分离, 以及一个网站为什么要拆成两半
2. 说清那两半之间怎么通信, 传的是什么格式的东西
3. 说出拆开之后多出来的三样麻烦, 以及这个项目各自怎么处理的
4. 描述这个项目本地那条转发规则, 并说清线上它变成了什么
5. 用一份排查清单把起不来的问题定位到某一层

## 5. 前后端分离到底是什么意思

先从一个你天天在用的东西说起.

你打开一个购物网站, 看到商品列表. 这一屏东西可以拆成两部分:

| 部分 | 例子 |
| :--- | :--- |
| **长什么样** | 卡片是圆角的, 价格是红色的, 图片在左边文字在右边, 鼠标划过去会变色 |
| **是什么内容** | 这件商品叫什么, 卖多少钱, 还剩几件 |

**长什么样这件事, 换个商品也不会变.** 而**是什么内容**, 每个商品都不一样, 而且它藏在一个
数据库里.

早年间, 这两件事是**一个程序** 干的. 服务器上跑着一段代码, 它去数据库里查出商品, 然后把
数据和样式拼成一整个网页, 整页发给浏览器. 浏览器收到的是一份已经拼好的成品.

**前后端分离就是把这一个程序劈成两个.**

| | 前端 | 后端 |
| :--- | :--- | :--- |
| 管什么 | 长什么样, 怎么交互 | 数据从哪来, 业务规则是什么 |
| 跑在哪 | 主要在你的**浏览器** 里 | 在**服务器** 上 |
| 这个项目里是谁 | Next.js, 那堆 `.tsx` 文件 | FastAPI, 那堆 `.py` 文件 |
| 它需要知道对方什么 | 只需要知道**去哪个地址要数据** | 只需要知道**要返回什么格式** |

最后一行是关键: **两边只通过一个约定好的接口打交道, 互相不知道对方内部长什么样.**

前端不知道数据是从 PostgreSQL 来的还是从一个文件来的; 后端不知道那个数字最后是显示成一张
柱状图还是一行文字.

## 6. 它们之间怎么说话

既然拆成两个程序了, 它们就得有个说话的方式. 那个方式叫 **HTTP 请求**, 而它的形状简单得
出乎意料: **一问一答.**

前端问一句:

```text
POST /api/chat
{"messages": [{"role": "user", "parts": [{"type": "text", "text": "Grade C 的定价对吗?"}]}]}
```

后端答一句:

```text
{"answer": "Grade C 的实际违约率是 9.9%, 而定价假设是 6.0%..."}
```

就这样. 没有别的.

**三件值得注意的事:**

**第一, 传的是数据, 不是页面.** 后端返回的是一堆值, 不是一段已经排好版的 HTML. 怎么把它
画出来是前端的事. 这正是第 12 篇
([一段文本怎么变成表格和图](../12-render-text-into-blocks/README-cn.md)) 讲的那件事.

**第二, 格式通常是 JSON.** 那是一种所有语言都读得懂的文本格式, 长得像 Python 的字典或者
JavaScript 的对象. 选它不是因为它最好, 是因为**所有语言都支持它**, 而前后端很可能是两种
不同的语言.

**第三, 每一问一答之间, 后端什么都不记得.** 这一点后面反复会用到. 第 21 篇
([多轮对话和缓存](../21-multi-turn-and-caching/README-cn.md)) 会让你亲手撞上它的一个后果: 对话
历史得由前端每次重新送上来.

## 7. 为什么要分开, 以及分开的代价

拆开是有好处的, 但也不是白拿的. 两边都说一下.

### 好处

**一, 两边可以用各自最合适的语言.** 前端要跑在浏览器里, 那基本只能是 JavaScript 这一系;
而这个项目的后端要连数据库, 要调 AI 模型, 而这些库在 Python 世界里最成熟. 不分开的话, 你
得在一种语言里把两件事都干了.

**二, 两边可以各自换掉.** 后端从 Python 换成 Go, 只要那个接口的形状不变, 前端一个字都不用
改. 反过来也一样. 这一点在第 17 篇 ([AI SDK 协议](../17-the-ai-sdk-protocol/README-cn.md))
会被放大成一个更重要的话题.

**三, 同一个后端可以喂很多个前端.** 网页, 手机 app, 别人写的脚本, 都可以问同一个地址.

### 代价

**一, 你现在要管两个程序.** 装两套依赖, 起两个服务器, 看两处日志. 这个项目用
[`mise.toml`](../../mise.toml) 里一条命令把这件事包起来了, 但复杂度只是被藏起来, 没有消失.

**二, 它们要能找到对方.** 前端得知道后端在哪. 本地是两个端口, 线上又是另一回事. 这正是
下一节要讲的.

**三, 浏览器有一条安全规则挡在中间.** 浏览器默认**不允许** 一个页面去请求另一个地址的数据.
这条规则叫同源策略, 它防的是恶意网站偷偷拿你在别的网站上的数据.

对我们来说它是个麻烦: 页面在 3000, 后端在 8000, 在浏览器眼里这就是两个不同的地方. 直接请求
会被拦下来.

**这个项目用一个很干净的办法绕开了它**, 下一节讲.

## 8. 这个项目是怎么接的

浏览器打开 `localhost:3000`, 拿到页面. 页面上按下发送键, 前端往 `/api/chat` 发一个请求.

**注意这个地址没有写主机名**, 所以浏览器把它当成 `localhost:3000/api/chat` —— 也就是说,
这个请求是发给前端那个进程的, 不是发给后端的.

接住它的是 [`next.config.js`](../../next.config.js) 里那段转发规则:

```js
rewrites: async () => {
  return [
    {
      source: "/api/:path*",
      destination:
        process.env.NODE_ENV === "development"
          ? "http://127.0.0.1:8000/api/:path*"
          : "/api/",
    },
    // ...
  ]
}
```

读法很简单:
**任何以 `/api/` 开头的请求, 开发环境下转发到 8000 那个进程, 生产环境下走另一条路.**

于是整条通路是:

| 步 | 谁在做 |
| :--- | :--- |
| 1 | 浏览器往 `localhost:3000/api/chat` 发请求 |
| 2 | 前端服务器收到, 发现路径匹配 `/api/:path*` |
| 3 | 前端服务器把这个请求原样转发到 `127.0.0.1:8000/api/chat` |
| 4 | 后端处理, 调 agent, 把回答流回给前端服务器 |
| 5 | 前端服务器再流回浏览器 |

**浏览器全程不知道 8000 的存在.** 从它的角度看, 这就是一个普通网站, 所有东西都来自 3000.
上一节那条浏览器安全规则因此完全不会被触发 —— 因为在浏览器看来根本没有跨到别的地方去.

### 这个词叫 rewrite, 不叫 redirect

两者很容易混, 但差别很大:

| | rewrite (转发) | redirect (重定向) |
| :--- | :--- | :--- |
| 浏览器知道吗 | **不知道**, 地址栏不变 | 知道, 地址栏会变 |
| 请求走几趟 | 一趟, 服务器内部转 | 两趟, 浏览器再发一次 |
| 这里用哪个 | **rewrite** | 用它就等于把 8000 暴露给浏览器, 那条安全规则立刻回来 |

## 9. 线上没有这套东西

这是这一篇最要紧的一句话.

看那段转发规则里的判断: **只有开发环境才转发到 8000.** 生产环境下目的地是 `/api/`, 而那个
路径由部署平台自己接管 —— 它扫描仓库里的 [`api/`](../../api) 目录, 把里面的 Python 变成一个
按需拉起的函数.

对照一下:

| | 本地开发 | 线上 |
| :--- | :--- | :--- |
| 有几个进程 | **两个** | 前端是静态产物, 后端是按需拉起的函数 |
| 8000 端口 | 有 | **不存在** |
| 谁接住 `/api/chat` | 前端服务器转发给后端 | 平台直接路由到那个函数 |
| 有没有常驻的后端 | 有 | **没有**, 请求来了才拉起 |

最后一行解释了后面很多事. 最直接的一个: **后端不能有任何跨请求的记忆**, 因为线上两次请求
可能落在两个完全不同的函数实例上. 第 28 篇 ([一次 chat 请求](../28-one-chat-request/README-cn.md)) 会讲那个每次清空 agent 记忆的
决定, 根子就在这儿.

## 10. 两个工程决定

这一节讲的两件事都属于同一类问题: **一台机器上同时有好几个这样的项目在跑, 怎么不互相踩.**

这个脚手架的全部意义就是长出很多个项目, 所以这不是假想的情况.

### 端口为什么被钉死

[`mise.toml`](../../mise.toml) 里前端那个任务写的是 `next dev --port 3000`, 而这个 3000 是
钉死的.

**Next.js 默认的行为是: 3000 被占了就自动跳到 3001.** 听起来很贴心, 在这里却是个陷阱, 因为
那个转发目的地 `127.0.0.1:8000` 是写死的:

| 情况 | 会发生什么 |
| :--- | :--- |
| 3000 空着 | 一切正常 |
| 3000 被另一个项目占着, 允许自动跳 | 你的前端跑在 3001, 但它仍然把 `/api/*` 转发到 8000, 而**坐在 8000 上的是另一个项目的后端** |

第二种情况最阴: 页面能打开, 按钮能点, agent 也会回答, 只是它回答的是**另一个项目的数据**.
不报错, 不崩溃, 你要盯着答案看很久才会觉得不对劲.

所以这里选了另一边: **起不来比静默接错好.**

**这是这个仓库反复出现的一个取舍**: 在能跑但可能是错的, 和当场失败之间, 一律选后者.

### 杀服务器凭什么判定是我的

`mise run dev` 第一件事是先跑 `mise run kill`, 而那背后是
[`kill-dev-servers.py`](../../kill-dev-servers.py) 这个专门写的脚本.

一个杀进程的小工具值得几百行代码, 因为三件事叠在一起: 开发服务器**永远不会自己退出**; 一台
机器上常常有**好几个这样的项目**; 而它们**用同一对端口**.

所以关掉我的服务器这句话里的**我的**, 需要被精确定义. 定义错了就会杀掉别人的.

两种想当然的做法都会误杀:

| 做法 | 为什么不行 |
| :--- | :--- |
| 扫进程列表, 命令行里含 `uvicorn` 或 `next dev` 就杀 | 完全不看进程属于哪个目录. 机器上任何一个 Node 项目的开发服务器都会中枪 |
| 对 3000 和 8000 无条件查出占用者然后杀 | 查端口的命令**不区分在监听还是只是连着**. 一个浏览器标签页也可能被返回并杀掉 |

这个脚本用的规矩是:

> **一个进程只有能被证明属于这个 checkout, 才会被杀.**

证明有三种, 满足任意一种即可:

| 证据 | 说明 |
| :--- | :--- |
| 环境变量里带着这个 checkout 的标记 | `mise.toml` 给两个 dev 任务都设了一个环境变量, 值是**这个 checkout 的绝对路径**. 子进程自动继承, 所以给树顶打标就等于给整棵树打标 |
| 工作目录就是项目根目录 | 手工起的服务器的兜底 |
| 它是满足上面两条之一的进程的后代 | 顺着进程树往下找 |

其余一律不动, 只报告, 并且**退出码非零**, 于是依赖它的 `mise run dev` 会停下来.

顺带说一个小设计: 那个标记的**名字** 对所有从这个脚手架长出来的项目是一样的, 身份藏在**值**
里 (checkout 的绝对路径). 所以你的第二个第三个项目可以用同一个变量名, 谁也杀不到谁.

### 顺便: `package.json` 里那几个同名命令不要用

打开 [`package.json`](../../package.json), 你会看到 `dev`, `next-dev`, `fastapi-dev` 这几个
名字, 和 mise 里的任务一模一样.

**别用它们.** 它们少了那个环境变量标记 (于是杀不掉), 也少了先 kill 那一步 (于是端口可能还
被占着). 它们留着只是因为部署平台的构建过程要读 `package.json` 里的 `build`.

## 11. 排查清单

这一节是拿来用的, 不是拿来读的. 起不来的时候按顺序过一遍.

| 症状 | 大概率是什么 | 怎么办 |
| :--- | :--- | :--- |
| 报端口被占, 而且 kill 那一步退出码非零 | 有别的东西占着端口, 而且脚本证明不了它是你的 | 找出那个进程自己停掉; 确定要抢的话, 那个脚本有一个强制参数 |
| 页面能开, 但按钮点了没反应 | 后端那个进程没起来, 或者挂了 | 看终端里后端那一路的输出 |
| 页面能开, agent 也答, 但答的东西不像你的数据 | 你的前端不在 3000 上, 转发接到了别人的后端 | 确认前端到底跑在哪个端口 |
| 改了 `data/` 下的文件页面没变 | 那几个文件是构建时读的 | 终端里 Ctrl+C, 再 `mise run dev` |
| 改了组件页面没变 | 少见, 通常是热更新卡了 | 同上, 重启一次 |

**卡住了就把这一节连同你看到的报错一起复制给 AI.** 这类问题的信息量全在报错的具体措辞里,
而那正是它擅长读的东西.

## 12. 练习

### 练习 1: 亲眼看那条转发规则在工作

**目标:** 确认 8000 那个进程真的存在, 而且浏览器确实不知道它.

**怎么做:**

1. 起开发服务器, 保持它跑着
2. 浏览器打开 `http://localhost:3000`, 正常
3. 现在直接打开 `http://localhost:8000/api/hello`. **这是后端的健康检查地址**, 你应该看到
   一小段 JSON
4. 再打开 `http://localhost:3000/api/hello`. 你应该看到**同样的 JSON**, 而地址栏还停在 3000
5. 打开 `http://localhost:8000`, 看看会发生什么

**你会观察到:**

第 3 步和第 4 步的内容一样, 但走的路不一样: 前者你直接敲了后端, 后者是前端服务器替你转发的.
而第 5 步大概率什么都没有, 因为**后端只管 `/api/` 那几个路径**, 页面全在前端那边.

> **关键洞见:** 这两个端口在开发时是两个真实存在的服务器, 而线上只有一个入口. 本地这套接线
> 是临时结构, 别把它当成这个 app 的架构.

### 练习 2: 让那个 kill 脚本报告一次

**目标:** 看清它凭什么判定一个进程是你的.

**怎么做:**

1. 保持开发服务器跑着, 另开一个终端
2. 跑一次只报告不动手的模式:

```bash
.venv/bin/python kill-dev-servers.py --dry-run
```

3. 读输出: 它列出了哪些进程, 每个是凭哪条证据被认领的
4. 现在换一种起法, 先把原来的停掉, 手工在项目根目录起一个前端:
   `pnpm exec next dev --port 3000`. 再跑一次 `--dry-run`, 看它还认不认得出来
5. 停掉一切, 回到 `mise run dev`

**你会观察到:**

第 3 步里每个进程后面都跟着一条理由. 第 4 步那个手工起的进程**没有那个环境变量标记**, 但
它的工作目录是项目根, 所以第二条证据接住了它.

> **关键洞见:** 一个安全的批量操作, 靠的不是把匹配条件写得更严, 是要求每个目标都能被证明
> 属于这次操作的范围. 证明不了就不动, 并且说出来.

## 13. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 前后端分离 | 把一个网站劈成两半: 一半管长什么样, 一半管数据和业务规则 |
| 它们怎么说话 | HTTP 请求, 一问一答, 传的是 JSON 数据不是拼好的页面 |
| 分开的好处 | 各用最合适的语言, 各自可以被换掉, 一个后端可以喂很多个前端 |
| 分开的代价 | 要管两个程序, 它们要能找到对方, 还有浏览器那条跨地址的安全规则 |
| 这个项目怎么接 | 一条 rewrite 规则, 把 `/api/*` 从 3000 转发到 8000. 浏览器全程不知道 |
| rewrite 不是 redirect | 浏览器不知道, 地址栏不变, 请求只走一趟. 那条安全规则也就不会被触发 |
| 线上没有这套 | 只有开发环境才转发. 线上前端是静态产物, 后端是按需拉起的函数 |
| 端口钉死 | 允许自动跳的话可能接到别的项目的后端. 起不来比静默接错好 |
| kill 的规矩 | 能被证明属于这个 checkout 才杀. 三种证据: 环境标记, 工作目录, 是它们的后代 |

## 14. 导师寄语

**为什么这一篇一大半在讲概念:**

前后端分离这个词你以后会一直听到, 而它其实很简单: 把长什么样和数据是什么拆成两个程序.

值得花时间的不是这个定义, 是**它带来的连锁反应**. 一旦拆开, 你就要处理它们怎么找到对方,
浏览器的安全规则怎么绕, 本地和线上结构为什么不一样, 两个进程怎么管. 这些都不是可选的麻烦,
是拆开这个决定的必然后果.

看清一个决定的连锁反应, 比记住那个决定本身有用得多. 因为你以后自己做设计的时候, 要判断的
恰恰是这个: 这么做, 后面会多出什么麻烦, 我认不认.

**关键洞见:**

- 前后端只通过一个约定好的接口打交道, 互相不知道对方内部长什么样
- 本地开发的结构不等于线上的架构. 分不清这一点, 线上出问题时你会去找一个不存在的东西
- 破坏性操作要求证明, 不要求匹配. 证明不了就不动, 并且说出来

**下一步:**

这一篇说两边靠一个约定好的接口打交道. 那个约定具体长什么样, 谁定的, 为什么值得郑重其事地
叫它一个协议? 第 17 篇 ([AI SDK 协议](../17-the-ai-sdk-protocol/README-cn.md)) 讲这件事.

## 15. 速查

**两个端口:**

```text
3000   前端开发服务器 (Next.js)
8000   后端 (uvicorn 跑 FastAPI)
```

**转发规则在哪:**

[`next.config.js`](../../next.config.js) 的 `rewrites`. 开发环境把 `/api/*` 转到
`127.0.0.1:8000`, 生产环境走平台自己的路由.

**日常命令:**

```bash
mise run dev
```

它先 kill, 再并发起两个服务器.

```bash
mise run kill
```

它只停掉本 checkout 的服务器, 别人的不动.

**排查:**

```bash
.venv/bin/python kill-dev-servers.py --dry-run
```

带上 `--dry-run` 就只报告它认为该杀哪些进程, 不真的动手.

**两条不要:**

- 不要用 [`package.json`](../../package.json) 里那几个同名命令
- 不要让前端自动跳端口
