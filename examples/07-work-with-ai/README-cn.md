# 和 AI 一起改这个仓库

> 这个仓库不是碰巧能被 AI 改, 它是照着让 AI 改得动的样子设计的. 这一篇讲那些设计是什么.

## 1. 概览

第 4 篇 (把它跑起来) 教了怎么把助教叫起来, 第 6 篇 (教学层和生产层) 讲了那条边界的一个副
作用: 层次分明的仓库, 派给 AI 的任务写得成一句话.

这一篇把这件事讲完整. 它回答三个问题: **AI 打开这个仓库先读到什么, 它被允许碰什么, 以及
你该怎么派活.**

这不是一篇讲 prompt 技巧的文章. 讲的是**仓库这一侧要准备什么**, 因为一个 AI 干得准不准,
大半取决于它面对的是一个什么样的代码库.

---

## 2. 学习目标

先说一个对比, 它解释了这一篇为什么值得单独占一篇.

**任务一**: 把界面上所有提到贷款的地方改成提到订单. 在这个仓库里, 这句话等于打开
`data/site.toml` 改. 在一个文案散在二十个组件里的仓库里, 这句话等于全仓库搜一遍, 然后逐处
判断哪些该改哪些不该, 而这件事**每次都会漏, 而且漏得不报错**.

同一个模型, 同一句提示, 结果差得远, 差的不是模型是仓库.

反过来在 review 的时候也一样. 一次换数据集的改动
**应该只落在 `data/`, `dataset/` 和 `.env.defaults` 三个地方**.
落到别处就是信号, 你不用逐行读也知道有东西越界了. 边界清晰的仓库, 改动的形状本身就是一种
检查.

学完这个 Task, 你将能够:

1. 说出这个仓库给 coding agent 准备的三套东西各是什么, 分别在什么时候被读到
2. 解释为什么长文档要拆成一份总纲加一批按需加载的 skill
3. 读懂权限文件, 说出哪些操作被无条件拒绝以及为什么是这几个
4. 用一句话派出一个改得准的任务, 并用改动落点检查它有没有越界

## 4. 你将学到什么

一张这个仓库和 AI 之间的接口地图, 加一条派活的纪律.

带走的那条纪律是: **让它先说计划, 一步一步做, 然后拿改动落点验收.** 这三件事任何一件缺了,
你都会收到一堆看起来对但你不敢合并的改动.

---

## 5. AI 进门先读到什么

不同的 coding agent 认不同的文件名, 所以这个仓库把同一份内容摆在几个地方:

| 文件或目录 | 谁读 | 说明 |
| :--- | :--- | :--- |
| `CLAUDE.md` | Claude Code | 这个仓库的总纲, 进门自动读进去. 里面是目录结构, 两种配置的区别, 改什么就改哪个文件的对照表, 以及跑测试和起服务的命令 |
| `AGENTS.md` | 多数别的 agent | 一份很短的开发环境说明. 它故意短, 因为长内容都在 skill 里, 不该塞进一份每次都全量读进上下文的文件 |
| `.agents/rules/`, `.codex/rules/` | 其它 agent 各自的规则文件 | 同一批约定换个格式再放一份. 顶上那行 `trigger: always_on` 是那个工具用来决定要不要每次都加载的标记 |
| `.claude/skills/`, `.agents/skills/` | 两套 agent 各自读自己那份 | 按需加载的深度文档. 两份内容一样, 只有里面写的路径各指各的目录 |

**为什么要分成总纲和 skill 两层**, 而不是把所有东西写进一个大文件:

一份进门就全量读进去的文档, 每多一千字就多花一千字的上下文, 而且
**跟当前任务无关的那部分还会分散注意力**.
所以总纲只放地图和索引, 真正展开的内容切成一篇篇 skill, 用到哪篇加载哪篇.

打开 `.claude/skills/about-bi-agent-app-scaffold-cn/SKILL.md` 你会看到它开头就是一张
按任务查的表: 要重构就读这篇, 要加 agent tool 就读那篇, 要换数据集就读另一篇. **skill 的
入口文件本身是一个路由器, 不是内容.**

## 6. 这个仓库有哪几个 skill

| skill | 什么时候用 | 说明 |
| :--- | :--- | :--- |
| `about-bi-agent-app-scaffold-cn` | 动手改这个仓库之前 | 事实标准, 分架构, 后端, 前端, 运维四块, 三十多篇. 讲的是这个仓库为什么长成这样, 哪条边界破了会怎样 |
| `swap-dataset-cn` | 想搞清楚换数据集的全貌 | 只是索引和路由, 本身不含任何操作步骤. 它回答这件事分几个阶段, 现在该敲哪条命令 |
| `run-swap-dataset-phase-1-cn` | 真的要换数据集, 第一阶段 | 造库, 同步 PostgreSQL, 重写提示词和全部界面文案 |
| `run-swap-dataset-phase-2-cn` | 第二阶段 | 照着新行业的调性重新设计前端: 布局, 配色, 字体 |
| `frontend-design` | 做视觉设计 | 通用的前端设计规范, 不是这个仓库特有的 |

换数据集为什么要拆成一个索引加两条命令, 而不是写成一个大 skill: 一个 skill 被调用之后
**以一条消息的形式留在对话里**, 后面不会被重新读取, 而上下文压缩时每个 skill 只保留开头
一部分.
把两个阶段写在一起, 跑完第一阶段通常已经压缩过, 排在文件末尾的第二阶段正好是被截断的那一段.
拆开之后, 第二阶段在真正需要它的那一刻才第一次完整进入上下文.

这两条命令你在第 36 篇 (换数据集) 和第 37 篇 (重新设计前端) 会真的敲.

## 7. AI 被允许碰什么

`.claude/settings.json` 是权限文件. 它有两个名单.

**allow 名单** 列出不需要每次问你就可以做的事: 改 `data/` 下的内容, 改各种 Markdown 文档,
改 `scripts/` 下的 Python, 跑 `mise` 命令, 跑 `.venv/bin/python scripts/**`, 联网搜索.

**deny 名单只有很短的几条, 但它是这个文件里最重要的部分**:

```json
"deny": [
    "Read(.env)",
    "Read(.env.local)",
    "Read(.envrc)",
    "Edit(.env)",
    "Edit(.env.local)",
    "Edit(.envrc)",
    "Read(~/.aws/credentials)"
]
```

**读和写都被拒绝, 而且是无条件的.** 这几个文件装的是你的 API key, 数据库密码, AWS 凭据.

这条限制和第 4 篇那条**不要把 key 贴进任何聊天窗口** 是同一件事的两半: 那一半管你的手, 这
一半管 AI 的手. 少了任何一半, 凭据都会流进一个你控制不了的地方 (对话记录, 日志, 别人的
服务器).

**副作用是好的**: 因为 AI 打不开 `.env`, 你让它帮忙调配置时它只能改 `.env.defaults`, 而那
个文件里没有秘密, 还进 Git, 所以它改了什么在 `git diff` 里一目了然.

这也解释了第 4 篇里那句话: 换数据集时 AI 可以自由编辑 `.env.defaults`, 但碰不到任何人的
凭据.

## 8. 怎么派活

三条, 按顺序.

### 一, 让它先说计划

派活的时候要求它**先列出打算改哪些文件, 每个文件改什么, 然后停下来等你确认**. 不要一上来
就让它动手.

理由是这个仓库有一堆不写出来就看不见的边界 (组件里不许有业务文案, 生产路径不 import 教学层,
渲染契约的三半要一起改). 一个计划是纯文本, 你扫一眼就知道它有没有踩线; 一堆已经写好的
改动要看懂就贵多了.

### 二, 一步一步做

这条第 4 篇已经讲过, 这里再钉一遍, 因为它在真正改代码的时候更要紧: ** 一次改一件事, 改完
你自己跑一遍验证, 再走下一步.**

一口气改十个文件的问题不是它会改错, 是**出错的时候你不知道是哪一步错的**. 拆开之后每一步
都有一个明确的验收动作, 错了当场就知道.

### 三, 拿改动落点验收

改完先看 `git status` 和 `git diff --stat`, 别急着读内容. **落点不对就不用读了.**

| 你派的活 | 改动应该只落在 |
| :--- | :--- |
| 改一句界面文案 | `data/site.toml` |
| 换整个业务领域 | `data/`, `dataset/`, `.env.defaults` |
| 给 agent 加一个工具 | `agent_app/one/one_04_agent.py`, `data/system-prompt.md` |
| 改配色 | `tailwind.config.ts` |

落到别处就是越界的信号. 这个检查便宜到几乎免费, 而且它在你读一行代码之前就能给出结论.

## 9. 练习

### 练习 1: 派一个真实的小任务, 拿落点验收

**目标:** 走一遍完整的派活流程, 并用改动落点检查结果.

**怎么做:**

1. 确认工作区是干净的: `git status --short`
2. 加载 skill: 敲 `/about-bi-agent-app-scaffold-cn`
3. 派这个任务, 并且明确要求先出计划:

```text
把 agent 页输入框的 placeholder 文字改成一句更具体的提示.
先告诉我你打算改哪些文件, 每个文件改什么, 然后停下来等我确认, 不要直接动手.
```

4. 读它给的计划. 它应该只提到一个文件
5. 确认之后让它改, 然后跑 `git diff --stat`
6. 跑 `mise run dev` 打开 agent 页, 确认那句话真的变了
7. `git checkout -- .` 还原

**你会观察到:**

计划里应该只有 `data/site.toml` 一个文件. 如果它提出要改
`components/chat/multimodal-input.tsx`, 那说明它没读到组件里不许有业务文案这条规矩, 这时候
把它指回那份 skill.

> **关键洞见:** 改动落点是一个在你读代码之前就能用的检查. 一个边界清晰的仓库, 越界这件事
> 在 `git diff --stat` 那一屏上就看得见.

### 练习 2: 让它撞一次权限墙

**目标:** 亲眼确认 deny 名单是真的拦得住, 而不是一句约定.

**怎么做:**

1. 问它一个需要读 `.env` 才能回答的问题, 比如:

```text
读一下 .env, 告诉我 DB_HOST 现在填的是什么
```

2. 看它的反应
3. 再问一个它能答的: 让它读 `.env.defaults`, 告诉你 `SCHEMA_NAME` 是什么
4. 对比两次的差别

**你会观察到:**

第一次它读不到, 因为那条路径在 deny 名单里. 第二次它能读, 因为 `.env.defaults` 里没有秘密.
这条线不是靠 AI 自觉, 是配置文件写死的.

> **关键洞见:** 涉及凭据的规矩不要写成提示词里的一句请不要, 要写成一条机械的拒绝. 前者是
> 建议, 后者是墙.

## 11. 导师寄语

**为什么这一篇不是讲 prompt 技巧:**

网上大量内容在教怎么把话说得更巧, 而实际工作里, 同一句话在两个仓库里的效果可以差出十倍.
差别不在措辞, 在那个仓库有没有把该集中的东西集中起来, 有没有把该拦的东西拦住.

所以想让 AI 帮上忙, 花在整理仓库上的时间, 通常比花在打磨提示词上的时间回报高得多. 这一篇
讲的每一样东西都是这个方向的投资.

**关键洞见:**

- 一个 AI 干得准不准, 大半取决于它面对的是一个什么样的代码库, 不是取决于你怎么说话
- 先要计划再要代码. 计划是纯文本, 扫一眼就能判断有没有踩线
- 涉及凭据的限制要做成机械的拒绝, 不要做成提示词里的一句请不要

## 12. 速查

**三套东西:**

- 总纲: `CLAUDE.md` (Claude Code), `AGENTS.md` 与各家的 rules 文件 (其它 agent)
- 深度文档: `.claude/skills/` 与 `.agents/skills/`, 按需加载
- 权限: `.claude/settings.json` 的 allow 与 deny 名单

**这个仓库的 skill:**

```text
/about-bi-agent-app-scaffold-cn    改这个仓库之前先读
/swap-dataset-cn                   换数据集的索引与路由
/run-swap-dataset-phase-1-cn       换数据集, 换内容
/run-swap-dataset-phase-2-cn       换数据集, 换视觉
```

**派活三步:**

1. 先要计划, 不要代码
2. 一步一步做, 每步自己验一次
3. `git diff --stat` 看落点, 落点不对就不用读内容了
