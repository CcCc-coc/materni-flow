# 内容也会错, 而且一样不报错

> 上一篇讲的是代码的检查. 但这个项目里最容易出错的那些东西根本不是代码: 提示词, 界面文案,
> 那 12 个按钮, 数据本身.

## 1. 概览

上一篇结尾留了一个口子: 那套跑得飞快的测试保护的全是 `agent_app/` 里的 Python.

**可这个项目一半的正确性根本不在 Python 里.**

想想换一次数据集会改哪些东西 (第 2 篇那张表): 提示词, 界面文案, 首页那份长说明, 数据本身.
这几样全是人写的散文和配置, 一个 Python 测试都盖不到. 而它们出错的方式和配置一样阴:

| 哪里错了 | 症状 |
| :--- | :--- |
| 提示词里的 SQL 例子查了一张不存在的表 | 不报错. 模型照抄, 数据库拒绝, 模型换个写法接着编 |
| 那 12 个按钮里有一条徽章和实际输出对不上 | 不报错. 按钮画着表格图标, 点开是一段散文 |
| `data/` 下少了一个文件 | 不报错. 那块界面渲染成空白 |
| 数据的外键成环 | 不报错. 灌数据的时候才发现没有任何顺序能满足 |

所以这个项目有第二套检查, 专门查内容. 它就是你从第 5 篇起看过好几次的那条命令:

```bash
mise run cli-check-content
```

**但这一篇真正的重点在后半段.** 前面讲那四项检查各拦住什么, 后面讲一个更难的问题:
**什么东西不该做成检查, 以及那时候该用什么代替.**

### 卡住了怎么办

这一篇每一步都可能出错: 检查命令跑不起来, 或者你看到的输出和这里写的不一样.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/32-content-checks/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/32-content-checks/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

大多数关于自动化检查的讨论只有一个方向: **还能再加什么检查.** 加得越多听起来越负责.

这一篇想给你另一半, 而且那一半更难:

> **一个会误报的检查, 比没有检查更糟.**

理由很简单也很致命: **它训练人忽略输出.** 一个每次都报三条警告而三条都不用管的检查, 跑上
两个星期之后, 所有人都学会了直接翻过那一屏. 那一天起, 它连真正的错误也拦不住了, 而且没
有人知道它已经失效了.

所以决定加一个检查之前, 那个真正的问题不是这件事重不重要, 而是:

> **这件事的判据, 机械可判吗?**

判得了就写成脚本. 判不了的话, 这一篇会给你另一个办法, 而且那个办法零成本.

学完这个 Task, 你将能够:

1. 说出内容检查的四项各拦住什么样的失败
2. 解释那 12 个按钮的检查为什么必须**两个方向都查**, 只查一边会漏掉哪一半
3. 用机械可判这条判据, 决定一件事该不该做成自动检查
4. 说出判不了的时候该用什么代替, 以及为什么那个办法零成本
5. 说清这个项目里还有哪几件事**没有任何自动检查**, 只能靠人

## 4. 你将学到什么

四项检查的清单, 加两条判据.

第一条判据是**加不加**: 机械可判吗.

第二条判据更值钱, 是**判不了的时候怎么办**. 剧透一下答案: **用顺序代替检查.** 它听起来
太简单了, 但它是这个项目里最有效的一个设计, 而且不花一分钱维护成本.

## 5. 四项检查, 各拦住什么

跑一次:

```bash
mise run cli-check-content
```

输出大概是这样:

```text
Content consistency check
============================================================
  PASS  table insert order (10 tables)
  PASS  prompt table references (9 found)
  PASS  content files
  PASS  render quota (12 questions)
============================================================
```

四项, 一项一项看它们各在防什么.

**一, 建表顺序.** 它不检查顺序对不对, 顺序是算出来的 (第 15 篇讲过), 算出来的东西不会
算错. 它检查的是**算得出来吗**: 数据的外键有没有成环. 成了环, 任何顺序都不成立, 而这件事
要到灌数据灌到一半才暴露.

**二, 提示词里的表名.** 它把提示词里所有 SQL 例子挑出来, 看它们 `FROM` 和 `JOIN` 的表在不
在真实的库里. 这一条拦的正是换数据集最典型的事故: 文案都改了, 提示词里某段 SQL 还留着上一个
行业的表名.

**三, 内容文件在不在.** `data/` 下该有的三个文件, 缺一个或者只剩一个空壳都算失败.

**四, 那 12 个按钮的配额.** 下一节单独讲, 因为它是四项里设计得最有意思的一项.

### 顺带一个和教学层有关的细节

前两项要读那份本地数据种子, 而种子属于教学层, 学生学完之后会把整个教学层删掉 (第 7 篇
讲过).

那删掉之后这条命令会怎样? **它不会崩.** 那两项降级成跳过, 另外两项照常跑.

这个处理是刻意的, 而且理由不是为了少改一行配置: 剩下那两项 (内容文件在不在, 12 条按钮的
配额对不对) 在一个**已经交付出去的仓库** 里**仍然有意义**. 它们守的是 `data/` 和前端之间的
契约, 和课程没有关系.

> **一条可以带走的做法**: 当一个检查依赖一个可能被删掉的东西时, 让它**降级**, 不要让它
> 崩. 一个带着报错死掉的命令, 会把那些本来还能跑的检查一起拖下水.

## 6. 那 12 个按钮: 为什么要查两遍

这一项值得单独讲, 因为它示范了一件容易想漏的事: **一个契约有两半的时候, 只查一半等于没查.**

回忆第 11 篇: 每个 kickstart 按钮有两样东西.

| 是什么 | 干什么用 |
| :--- | :--- |
| `render` 字段 | **对读者的承诺**. 前端据它在按钮上画表格 / 流程 / 柱状的小图标 |
| `action` 里那句触发短语 | **真正让那种东西出现的原因**. 模型跟的是措辞 |

这两样**可以各自独立地写错**:

- `render` 写着 `chart`, 措辞里忘了写那句触发短语, 于是按钮画着柱状图标, 点开是一段散文
- 措辞里有那句短语, `render` 却写成 `free`, 于是会画出图, 但按钮没有告诉读者

**只查 `render`, 第一种漏掉; 只查短语, 第二种漏掉.** 所以这个检查两个方向都跑.

亲手看一次:

```bash
.venv/bin/python examples/32-content-checks/01_both_directions.py
```

这个脚本用几条**编出来的** 问题喂给真正的判定函数, 不碰 `data/site.toml`. 你会看到四种不
一致各自长什么样, 包括一个很容易犯的: 措辞漂成了一个同义词.

### 为什么短语要写死成字面量

看那个脚本最后打印的短语表, 你会发现它们是逐字匹配的. `as a bar chart` 算, `as a bar graph`
不算.

这看起来太死板了, 但它是有理由的: **这个项目要跑得起小模型, 而小模型跟的是措辞, 不是意图.**
一个大模型也许能从 bar graph 领会到你要一张图, 一个小模型不会.

所以这份检查的严格, 是在保护那些跟不上意图的模型.

## 7. 判不了的时候: 用顺序代替检查

现在到这一篇最重要的一节.

上面那些检查有一个共同点: **它们的判据都是机械的.** 数一数是不是三条, 字符串里有没有那句
话, 文件在不在, 图里有没有环. 这些事情写成脚本很自然.

那**判不了的那些** 呢? 比如这一条:

> 那 12 个问题**问得好不好**?

这件事比任何一项机械检查都重要. 一个问得很烂的按钮, 措辞完全合法, 配额完全正确, 每一项检查
都绿, 而读者点下去看到的是一堆没用的东西.

**那要不要给它加一个检查?**

不要. 因为它的判据是自然语言语义, 你只能做成模糊匹配, 而模糊匹配必然产出一堆需要人工判断的
警告, 于是回到开头那条: **它会训练人忽略输出.**

### 那怎么办

这个项目的答案是**用顺序**.

换数据集的时候, 那几样内容不是并行写的, 而是**排成一条链**:

```text
数据集的源文档  ->  提示词  ->  12 个按钮 / 能力卡 / 首页文案
```

而规矩是: **每一步只从上一步的产物推导, 不回头读原始文档.**

于是那 12 个按钮是**照着提示词** 改写成用户口吻的. 提示词里没教过的分析, 你在按钮里写不
出来, 因为你手上根本没有那个素材.

**漂移因此无从发生**, 不是因为有东西在拦, 是因为**产生它的那条路径上不存在那个可能**.

### 它有多便宜

对比一下两种做法的成本:

| | 加一个检查 | 用顺序 |
| :--- | :--- | :--- |
| 写的时候 | 要写代码, 要写它的测试 | 不写任何东西 |
| 用的时候 | 每次跑, 每次要人判断警告 | 什么都不用做 |
| 出错的时候 | 可能误报, 而误报会累积成忽略 | 不存在误报 |
| 维护 | 判据变了要跟着改 | 不用维护 |

**顺序是零成本的, 检查是有成本而且不可靠的.**

> **这一节是这篇最想让你带走的东西**: 下次你想给一件事加检查的时候, 先问机械可判吗;
> 判不了的话, 别急着做一个模糊的检查,
> 先想想**能不能改变产生它的顺序, 让那个错误压根没有机会发生**.

## 8. 绕开顺序有多容易

上一节那条规矩听起来很稳, 但它有一个非常自然的破法, 值得单独点出来.

写那 12 个按钮的时候, 手边有两份材料: 提示词, 和数据集那份原始的分析文档. 后者更详细, 例子
更多, **看起来是更好的素材**.

于是一个很合理的动作就是: 打开原始文档, 从里面挑 12 个漂亮的问题写成按钮.

**这么做, 所有检查都会通过.** 措辞合法, 配额正确, 表名也都存在.

**而那些按钮里会混进几条提示词根本没教过的分析.** 只有当一个真实的读者点下去, 模型才开始
即兴发挥.

所以那条规矩的完整版是:
**提示词定义能力边界, 下游只能换措辞, 不能新增一项提示词没教过的能力.**
挑不出 12 条来, 说明提示词覆盖不够, 该回去补提示词, 而不是在这里现编.

> 这也解释了为什么顺序这个办法虽然零成本, 却仍然需要被**写下来**. 它不像检查那样会自己
> 拦你, 它只在你知道它存在的时候才起作用.

## 9. 还有三件事完全没有自动检查

诚实收尾. 这个项目里最贵的三条边界, **一条自动检查都没有**:

| 没被检查的 | 只能怎么办 |
| :--- | :--- |
| 换数据集时 `agent_app/` 真的一行没改 | 看 `git diff` 的落点. 落到别处就是越界 |
| 模型真的照着提示词产出了那些块 | 手点一遍那 12 个按钮 |
| 提示词里的 SQL 在真库上跑得通 | 自己对着真库跑一遍 |

前面那些能自动化, 是因为它们的判据机械可判. 这三条不是, 它们全都要求你**看结果对不对**,
而对不对这件事没有字符串能表达.

**第二条尤其要认.** 那个配额检查只能证明**问法写对了**, 证明不了**模型照做了**. 这两件事
之间的差距只有人点一次才看得见, 而且这个差距在换一个更小的模型之后会变大.

> 这不是设计上的缺憾, 是能力的边界. 而把它**明确写出来** 本身就有价值: 一个团队知道自己的
> 自动化盖到哪儿为止, 比一个以为全都盖住了的团队安全得多.

## 10. 练习

### 练习 1: 看清楚一个契约的两半

**目标:** 亲眼确认为什么只查一个方向会漏掉一半错误.

**这个练习不改任何文件, 不需要凭据, 不需要联网.**

**怎么做:**

1. 先跑一次真实的检查, 看它四项全绿:

```bash
mise run cli-check-content
```

2. 再跑这一篇那个脚本:

```bash
.venv/bin/python examples/32-content-checks/01_both_directions.py
```

3. 读那五个例子, 对每一个不一致的问自己一句: **如果只查 `render` 会不会漏掉它? 只查短语呢?**
4. 看它打印的那张短语表, 找出 `table` 那一行和别的行的区别
5. 打开 [`data/site.toml`](../../data/site.toml) 找到那 12 条, 挑一条 `render` 是 `table`
   的, 在它的 `action` 里把那**两句** 短语都找出来

**你会观察到:**

第 3 步里, 那五个例子里有两个只查 `render` 会漏, 有一个只查短语会漏. 两个方向都查, 才一个
不漏.

第 4 步那个区别是: `table` 需要**两句** 短语同时出现, 一句要表格, 一句要那段 SQL. 少了
后面那句, 读者就没法验算模型给的数字.

> **关键洞见:** 一个契约如果有两半, 那检查也必须有两半. 只查一边的检查会给你一种已经查过
> 了的错觉, 而那种错觉比不查更危险.

### 练习 2: 亲手弄坏一次, 看它拦不拦得住

**目标:** 确认这些检查不是摆设, 并且看清它的报错说不说得清该改哪儿.

**怎么做:**

1. 开一个叫 `32-content-checks` 的 branch
2. 打开 [`data/site.toml`](../../data/site.toml), 找到那 12 条 kickstart 里**任意一条**
   `render = "chart"` 的
3. 把它的 `render` 改成 `"free"`, 别动 `action` 那句话
4. 跑 `mise run cli-check-content`, 读那条报错
5. 把 `render` 改回去, 这次改 `action`: 把里面那句 `as a bar chart` 删掉, 别动 `render`
6. 再跑一次检查, 读这一条报错
7. 对比第 4 步和第 6 步: **这两条报错一样吗? 它们各自告诉你去改哪儿?**
8. 全部改回原样, 跑一次确认四项恢复全绿
9. 跑 `git status`, 确认工作区干净

**你会观察到:**

第 4 步和第 6 步都会失败, 但报错内容不同: 一条说 `render` 声明的和措辞产生的对不上, 另一条
还会顺带报出某一类的数量不够. **两条都点名了是第几个问题, 以及它的标题.**

第 5 步那种改法最像真实事故: 换数据集的时候重写措辞, 顺手把那句触发短语丢了, 而 `render`
没动.

> **关键洞见:** 一个检查的价值不只在于它拦住了, 还在于它拦住之后你要花多久才知道该改哪儿.
> 这几条报错都带着位置和标题, 就是为了省掉那段时间.

## 11. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 为什么内容需要单独的检查 | 这个项目一半的正确性在人写的散文和配置里, Python 测试一个都盖不到 |
| 四项检查 | 外键有没有成环, 提示词的表名在不在, 内容文件缺没缺, 12 个按钮的配额对不对 |
| 降级而不是崩 | 依赖教学层的那两项在教学层被删掉之后跳过, 另外两项照常跑 |
| 两个方向都查 | `render` 是给读者的承诺, 短语是真正的原因. 只查一边就漏一半 |
| 短语写死成字面量 | 因为这个项目要跑得起小模型, 而小模型跟的是措辞不是意图 |
| 加不加检查的判据 | 判据机械可判吗. 判不了就别做成模糊检查 |
| 判不了的时候 | **用顺序代替检查.** 每一步只从上一步的产物推导, 漂移就没有机会发生 |
| 顺序的成本 | 零. 不用写, 不用维护, 不会误报 |
| 顺序的弱点 | 它不会自己拦你, 所以必须被写下来 |
| 一个会误报的检查 | 比没有检查更糟, 因为它训练人忽略输出 |
| 剩下三件事没检查 | 换数据集的 diff 落点, 模型照没照做, 提示词的 SQL 跑不跑得通 |

## 12. 导师寄语

**为什么这一篇的后半段比前半段重要:**

前半段那四项检查, 你换个项目就用不上了, 它们是这个仓库特有的.

后半段那两条判据换到哪儿都成立. 而且第二条 (用顺序代替检查) 是很多有经验的人也没意识到的
一个选项. 大多数人面对一个不好检查的问题, 要么硬做一个模糊的检查, 要么放弃说这个只能靠人.

**其实还有第三条路: 改变产生它的流程, 让那个错误压根没机会发生.**

这个思路在别的地方也到处能用. 一个值不会不同步, 因为它只有一份; 一个顺序不会抄错, 因为它
是算出来的; 一条文案不会在两个页面上漂移, 因为两个页面读的是同一份数据. 你在前面几十篇里
其实已经见过这个思路很多次了, 这一篇只是第一次给它起了个名字.

**关键洞见:**

- 一个会误报的检查比没有检查更糟, 因为它训练人忽略输出
- 一个契约有两半, 检查也必须有两半
- 判据机械可判就写成脚本; 判不了就别硬做, 先想想能不能用顺序把那个错误挡在门外
- 顺序是零成本的, 但它不会自己拦你, 所以必须被写下来
- 明确知道自动化盖到哪儿为止, 比以为全都盖住了安全得多

这一组还剩两篇. 第 33 篇 ([花费上限](../33-the-spend-cap/README-cn.md)) 讲一个默认关着的
功能: 当这个 agent 被放到公网上, 付钱的人和打字的人不再是同一个人时, 你需要一道闸门.
它的设计里有一个很值得学的决定: **开关住在哪儿.**

## 13. 速查

**两条命令:**

```bash
mise run cli-check-content
```

```bash
.venv/bin/python examples/32-content-checks/01_both_directions.py
```

**四项检查:**

| 检查 | 拦住什么 |
| :--- | :--- |
| 建表顺序 | 外键成环, 或者种子里一张表都没有 |
| 提示词表名 | SQL 例子里 `FROM` 或 `JOIN` 了一张不存在的表 |
| 内容文件 | `data/` 下该有的文件缺失或者只剩空壳 |
| 渲染配额 | 12 个按钮的 `render` 和措辞对不上, 或者四类不是各 3 条 |

**两条判据:**

- **加不加**: 这件事的判据机械可判吗. 判不了就不加
- **判不了怎么办**: 用顺序代替检查. 每一步只从上一步的产物推导

**换数据集时那条顺序:**

```text
数据集源文档 -> 提示词 -> 12 个按钮 / 能力卡 / 首页文案
```
