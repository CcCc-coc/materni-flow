# 看懂内容那一半的检查

## 1. 目标

上一篇讲的是代码的检查. 但这个项目一半的正确性根本不在 Python 里: 提示词, 界面文案, 首页
那份长说明, 数据本身. 它们一样会错, 而且和配置一样, **错了不报错**.

所以有第二套检查, 就是你从第 5 篇起看过好几次的那条内容检查命令.

**但这一篇真正的重点在后半段**, 而且它比前半段耐用得多:

> **一个会误报的检查, 比没有检查更糟.** 它训练人忽略输出.

所以决定加一个检查之前, 真正的问题不是这件事重不重要, 而是**它的判据机械可判吗**. 判不了
的时候这一篇给了另一个办法, 而且那个办法零成本: **用顺序代替检查**, 每一步只从上一步的
产物推导, 于是漂移没有机会发生.

**练习 2 要动 `data/site.toml`, 记得先开 branch, 做完还原.** 那两处改法都是真实事故的样子,
所以值得亲手撞一次.

**卡住了别硬扛.** 把三样东西一起给 AI: 你在读哪一篇的路径, 你敲的那条命令, 以及
**终端打出来的原文** (整段复制, 不要截图, 不要只说一句报错了).

---

## 2. 要做的事情

1. 读完 README, 重点是第 7 节用顺序代替检查, 和第 9 节那三件没有自动检查的事.
2. 跑 `mise run cli-check-content`, 确认四项全绿, 并说出每一项在防什么.
3. 跑 `.venv/bin/python examples/32-content-checks/01_both_directions.py`, 读那五个例子.
4. 对每个不一致的例子回答一句: 只查 `render` 会不会漏掉它, 只查短语呢.
5. 看脚本打印的短语表, 说清 `table` 那一行和别的行差在哪, 以及为什么要那样设计.
6. 打开 `data/site.toml` 找到那 12 条, 挑一条 `render` 是 `table` 的, 在它的措辞里把两句
   短语都找出来.
7. 开一个叫 `32-content-checks` 的 branch.
8. 挑一条 `render` 是 `chart` 的, 只把 `render` 改成 `free`, 跑检查, 读报错.
9. 改回去, 这次只把措辞里那句触发短语删掉, 再跑检查, 读这一条报错.
10. 对比两条报错, 说清它们各自告诉你去改哪儿.
11. 全部还原, 跑一次确认四项恢复全绿, 再跑 `git status` 确认工作区干净.
12. 用机械可判这条判据, 判断三件事该不该做成检查: 提示词里有没有错别字, 那 12 条问得好不好,
    数据里有没有孤儿外键.

**预计用时:** 50 到 80 分钟

---

## 3. 检查清单

- [ ] **四项各防什么**: 你能说出建表顺序, 提示词表名, 内容文件, 渲染配额四项各拦住什么样
      的失败, 并说清前两项为什么在教学层被删掉之后是跳过而不是崩.
- [ ] **两个方向**: 你能说清 `render` 和触发短语分别是什么, 以及只查其中一边各会漏掉哪一种
      错误.
- [ ] **字面量匹配**: 你能解释那些短语为什么写死成逐字匹配, 理由要落在小模型跟的是措辞这
      件事上.
- [ ] **亲手弄坏过两次**: 你分别只改 `render` 和只改措辞各触发过一次失败, 能说清两条报错的
      差别, 以及哪一种更像真实事故.
- [ ] **加不加的判据**: 对那三件假想的事你都给出了判断, 并且理由用的是机械可判这条判据.
- [ ] **顺序代替检查**: 你能说出换数据集时那条链是什么, 以及为什么它能让漂移没有机会发生.
- [ ] **顺序的弱点**: 你能说清顺序不像检查那样会自己拦你, 所以它必须被写下来; 也能说出那个
      很自然的破法是什么.
- [ ] **知道盖不到哪儿**: 你能说出这个项目里完全没有自动检查的那三件事, 以及为什么配额检查
      证明不了模型照做了.
- [ ] **工作区干净**: 练习 2 改的每一处都还原了, `git status` 没有留下改动.
