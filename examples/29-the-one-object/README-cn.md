# 那一个对象 one

> 后端任何一个文件, 想要数据库连接, 想要配置, 想要 agent, 都是同一句
> `from agent_app.api import one`. 这一篇讲为什么可以这样, 以及代价是什么.

## 1. 概览

上一篇那条路走下来, `one.config`, `one.engine`, `one.agent` 出现了七八次. 再往前, 第 6 篇
([读一遍这个仓库](../06-read-the-codebase/README-cn.md)) 那张九步表上也全是它.

那是**同一个对象**. 整个后端只有它一个.

打开 [`agent_app/one/one_00_main.py`](../../agent_app/one/one_00_main.py), 这个文件短得可以
整个抄下来:

```python
class One(
    ConfigMixin,
    DbMixin,
    Boto3Mixin,
    AgentMixin,
):
    """Central class that combines all mixin functionalities for the application."""


one = One()
```

**就这些.** 一个类, 四个父类, 一个实例. 没有方法, 没有初始化逻辑, 连一行代码都没有.

而这一篇要讲清楚的是: **这么一个什么都不做的类, 凭什么值得单独一篇.**

### 卡住了怎么办

这一篇每一步都可能出错: 脚本跑不起来, 或者打印出来的东西和这里写的对不上.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/29-the-one-object/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/29-the-one-object/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

先想一个很实际的问题.

后端要用到的东西有好几样: 配置, 两个数据库连接, 一个 AWS 会话, 一个模型对象, 一个 agent.
它们之间还有依赖 —— 建 agent 要先有模型, 建模型要先有配置.

**这些东西该在什么时候建, 建了之后放哪儿?**

三种常见做法, 各有各的问题:

| 做法 | 问题 |
| :--- | :--- |
| 每次要用就现建一个 | 每个请求重开一次数据库连接, 重建一次 agent. 慢, 而且浪费 |
| 程序一启动就全建好 | **启动就要连数据库, 要有 API key** —— 一个只想跑单元测试的人也得先把这些配齐 |
| 到处传参数 | 每个函数都要多几个参数, 而且加一样东西要改一路的签名 |

第二条在这个项目上尤其致命, 因为它要**部署到一个按需拉起的环境** 里 (第 16 篇讲过). 冷启动
时多建一样东西, 用户就多等一会儿 —— 而那样东西可能这一次请求根本用不上.

### 这个项目的答案

> **一个全局对象, 上面每一样东西都是用到才建, 建了就记住.**

用大白话说, 它像一个**工具箱**: 箱子本身随手就能拿到, 但里面每一件工具是你伸手去拿的那一刻
才造出来的; 造好了就留在箱子里, 下次直接用.

学完这个 Task, 你将能够:

1. 说清用到才建这个模式解决了哪三个问题
2. 亲手验证 `one` 上的东西确实是按需建出来的
3. 说出那四个 mixin 各自管什么, 以及它们之间的依赖为什么只有一个方向
4. 解释为什么 boto3 那几个客户端是方法而不是属性
5. 说清一个全局单例的代价, 以及这个项目怎么处理它

## 5. 亲眼看一次用到才建

这一篇目录下有个脚本, 打印 `one` 上哪些东西已经建好了:

```bash
.venv/bin/python examples/29-the-one-object/01_what_gets_built.py
```

输出是这样:

```text

    engine                     -
    remote_postgres_engine     -
    boto_ses                   -

    agent                      -

Now read one.config.schema_name ...
  -> 'fintech_smb_lending_pipeline_medium'
```

**刚导入的时候, 六样东西一样都没建.** 读了一次配置之后, 只有配置建好了, 别的还是空的.

### 这解释了一件很实际的事

**这就是为什么这个项目 269 个测试一个都不联网** (第 31 篇会讲测试那一套) —— 不是因为测试
写得特别小心, 是因为**默认什么都不建**.

## 6. 那四个 mixin

`mixin` 这个词听起来很技术, 意思其实很朴素:
**把一个大类的功能, 按主题拆成几个文件, 再拼起来.**

打个比方. 那个工具箱如果做成一整块, 就是一个几百行的文件, 什么都在里面. 拆成四个抽屉之后,
你想改数据库那部分, 只打开那个抽屉就行.

| 抽屉 | 文件 | 里面装着 |
| :--- | :--- | :--- |
| 配置 | `one_01_config.py` | `config` |
| 数据库 | `one_02_db.py` | 两个引擎, 库结构字符串, 跑 SQL 的方法 |
| AWS | `one_03_boto3.py` | 会话, 以及几个服务客户端 |
| agent | `one_04_agent.py` | 模型, agent, 三个工具 |

### 文件名前面那个编号是有意义的

`01`, `02`, `03`, `04` 不只是排序, 它是**依赖方向**:

```text
01 配置   <- 谁都不依赖
02 数据库  <- 要用 01 的配置
03 AWS    <- 要用 01 的配置
04 agent  <- 要用 01 的配置, 03 的会话, 02 的库结构
```

**箭头只指向编号更小的.** 04 用 01, 但 01 从不回头用 04.

为什么这条规则重要? 因为它让你**可以从任意一个抽屉开始读**, 而不用担心读到一半发现它又绕回
前面去了. 你在第 6 篇读过一次这条链, 那时候是从叶子到入口; 现在你知道那个顺序是被文件名钉
住的.

> **给文件编号是一种很便宜的文档.** 它不需要任何人维护, 而且违反它的时候, 那行 import 语句
> 自己就很扎眼.

## 7. 为什么 boto3 的客户端是方法, 不是属性

这一节讲一个很小的例外, 它正好说明这个模式的边界在哪儿.

打开 [`agent_app/one/one_03_boto3.py`](../../agent_app/one/one_03_boto3.py), 你会看到:

- `boto_ses` (那个会话) 是**建一次记住** 的
- 而 `bedrock_runtime_client()` 和 `dynamodb_client()` 是**普通方法**, 每次调用都新建

为什么不一视同仁?

代码注释给的理由是: **建一个 boto3 客户端要解析那个服务的接口定义, 而这在冷启动时不便宜.**
一个不用 DynamoDB 的部署, 不该为一个它永远不碰的客户端付这个钱.

而做成方法的效果是: **一个都不用的部署, 一个都不会建.**

### 这里有个值得注意的分寸

如果连会话也做成方法, 那每次都要重新读一遍凭据, 那才叫浪费. 所以:

| 这个 | 怎么处理 | 为什么 |
| :--- | :--- | :--- |
| 会话 (所有客户端共用) | 建一次记住 | 大家都要用, 而且建一次就够 |
| 各个服务的客户端 | 每次新建 | **可能一次都用不上** |

> **判据不是能省就省, 是这样东西大概率会被用到吗.** 会的就记住, 不一定会的就别提前建.

## 8. 一个全局对象的代价

前面都在讲好处. 这一节讲代价, 因为**全局单例在很多地方是被当成坏味道的**, 你迟早会遇到有人
这么说.

那个批评是有道理的, 它指的是这些:

| 代价 | 具体是什么 |
| :--- | :--- |
| **状态是共享的** | 一个地方改了它上面的东西, 别处也变了 |
| **测试要小心** | 上一个测试碰过它, 下一个测试拿到的就不是干净的 |
| **依赖是隐形的** | 一个函数用了 `one.engine`, 从它的签名上完全看不出来 |

### 这个项目怎么处理这三条

**第一条**, 你在第 28 篇 ([一次 chat 请求](../28-one-chat-request/README-cn.md)) 已经亲手
撞到过一次: agent 对象是跨请求活着的, 所以每次请求要
**先把它的记忆清空** 再灌历史 —— 不清空的话, 第二个用户会读到第一个用户的对话.

**第二条**, 靠的是第 5 节那个默认什么都不建 —— 大多数测试根本不碰 `one`.

**第三条** 没有被完全解决, 但被限制住了: 那些真正干活的底层函数 (比如
[`sql_utils.py`](../../agent_app/sql_utils.py) 里那几个) **都是纯函数**, 第一个参数就是那个
连接 —— 你在第 24 篇和第 27 篇见过这个形状.

于是形成了一个分工:

| 谁 | 依赖怎么来 |
| :--- | :--- |
| `one` 上的那些方法 | 从 `self` 上拿, 方便 |
| 底层纯函数 | **参数传进去**, 可测 |

> **关键洞见:** 全局单例的问题不在于它存在, 在于**它渗透得有多深**. 这个项目把它挡在了一层
> 薄壳上, 壳底下全是纯函数.

## 9. 练习

### 练习 1: 跑那个脚本, 然后画出那条依赖链

**目标:** 亲眼确认用到才建, 并把四个抽屉的关系理清楚.

**怎么做:**

1. 开一个叫 `29-the-one-object` 的 branch
2. 跑一次那个脚本:

```bash
.venv/bin/python examples/29-the-one-object/01_what_gets_built.py
```

3. 对着输出回答: 刚导入时建了几样? 读了一次配置之后建了几样?
4. 打开 [`agent_app/one/`](../../agent_app/one) 下面那四个编号文件, 每个花两分钟,
   **只看它提供了什么**, 不用读懂实现
5. 现在画一张依赖图 (纸上或者一段文字都行): 四个抽屉之间, 谁用了谁
6. 验证你画的对不对 —— 在每个文件里搜 `self.`, 看它用到了别的抽屉里的哪些东西
7. 确认一件事: **有没有哪个箭头是从编号大的指向编号小的?**
8. 最后打开 [`agent_app/one/one_00_main.py`](../../agent_app/one/one_00_main.py), 数一数
   这个文件一共有几行**真正的代码**

**你会观察到:**

第 3 步: 刚导入时**一样都没建**, 读一次配置之后**只建了配置**.

第 7 步的答案是**没有**, 箭头全是从大指向小. 第 8 步那个文件真正的代码只有两处: 一个类声明,
一个实例. **整个应用的组装点, 就是这两行.**

> **关键洞见:** 一个系统最值得先读的地方, 往往是它**最短** 的那个文件 —— 因为组装点通常很短,
> 而组装点告诉你这个系统由哪几块构成.

### 练习 2: 让一样东西提前建出来, 看代价

**目标:** 亲手感受一下如果不是用到才建会怎样.

**怎么做:**

1. 在那个脚本的 `main()` 里, 在第一次 `snapshot` **之前** 加一行, 强行去碰数据库引擎:

```python
one.engine
```

2. 再跑一次, 看输出有什么不同
3. 现在断开网络 (或者把 `.env` 里的 `DB_HOST` 临时改成一个不存在的地址), 再跑一次
4. 观察: 它是在哪一步失败的? 失败之前那句打印出来了吗
5. 把加的那一行删掉, 网络和 `.env` 都恢复, 再跑一次确认正常
6. 想清楚一件事: 如果 `one` 是在导入的时候就把所有东西建好的, 那第 3 步会发生什么

**你会观察到:**

第 2 步那个引擎在第一份快照里就已经是 built 了. 第 3 步会**在建引擎那一行就失败**, 后面的
输出一行都没有.

第 6 步的答案是最重要的: 那样的话, **任何一个 import 了 `one` 的文件都会在导入时崩溃** ——
包括那 269 个本来根本不碰数据库的测试.

> **关键洞见:** 用到才建换来的不只是快, 更是**故障的局部化**: 数据库连不上, 只有真正要用
> 数据库的那条路径失败, 别的照常.

## 10. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| `one` 是什么 | 整个后端唯一那个对象. 四个 mixin 拼成一个类, 一个实例 |
| 组装点有多大 | **两行真正的代码**: 一个类声明, 一个实例 |
| 用到才建 | 每样东西第一次被碰到时才造, 造好就记住 |
| 它解决了什么 | 不用每次重建 (慢), 不用启动就全建 (要凭据), 不用到处传参数 (签名变长) |
| 最实际的好处 | `one` 可以从任何地方安全导入. **269 个测试不联网, 靠的是默认什么都不建** |
| mixin 是什么 | 把一个大类按主题拆成几个文件再拼起来. 想改哪块就开哪个抽屉 |
| 文件名的编号 | 是**依赖方向**. 箭头只从大指向小, 所以可以从任意一个开始读 |
| 客户端为什么是方法 | 建它要解析服务定义, 冷启动不便宜. **判据是这东西大概率会被用到吗** |
| 全局单例的代价 | 状态共享, 测试要小心, 依赖隐形 |
| 怎么挡住的 | 把它限制在一层薄壳上, **壳底下全是纯函数** |

## 11. 导师寄语

**为什么一个两行的文件值得一篇:**

因为你以后接手任何一个陌生后端, 第一件想找的东西就是它 ——
**这个系统由哪几块拼成, 在哪儿拼的.**

大多数项目没有这么一个地方. 东西散在各处, 有的在模块顶层建好, 有的在函数里现建, 有的靠一个
框架的依赖注入绕来绕去. 你要读五个文件才拼得出一张图.

这个项目把那张图压缩成了两行, 外加四个按依赖编号的文件名.
**这不是聪明, 是有人愿意花时间把入口收拢到一个地方.**

**另外一件事值得你留意.** 第 8 节那三条代价我写出来了, 而没有辩解说这个项目不一样. 全局
单例确实有那些问题, 这个项目也确实没有全部解决 —— 依赖隐形那一条就还在.

**一个设计的说明里如果只有好处没有代价, 那份说明多半不完整.** 你以后写设计文档的时候,
把代价那一栏也填上, 读的人会更信你.

**关键洞见:**

- 没人要的东西不该被建出来
- 文件名编号是最便宜的依赖文档, 因为违反它的那行 import 自己就很扎眼
- 判据不是能省就省, 是这东西大概率会被用到吗
- 全局单例的问题不在于它存在, 在于它渗透得有多深
- 一个系统最值得先读的, 常常是最短的那个文件

**下一步:**

组装点讲完了. 第 30 篇 ([配置](../30-configuration/README-cn.md)) 接着往下: 这个对象手上
那份配置是怎么读进来的, 两个文件怎么分层, 以及为什么有些校验被特意提前到了启动那一刻,
而不是等第一次用到.

## 12. 速查

**看谁被建出来了:**

```bash
.venv/bin/python examples/29-the-one-object/01_what_gets_built.py
```

**四个抽屉和依赖方向:**

```text
01 config   <- 谁都不依赖
02 db       <- 用 01
03 boto3    <- 用 01
04 agent    <- 用 01, 02, 03

箭头只从大指向小
```

**建一次记住 vs 每次新建:**

| 建一次记住 | 每次新建 |
| :--- | :--- |
| `config`, 两个引擎, `boto_ses`, `model`, `agent` | 各个 AWS 服务客户端 |
| 大家都要用 | 可能一次都用不上 |

**一条判据:**

没人要的东西不该被建出来.
