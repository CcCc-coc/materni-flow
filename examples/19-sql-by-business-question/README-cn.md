# 用业务问题学 SQL

> 学 SQL 最没效率的方式, 是把语法从头到尾过一遍. 最有效率的方式, 是拿一个你真的想知道
> 答案的问题去撞它.

## 1. 概览

上一篇你知道了有哪些表, 也知道它们怎么连. 这一篇换一个方向.

**不从表出发, 从问题出发.**

[`dataset/`](../../dataset) 里 `03-` 那份文档有二十个 SQL 查询. 它不是一份语法教程 —— 它
更像一份工作交接: 经理把二十道题交给一个刚入职的分析师, 说这周你把它们逐一做完, 并且要
理解为什么这么写.

而每一道题都以**一个人真的会问的问题** 开头, 而不是以某个 SQL 特性开头.

### 这两种教法的差别

| | 从语法出发 | **从业务问题出发** |
| :--- | :--- | :--- |
| 一节的标题 | 什么是 CTE | 被我们拒掉的申请里, 有没有本来该批的? |
| 你学会之后 | 知道 CTE 怎么写 | 知道**什么时候该用** CTE |
| 遇到新问题 | 不知道该用哪个特性 | 从问题往回推, 自然就找到了 |
| 记不记得住 | 三天后忘 | 记得住, 因为它挂在一个具体场景上 |

第三行是关键. **SQL 的语法很少, 难的从来不是语法.** 难的是把一个含糊的业务问题, 翻译成
碰哪几张表, 按什么粒度聚合, join 往哪个方向.

这一篇不会带你读完二十个, 那是你自己的事. 它拆开三个 —— 一个最简单的, 一个中等的, 一个
最难的 —— 让你看清那个翻译过程长什么样.

---

## 2. 学习目标

先说清楚这一篇**不是** 什么: 它不是 SQL 入门教程. 如果你连 `SELECT` 和 `JOIN` 都没写过,
先去补第 3 篇 ([开工之前的四门前置课](../03-prerequisites/README-cn.md)) 里那门 SQLite 课.

它要教的是**翻译** 这件事, 而翻译有一个固定的套路. 那份文档里每个查询都按同一个五段式组织:

| 第几段 | 是什么 | 为什么它在这个位置 |
| :--- | :--- | :--- |
| 1 | **业务背景** | 谁在问, 为什么问, 答案要支撑什么决策 |
| 2 | 类别 / 难度 / 角色 | 三个标签, 让你知道这题练的是什么 |
| 3 | **解题思路** | 在你看到 SQL 之前, 先讲清楚碰哪些表, 怎么 join, 为什么用或不用 CTE |
| 4 | SQL 代码 | 可以直接跑 |
| 5 | 期望结果说明 | 结果长什么样, 哪个数字对应哪个业务陷阱 |

**第 3 段是这份文档最值钱的地方**, 而它恰恰是绝大多数 SQL 教程没有的.

因为教程通常直接给你答案, 而你看懂了答案不等于你下次写得出来 —— 你缺的是从问题走到答案
中间那一段思考. 这份文档把那一段写出来了, 而且**特意放在 SQL 前面**, 就是要你先自己想一遍.

### 用法: 先盖住 SQL

这是这一篇唯一的方法论, 而且它很硬:

> **读到第 3 段结束就停下来, 把第 4 段盖住, 自己先写一遍.**

写不出来也没关系, 写到卡住的地方停下, 再去看答案. 那个卡住的位置就是你真正要学的东西 ——
它比看完整段 SQL 有用得多.

学完这个 Task, 你将能够:

1. 用五段式的思路读一个 SQL 查询, 而不是直接看代码
2. 把一个业务问题拆成碰哪些表, 什么粒度, join 往哪边这三个决定
3. 说清 LEFT JOIN 和 INNER JOIN 在算比率时的差别, 以及选错会算出什么荒唐结果
4. 说清为什么算百分比时要写 `100.0` 而不是 `100`
5. 指出这二十个查询的方言问题, 以及它为什么会在后面咬人

## 5. 二十个查询是怎么排的

先看一眼全貌, 因为它本身就是一份对这门生意的切片.

那二十道题按**谁在问** 分成五类:

| 谁在问 | 几道 | 他关心什么 |
| :--- | :--- | :--- |
| 高管 | 4 | 整个组合赚不赚钱, 风险集中在哪 |
| 经理 | 4 | 我这条线的人和客户表现如何 |
| 分析师 | 5 | 数字背后的原因是什么 |
| 运营 | 4 | 今天有什么要处理的 |
| 财务 | 3 | 钱什么时候进来, 收得回来多少 |

**这五个角色几乎每家公司都有**, 而且他们关心的东西差别很大. 高管问的是趋势和结构, 运营
问的是今天这一批. 同一个数据库, 五种问法.

按难度则是四道基础, 九道中等, 七道进阶. 建议的读法是**先把四道基础的读完**, 建立信心,
再挑你自己那个角色感兴趣的往下走.

## 6. 例一 (基础): 上个月申请量是多少

先看最简单的一类, 好让那个套路清楚地显出来.

**业务问题:** 运营想知道每个月进来多少份申请, 趋势是涨还是跌.

**翻译成三个决定:**

| 决定 | 答案 | 为什么 |
| :--- | :--- | :--- |
| 碰哪张表 | 只碰 application | 申请量这个问题不涉及别的东西 |
| 什么粒度 | 一个月一行 | 问的是每个月 |
| 怎么 join | 不用 join | 单表 |

于是 SQL 的骨架就出来了: 从 application 里, 按月份分组, 数行数.

**这就是基础题的全部难度.** 值得注意的是: 这道题**用不着 agent**. 业务方自己在报表上就能
看到, 而这正是第 2 篇说过的 —— agent 的价值不在数数上.

## 7. 例二 (中等): Grade C 是不是定价定低了

这是这个数据集的**招牌问题**, 也是第 18 篇里那个被特意埋进去的故事.

**业务问题:** 每个风险等级在定价时都假设了一个违约率, 并按它定利率. 那么**实际违约率** 是
多少? 两个数字对得上吗?

**翻译成三个决定:**

| 决定 | 答案 | 为什么 |
| :--- | :--- | :--- |
| 碰哪些表 | loan, risk_grade, default_event | 贷款是主体, 等级给假设值, 违约事件给实际值 |
| 什么粒度 | 一个等级一行 | 问的是每个等级 |
| 怎么 join | risk_grade 用 JOIN, **default_event 用 LEFT JOIN** | 下面细说 |

### 这里有一个会算出荒唐结果的坑

第三行那个 LEFT JOIN 值得停下来想清楚, 因为选错了**不会报错**, 只会给你一个错得离谱但
看起来很正常的数字.

回忆第 18 篇: 一笔贷款**最多** 有一条违约记录, 而绝大多数贷款一条都没有.

| 你用哪个 | 结果里有哪些贷款 | 算出来的违约率 |
| :--- | :--- | :--- |
| INNER JOIN | **只有违约了的** | 100%. 因为没违约的全被过滤掉了 |
| **LEFT JOIN** | 全部 | 正确 |

**分母必须是所有贷款**, 而 INNER JOIN 会把分母悄悄换成违约的贷款. 于是你得到一个 100%
的违约率, 而这个数字荒唐到你一眼能看出不对 —— 算你运气好. 更常见的情况是它只是偏高一点,
偏得刚好不足以让你起疑.

> **一条通用的判据: 只要你在算比率, 就停下来问一句分母对不对.** 分母出错是最难发现的一类
> bug, 因为结果永远是一个看起来合理的数字.

### 还有一个更阴的坑: 整数除法

算百分比的时候要写 `100.0 * ... / ...`, **不能写 `100`**.

原因是**两个整数相除, 结果还是整数**, 小数部分被直接砍掉. 而这个坑真正阴的地方在于, 它
**错成什么样取决于你把乘 100 写在哪一边**:

| 你怎么写 | Grade C 算出来 | 有多容易被发现 |
| :--- | :--- | :--- |
| `100.0 * 违约数 / 贷款数` | **9.89** | 正确 |
| `100 * 违约数 / 贷款数` | **9** | **很难**. 只少了小数, 一眼看过去完全正常 |
| ` 违约数 / 贷款数 * 100` | **0** | 容易. 全是 0, 一眼知道不对 |

看中间那一行. 先乘后除, 所以除法之前分子已经被放大了, 结果只是**被砍掉小数**: 9.89 变成 9.

**这个数字不会让任何人起疑.** 它出现在一份报告里, 读的人只会觉得违约率是 9%, 而真实值接近
10%. 差的那 0.89 个百分点, 在一个上亿的贷款组合上是很大一笔钱.

写成 `100.0` 就把整个式子提升成小数运算了. 这是一个每种数据库都要踩一遍的经典坑.

### 结果

两个数字并排放出来之后, Grade C 那一行会很扎眼: 定价假设 6%, 实际接近 10%, 而它是组合里
占比最大的一档.

**这一行就是这个项目存在的理由.** 这家公司在自己最大的一块业务上长期少收了钱, 而没有任何
一张现成报表会告诉它.

这一篇目录下的 [`01_pricing_gap.py`](01_pricing_gap.py) 就是这个查询, 可以直接跑:

```bash
.venv/bin/python examples/19-sql-by-business-question/01_pricing_gap.py
```

## 8. 例三 (进阶): 被我们拒掉的人里, 有没有本来该批的

这道题是二十个里最有意思的一个, 因为**它问的是不存在的东西**.

**业务问题:** 信贷副总担心我们拒错了人. 每拒错一个, 就是一笔本该赚到的利息没赚到. 那么在
被拒的申请里, 有没有人的资质其实和那些还得好好的客户差不多?

### 为什么这道题难

前面两道题问的都是已经发生的事. 这道题问的是**如果当初批了会怎样**, 而那件事没有发生,
数据库里当然也没有记录.

所以它需要一个绕:

| 步 | 干什么 |
| :--- | :--- |
| 1 | 先看**成功的客户** 长什么样: 把还得好好的那批人的信用分, 收入, 员工数各算一个平均值 |
| 2 | 拿这个平均画像去**被拒的池子** 里筛, 找出长得像他们的 |
| 3 | 把筛出来的列给承保委员会人工复核 |

第 1 步算出来的是**一行** 数据 (三个平均值), 而第 2 步要拿这一行去和**每一份** 被拒申请比较.

### CTE 是在这里出现的, 不是凭空出现的

回到第 2 节那句话: **重要的不是 CTE 怎么写, 是什么时候该用它.**

这道题就是那个时候. 那个平均画像要被每一条申请引用, 你有两个选择:

| 做法 | 后果 |
| :--- | :--- |
| 把那段求平均的 SQL 抄进去好几遍 | 能跑, 但读的人要看三遍才知道那是同一个东西 |
| **写成 CTE, 起个名字** | 一眼看出这是先算一个东西, 再拿它去比 |

**CTE 的价值是给一个中间结果起名字.** 它让一段复杂 SQL 有了段落感, 就像写文章分段一样.

顺带一提, 把那一行平均值广播到每条申请上, 用的是 `CROSS JOIN`. 平时听到 CROSS JOIN 你该
警惕 —— 它会让行数爆炸. 但在这里另一边只有**一行**, 所以行数不变, 它只是把那三个数字接到
每一行后面. 这是 CROSS JOIN 少数几个正当用法之一.

## 9. 一个后面会咬人的方言问题

这一节现在读起来像一个技术细节, 但它是这一组四篇里最重要的伏笔.

那二十个查询是**对着 SQLite 写的**. 文档最后自己也说了这件事, 还给了迁移提示. 里面用到了
这些只有 SQLite 才有的写法:

| SQLite 写法 | 干什么 | 在 PostgreSQL 上 |
| :--- | :--- | :--- |
| `strftime('%Y-%m', d)` | 把日期截成年月 | **不存在** |
| `JULIANDAY(a) - JULIANDAY(b)` | 算两个日期差几天 | **不存在** |
| `DATE(d, '-90 days')` | 往前推 90 天 | **不存在** |

**而 agent 查的不是 SQLite, 是 PostgreSQL.**

于是问题来了: 这二十个查询里有一部分会被精选进
[`data/system-prompt.md`](../../data/system-prompt.md), 当作给模型照抄的模板. 如果照抄的
是 SQLite 方言, 那模型写出来的 SQL 在线上一条都跑不通.

### 而这件事不会崩

这是最阴的地方. agent 的 SQL 工具会把数据库的报错**转成文字还给模型**, 模型看到报错就换个
写法再试, 或者干脆绕过这个问题回答别的.

所以症状不是异常, 是**答案悄悄变差**. 没有任何监控会报这种事.

第 20 篇 ([把种子发布到 PostgreSQL](../20-seed-to-postgres/README-cn.md)) 会讲这个项目怎么
从根上解决它, 而那个解法可能和你猜的不一样.

现在你只需要记住一件事:
**你在这一篇里跑的 SQL 是对着本地 SQLite 跑的, 而 agent 跑的是另一个数据库.**

## 10. 练习

### 练习 1: 盖住答案, 自己写三个

**目标:** 把第 2 节那条方法真的执行一次, 而不是读过就算.

**怎么做:**

1. 开一个叫 `19-sql-by-business-question` 的 branch
2. 打开 [`dataset/`](../../dataset) 里 `03-` 那份文档, 从四道基础题里挑一道
3. **读到解题思路那一段结束就停**, 把下面的 SQL 盖住
4. 自己写一遍, 写完把它粘进 [`02_run_any_sql.py`](02_run_any_sql.py) 里那个 `QUERY`, 跑:

```bash
.venv/bin/python examples/19-sql-by-business-question/02_run_any_sql.py
```

5. 再看文档给的答案, 对比差别 —— 不是对错, 是**为什么它那样写**
6. 换一道中等的, 重复一遍
7. 最后挑一道进阶的, 这次允许你写不出来, 但要写下**你卡在哪一步**

**你会观察到:**

基础题你大概率写得出来, 中等题会在 join 方向或者聚合粒度上和答案不一样, 进阶题多半卡在
第一步 —— 不知道该从哪儿下手.

**那个卡住的位置就是这一篇真正的收获.** 它告诉你缺的不是语法, 是把问题拆成三个决定的习惯.

> **关键洞见:** 看懂一段 SQL 和写得出一段 SQL, 中间隔着的距离比你以为的大. 唯一的办法是
> 盖住答案自己写一次.

### 练习 2: 亲手把违约率算成 100%

**目标:** 亲眼看一次分母出错, 因为它不报错.

**怎么做:**

1. 先跑一次正确的版本, 记下每个等级的实际违约率:

```bash
.venv/bin/python examples/19-sql-by-business-question/01_pricing_gap.py
```

2. 打开 [`01_pricing_gap.py`](01_pricing_gap.py), 把那行 `LEFT JOIN default_event` 改成
   `JOIN default_event`
3. 再跑一次, 看每一行的违约率变成了什么
4. 改回去. 现在把两处 `100.0` 都改成 `100`, 跑第三次, **仔细看 Grade C 那一行**
5. 再改一次: 把式子从 `100.0 * COUNT(de.id) / COUNT(l.id)` 换成
   `COUNT(de.id) / COUNT(l.id) * 100.0` 之外的整数版本
   `COUNT(de.id) / COUNT(l.id) * 100`, 跑第四次
6. 全部改回去, 确认恢复第 1 步的结果
7. 现在回答: 第 3, 4, 5 步这三种错误, **哪一种最危险?**

**你会观察到:**

| 第几步 | Grade C 那一行 | 三次都没有报错 |
| :--- | :--- | :--- |
| 1 (正确) | 9.89 | |
| 3 (INNER JOIN) | 100.00 | 荒唐, 一眼看出 |
| 4 (`100` 先乘) | **9** | **正常, 看不出来** |
| 5 (`100` 后乘) | 0 | 荒唐, 一眼看出 |

第 7 步的答案是**第 4 步**. 另外两个错得太离谱, 你一秒钟就会发现; 而 9 这个数字会安安静静
地走进一份给高管的报告, 没有人会停下来问一句.

> **关键洞见:** 一个错得离谱的结果其实是运气好. 你真正要防的是那种**错得刚好合理** 的结果.
> 防它只有两个办法: 每次算比率都确认分母, 以及对着一个你心里有数的数字校验一次.

## 12. 导师寄语

**为什么这一篇不教语法:**

SQL 的语法非常小, 一个下午就能过一遍, 而且到处都查得到. 但会背语法的人写不出好查询, 这件
事我见过太多次了.

卡住他们的从来不是不知道 `GROUP BY` 怎么写, 是
**面对一个模糊的业务问题时, 不知道从哪儿下手**. 老板说帮我看看我们是不是在某些客户身上
亏钱了 —— 这句话里没有一个词是 SQL.

从问题到 SQL 中间那一步翻译, 才是真正的功夫. 而练它的唯一办法是拿真问题反复练, 这也是那
份文档为什么写成一份工作交接而不是一份教程.

**还有一件事**: 你在这一篇里练的东西, 和你后面要教给 agent 的东西是同一样东西. 第 24 篇
你要写系统提示词, 而写提示词本质上就是把你在这一篇学到的翻译能力, 转述给一个模型.
**你自己不会翻译, 就不可能教会它.**

**关键洞见:**

- 难的不是语法, 是把业务问题拆成碰哪些表, 什么粒度, join 往哪边
- 盖住答案自己写一次, 抵得上读十遍
- 每次算比率都确认分母. 错得离谱是运气好, 错得刚好合理才要命
- CTE 的价值是给中间结果起名字, 不是显得高级

**下一步:**

到这里你已经能在本地查这个库了. 但 agent 还是用不了 —— 它查的根本不是这个数据库. 第 20 篇
([把种子发布到 PostgreSQL](../20-seed-to-postgres/README-cn.md)) 会把数据发布上去, 并且
回答上一节留下的那个方言问题.

## 13. 速查

**读一个查询的正确姿势:**

```text
1. 读业务背景, 搞清楚谁在问什么
2. 读解题思路
3. 停! 盖住 SQL, 自己写一遍
4. 再对答案, 看差别在哪
```

**翻译三问:**

- 碰哪些表?
- 聚合到什么粒度, 也就是结果里一行代表什么?
- join 往哪个方向, 该用 LEFT 还是 INNER?

**两个不报错的坑:**

| 坑 | 症状 |
| :--- | :--- |
| 算比率用了 INNER JOIN | 分母被悄悄换掉, 这个库里会变成 100% |
| 百分比写了 `100` 而不是 `100.0` | 小数被砍掉. 先乘后除时结果看起来完全正常 |
