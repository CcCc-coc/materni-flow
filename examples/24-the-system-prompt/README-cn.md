# 系统提示词: 把领域知识灌进去

> 前三篇讲的是模型能看到什么和能做什么. 这一篇讲它**应该知道什么** —— 而这是唯一一件
> 框架帮不了你的事.

## 1. 概览

拆开 agent 的最后一篇. 前三篇分别是眼睛, 手, 和那只最要紧的手; 这一篇是**脑子**.

打开 [`data/system-prompt.md`](../../data/system-prompt.md), 五百六十多行. 它每一次请求都
被完整发给模型 —— 你在第 16 篇 ([多轮对话和缓存](../16-multi-turn-and-caching/README-cn.md))
知道了模型什么都不记得, 所以这五百多行**每问一句话就重发一次**.

它凭什么值这个价钱?

因为它装着一样别处都没有的东西: **这门生意的知识.** 库结构告诉模型有哪些表, SQL 工具让它
能查, 但**没有任何一个地方告诉它定价缺口是什么意思** —— 除了这份文件.

这一篇不带你逐行读完它 (那是你自己的事), 而是回答三个问题:

| 问题 | 在第几节 |
| :--- | :--- |
| 什么必须写进去, 什么该相信模型自己会 | 第 5, 6 节 |
| 一条领域知识该写成什么形状 | 第 7 节 |
| 这么长一份散文, 拿什么保证它是对的 | **第 9 节, 而答案是: 基本没有** |

---

## 2. 学习目标

先说一件让很多人意外的事.

**这份提示词里没有一句是在教模型写 SQL.** 没有讲什么是 JOIN, 没有讲 GROUP BY 怎么用,
没有讲子查询.

因为**模型早就会了**. 它在训练时见过的 SQL 比你这辈子写的多得多.

那它不会什么?

| 模型天生就会 | 模型不可能知道 |
| :--- | :--- |
| SQL 语法, JOIN, 聚合, 窗口函数 | **你们公司管这个指标叫什么** |
| 一般的商业常识 | **你们算这个指标用的是哪个口径** |
| 怎么读一张表 | **你们这行哪个数字是异常的** |
| 常见的数据分析套路 | **哪些状态码只能配哪个实体** |

右边这一列有个共同点: **它们全都是约定, 不是推导.** 没有任何聪明程度能让人凭空猜出你们公司
把违约率定义成了什么.

于是这一篇的中心问题就出来了:

> **一份好的提示词, 是把右边那一列写清楚, 同时一个字都不浪费在左边.**

这两半同样重要. 少写了右边, 模型就编; 多写了左边, 你就在花钱把一个专家当新人培训, 而且
**把真正要紧的话淹掉了**.

学完这个 Task, 你将能够:

1. 用必须写还是该相信这条判据, 给一段候选内容分类
2. 说清一条派生指标为什么要连公式带 SQL 例子一起给
3. 指出这份提示词里哪几节其实属于渲染契约, 以及为什么它们不在这一篇讲
4. 说出这份文件里有哪些东西是**没有任何检查在看着的**
5. 亲手找出至少一处提示词和数据库对不上的地方

## 5. 它由哪几块组成

先看骨架. 五百多行分成这么几块:

| 这一块 | 干什么 | 有多长 |
| :--- | :--- | :--- |
| 身份和工具清单 | 你是谁, 你有哪三只手 | 十行 |
| **核心领域概念** | 这门生意怎么运转, 风险等级表, 客户类型 | 几十行 |
| 分析索引 | 这个数据集**能被问什么**, 列出来 | 三十行 |
| **派生指标** | 十五个算出来的指标, 每个带公式和 SQL | **两百多行, 最大的一块** |
| 表关系 | 怎么 join, 用箭头列出来 | 十几行 |
| 状态码 | 哪些码是申请的, 哪些是贷款的 | 十行 |
| **SQL 方言** | 写 PostgreSQL, 别写 SQLite | 三十行 |
| SQL 模式 | 这个领域里反复出现的几个写法 | 三十行 |
| 回答规范 | 限 20 行, 小数两位, 先结论后数据 | 十行 |
| 渲染那几节 | 什么时候画表格, 画流程图, 画图表 | 一百多行 |
| 安全 | 只读, 不许改数据 | 五行 |

**加粗的三块是这一篇的重点**, 因为它们各自代表一种不同的知识.

### 渲染那几节这一篇不讲

一百多行是不小的一块, 但它属于另一个话题: **渲染契约**, 也就是提示词, 前端查找表, 和
kickstart 配额这三样怎么互相对齐.

你在第 12 篇 ([一段文本怎么变成表格和图](../12-render-text-into-blocks/README-cn.md)) 已经
见过前端那一半了, 而第 29 篇 (渲染契约) 会把三半合起来讲. 这一篇碰它只会讲一半.

## 6. 判据: 必须写, 还是该相信

现在拿几个具体例子过一遍那条判据.

| 这一条 | 写不写 | 为什么 |
| :--- | :--- | :--- |
| 什么是 LEFT JOIN | **不写** | 模型比你熟 |
| 违约率 = 违约数 / 贷款总数 × 100 | **写** | 这是你们的口径. 分母取什么是一个决定 |
| 什么是信用分 | **不写** | 常识 |
| A 级是 720 到 850 分 | **写** | 你们公司自己划的线, 没法猜 |
| 定价缺口 = 假设违约率 - 实际违约率 | **写** | 这个词是你们发明的 |
| 负的缺口 = 定价偏低 = 在亏钱 | **写** | **这是业务解释, 不是数学** |
| 怎么写一个 CTE | **不写** | 模型会 |
| 申请的状态码只有那四个 | **写** | 第 18 篇讲过, **数据库自己都不知道这条** |

最后一行值得停一下. 你在第 18 篇发现过: `loan_status` 那张表被申请和贷款共用, 而各自只能
用其中一部分状态码 —— **数据库不强制这件事**.

那它由谁来守? 第 18 篇的答案是生成器, 文档, 和写查询的人. 现在多了第四个: **提示词**.
因为对 agent 来说, 提示词就是它的文档.

### 一条更好用的自查

上面那张表是结果, 但你自己写的时候需要一个能当场用的问法. 这个最好使:

> **一个刚入职, 很聪明, 但完全不了解你们公司的人, 会不会问这个问题?**

会问的就写. 不会问的 (因为那是常识或者通用技能) 就别写.

这个问法好用是因为它把两件事同时框住了: 聪明排除掉基础知识, 完全不了解你们公司框住了所有
本地约定.

## 7. 一条领域知识该写成什么形状

现在看那块最大的 —— 十五个派生指标. 它们全都长成同一个样子, 而那个形状值得抄走.

拿定价缺口当例子, 它有**三段**:

**第一段, 一句话公式:**

```text
Pricing Gap = implied_default_rate - actual_default_rate
```

**第二段, 怎么解读:**

```text
正数 = 定价偏高 (可能流失客户)
负数 = 定价偏低 (在亏钱)
```

**第三段, 一条能直接跑的 SQL:**

```sql
SELECT rg.grade_code,
       rg.implied_default_rate AS pricing_assumption,
       ROUND((100.0 * COUNT(de.id) / COUNT(l.id))::numeric, 2) AS actual_rate,
       ...
FROM risk_grade rg
JOIN loan l ON rg.id = l.risk_grade_id
LEFT JOIN default_event de ON l.id = de.loan_id
GROUP BY rg.id, rg.grade_code, rg.implied_default_rate
```

### 为什么三段都要有

去掉任何一段都会坏, 而坏法各不相同:

| 少了哪段 | 后果 |
| :--- | :--- |
| 公式 | 模型自己编一个口径, 而且每次可能不一样 |
| **解读** | 它算得出数字, 但**不知道那个数字是好是坏**, 于是只会念数 |
| SQL 例子 | 它得自己想 join 方向和分母, 而第 19 篇你知道那有多容易错 |

**中间那一段最容易被漏掉, 而它恰恰是价值所在.** 一个能算出 Grade C 缺口是 -3.89 的 agent
没什么用; 一个能说出 Grade C 定价偏低, 而且它是组合里最大的一档, 所以这事很要紧的 agent
才有用.

### 那条 SQL 例子在替你干两件事

注意那段 SQL 里的两个细节, 你在第 19 篇都吃过亏:

- `LEFT JOIN default_event` —— 分母必须是所有贷款
- `100.0` 而不是 `100` —— 整数除法会砍掉小数

**提示词里的 SQL 例子不只是示范怎么查, 它在示范怎么不出错.** 模型照抄的时候, 把这两个坑
一起抄走了.

> **这就是示范优于说明的道理**: 与其写一段话解释要注意分母, 不如给一条已经处理好分母的
> SQL 让它照抄.

## 8. 方言那一节, 是第 19 到 20 篇的收口

翻到 SQL 方言那一节, 你会看到这句:

> The database is **PostgreSQL**, in every environment. Write PostgreSQL.

后面跟着一张表, 左边是**在 SQLite 上合法但在这里非法** 的写法:

| 别写 | 写这个 |
| :--- | :--- |
| `strftime('%Y-%m', d)` | `TO_CHAR(d, 'YYYY-MM')` |
| `DATE(d, '-90 days')` | `d - INTERVAL '90 days'` |
| `JULIANDAY(a) - JULIANDAY(b)` | `a - b` |
| `WHERE is_repeat_customer = 1` | `WHERE is_repeat_customer` |

**这张表就是第 19 篇那个伏笔和第 20 篇那个决定的最终落点.**

回想一下这条线:

1. 第 19 篇: 数据集自带的二十个查询是 **SQLite 方言** 写的
2. 第 20 篇: 而 agent 查的是 PostgreSQL, 所以**提示词只有一份, 它必须对着一个确定的数据库写**
3. 这一篇: 于是有人坐下来, 把那些会咬人的差别一条一条列成了这张表

**三篇讲的是同一件事**, 只是一篇比一篇具体.

而这张表的存在方式很值得注意: 它不是一条规则, 是一份**清单**. 它防的不是模型不会写
PostgreSQL, 是模型**看过太多 SQLite 教程**, 所以会顺手写出来.

## 9. 散文没有编译器

这是这一篇最重要的一节, 而且它讲的是一件让人不舒服的事.

前面几篇里每一样东西都有东西看着它:

| 东西 | 谁在看着 |
| :--- | :--- |
| 库结构编码 | 它是从真实数据库反射出来的, **不可能过期** |
| 工具的参数 | Python 的函数签名 |
| SQL 工具的只读 | 那个永远回滚的事务 |
| 前端文案的 key | 构建时会报错 |
| 提示词里的表名 | `mise run cli-check-content` 会扫 |
| **提示词里的数字** | **没有任何东西** |

最后一行就是这一节的全部内容.

### 两个真实的例子

**例子一:** 提示词的风险等级表里, D 级那一行写着假设违约率 12.0%.

去数据库里查一下:

```bash
mise run cli-print-db-schema   # 先确认表在
```

然后在 agent 页问一句每个风险等级的假设违约率是多少. 数据库给的答案是 **13.0%**.

**提示词写 12.0, 数据库里是 13.0.**

**例子二:** 讲定价缺口那一节里有一句 Grade C 大约有 -5% 的缺口.

而你在第 19 篇亲手跑出来的是 **-3.89**.

### 这有多严重

第一个例子更糟, 因为**模型可能直接引用那个数字** 而不去查库 —— 它就写在提示词里, 看起来
权威得很. 于是用户会拿到一个错的定价假设.

第二个例子轻一些 (那句话本来就写着大约), 但它同样会漂移.

**而这两处都不会被任何东西发现:**

- `mise run cli-check-content` 只检查提示词里提到的**表名** 存不存在, 不看数字
- 没有测试读这份文件
- 构建不碰它
- agent 跑起来一切正常

### 为什么会这样

不是有人偷懒. 是因为这两个数字来自**两个会各自变化的地方**:

- 提示词是**人写的散文**
- 那些数字的真相在**生成器造出来的数据里**

数据集换一版, 生成器调一个参数, 数据就变了, 而**没有任何机制会去提醒那份散文**.

> **关键洞见:** 一个事实如果在两个地方各存了一份, 它们迟早会不一样. 唯一的问题是
> **你会不会发现**. 而散文里的那一份, 通常不会.

这正是第 21 篇那个 70% 说法的同一类问题, 只是这次的后果更直接.

### 那怎么办

有几条现实的路, 各有代价:

| 做法 | 代价 |
| :--- | :--- |
| 提示词里干脆不写具体数字, 只写去查 `risk_grade` 表 | 模型每次多一次工具调用 |
| 加一个检查, 把提示词里的数字和数据库对一遍 | 要写代码, 而且只能覆盖有结构的那部分 |
| 换数据集时人工过一遍 | 靠纪律, 而纪律会松 |

**这一篇不给你标准答案**, 因为它确实没有一个便宜的答案. 但你得知道这个洞在那儿 —— 而这
本身就是这一节的目的.

## 10. 练习

### 练习 1: 亲手找出那处对不上的数字

**目标:** 亲眼看一次散文和数据的漂移, 因为读一百遍都不如撞一次.

**怎么做:**

1. 开一个叫 `24-the-system-prompt` 的 branch
2. 打开 [`data/system-prompt.md`](../../data/system-prompt.md), 找到风险等级那张表, 抄下
   五个等级的假设违约率
3. 起开发服务器, 在 agent 页问: **每个风险等级的假设违约率是多少? 直接查表告诉我**
4. 把 agent 给的五个数字和第 2 步抄的对一遍, 找出对不上的那一行
5. 现在换个问法, 不让它查库: **根据你的系统提示词, D 级的假设违约率是多少?**
6. 对比两次的回答
7. 再跑一次 `mise run cli-check-content`, 确认它**全绿**
8. 最后想一件事: 如果一个用户只问了第 5 步那种问题, 他会知道自己拿到的是错的吗

**你会观察到:**

第 4 步会找到 D 级那一行对不上. 第 6 步是这个练习的重点:
**同一个 agent, 同一份提示词, 两种问法给出两个不同的答案** —— 一个来自数据库, 一个来自
那份散文.

第 7 步会让你有点不适应: 检查全绿, 而错误就摆在那儿.

> **关键洞见:** 一个通过了全部检查的系统, 不等于一个正确的系统. 检查只覆盖它被写出来覆盖
> 的那部分, 而**没被覆盖的部分不会举手**.

### 练习 2: 找出那几条缺了中间一段的指标

**目标:** 用一次三段式这把尺子, 而且量的是这份出厂提示词自己.

**怎么做:**

1. 打开 [`data/system-prompt.md`](../../data/system-prompt.md), 翻到派生指标那一大块,
   一共十五条
2. 拿三段式当尺子, **逐条检查它齐不齐**: 有没有公式, 有没有怎么解读, 有没有 SQL 例子
3. 把缺了**中间那段解读** 的挑出来. 判据是: 这一条有没有告诉你什么样算好, 什么样算坏,
   或者多少算异常
4. 数一数一共有几条缺
5. 挑其中一条, 对照第 7 节定价缺口那个样子, **把缺的那段解读补写出来** —— 写在草稿里就行,
   不用改文件
6. 现在验证你写的对不对: 起开发服务器, 在 agent 页问那条指标的当前值, 看你写的那句
   什么样算异常放在真实数字上成不成立

**你会观察到:**

十五条里有**五条** 缺了解读 (提示是: 都集中在前半段). 也就是说这份提示词自己就漏掉了它最
值钱的那一段, 漏掉了三分之一.

第 5 步比你想的难. 公式和 SQL 都是照抄现成的, 而
**什么样算异常需要你真的看过这门生意的数字** —— 这也是为什么第 6 步要你去问一次真实值.

> **关键洞见:** 这一篇讲的那个洞不是别人的问题, 它就在你正在读的这份文件里. 一份长文档
> 里少了几段, **没有任何东西会举手** —— 只有拿着一把尺子逐条量过的人才发现得了.

## 12. 导师寄语

**为什么这一篇是这一组的压轴:**

前三篇讲的东西都有明确的对错. 编码格式对不对, 工具能不能调, 事务有没有回滚 —— 都可以验证.

**这一篇讲的东西没有对错, 只有好坏.** 一句话该不该写进提示词, 没有编译器能告诉你; 写多了
模型被淹, 写少了模型乱编, 而两种失败都不报错.

这就是为什么我说这门课真正的差异不在技术上. 接一个模型是一个下午的事; 而
**判断你这门生意里哪十五个指标值得写进去, 以及每一个该怎么解读** —— 那需要你真的懂它.

**第 9 节我犹豫过要不要写.** 指出自己教材里的两处错误不太体面, 而且我完全可以先悄悄改掉
再写这一篇.

但那样你会错过这一篇最真的部分: **这类漂移不是疏忽, 它是这种做法自带的成本.** 只要一份
知识同时活在散文和数据里, 它就会漂. 你以后自己维护提示词的时候一定会遇到, 而提前知道它
长什么样, 比学会任何一条格式规范都有用.

**关键洞见:**

- 不写模型会的, 写模型不可能知道的. 判据是那个刚入职的聪明人会不会问
- 一条领域知识要三段: 公式, 怎么解读, SQL 例子. **中间那段最值钱**
- 示范优于说明 —— 一条处理好了分母的 SQL, 抵得上一段讲分母的话
- 散文没有编译器. 检查全绿不等于内容正确
- 一个事实存两份就会漂, 问题只是你会不会发现

**下一步:**

这个 agent 的四个部分讲完了: 眼睛, 手, 那只最要紧的手, 和脑子.

接下来转向它的**输出**. 第 25 篇 (最后一条消息不一定是答案) 讲一件很小但坑过很多人的事:
模型交回来的是一整串消息, 而从里面挖出思考和答案两样东西, 比你想的容易写错.
