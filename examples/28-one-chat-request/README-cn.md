# 一次 chat 请求, 从头到尾

> 第 5 篇你走过一遍这九步, 那时候是为了认路. 这一篇回到同一条路上, 停在每一个有人踩过坑的
> 地方.

## 1. 概览

前面十几篇把零件一个个拆开看过了: 前端, 协议, 库结构, 工具, 提示词, 挖答案, 那个 `one`.

这一篇把它们**串起来**.

代码在 [`api/index.py`](../../api/index.py), 全文一百六十行, 而且**它自己不做任何业务** ——
它只是把那些零件按顺序摆好. 第 5 篇说过, 一个把别人串起来而自己不干活的文件, 通常就是一个
系统的主干.

先回忆一下那四段 (第 5 篇教的记法):

| 哪一段 | 第几步 | 在干什么 |
| :--- | :--- | :--- |
| **进门** | 1 到 3 | 收下那包东西, 拆开, 找出用户到底问了什么 |
| **准备** | 4 到 5 | 给 agent 装上记忆, 花钱之前先看一眼预算 |
| **干活** | 6 | 真正调模型 |
| **出门** | 7 到 9 | 记账, 挖出要的东西, 编码发回去 |

**这一篇不重复那张表**, 它讲的是那条路上的六个决定 —— 每一个换个写法程序照样跑, 但会
**静默地出错或者多花钱**.

先说这一篇为什么值得单独存在, 而不是并进第 5 篇.

## 5. 决定一: 日志里的敏感请求头要打码

**在第 1 步.** 请求刚进门, 代码先记一条日志, 而记的时候会把 `authorization` 这类请求头
**打码**.

| | 打码 | 不打码 |
| :--- | :--- | :--- |
| 日志能不能用来排查 | 能 | 能 |
| 线上留存的日志里有什么 | 一串星号 | **一份凭据的副本** |

**关键是线上的日志是留存的.** 它可能被收集到一个日志服务里, 可能被好几个人看到, 可能保留
好几个月. 把凭据打进去, 等于把它复制到了一个你没打算保护的地方.

而这件事**永远不会报错**. 日志写成功了, 系统一切正常, 只是多了一份不该存在的副本.

> 这是安全问题里很典型的一类: **不是有人攻破了什么, 是有人把东西放错了地方.**

## 7. 决定三: 每次都把 agent 的记忆清空

**在第 4 步**, 也是这九步里最反直觉的一个.

代码做的事是: 拿到 agent, **先把它的消息列表清空**, 再把前端送来的历史灌进去.

### 为什么这看起来很浪费

因为上一轮的对话明明还在里面. 清空再重灌, 等于把刚才那些东西扔掉又捡回来.

### 为什么必须这么做

三篇的知识合起来才说得通:

| 这一条 | 来自 | 说的是 |
| :--- | :--- | :--- |
| `one.agent` 跨请求活着 | 第 27 篇 | 它是缓存的, 建一次就一直在那儿 |
| 权威的历史在前端 | 第 16 篇 | 模型没有记忆, 历史是前端每次重送的 |
| 服务器可能同时服务很多人 | 第 13 篇 | 线上是按需拉起的函数, 一个实例接连处理不同用户的请求 |

**把三条放在一起, 结论就出来了**: 那个 agent 对象上残留的消息, 属于**上一个请求**, 而上一个
请求可能来自**另一个用户**.

不清空的后果是: **第二个用户会读到第一个用户的对话.**

### 这个后果有多严重

它不是答案不准, 是**数据泄漏**. 而且:

| | |
| :--- | :--- |
| 会不会报错 | 不会 |
| 本地开发时会不会出现 | **几乎不会** —— 你一个人用, 前后两轮本来就是同一段对话 |
| 什么时候出现 | 上线之后, 两个用户同时用的时候 |

**一个只在有第二个用户时才出现的 bug**, 是你本地测一百遍都测不出来的那种.

> **关键洞见:** 一个跨请求活着的对象, 它上面**任何** 残留的状态都是一个潜在的串台. 处理办法
> 只有两个: 要么每次清空, 要么干脆别让它跨请求活着.

**在第 5 步.** 这一步的位置本身就是全部的设计.

看它在哪儿: **在清空和灌历史之后, 在调模型之前.**

| 如果放在调模型之后 | 现在这样 |

## 9. 决定五: 把 stdout 临时顶掉

**在第 6 步**, 调模型的时候. 代码在调用前后做了一件很怪的事:
**把标准输出临时换成一个丢弃用的容器**, 调完再换回来.

### 这在防什么

strands 那个框架在跑的时候会往标准输出打东西 (进度, 中间结果). 本地开发时这很有用.

但在**线上那个按需拉起的环境** 里, 打到标准输出的东西**会混进发给浏览器的字节流里**.

而你在第 14 篇学过, 那个字节流是有严格格式的 —— 一行 `data:` 加一段 JSON, 后面一个空行.
中间插进去几行框架的日志, 那段流就**解析不出来了**.

### 症状长什么样

| 在哪儿 | 表现 |
| :--- | :--- |
| 本地 | **完全正常** (本地的输出不进响应流) |
| 线上 | 页面上什么都不显示, 或者显示到一半断掉 |
| 后端日志 | 一切正常, 200 |

**这是最难查的那一类 bug: 本地复现不出来.** 你在本地跑一百次都是好的, 因为本地根本没有那个
把标准输出和响应流接在一起的机制.

> **关键洞见:** 一个只在某个部署环境里出现的 bug, 通常来自那个环境的某条你不知道的规则.
> 这类东西读文档读不到, 只能撞一次, 然后写进注释里 —— 而这个仓库正是这么做的.

## 10. 决定六: 记账要取这一轮的用量

**在第 7 步.** 模型跑完了, 要记下这一轮花了多少 token.

框架提供了两个数字, 而它们长得很像:

| 这个 | 是什么 |
| :--- | :--- |
| 累计用量 | 这个 agent **对象活到现在** 用掉的总量 |
| **这一轮的用量** | 刚刚这一次调用用掉的 |

直觉会选第一个, 因为它的名字听起来就是用量. **而它是错的**, 理由又回到第 27 篇: `one.agent`
是缓存的, 它活很久, 所以那个累计量包含了**这个进程处理过的每一次请求**.

### 错了会怎样

假设一个进程连续处理十次请求, 每次真实用量是 100:

| 第几次请求 | 真实用量 | 取累计量会记成 | 累计记账总数 |
| :--- | :--- | :--- | :--- |
| 1 | 100 | 100 | 100 |
| 2 | 100 | 200 | 300 |
| 3 | 100 | 300 | 600 |
| ... | | | |
| 10 | 100 | 1000 | **5500** |

真实总量是 1000, 记成了 5500. **而且请求越多, 偏得越离谱** —— 这就是按平方膨胀的意思.

后果是那个月度上限会**远远提前** 触发, 于是用户看到的是这个 demo 这个月的预算用完了, 而实际
上你只花了五分之一.

> **关键洞见:** 两个名字相近的数字, 一个对一个错, 而且错的那个在本地单次测试里
> **看起来完全正常** (第一次请求时两个数字相等). 这类 bug 只在连续跑很多次之后才显形.

   - 把 stdout 顶掉的那两行
   - 记账取用量那几行
4. 对**清空记忆** 那一处, 读它上面的注释, 确认它说的和第 7 节一致
5. 对**记账** 那一处, 读注释, 找出它明确说了**不要用** 哪个东西
6. 数一数这个文件一共有几个 `import`, 想清楚为什么这么多 —— 它自己不干活, 全在调别人
7. 最后回答: 这九步里, 有几步的知识来自你前面读过的某一篇? 各是哪一篇

**你会观察到:**

第 5 步那段注释写得很直白, 直接点名了那个错误的选项 —— 这类**说清楚不要用什么** 的注释, 你在
第 23 篇 (那个关键词检查不是安全边界) 也见过一次.

第 7 步会让你发现: **这一百六十行里几乎没有一句是新知识**, 它全是前面十几篇的组合.

> **关键洞见:** 一个系统的主干文件通常很薄, 因为它的工作是**编排** 而不是实现. 你读懂了零件,
> 主干就是免费的.

### 练习 2: 把清空那一行注释掉, 看两个用户串台

**目标:** 亲手制造一次数据泄漏, 因为它不报错而且本地几乎不会自己出现.

**怎么做:**

1. 起开发服务器, 打开 agent 页, 问一个有记忆特征的问题, 比如
   **记住一个数字 7, 别的什么都不用做**
2. 打开 [`api/index.py`](../../api/index.py), 把清空 agent 记忆那一行**注释掉**
3. 重启开发服务器 (Ctrl+C 退出, 再 `mise run dev`)
4. **开一个全新的浏览器标签页** (或者无痕窗口) 打开 agent 页 —— 这模拟第二个用户
5. 在这个新页面里, 第一句话就问: **我刚才让你记的数字是多少?**
6. 观察它答得出来吗
7. 把那一行恢复, 重启, 重复第 4 到 5 步, 对比
8. 全部还原

**你会观察到:**

第 6 步它**可能答得出 7** —— 而那个新标签页从来没提过 7. 那段记忆来自你第 1 步那次对话, 残留
在了那个跨请求活着的 agent 对象上.

第 7 步恢复之后, 新页面会说它不知道 —— **这才是对的**.

注意第 6 步用的是**可能**: 它取决于那次请求落在哪个进程上, 所以不一定每次都复现.
**这个不确定性本身就是这类 bug 最讨厌的地方** —— 它偶尔出现, 而偶尔出现比每次出现难查得多.

> **关键洞见:** 你刚刚注释掉的是一行看起来纯属浪费的代码. 这一篇每一节讲的都是同一件事 ——
> **看起来多余的动作, 背后大概率有一次事故.**

## 14. 导师寄语

**为什么把这九步讲两遍:**

第 5 篇讲的时候你只能记住顺序, 因为那时候零件你一个都不认识. 现在再走一遍, 每一步背后都有
一篇的知识撑着 —— 第 4 步要用第 16, 27 篇, 第 6 步要用第 14 篇, 第 7 步要用第 27 篇.

**这本身就是读代码的一种方式**: 先粗粗走一遍认路, 学完零件再回来走一遍. 第二遍看到的东西
和第一遍完全不同, 而且第二遍才是真正读懂.

**这一篇六个决定有一个共同点, 我想让你带走的是这个.**

它们都是**看起来多余的动作**: 明明有记忆还要清空, 明明有个用量数字还要挑一个, 明明能直接调
模型还要先绕一下 stdout.

你以后接手别人的代码, 一定会遇到一行看不出为什么存在的代码. 那时候有两种反应:

| 反应 | 后果 |
| :--- | :--- |
| 看起来没用, 删了 | 有机会重新经历一次它当初防住的那个事故 |
| **先假设它有理由, 去找那个理由** | 找不到再删, 而且删的时候心里有数 |

而这个仓库做的是**第三件事**: 把理由写在旁边. 你读到的那些注释, 每一条都是在替未来那个想
删掉它的人回答问题.

**关键洞见:**

- 看起来多余的动作, 背后大概率有一次事故
- 一个跨请求活着的对象, 任何残留状态都是潜在的串台
- 两个名字相近的数字, 一个对一个错, 而错的那个在单次测试里看起来正常
- 只在某个部署环境出现的 bug, 本地复现不出来 —— 只能撞一次然后写进注释
- 主干文件很薄, 因为它的工作是编排. 零件读懂了, 主干就是免费的

**下一步:**

后端这条主线到这里走完了. 第 29 篇 (渲染契约) 回到那个横跨前后端的话题: 提示词里的触发短语,
kickstart 的配额, 前端的查找表 —— 三样东西必须对齐, 而对不齐的时候**三边都不报错**.

## 15. 速查

**四段:**

```text
进门 1-3   收下, 拆开, 找出问题
准备 4-5   清空记忆灌历史, 查预算
干活 6     调模型 (stdout 要顶掉)
出门 7-9   记账, 挖答案, 编码发回
```

**六个决定和它们的症状:**

| 决定 | 不这么做的症状 |
| :--- | :--- |
| 日志打码 | 凭据被复制进留存日志 |
| 解析宽松 | 前端升级把后端弄崩 |
| 清空记忆 | **用户之间串台** |
| 先查预算 | 钱花完才拦 |
| 顶掉 stdout | 线上响应流被污染, 本地正常 |
