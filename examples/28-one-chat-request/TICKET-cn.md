# 一次 chat 请求, 从头到尾

## 1. 目标

第 6 篇你走过一遍这九步, 那时候是为了**认路** —— 你还不知道提示词是什么, 工具怎么定义,
答案怎么挖出来.

**现在你全知道了, 所以同一条路可以读出完全不同的东西.** 这一篇回到同一条路上, 停在每一个
有人踩过坑的地方.

代码是 `api/index.py`, 全文一百六十行, 而且**它自己不做任何业务** —— 全是编排. 这一篇要讲的
是那条路上的**六个决定**, 每一个换个写法程序照样跑, 但会**静默地出错或者多花钱**.

**其中最要紧的是第 4 步那个清空 agent 记忆.** 它看起来纯属浪费, 但三篇的知识合起来才说得通:
那个 agent 对象建一次就一直留着所以跨请求活着, 权威的历史在前端 (第 21 篇), 线上一个实例会
连着服务不同用户 (第 16 篇). **不清空的后果是第二个用户读到第一个用户的对话** —— 那不是答案
不准, 是数据泄漏.

**练习 2 会让你亲手制造一次.** 这个 bug 本地几乎不会自己出现, 因为你一个人用的时候前后两轮
本来就是同一段对话.

带走的那句话是: **看起来多余的动作, 背后大概率有一次事故.**

---

## 2. 要做的事情

1. 读完 README, 六个决定每一个都要读到它的症状那一段.
2. 开一个叫 `28-one-chat-request` 的 branch.
3. 打开 `api/index.py`, 从上往下通读一遍, 不用读懂每一行.
4. 按顺序找出这六处并记下行号: 记日志, 解析请求体, 清空记忆, 查配额, 顶掉 stdout, 记账.
5. 读清空记忆那一处上面的注释, 确认它说的和 README 第 7 节一致.
6. 读记账那一处的注释, 找出它明确说了不要用哪个东西, 以及为什么.
7. 数一数这个文件有几个 `import`, 想清楚为什么这么多.
8. 回答: 这九步里有几步的知识来自你前面读过的某一篇, 各是哪一篇.
9. 起开发服务器, 在 agent 页问一个有记忆特征的问题, 比如让它记住数字 7.
10. 把清空记忆那一行注释掉, 重启服务器.
11. 开一个全新的浏览器标签页或者无痕窗口打开 agent 页, 第一句就问刚才让你记的数字是多少.
12. 观察它答不答得出来, 想清楚那段记忆是从哪儿来的.
13. 恢复那一行, 重启, 重复第 11 步对比.
14. 全部还原.

**预计用时:** 60 到 90 分钟

      记忆残留, 也确认了全程没有报错.
- [ ] **为什么本地测不出来**: 你能说清这个 bug 为什么在本地一个人用的时候几乎不出现.

      看起来正常.

- [ ] **工作区干净**: 注释掉的那一行还原了.
