# 看懂那两条发布命令做了什么

## 1. 目标

第 13 篇你敲过 `sync-db` 和 `verify-db` 两条命令, agent 那时候就活了. 但当时你只是照做,
那五分钟里到底发生了什么, 你还不知道.

**这一篇就是回头把它讲清楚**, 而且一多半篇幅不在讲命令, 在讲**三个当初都选错过的决定**:
本地开发读哪个库, 多项目共用一个实例怎么隔离, 以及怎么让连接认准我们那个 schema.

**三个决定有一个共同点, 也是这一篇最想让你带走的: 它们选错的时候全都不报错.**

第一个决定回答一个你迟早会问的问题. 数据集自带的那二十个查询是 SQLite 方言写的, 而 agent
查的是云上的 PostgreSQL, 所以直觉的做法是按环境切换引擎: 本地读 SQLite, 线上读 PostgreSQL.
这个做法行不通, 理由只有一条: **查这个库的不是人, 是模型**.
而模型照抄的那份提示词**只有一份**, 没办法两个环境两个样.

**练习 2 那条不同步的报错要亲手撞一次.** 它是这两篇数据内容的收口: 一个能被机械判断的坏
状态, 应该当场抛异常, 而不是写进文档等人记住.


**卡住了别硬扛.** 把三样东西一起给 AI: 你在读哪一篇的路径, 你敲的那条命令, 以及
**终端打出来的原文** (整段复制, 不要截图, 不要只说一句报错了).
粘贴前先把连接串和 key 的片段打码.

---

## 2. 要做的事情

1. 读完 README, 重点是那三个决定, 尤其是 `search_path` 那三种写法.
2. 开一个叫 `15-seed-to-postgres` 的 branch.
3. 先确认连得上: `mise run cli-test-db-conn`. 它只做一次 `SELECT 1`, 不碰任何表.
4. 再跑一次 `sync-db` (第 13 篇已经跑过一次了), 把它报出来的那个建表顺序完整抄下来.
5. 跑 `verify-db`, 确认每张表行数都和上一次一样.
6. 看着抄下来的那个顺序, 把最前面三张和最后面三张的表名念一遍, 说清排在最前面的那几张从
   名字上看有什么共同点.
7. 想清楚 `cli-test-db-conn` 和 `verify-db` 各自失败时, 分别说明了什么.
8. 在 `.env` 里加一行把 `SCHEMA_NAME` 指到一个不存在的名字, 重启开发服务器后再问一次,
   读那条报错.
9. 做一个思想实验: 如果没有那个检查, agent 会回答什么.
10. 删掉那一行, 重启, 确认恢复正常.

**预计用时:** 45 到 70 分钟 (同步本身要跑几分钟)

## 3. 检查清单

- [ ] **同步是幂等的**: 你再跑了一次 `sync-db`, 表顺序和行数都和第 13 篇那次一样, 并且能
      说清为什么跑一次和跑十次结果相同.
- [ ] **建表顺序的形状**: 你能说出排在最前面的那几张表有什么共同点, 以及为什么删表要倒着走.
- [ ] **为什么两边都读 PostgreSQL**: 你能说清这个项目为什么不按环境切换引擎, 理由要落在
      提示词只有一份这件事上; 也能说清方言不对时的症状为什么是答案变差而不是报错.
- [ ] **schema 不是前缀**: 你能用文件夹这个比方解释 schema, 并说清加表名前缀会让提示词在
      哪个环境错.
- [ ] **`search_path` 三种写法**: 你能说出三种分别会怎样, 特别是第二种为什么是间歇性失效,
      以及为什么事务是对的粒度.
- [ ] **校验为什么比行数**: 你能说清只问一句远程有没有数据的检查, 会漏掉哪种失败.
- [ ] **不同步的后果**: 你亲眼见过那条异常, 也能说清如果没有它 agent 会编出什么.
- [ ] **工作区干净**: 那一行临时改动还原了, 重启后 agent 又能正常回答, `git status` 没有
      留下未还原的东西.
