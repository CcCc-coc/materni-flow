# 把种子发布到 PostgreSQL

> 本地那份种子是 SQLite, 而 agent 查的是云上的 PostgreSQL. 那这个项目的提示词该照着哪一个
> 写? 答案可能和你猜的不一样.

## 1. 概览

数据现在躺在你硬盘上的一个 SQLite 文件里. 但 **agent 从来不读那个文件**.

第 13 篇 ([接上真数据和真模型](../13-light-it-up/README-cn.md)) 你已经把它搬过去了, agent
那时候就活了. **这一篇讲那五分钟里到底发生了什么.**

命令只有两条, 但这一篇一多半篇幅不在讲命令, 在讲**三个当初都选错过的决定**:

| 决定 | 那个看起来对的选项 | 实际选的 |
| :--- | :--- | :--- |
| 本地开发读哪个库 | 本地读 SQLite, 线上读 PostgreSQL | **两边都读 PostgreSQL** |
| 多个项目共用一个实例怎么隔离 | 给每张表加个前缀 | **用 schema** |
| 怎么让连接认准我们那个 schema | 连接时带一个参数 | **每笔事务里设一次** |

三个决定有一个共同点, 而这一篇最想让你带走的就是它: **它们选错的时候, 全都不报错.**

### 卡住了怎么办

这一篇每一步都可能出错: 连不上库, 同步中途失败, 或者核对出来行数对不上.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/15-seed-to-postgres/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/15-seed-to-postgres/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

先把上一篇那个悬念收掉, 因为它就是第一个决定.

### 那个看起来完全合理的做法

打开 [`dataset/`](../../dataset) 里那份 `03-` 开头的查询文档扫一眼, 你会看到 `strftime`,
`JULIANDAY` 这类**只有 SQLite 才有的函数**. 那二十个查询是对着本地那份种子写的.

可 agent 查的是云上的 PostgreSQL.

那怎么办? 几乎所有人的第一反应都是同一个: **按环境自动选.** 本地开发读那份现成的 SQLite,
方便又不用连网; 线上读 PostgreSQL. 两边都舒服.

**这个做法在这个项目里行不通**, 而理由只有一条:

> **查这个数据库的不是人, 是模型.**

人可以在两套方言之间切换 —— 你在本地写 `strftime`, 到线上自然会换成别的写法, 因为你知道
自己换了数据库.

**模型不会.** 模型写 SQL 的依据是 [`data/system-prompt.md`](../../data/system-prompt.md) 里
那些 SQL 例子, 它们是给它照抄的模板. 而**提示词只有一份**, 它没办法在本地是一个样子, 到
线上是另一个样子.

于是如果那些例子是对着 SQLite 写的, 发到线上之后:

| 提示词里写的 (SQLite) | PostgreSQL 上 |
| :--- | :--- |
| `strftime('%Y-%m', d)` | 不存在 |
| `JULIANDAY(a) - JULIANDAY(b)` | 不存在 |
| `DATE(d, '-90 days')` | 不存在 |
| `WHERE is_flag = 1` | 报错: 布尔和整数不能比 |

### 而线上永远不会崩

这是最要命的一步. agent 的 SQL 工具**把数据库报错转成文字还给模型**, 而不是抛出异常 ——
因为它的调用方是一个模型, 一个 traceback 会直接结束它这一轮.

于是模型收到一句这个函数不存在, 它就换个写法再试, 或者干脆绕开这个角度回答别的.

**症状不是异常, 是答案悄悄变差.** 没有任何监控会报这种事, 因为从系统的角度看一切正常:
请求成功, 有回答, 状态码 200.

### 所以结论是

**一份提示词只能对着一个确定的数据库写.** 那就让每个环境都用那一个, 笔记本也不例外.

代价要认清楚: 本地开发从此需要 `DB_*` 那几个环境变量, 而且第一次必须跑一次同步. 这是一个
安装步骤, 换掉的是一个**永远查不出来的错误答案**.

SQLite 没有消失, 它退回到它真正擅长的位置: **一个种子和一个同步源**, 而不是任何人查询的
对象. 第 19 篇 ([用业务问题学 SQL](../19-sql-by-business-question/README-cn.md)) 你会拿它
练查询, 那是在学 SQL, 不是在用这个 app.

学完这个 Task, 你将能够:

1. 解释为什么这个项目不按环境切换数据库, 理由要落在提示词只有一份上
2. 说清多项目共用一个实例时, 为什么隔离要用 schema 而不是表名前缀
3. 描述同步这件事的五步, 并说清为什么它每次都先删再建
4. 说出把连接钉在一个 schema 上的三种写法, 以及为什么前两种在这里会坏
5. 解释为什么校验要拿本地行数来比, 而不只是问一句远程有没有数据

## 6. 同步做了什么

先给个画面, 因为它和大多数人以为的不一样:
**它不是把新数据补进去, 它是把那个 schema 整个推倒重来.**

好, 慢慢来看. 一共五步.

**第一步, 先读一遍本地那个库长什么样.** 有哪些表, 每张表有哪些列, 谁的外键指向谁. 这一步
什么都还没搬, 但后面每一步都要用这张结构图 —— 不先拿到它, 你连该按什么顺序建表都不知道.

**第二步, 把每张表的数据读进内存, 按依赖顺序.** 所谓依赖顺序就是先父后子: 一张表如果有
外键指向另一张, 那另一张得排在它前面. 这个顺序不是谁手写的, 下面第 7 节讲它是怎么算出来的.

**第三步, 确保 schema 存在, 然后倒着删掉里面的表.** 注意是倒着. 建的时候先爹后儿子, 删的
时候就得先儿子后爹 —— 一张还被别人引用着的表是删不掉的.

那要是写反了呢? **数据库会当场拦住你**, 报一句外键还被引用着. 这是个好消息: 这类错误属于
能被机械判断的那种, 所以它当场失败, 而不是删掉一半留下一个残缺的库.

**第四步, 按同样的结构重新建表.** 表名和本地一模一样, 只是换了个 schema. 表名两边一致是
这里的全部设计目标, 下面第 7 节会讲为什么.

**第五步, 正着灌数据, 一批一千行.** 顺序又回到先父后子, 理由和第二步一样: 插一行子记录的
时候, 它爹得已经在那儿了.

**为什么要分批**: 一次性发一张六位数的表, 有超出驱动参数上限的风险, 而且会把整张表缓冲在
内存里; 一行一次往返又慢到不能用. 一千行是这两头之间的一个折中.

### 为什么要先删再建

因为这样它就是**幂等** 的: 跑一次和跑十次结果完全一样.

想想另一种做法 —— 只补新数据. 那你就要处理一堆问题: 这一行是新的还是改过的? 本地删掉的行
远程要不要删? 上次同步到一半断了怎么办?

**而这个库只是一份种子, 它没有任何值得保留的历史.** 既然重建的代价只是几分钟, 那就重建,
换来一个永远不用推理的状态: **同步完成 = 远程和本地一模一样.**

> **一条通用判断**: 一个操作如果能做成重复执行结果不变的, 就做成那样. 它省下的不是代码,
> 是你以后每次出问题时的推理负担.

### 它只碰自己那一个 schema

第 3 步在删表, 而这是一个共用的数据库实例 —— 别的项目的表也在里面.

**整个同步过程从头到尾没有任何一处会提到别的 schema 的名字.** 它删的每一张表都带着我们自己那个
schema 的前缀, 所以它够不着别人.

这正是下一节要讲的隔离设计带来的好处.

### 还有一道防呆

这个函数接两个引擎: 一个读 (SQLite), 一个写 (PostgreSQL). 它们在代码里是同一个类型, 所以
**没有任何东西拦得住你把它们传反**.

而传反的后果非常严重, 因为它第三步就开始删表 —— 它会去删你手里那个它以为是目标的东西.

所以函数一开始就检查这两个引擎各自是哪种数据库, 不对就当场拒绝. 那条报错还会直接提醒你
检查参数顺序.

> 这是一个很小但很典型的设计:
> **一个错误如果代价极高而且完全可以机械判断, 就在动手之前检查一次.**
> 类型系统在这里帮不了你, 因为两个引擎的类型确实一样.

## 7. 隔离用 schema, 不用表名前缀

第二个决定. 这个决定当初选错过一次, 而且是全部推倒重来才改回去的.

**背景:** 线上那个 Neon 实例是和别的项目共用的. 那怎么让几个项目的表不打架?

### 那个看起来更简单的做法

给每张表加一个前缀. 我们这个项目的表叫 `smbll_loan`, `smbll_customer`, 别人的叫别的.
不用学什么新概念, 改个名字就完事了.

**这个做法确实曾经在这个仓库里跑过, 然后被整个换掉了.**

### 它坏在哪

问题出在**本地和远程的表名从此不一样了**:

| | 本地 SQLite | 远程 PostgreSQL |
| :--- | :--- | :--- |
| 加前缀 | `loan` | `smbll_loan` |
| **用 schema** | `loan` | `loan` |

看第一行. 表名取决于背后是哪个引擎, 于是
**提示词里每一段 SQL 都在一个环境里对, 在另一个环境里错**.

而它错的方式和第 2 节那个方言问题一模一样: 不崩, 只是答案变差.

### schema 是怎么解决的

用大白话说, **schema 就是数据库里的一个文件夹.**

你电脑上两个不同的文件夹里可以各有一个叫 `report.txt` 的文件, 互不干扰, 而且你不需要把
文件改名叫 `project-a-report.txt`.

schema 干的是一样的事:

同一个 Neon 实例里可以并排放好几个 schema, 各装各的表:

| 实例里的这个 schema | 里面的表 | 说明 |
| :--- | :--- | :--- |
| `fintech_smb_lending_pipeline_medium` | `loan`, `customer`, ... | **我们的** |
| 别的项目的那个 | `loan`, ... | 表名**同名, 毫无问题** |

**表名回到了 `loan`, 两边一样.** 于是一份提示词在哪儿都是诚实的.

那个 schema 的名字写在 [`.env.defaults`](../../.env.defaults) 里的 `SCHEMA_NAME`, 而它是
这个数据集**唯一的标识符**.

> **把这条抽象出来: 需要隔离的时候, 把隔离放在名字外面, 不要塞进名字里.** 塞进名字里,
> 名字就随环境变了, 而所有引用那个名字的东西都得跟着变. 这条判断在很多地方都成立 ——
> 命名空间, 目录, 容器, 都是同一个思路.

## 8. 怎么让连接认准那个 schema

第三个决定, 也是最技术的一个. 它值得讲, 因为**前两种写法都试过, 都坏了**, 而且坏的方式
一次比一次难查.

先说清楚要解决什么: schema 有了, 但 agent 写的 SQL 里只写 `FROM loan`, 没写 schema 名字.
那数据库怎么知道去哪个文件夹里找?

答案是有一个设定叫 `search_path`, 相当于**当前目录**. 把它设成我们那个 schema, `loan` 就
自动解析到我们的表.

问题是: **在哪一步设?**

### 三种写法

| 写法 | 结果 |
| :--- | :--- |
| 1. 建立连接时当参数带上去 | **连接直接被拒**, app 根本连不上数据库 |
| 2. 连上之后立刻设一次 | **看起来好的, 但不安全** |
| 3. 每笔事务开始时设一次 | **对** |

**第一种** 是最直觉的写法. 它在普通 PostgreSQL 上没问题, 但这个项目连的是一个
**带连接池的地址**, 而连接池不认识这个参数, 于是它拒掉的是整个连接. 好消息是这个失败
非常响 —— 你会立刻发现连不上, 排查方向也很明确.

**第二种是真正危险的那个.** 你连上之后设一次, 测试全过, 上线一切正常, 然后某天开始出怪事.

原因要解释一下什么是连接池: 为了不让每个请求都重新握手一次, 中间有一个池子攥着一批连接
轮流借给你. 而这个池子的借出单位是**一笔事务**, 不是一次会话 —— 你这次查询借到的那根连接,
和上次那根**可能根本不是同一根**.

于是你在连上时设的那个当前目录, 下一次查询时可能根本不在那根连接上.

**症状是: 一张明明存在的表, 突然报不存在.** 而且是间歇性的, 取决于你这次借到了哪根连接.
这种问题查起来极其痛苦.

**第三种是对的**, 因为它把设定放在**事务** 这个粒度上 —— 而事务恰恰是连接池保证不会中途换
连接的那个单位. 池子再怎么调度, 一笔事务从头到尾都在同一根连接上.

> **关键洞见:** 一个设定该在什么粒度上做, 取决于**底下那层保证什么粒度不变**. 你猜错了,
> 代码不会报错, 只会偶尔出错 —— 而偶尔出错比一直出错难查一百倍.

## 9. 校验为什么要比行数

`verify-db` 看起来只是个可有可无的收尾. 它不是, 而理由很值得学.

**一个偷懒的校验会这么写: 连上远程, 看看有没有数据. 有就算过.**

这个检查**永远会通过**, 只要同步跑过一次, 哪怕它跑到一半断了.

而跑到一半是同步最常见的失败方式: 网断了, 超时了, 某一张表插到一半挂了. 这时候远程库里
**有数据**, 只是**少了一些**.

| 检查方式 | 半途而废的同步 |
| :--- | :--- |
| 远程有没有数据 | **通过**. 什么都看不出来 |
| **逐表对比本地行数** | **失败**, 并指出哪张表差多少 |

所以这个校验对每张表检查三件事: 表在不在, 是不是空的, 以及**行数和本地一不一致**. 第三条
才是真正干活的那条.

它不一致就 exit 1, 所以它可以直接当一道闸门用.

> **通用判据: 一个检查如果对着一个不会变的常数比, 它通常是没用的.** 有用的检查要对着
> **另一个独立算出来的值** 比 —— 这里是本地的行数.

## 10. 不同步会发生什么

最后说这两篇数据内容一直在铺垫的那个失败.

跳过同步不会让程序崩. 会发生的是:

**agent 连上一个空的 schema, 反射出零张表, 然后凭空编出一些看起来非常合理的表名来回答你.**

为什么它会编? 因为对反射器来说, **一个不存在的 schema 和一个空的 schema 长得一模一样** ——
两种情况它都返回零张表. 而模型拿到一句这个库里没有表, 它不会停下来, 它会尽力回答.

所以代码里专门有一个检查挡这件事: 反射出零张表就**当场抛异常**, 而且错误信息里直接写着
去跑哪条命令.

**这条报错你在第 5 篇没见过**, 因为那台机器连库都连不上, 根本走不到反射这一步. 它是下面
练习 2 里你要亲手撞一次的那条.

> 这是数据那两篇的收口, 也是整个仓库反复出现的那条判断:
> **在能跑但可能是错的, 和当场失败之间, 一律选后者.**

## 11. 练习

### 练习 1: 再同步一次, 看它是幂等的

**目标:** 确认这条命令跑几次结果都一样, 并把那个建表顺序和外键对上.

**怎么做:**

1. 开一个叫 `15-seed-to-postgres` 的 branch
2. 先确认能连上: `mise run cli-test-db-conn`
3. **再跑一次** `sync-db` (第 13 篇已经跑过一次了), 把它报出来的表顺序完整抄下来
4. 跑 `verify-db`, 确认每张表行数都和上一次一样
5. 看着抄下来的那个顺序, 把**最前面三张** 和**最后面三张** 的表名念一遍
6. 用一句话回答: 排在最前面的那几张, 从名字上看有什么共同点

**你会观察到:**

第 3 步和第 13 篇那次的顺序**一模一样**, 行数也一样. 这不是碰巧, 是这条命令被设计成幂等的:
它每次都先倒着删掉本项目 schema 里的表再重建, 所以跑一次和跑十次结果相同.

第 5 步你会发现排在最前面的那几张**一个外键都没有**, 而排在最后的那几张指向了好几张别的表.
这就是先父后子.

> **关键洞见:** 一个可以放心重跑的命令, 和一个跑之前要先想一想的命令, 在真实工作里是两种
> 完全不同的东西. 幂等不是洁癖, 它决定了你敢不敢在半夜出问题的时候敲下它.

### 练习 2: 亲眼看一次编造被拦下来

**目标:** 理解为什么不同步比连不上更糟.

**怎么做:**

1. 在 `.env` 里加一行, 把 schema 指到一个不存在的地方:
   `SCHEMA_NAME="nowhere_at_all"`
2. 重启开发服务器, 在 agent 页问一个关于数据的问题
3. 读那条错误信息, 特别看它有没有告诉你该跑什么
4. 现在做一个思想实验: **假如没有那个检查, 你猜 agent 会回答什么?**
5. 把那一行删掉, 重启, 确认恢复正常
6. 最后再想一遍: 为什么这个检查不能写成一句文档里的提醒就算了?

**你会观察到:**

第 3 步你拿到的是一条指名道姓的异常, 而不是一个编出来的答案.

第 4 步的答案是: 它会编. 模型看到这个库里没有表, 但用户在问违约率, 于是它会假设有一张叫
loans 或者 defaults 的表, 写一条语法完全正确的 SQL, 然后基于那条 SQL 的报错或者干脆基于
常识给你一个数字. **那个数字看起来和真答案毫无区别.**

> **关键洞见:** 第 6 步的答案是这两篇的总结 ——
> **一个能被机械判断的坏状态, 应该在启动时抛异常, 而不是写进文档等人记住.**
> 文档挡不住任何人, 而这个坏状态的代价是一个你永远发现不了的错答案.

## 12. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 为什么两边都读 PostgreSQL | 因为查库的是模型, 而**提示词只有一份**, 它没法两个环境两个样 |
| 方言问题的症状 | 不崩. SQL 工具把报错转成文字还给模型, 模型换个写法接着编, **答案悄悄变差** |
| SQLite 退到哪儿去了 | 一个种子和一个同步源, 不再是任何人查询的对象 |
| 隔离用 schema | schema 就是数据库里的文件夹. **表名两边一样**, 这是全部设计目标 |
| 那条通用判断 | 需要隔离时, 把隔离放在**名字外面**, 别塞进名字里 |
| 同步是幂等的 | 每次推倒重来. 换来一个不用推理的状态: 同步完成 = 两边一样 |
| 引擎传反的防呆 | 它第三步就删表, 而两个引擎类型一样. 代价高又能机械判断, 就先检查 |
| `search_path` 三种写法 | 连接时带参数会被池子拒; 连上设一次会间歇失效; **每笔事务设一次** 才对 |
| 那条洞见 | 一个设定该在什么粒度上做, 取决于底下那层保证什么粒度不变 |
| 校验为什么比行数 | 问一句有没有数据的检查永远通过. 半途而废的同步只有对行数才查得出来 |
| 不同步的后果 | 空 schema 和不存在的 schema 长得一样, agent 会编表名. 所以有检查当场拦住 |

## 13. 导师寄语

**为什么这一篇讲的三个决定值得记住:**

它们表面上是三件毫不相干的事: 读哪个库, 怎么隔离, 在哪儿设一个参数. 但它们的形状完全一样.

每一个都有一个更方便, 更直觉, 而且**当场就能跑通** 的选项. 每一个都在几周或几个月之后,
以一种查不出来的方式坏掉.

**这就是工程判断力和写代码的区别.** 写代码是让它跑起来, 而判断力是知道哪一种跑起来是假的.

这三个决定我都是踩过才知道的 —— 表名前缀那一版是整个推倒重来的, `search_path` 那一版是在
一个间歇性的表不存在报错上耗了很久才想明白的.

**所以这一篇你真正该带走的不是这三个答案, 是那个提问的习惯:** 每次你选了一个更方便的做法
时, 停下来问一句 —— **如果它错了, 我会怎么知道?** 如果答案是我不会知道, 那就换一个.

**关键洞见:**

- 提示词只有一份, 所以它必须对着一个确定的数据库写
- 需要隔离时, 把隔离放在名字外面
- 一个设定该在什么粒度上做, 取决于底下那层保证什么粒度不变
- 对着常数比的检查通常没用, 有用的检查对着另一个独立算出来的值比
- 能机械判断的坏状态要当场抛异常, 而不是写进文档等人记住

| 在哪儿设 `search_path` | 每笔事务里 | 间歇性地报表不存在 |
