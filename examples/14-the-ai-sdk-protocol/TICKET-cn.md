# 看懂前端和 agent 之间的翻译层

## 1. 目标

第 13 篇把请求送到了后端进程. 这一篇讲它进门之后的第一件事: **翻译**.

前端和 agent 描述一段对话的方式完全不同. 前端一条消息的正文是一串带类型的 part, agent 要的
是内容块列表; 前端每次送完整历史, agent 要的是历史和当前问题分开. 有一层代码同时懂两边, 而
它只有一百多行.

**这一篇要大量对着真实代码读, 但不用背.** 目标是能顺着找到, 以及能说清几个决定为什么这么做.

**最值得带走的是一条通用判据: 对读的东西严格, 对不读的东西宽容.** 那个请求数据模型故意写得
很松, 多出来的字段一律接受并忽略, 不认识的消息类型也不炸. 这不是偷懒, 是在防一个很贵的失败:
前端库半年后升级加了新字段, 而严格校验的后端会在别人跑一次依赖升级的那天开始拒绝合法流量,
报错还发生在离原因十万八千里的地方.

练习 1 要你打开浏览器的网络面板看真实的请求和响应. **这个动作本身比这一篇的内容更值钱**,
因为它对任何 web 项目都成立.

---

## 2. 要做的事情

1. 读完 README, 重点是那个数据模型为什么故意宽松, 和出去那条事件流的四个不能省的细节.
2. 打开 `agent_app/vendor/vercel_ai_sdk.py`, 找到那个允许多余字段的配置, 和那个装不认识的
   类型的通用类, 以及把类型映射到模型类的那张表.
3. 打开 `agent_app/ai_sdk_adapter.py`, 找到进来方向那两个函数, 读它们各自丢掉了什么.
4. 在同一个文件里找到那三个 HTTP 头, 确认它们和产出事件的那个函数在一起.
5. 起开发服务器, 打开 agent 页, 打开浏览器开发者工具的网络面板.
6. 点一个 kickstart 按钮, 在请求列表里找到那条 chat 请求.
7. 看请求那一侧: 找到发上去的 JSON, 对照 README 第 6 节那个形状, 认出 `messages` 和 `parts`.
8. 看响应那一侧: 从头读到尾, 找出三段式那几行, `finish`, 和最后那个结束标记.
9. 再点一个别的按钮, 这次找找有没有思考那三行事件; 想清楚什么情况下它们会整段消失.
10. 开一个叫 `14-the-ai-sdk-protocol` 的 branch, 加载 `/about-bi-agent-app-scaffold-cn`,
    问它前端新增一种 part 类型时后端要动哪些文件, 明确要求先不要动手.
11. 再问它换一家 LLM 供应商要不要动 vendor 那个文件, 看它答不答得出理由.

**预计用时:** 60 到 90 分钟

---

## 3. 检查清单

- [ ] **请求体的形状**: 你能说出一条消息的正文为什么是一串 part 而不是一个字符串, 以及前端
      为什么每次都送完整历史.
- [ ] **看过真实请求**: 你在网络面板里看过一次发上去的 JSON, 能指出 `messages` 和 `parts`
      在哪.
- [ ] **看过真实响应**: 你在同一处看过那条事件流, 能找出三段式那几行, `finish`, 和结束标记.
- [ ] **宽松的理由**: 你能说清那个数据模型为什么故意宽松, 并描述严格校验会在什么时候, 以什么
      形式咬人.
- [ ] **那条判据**: 你能复述对读的东西严格对不读的东西宽容, 并举出这个仓库里另一处同样思路
      的设计.
- [ ] **丢掉的两样**: 你能说出翻译历史时丢掉了什么, 以及各自的理由.
- [ ] **四个不能省的细节**: 三段式, 块的 id, `finish` 事件, 结束标记, 你能各说出少了会怎样.
- [ ] **头为什么打包**: 你能说清那三个 HTTP 头为什么和生成器住在一起, 以及散开写漏掉一处的
      症状是什么.
- [ ] **边界感**: 你能说出什么东西不该进 vendor 那个文件, 并说清理由.
