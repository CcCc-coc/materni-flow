# AI SDK 协议: 进来的请求体, 出去的事件流

> 前端说的是 message parts, agent 说的是 content blocks. 有一层代码同时懂两边, 而它只有
> 一百多行.

## 1. 概览

第 13 篇把请求送到了后端那个进程. 现在它进门了, 接下来会发生什么?

第一件事是**翻译**. 因为前端和 agent 描述 "一段对话" 的方式不一样, 而且不是小差异:

| | 前端送上来的 | agent 要的 |
| :--- | :--- | :--- |
| 一条消息的正文 | 一串带类型的 part (文字, 思考, 将来还会有别的) | 一个内容块列表 |
| 谁在说话 | `role` 字段 | 也是 `role`, 但结构不同 |
| 回答怎么回去 | 一串按协议定义的事件, 走一条长连接 | agent 只交回两个字符串 |

`agent_app/ai_sdk_adapter.py` 是**唯一同时懂两边** 的地方. 这一篇就读它, 加上它旁边那个数据
模型文件.

**这一篇会大量指着真实代码讲.** 不用背, 但要能顺着找到.

---

## 2. 学习目标

先说一个这一层最值得学的决定, 它和你以后写任何对接代码都有关.

前端那个 AI SDK 是一个**跑得很快的库**. 它会不断加新的消息类型, 新的字段. 而后端是 Python
写的, 和前端不在一个发布节奏上.

于是有一个很容易踩的坑: ** 后端把请求体校验得很严, 然后在别人跑一次前端依赖升级的那天开始
拒绝完全合法的流量.**
而失败发生在 Python 这边, 离引发它的那次升级十万八千里.

这个仓库的做法是一条老规矩: **对读的东西严格, 对不读的东西宽容.** 这一篇会讲它具体怎么落地,
以及为什么那个文件被单独放在一个叫 vendor 的目录里.

学完这个 Task, 你将能够:

1. 说出前端送上来的请求体大致长什么样, 以及一条消息为什么是一串 part 而不是一个字符串
2. 解释那个数据模型为什么故意宽松, 以及不宽松会在什么时候咬人
3. 复述出去那条事件流的形状, 说出三段式和那个结束标记各自在防什么
4. 说清那三个 HTTP 头为什么必须和生成器住在一起, 而不是在调用处拼
5. 说出翻译时被丢掉的两样东西, 以及为什么丢掉它们是对的

## 5. 两个文件, 分工不能混

| 文件 | 是什么 | 说明 |
| :--- | :--- | :--- |
| `agent_app/vendor/vercel_ai_sdk.py` | **纯数据模型** | 前端 POST 上来那包 JSON 的 Python 镜像. 它只描述形状, 不做任何转换 |
| `agent_app/ai_sdk_adapter.py` | **翻译和编码** | 把模型转成 agent 要的消息, 以及把 agent 的回答编码成事件流 |

这个划分值得注意: **描述数据的代码和转换数据的代码分开了.** 前者会随着前端库升级而变, 后者
随着这个 app 自己的需求而变, 两者的变化原因不同, 所以不放一起.

### 那个目录为什么叫 vendor

`vendor` 是一个约定俗成的名字, 意思是**从别处拷进来的第三方代码, 不是我们写的**.

这个文件确实是从一个外部小包拷进来的. **拷而不是装依赖**, 两个理由:

- 它只有一百来行数据模型, 不值得为它引入一个我们控制不了发版节奏的依赖
- 下一节那个宽松行为是这个仓库加的, 不是上游的

放进 `vendor/` 是在给后来的人一个信号: **这里的代码规矩和别处不一样, 动它之前先想想上游.**

## 6. 进来的请求体长什么样

前端每次发请求, 送上来的是这样一包东西 (简化过):

```json
{
  "id": "...",
  "messages": [
    {
      "id": "...",
      "role": "user",
      "parts": [
        { "type": "text", "text": "Grade C 的定价对吗?" }
      ]
    },
    {
      "id": "...",
      "role": "assistant",
      "parts": [
        { "type": "reasoning", "text": "我需要先看一下风险等级表..." },
        { "type": "text", "text": "Grade C 的实际违约率是 9.9%..." }
      ]
    }
  ]
}
```

两件事值得停一下.

**第一, 一条消息的正文是一串 part, 不是一个字符串.** 因为一条 agent 消息里可能同时有思考和
正文, 将来还可能有工具调用记录, 图片, 引用. 用一个列表装, 加新类型时不用改结构.

**第二, 前端每次都送完整的历史.** 不是只送新问的那一句. 这意味着
**对话状态住在浏览器里, 后端是无状态的**, 而那正是它能跑在 serverless 上的原因,
第 13 篇讲过.

## 7. 那个数据模型为什么故意宽松

打开 `agent_app/vendor/vercel_ai_sdk.py`, 你会在几个类上看到这样一行:

```python
model_config = ConfigDict(extra="allow")
```

意思是: **多出来的字段一律接受并忽略, 不报错.**

还有一个类叫 `UnknownUIPart`. 它是干什么的? 文件里有一张表:

```python
PART_MODEL_BY_TYPE: dict[str, type[BaseMessagePart]] = {
    ...
}
```

解析一个 part 时, 拿它的 `type` 去查这张表. **查不到就落到那个通用的壳**, 而不是抛异常.

### 这两条合起来在防什么

设想一个很具体的场景: 半年后 AI SDK 发了个新版本, 加了一种新的 part 类型. 某天有人跑了一次
前端依赖升级, 于是前端开始往后端送这种新 part.

| 如果后端严格校验 | 如果后端宽松 |
| :--- | :--- |
| 请求解析失败, 后端报错 | 那个 part 被解析成通用的壳, 后端照常处理它认识的那些 |
| 用户看到的是聊天彻底不能用 | 用户什么都没察觉 |
| 报错发生在 Python 这边, 而**原因是一次前端依赖升级** | 无事发生 |

最后一行是关键. **失败的地方和引发它的改动隔得非常远**, 而这类问题的排查成本极高.

### 判据: 对读的东西严格, 对不读的东西宽容

具体到这个文件:

| 字段 | 处理 |
| :--- | :--- |
| 后端真正会读的 (`messages`, 每个 part 的 `type` 和 `text`) | **有类型, 缺了就报错** |
| 其余一切多出来的字段 | 接受并忽略 |
| 不认识的 part 类型 | 不炸, 解析成通用的壳 |

这条判据不只适用于这里. ** 你以后写任何对接别人系统的代码, 都该问一句: 这个字段我真的会读
吗? 不读的话, 我凭什么因为它变了而失败?**

### 什么时候该改这个文件, 什么时候不该

| 情况 | 该不该改 |
| :--- | :--- |
| 后端开始需要读一种新的 part 类型 | **该**. 加一个模型类, 在那张表里加一行. 就这两步 |
| 想加任何和 LLM 供应商有关的东西 | **不该**. 这个文件里出现某家供应商的痕迹, 就意味着换供应商要动前端契约, 而这两件事毫无关系 |

## 8. 翻译进来的: 丢掉两样东西

`ai_sdk_adapter.py` 里有两个函数负责进来的方向.

**`get_last_user_message_text`** 取出这一轮要回答的那句话. 注意它只取**看得见的文字 part**,
所以一段思考永远不会被误当成用户说的话.

它在拿不到东西时**返回空而不是抛异常**. 理由写在函数文档里: 那是客户端的 bug, 而对它有用的
回应是一条消息, 不是一段崩溃堆栈.

**`request_body_to_agent_history`** 把之前的对话转成 agent 的格式. 它丢掉两样东西:

| 丢掉什么 | 为什么 |
| :--- | :--- |
| **所有思考 part** | agent 重读自己之前的思考没有好处, 而那些块很长. 留着的话每一轮都会重发一次, 并且**付一次钱** |
| **最后一条消息** | 那是现在要回答的问题. 它作为 agent 的输入进去, 不作为历史 |

还有一条防御: 一条消息如果一个文字 part 都没有, 就整条跳过, 而不是送一条空内容上去,
因为**供应商会拒绝空内容**.

第二条值得多想一秒: 历史和当前问题是**两个不同的参数**, 不是一个列表. 这是几乎所有 LLM
接口的共同形状, 第 16 篇 (多轮对话) 你会自己动手实现一遍.

## 9. 出去的: 一条事件流

回答不是一次性返回的, 是**一段一段流回浏览器** 的. 用的格式叫 SSE, 直译是服务器发送事件:
服务器把连接挂着, 想说什么就往里写一行, 浏览器边收边显示.

这个 app 发出去的事件长这样:

```text
data: {"type": "reasoning-start", "id": "..."}

data: {"type": "reasoning-delta", "id": "...", "delta": "..."}

data: {"type": "reasoning-end", "id": "..."}

data: {"type": "text-start", "id": "..."}

data: {"type": "text-delta", "id": "...", "delta": "..."}

data: {"type": "text-end", "id": "..."}

data: {"type": "finish", "finishReason": "stop"}

data: [DONE]

```

每个事件是一行 `data:` 加一段 JSON, 后面跟一个空行. 那个空行是格式规定的分隔符, 不能省.

### 四个不能省的细节

| 细节 | 少了会怎样 |
| :--- | :--- |
| **三段式**: 每种内容都是 start, delta, end | 前端不知道一个块什么时候开始什么时候结束, 没法开一个折叠框再填它 |
| **每个块带一个 id** | 前端分不清同时到达的两个块, 也没法把每个 delta 匹配回它所属的块 |
| **那个 `finish` 事件** | **界面会一直转圈**, 因为它不知道说完了 |
| **那个 `[DONE]` 标记** | 这是协议定义的流终止标记, 不是这个项目发明的 |

还有一条: **思考为空时整段跳过**, 三个 reasoning 事件一个都不发. 因为一个空块在界面上是一个
点开什么都没有的折叠箭头.

### 一个 delta 装完了整个字符串

看那段代码你会发现, `text-delta` 只发了一次, 里面装着完整的答案.

原因很朴素: **走到这一步的时候 agent 早就写完了**. 后端拿到的是一个完整字符串, 没有什么可以
一点点吐的.

**这不影响协议的正确性.** 真正的逐字流式会发很多个 delta, 而**协议的其余部分一个字都不用改**.
换句话说, 这一层已经为将来的逐字流式准备好了, 只是现在还没用上.

顺带解释一下那个 `yield`: 它让这个函数每产出一段就交出去一次, 而不是把所有内容攒完再返回.
这正是流式所需要的形状.

## 10. 那三个 HTTP 头和生成器住在一起

除了那些事件, 响应还必须带三个头:

```text
x-vercel-ai-ui-message-stream: v1
Cache-Control: no-cache
Connection: keep-alive
```

第一个是前端用来识别 "这是一个 v5 消息流" 的. **少了它前端不会按这个协议解析**, 于是页面上
什么都不显示.

后两个是让中间的代理和浏览器**别缓冲这个流**. 缓冲了的话, 用户会等到全部内容到齐才一次性
看到, 流式就白做了.

### 为什么它们不在调用处拼

代码里这三个头和那个生成器包在同一个函数里, 调用方只写一行就能拿到一个完整的响应.

设想另一种写法: 每个要返回流的地方各自拼一次响应对象, 各自加三行头. 那等于
**把协议的一部分交给使用者保管**:

- 协议改了要同时改每一处
- 而漏掉一处的症状是**前端静默地不渲染**, 不报错

这个 app 里返回流的地方不止一处: 正常回答是一处, 配额超了是一处, 请求为空又是一处. 三处
都得对.

**这是一条通用的规矩**: 一个东西的正确性依赖好几个部分同时到位时, 把它们打包在一起, 别让
调用者去记.

## 11. 练习

### 练习 1: 亲眼看那条事件流

**目标:** 确认屏幕上那段流式文字, 底下真的是一行行事件.

**怎么做:**

1. 起开发服务器, 打开 agent 页
2. 打开浏览器的开发者工具, 切到网络那一栏
3. 点一个 kickstart 按钮
4. 在请求列表里找到 `chat` 那一条, 点开它
5. 先看**请求** 那一侧: 找到发上去的 JSON, 对照第 6 节那个形状, 认出 `messages` 和里面的
   `parts`
6. 再看**响应** 那一侧: 你应该看到一行行 `data:` 开头的东西
7. 从头读到尾, 找出 `text-start`, `text-delta`, `text-end`, `finish`, 和最后那个 `[DONE]`
8. 再点一个别的按钮, 这次找找有没有 `reasoning-start` 那三行

**你会观察到:**

响应那一侧的内容和第 9 节那段示意几乎一模一样. 而请求那一侧, 如果你之前已经问过几轮,
`messages` 里会有好几条, 因为**前端每次都把整段历史送上来**.

> **关键洞见:** 界面上那些看起来很高级的东西, 底下往往是一段格式很朴素的文本. 学会打开网络
> 面板看真实的请求和响应, 比读十篇文档都快.

### 练习 2: 让 AI 拆一个协议改动, 并检查它的边界感

**目标:** 用第 8 篇那个方法, 验证一个和外部协议有关的改动.

**怎么做:**

1. 开一个叫 `14-the-ai-sdk-protocol` 的 branch, 加载 `/about-bi-agent-app-scaffold-cn`
2. 问它:

```text
假设前端的 AI SDK 升级之后, 开始往后端送一种新的 message part, 类型叫 "source",
而后端需要读它里面的一个字段. 请只告诉我要动哪些文件, 每个文件改什么. 先不要动手.
```

3. 读它的答案, 检查两件事:
   - 它有没有说清**改哪两处**, 也就是加一个模型类加在那张表里加一行
   - 它有没有**顺手去改别的地方**, 比如把翻译函数也改了
4. 再问一个反向的:

```text
如果我想让这个后端支持一家新的 LLM 供应商, 需要动 vendor 那个文件吗? 为什么?
```

5. 正确答案是**不需要**. 看它答不答得出理由

**你会观察到:**

第 2 步那个改动是两步, 而且**只在 vendor 那个文件里**. 第 4 步那个问题在考它知不知道这个
文件的边界: 前端契约和 LLM 供应商是两件毫不相干的事, 把供应商的痕迹写进这个文件, 就等于把
两件不相干的事绑死了.

> **关键洞见:** 判断一个人 (或者一个 AI) 是不是真懂一层代码, 最快的办法不是问它这一层是什么,
> 是问它**什么东西不该进这一层**.

## 13. 导师寄语

**为什么这一层值得单独读一遍:**

对接外部系统的代码有一个共同特征: **它的正确性一半不在你手里.** 对方会升级, 会加字段, 会改
行为, 而你收到的往往是一个和原因毫无关联的报错.

这一层给出的答案不是把校验写得更严, 是**把自己依赖的面缩到最小**: 我真正要读的就那几个字段,
其余的我不看也不管. 依赖的面越小, 别人的变化能伤到你的机会就越少.

同一个思路在这个仓库里出现过好几次. 组件不许拼句子, 是缩小组件对文案的依赖面; 生产路径不
import 教学层, 是缩小 app 对课程的依赖面. 都是同一件事.

**关键洞见:**

- 对读的东西严格, 对不读的东西宽容. 不读的字段变了, 你凭什么失败
- 判断懂不懂一层代码, 问它什么东西不该进这一层, 比问它是什么更管用
- 一个正确性依赖多个部分同时到位的东西, 打包在一起, 别让调用者去记

**下一步:**

到这里为止, 模型一直是一个黑盒: 你只知道 agent 会回答. 第 15 篇 (直接调模型) 会把所有框架
拆掉, 用三家供应商各自最底层的方式发一次请求, 看清楚线上跑的到底是什么形状.

## 14. 速查

**两个文件:**

- `agent_app/vendor/vercel_ai_sdk.py`: 请求体的数据模型, 故意宽松
- `agent_app/ai_sdk_adapter.py`: 翻译和编码, 两个方向都在这里
