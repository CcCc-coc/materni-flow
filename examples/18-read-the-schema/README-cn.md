# 读懂这个库: 十张表是怎么串起来的

> 面对一个陌生数据库, 第一件事不是把每张表都看一遍. 是先认出哪几张是主角.

## 1. 概览

上一篇你把数据造出来了. 现在硬盘上躺着一个有十张表, 十几万行的数据库, 而你对它一无所知.

这一篇教你怎么读它. 但**它不是一篇字典**, 不会带你把十张表逐个过一遍 —— 那份东西已经写在
[`dataset/`](../../dataset) 的 ER 文档里了, 需要的时候去查就行.

这一篇教的是**怎么读**, 那是一个可以带到任何一个陌生数据库上的方法:

| 步 | 干什么 |
| :--- | :--- |
| 1 | 先按角色把表分成三类, 认出哪几张是主角 |
| 2 | 顺着外键把主角串成一条业务生命线 |
| 3 | 找出那些数据库管不了, 但业务上必须守的规则 |

**为什么这个方法值钱?** 因为你以后进任何一家公司, 面对的都是一个几十上百张表的库, 而没有
人有空给你讲一遍. 能不能在半天之内摸清一个陌生库的主干, 是很实际的一项能力.

---

## 2. 学习目标

先说一件反直觉的事.

**一个数据库里的表, 重要性差别极大.** 十张表不是十个平等的东西, 它们大致分成三类, 而这三
类你要花的力气完全不同:

| 类型 | 大白话 | 这个库里的例子 | 你要花多少力气 |
| :--- | :--- | :--- | :--- |
| **查找表** | 一本小字典, 用来把代码翻译成人话 | industry, risk_grade, loan_status | **很少**. 扫一眼知道有哪些取值就行 |
| **主体表** | 这门生意里的主角 | customer, application, loan | **很多**. 它们是业务的骨架 |
| **流水表** | 主角身上发生的事, 一件一行 | repayment_schedule, payment, default_event | 中等. 关键是搞清它挂在谁身上 |

一个新人常犯的错误是**从第一张表开始按字母顺序读**. 那样读到第三张就晕了, 因为你不知道
自己在读什么.

正确的做法是**先找主角**. 而找主角有一个很朴素的信号: **谁被指向得最多, 谁就是主角.**

学完这个 Task, 你将能够:

1. 把一个陌生库的表分成查找表, 主体表, 流水表三类, 并说出判据
2. 顺着外键读出这门生意的主线, 用一句话讲清这家公司是怎么运转的
3. 看懂一张关系图上那些看着像密码的符号
4. 解释灌数据的顺序为什么必须是算出来的, 而不是写在配置里的
5. 指出至少一条数据库管不了但业务上必须守的规则, 并说清那种规则由谁来守

## 5. 先认字: 关系图上那些符号

打开 [`dataset/`](../../dataset) 里 `02-` 那份 ER 文档, 最上面有一张关系图. 第一次看会觉得
像密码, 其实只有两个符号要认.

每一行长这样:

```text
customer ||--o{ application : submits
```

翻译过来就是: **一个客户可以提交多份申请.**

中间那串符号是在说两边各自有几个, 读法是**贴着哪一边就说的是哪一边**:

| 符号 | 念作 | 例子 |
| :--- | :--- | :--- |
| `||` | 恰好一个 | 一份申请只属于一个客户 |
| `o{` | 零个或多个 | 一个客户可以有零份或者很多份申请 |
| `o|` | 零个或一个 | 一份申请最多变成一笔贷款, 也可能被拒了什么都没有 |

所以整个数据集里最常见的那种关系 `||--o{`, 念作**一对多**: 左边一个, 右边零到多个.

### 一对多是从哪来的

值得停一下想想这件事, 因为理解了它, 你以后看任何库都不用背符号了.

**一对多不是设计出来的, 是这门生意本来就长那样.** 一个客户当然可能申请好几次, 一笔贷款
当然会有很多期还款 —— 数据库只是把这个事实记下来.

具体记的方式很朴素: **在多的那一边, 放一列指回一的那一边.** 每份申请里存一个客户 id, 就
表达了这份申请属于谁. 那个列就叫**外键**.

所以看到一张表里有一列叫什么什么 id, 基本就可以断定: **这张表是多的那一边, 它挂在别人身上.**

## 6. 找主角: 这个库的主线

现在用第 2 节那个方法读一遍.

**三张查找表** —— industry (行业), risk_grade (风险等级), loan_status (状态码). 它们的共同
特征很好认: **行数很少, 没有外键指出去, 但被很多人指着.** 它们的作用就是把
`status_code = 'REJECTED'` 这种代码翻译成被拒这个人话.

**三张主体表** —— customer (客户), application (申请), loan (贷款). 这是主角.

**三张流水表** —— repayment_schedule (还款计划), payment (实际还款), default_event (违约事件).
它们全都挂在 loan 身上.

外加一张 loan_officer (信贷员), 是个配角.

### 主线是一条生命线

把主角按外键串起来, 你会看到一条非常清晰的线:

```text
客户 (customer)
  └─ 提交申请 (application)        一个客户可以申请很多次
       └─ 批了才有贷款 (loan)      被拒的申请到这里就断了
            ├─ 还款计划 (repayment_schedule)   放款时就排好的期数
            ├─ 实际还款 (payment)              真实发生的每一笔
            └─ 违约事件 (default_event)        最多一次, 大多数贷款没有
```

**这条线就是这门生意本身**: 有人来借钱, 我们审, 批了就放款, 然后收钱, 收不回来就是违约.

读懂这条线之后, 你其实已经理解这家公司在干什么了 —— 这正是第 2 篇那句
**一个项目跟一个行业绑定得最紧的是数据** 的具体样子.

### 两个地方值得多看一眼

**申请到贷款是零或一, 不是一对一.** 因为申请可能被拒. 这一个小符号背后是一整类业务分析:
被拒的那些人里有没有本来该批的? 那正是二十个查询里的第 3 个问的问题.

**违约事件最多一条.** 所以查违约率的时候要用 LEFT JOIN 而不是 INNER JOIN —— 用 INNER JOIN
的话, 没违约的贷款直接从结果里消失了, 你算出来的违约率会是 100%.

这个坑第 19 篇 ([用业务问题学 SQL](../19-sql-by-business-question/README-cn.md)) 会真刀真枪
地演一遍.

## 7. 这个数据集里埋了一个故事

这一节要说的东西, 在真实公司的数据库里是不会有的, 但它是这个教学数据集最巧妙的地方.

打开 ER 文档里 risk_grade 那张表, 看那几行示例数据:

| 等级 | 名称 | 信用分区间 | 利率 | **定价时假设的违约率** |
| :--- | :--- | :--- | :--- | :--- |
| A | Prime | 720-850 | 5.5% | 3.0% |
| B | Near Prime | 680-719 | 7.5% | 6.0% |
| C | Standard | 640-679 | 9.5% | **6.0%** |

最后一列是**定价的时候拍脑袋假设的违约率**. 公司按这个数字去定利率: 我预计这批人里有 6%
会赖账, 所以我得多收点利息把这块损失覆盖掉.

**而这个数据集故意让 Grade C 的真实违约率跑到了 10% 左右.**

假设 6%, 实际 10%, 差了 4 个百分点. 而 Grade C 恰恰是组合里占比最大的那一档.

**翻译成人话: 这家公司在自己最大的一块业务上, 长期少收了钱, 而且它不知道.**

### 为什么要埋这个

因为一个 BI agent 如果只会数数, 它是没有价值的. 有多少客户, 上个月放了多少笔 —— 这种问题
业务方自己在报表上就能看到.

**agent 的价值在于发现那些没人专门去查就看不见的事.** 而这类事的形状几乎都一样:
**两个本该一致的数字, 实际上不一致.**

所以这个数据集特意埋了一处这样的不一致, 好让整个项目有一个真正值得回答的问题. 第 24 篇
(系统提示词) 里那个定价缺口的公式, 就是为了让 agent 能自己找到它.

> **记住这件事, 第 35 篇造新数据集的时候你要再做一次.** 一个没有任何张力的数据集, 做出来的
> agent 只会数数, 面试官看两眼就没兴趣了.

## 8. 灌数据的顺序: 算出来的, 不是写死的

现在讲一个纯工程的问题, 它下一篇马上要用到.

假设你要把这十张表的数据灌进另一个数据库. **顺序不能乱来.**

道理很朴素: 一份申请里存着一个客户 id, 那这个客户必须**已经在库里了**, 否则数据库会拒收 ——
你指着一个不存在的人.

所以必须**先父后子**: 先灌 customer, 再灌 application, 再灌 loan, 最后灌那些流水表.

### 两种做法

| 做法 | 怎么做 |
| :--- | :--- |
| 写死 | 在配置里手抄一份表名列表, 按正确顺序排好 |
| **算出来** | 让程序去读外键, 自己排出一个合法顺序 |

这个项目选后者, 而理由不止是省事:

**一, 手抄的东西会错.** 一份手抄的顺序表就是一个可能出错的值, 而它出错的方式很难查 —— 灌到
第七张表才失败, 而错在你两个月前抄漏了一行.

**二, 加一张表要不要改配置?** 写死的话要, 而且很容易忘. 算出来的话**什么都不用改**: 你多
加一张表, 外键在那里, 顺序自己就更新了.

**三, 这件事本来就是一道标准算法题.** 按依赖关系排出一个先后顺序, 这在计算机里叫拓扑排序,
SQLAlchemy 已经实现好了, 直接用就行.

> **一条通用判据: 能算出来的东西, 不要写进配置.** 配置里每多一个值, 就多一个会和现实脱节
> 的地方, 而脱节通常是静默的.

### 有一种情况算不出来

如果外键绕成了一个圈 —— A 指着 B, B 指着 C, C 又指回 A —— 那**根本不存在** 任何合法顺序,
因为三张表都要求另外两张先进去.

这时候正确的做法是**当场报错**, 明确告诉你外键成环了.

而这里有个陷阱: SQLAlchemy 遇到环的时候默认只发一句**警告**, 然后返回一个把成环的那几条
忽略掉的列表. 那个列表看起来完全正常, 于是灌数据会顺利开始, 然后在中间某一张表上失败,
报的还是一条看不出根因的错.

所以这个项目把那句警告**升级成了异常**. 一句没人看的警告和一次当场失败之间, 选后者 ——
又是第 17 篇那条判断.

## 9. 数据库管不了的那些规则

最后一件事, 它是这一篇里最容易被新人忽略的.

**数据库能强制的规则, 比你以为的少得多.**

它能保证外键指向的行存在, 能保证某一列不为空, 能保证唯一列不重复. 但业务上大量的规则它
**完全管不了**.

这个库里就有一个现成的例子.

loan_status 那张状态码表被两个东西共用: 申请用它, 贷款也用它. 表里的状态分成三大类:

| 类别 | 状态举例 | 谁能用 |
| :--- | :--- | :--- |
| Application | 待审, 已批, 被拒 | **只有 application** |
| Active | 已放款, 还款中 | **只有 loan** |
| Closed | 违约, 已结清 | **只有 loan** |

**但数据库不知道这件事.** 从它的角度看, `application.status_id` 只要指向 loan_status 里
任意一行就是合法的 —— 你完全可以给一份申请标上已结清, 数据库照单全收.

### 那这种规则由谁来守

三个地方, 一个都不能少:

| 谁 | 怎么守 |
| :--- | :--- |
| **生成器** | 造数据的时候就只往合法的那一类里挑 |
| **文档** | ER 文档里白纸黑字写出这条约束, 并注明 DDL 不强制 |
| **写查询的人** | 你自己. 查申请的时候要记得只有那四个状态码是可能的 |

第三条对你有直接影响: 你写 SQL 的时候, 如果对着申请去筛一个只有贷款才会有的状态, 你会得到
**零行**, 而不是一条报错. 零行看起来像是业务上真的没有, 而实际上是你问错了问题.

> **关键洞见:** 一个查询返回零行, 有两种完全不同的原因 —— 真的没有, 或者你问错了. 这两种
> 在屏幕上长得一模一样. 遇到零行先怀疑第二种.

这一点对 agent 也一样成立, 而且更严重: 模型看不到 ER 文档里那段注释, 除非有人把它写进系统
提示词. 这正是第 24 篇 (系统提示词) 要解决的问题 —— **哪些规则必须写给模型看.**

## 10. 练习

### 练习 1: 用三步法读一遍, 然后自己画一张主线图

**目标:** 把第 2 节那个方法真的用一次, 而不只是读一遍.

**怎么做:**

1. 开一个叫 `18-read-the-schema` 的 branch
2. 打开 ER 文档, **先不要看第 6 节的答案**, 自己动手把十张表分成查找表, 主体表, 流水表三类
3. 判据: 行数很少而且被很多人指着的是查找表; 挂在别人身上, 一件事一行的是流水表
4. 分完之后对照第 6 节, 看你分对了几张, 分错的那几张想清楚为什么
5. 现在自己画一张主线图 (纸上, 或者一段文字都行), 只画主体表和流水表, 查找表不用画
6. 用**一句话** 把这条线讲出来, 讲给一个完全不懂放贷的人听
7. 最后跑一下 [`01_pricing_gap.py`](../19-sql-by-business-question/01_pricing_gap.py) 前面
   那个脚本的邻居 —— 也就是下一篇目录下的
   [`02_run_any_sql.py`](../19-sql-by-business-question/02_run_any_sql.py), 用它对着本地种子
   查一张你刚认出来的表, 确认你读的那张图和真实数据对得上

**你会观察到:**

第 6 步那句话如果说不顺, 通常是因为你还没搞清申请和贷款的区别. 这两个东西在日常语言里经常
混着说, 但在这个库里它们是两张表, 而分开的理由正是**被拒的申请不会变成贷款**.

第 7 步是一次很朴素的对账: **图上写的和库里真有的, 是不是一回事.** 读文档读出来的理解,
跑一次就能验.

> **关键洞见:** 一个数据库的主线, 通常能用一句人话讲完. 如果讲不完, 要么是你还没读懂,
> 要么是这个库确实设计得很乱 —— 而后者在真实工作里非常常见.

### 练习 2: 找一条数据库管不了的规则, 并想清楚谁在守

**目标:** 建立一个很重要的直觉 —— 数据库合法不等于业务正确.

**怎么做:**

1. 除了第 9 节讲的那条状态码约束, 在 ER 文档里再找出**至少一条** 数据库管不了的规则. 提示:
   去看那些写着业务逻辑约束的段落, 或者想想还款计划的日期和贷款的放款日期之间该有什么关系
2. 对你找到的那条, 回答三个问题:
   - 如果有人违反了它, 数据库会不会拦?
   - 现在是谁在保证它不被违反?
   - 如果 agent 不知道这条规则, 它可能给出什么样的错误答案?
3. 然后开一个新对话, 加载 `/about-bi-agent-app-scaffold-cn`, 问它:

```text
这个数据集里有哪些业务规则是数据库层面不强制, 只靠生成器和文档约定的?
请列出来, 并说明每一条如果被违反, 症状是什么. 先不要改任何文件.
```

4. 对比它给的答案和你自己找到的那条, 看有没有你漏掉的

**你会观察到:**

第 2 步第三小问最有价值. 一条规则如果模型不知道, 后果通常不是它报错, 而是它写出一条语法
完全正确, 但业务上问错了问题的 SQL, 然后给你一个看起来很合理的错答案.

> **关键洞见:** 数据库检查的是**结构** 合不合法, 不是**业务** 对不对. 这中间的空隙, 在真实
> 系统里永远存在, 而填补它的一直是人和文档.

## 12. 导师寄语

**为什么这一篇教的是方法而不是内容:**

十张表的细节, 你今天记住了, 三个月后也会忘. 而且到第 35 篇你换了数据集, 这十张表根本不存在
了.

真正带得走的是那个读法: 先分类, 再找主角, 再串主线. 我自己每接手一个陌生系统都是这么干的,
而且几乎每次都能在半天之内把主干摸清楚 —— 剩下那些细节, 需要的时候再查.

**还有一件事值得你现在就意识到.** 你在第 6 节把主线串起来的那一刻, 其实就已经理解这家公司
在做什么生意了. 不是通过读一份商业计划书, 是通过读它的表.

**数据是一门生意最诚实的描述.** PPT 会包装, 官网会吹, 但表结构不会 —— 一家公司真正在乎
什么, 它就会把什么记下来.

**关键洞见:**

- 一个库里的表重要性差别极大, 别按字母顺序读
- 谁被指向得最多谁就是主角
- 能算出来的东西不要写进配置
- 数据库检查结构, 不检查业务. 那个空隙永远由人和文档填
- 一个查询返回零行, 先怀疑是你问错了

你现在知道有哪些表, 也知道它们怎么连. 第 19 篇
([用业务问题学 SQL](../19-sql-by-business-question/README-cn.md)) 换一个方向: 不从表出发,
从**一个人真的会问的问题** 出发, 看那个问题怎么变成一条 SQL.

## 13. 速查

**三类表:**

| 类型 | 怎么认 | 这个库里 |
| :--- | :--- | :--- |
| 查找表 | 行数少, 不指别人, 被很多人指 | industry, risk_grade, loan_status |
| 主体表 | 业务主角, 互相之间有主线 | customer, application, loan |
| 流水表 | 挂在主角身上, 一件事一行 | repayment_schedule, payment, default_event |

**关系图符号:**

```text
||  恰好一个
o{  零个或多个
o|  零个或一个
```

**主线:**

```text
customer -> application -> loan -> (repayment_schedule / payment / default_event)
```

**对着本地种子查一下:**

```bash
.venv/bin/python examples/19-sql-by-business-question/02_run_any_sql.py
```

改那个文件里的 `QUERY` 就能跑自己的查询. agent 眼里的库结构长什么样是另一件事, 第 21 篇
(压缩库结构) 专门讲.

**两条判据:**

- 能算出来的东西, 不要写进配置
- 数据库合法不等于业务正确
