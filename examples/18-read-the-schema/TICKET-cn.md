# 读懂这个库: 十张表是怎么串起来的

## 1. 目标

上一篇把数据造出来了, 现在硬盘上躺着一个十张表, 十几万行的数据库, 而你对它一无所知.

**这一篇不是一份表字典.** 十张表的细节已经写在 ER 文档里了, 需要时去查就行, 而且到第 35 篇
你换了数据集, 那十张表根本不存在了.

**这一篇教的是读法**, 那是一个能带到任何陌生数据库上的方法: 先按角色把表分成查找表, 主体表,
流水表三类, 认出主角; 再顺着外键把主角串成一条业务生命线; 最后找出那些数据库管不了的规则.

**一个新人最常犯的错是从第一张表开始按字母顺序读.** 读到第三张就晕, 因为不知道自己在读什么.
找主角有个很朴素的信号: **谁被指向得最多, 谁就是主角.**

这一篇还有两个不是关于表的收获. 一个是判据: **能算出来的东西, 不要写进配置** —— 灌数据的
先后顺序就是算出来的, 加一张表什么都不用改. 另一个是直觉: **数据库合法不等于业务正确**,
中间那道空隙永远由人和文档填补.

---

## 2. 要做的事情

1. 读完 README 第 1 到 5 节, 把关系图上那三个符号认清楚.
2. 开一个叫 `18-read-the-schema` 的 branch.
3. 打开 ER 文档最上面那张关系图, **先不要看 README 第 6 节**, 自己把十张表分成三类.
4. 分完再对照第 6 节, 数一数分对了几张, 分错的想清楚为什么.
5. 自己画一张主线图, 只画主体表和流水表, 查找表不用画.
6. 用一句话把这条主线讲出来, 讲给一个完全不懂放贷的人听.
7. 读 README 第 7 节, 打开 ER 文档里 risk_grade 那张表, 找到被刻意埋进去的那处定价不一致.
8. 读第 8 节, 想清楚灌数据为什么必须先父后子, 以及手抄一份顺序表会怎样.
9. 读第 9 节, 然后在 ER 文档里另外找出至少一条数据库不强制的业务规则.
10. 对那条规则回答三个问题: 数据库会不会拦, 现在谁在守, agent 不知道它会答错成什么样.
11. 加载 `/about-bi-agent-app-scaffold-cn`, 让它列出这个数据集里所有不被数据库强制的业务
    规则, 和你自己找到的对比.
12. 用下一篇目录下的 `02_run_any_sql.py` 对着本地种子查一张你刚认出来的表, 确认图上写的和
    库里真有的是一回事.

**预计用时:** 60 到 90 分钟

## 3. 检查清单

- [ ] **三类分得出**: 你能把十张表分成查找表, 主体表, 流水表, 并说出每一类的判据.
- [ ] **符号认得出**: 你能读懂关系图上恰好一个, 零到多个, 零或一这三种写法, 并知道一对多在
      表里是靠哪一列表达的.
- [ ] **主线讲得出**: 你自己画过一张主线图, 并能用一句话讲给外行听.
- [ ] **申请和贷款分得清**: 你能说清为什么它们是两张表而不是一张, 理由要落在被拒的申请上.
- [ ] **LEFT JOIN 的理由**: 你能说清查违约率时用 INNER JOIN 会算出什么荒唐结果.
- [ ] **那个埋进去的故事**: 你找到了 Grade C 的定价不一致, 并能说清为什么一个教学数据集需要
      这样一处张力.
- [ ] **顺序为什么算出来**: 你能说清手抄一份顺序表有哪两个问题, 也能说清外键成环时为什么必须
      当场报错而不是只发警告.
- [ ] **找到一条数据库管不了的规则**: 你在状态码那条之外另外找到了一条, 并回答了那三个问题.
- [ ] **零行的两种原因**: 你能说清一个查询返回零行时, 为什么要先怀疑是自己问错了.
