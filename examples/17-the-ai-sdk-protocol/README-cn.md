# 协议的力量, 以及这个项目用了它的哪一小块

> 前端有 React, Vue, Angular, Svelte. 后端有 Python, Go, Java, Node, Rust. 要让它们两两
> 都能对上话, 难道要发明几十套办法?

## 1. 概览

第 16 篇 ([前后端分离](../16-wire-next-to-fastapi/README-cn.md)) 说到, 前后端只通过一个
**约定好的接口** 打交道, 互相不知道对方内部长什么样.

这一篇讲那个约定. 它有个更正式的名字, 叫**协议**.

而这个项目用的协议不是自己发明的. 它用的是 Vercel 那个 AI SDK 定义的流式协议,
**一份公开的, 任何人都能实现的规范**. 前端那一半是别人写好的库, 后端这一半是这个项目
自己用 Python 写的一百多行.

**两边从来没见过面, 却能对上话.** 这一篇就讲这件事为什么可能, 以及它为什么重要得远超过
这一个项目.

## 2. 学习目标

先把问题摆出来, 因为它比答案更能说明协议的价值.

**假设你要做一个 AI 聊天界面.** 前端可以用 React, Vue, Angular, Svelte, 或者干脆用手机
原生开发. 后端可以是 Python, Node, Go, Java, Rust, PHP.

如果每一对组合都要各自商量一套对接方式:

| 前端有几种 | 后端有几种 | 要发明多少套对接方式 |
| :--- | :--- | :--- |
| 5 | 10 | **50** |
| 8 | 12 | **96** |

而且每加一种新框架, 你要把它和已有的**每一个** 都对接一遍.

**这显然不可行.** 所以真实世界里从来不这么干.

真实的做法是: **定一份规范, 说清楚这类对话该长什么样, 然后每一边各自照着它实现一次.**

| | 两两对接 | 有一份协议 |
| :--- | :--- | :--- |
| 5 个前端 10 个后端要写几份代码 | 50 | **15** (每边各自实现一次) |
| 加一个新前端要对接几次 | 10 | **1** |
| 两边需要认识吗 | 需要 | **不需要** |

最后一行才是重点. **写这个项目后端的人, 和写那个前端库的人, 从来没有说过话.** 他们唯一
的共同点是都读过同一份文档.

学完这个 Task, 你将能够:

1. 用自己的话解释协议是什么, 以及它解决的那个组合爆炸问题
2. 说出这份 AI SDK 协议里有哪些事件类型, 以及这个项目实现了其中哪几个
3. 读懂三种这个项目**没有** 实现的事件, 并说清它们各自解决什么问题
4. 解释为什么那个请求数据模型要写得很宽松
5. 说清那三个 HTTP 头为什么必须和产出事件的代码打包在一起

## 5. 协议到底是什么

先说一个生活里的例子, 因为它和技术里的完全是一回事.

**你到一家餐厅, 服务员递给你一份菜单.** 你在纸上圈几个菜, 服务员拿走. 过一会儿菜端上来.

现在想一下这里面有多少东西是**事先约定好** 的:

- 菜单会列出菜名和价格, 而不是列出食材的进货渠道
- 你在纸上做标记表示要点这个, 而不是把纸撕掉表示要点
- 菜会一道一道上, 而不是全部做完一起端
- 你说买单的时候, 对方知道这是要结账不是要加菜

**你和这个服务员素不相识**, 你也不知道后厨有几个人, 用的是煤气还是电磁炉. 但你们能顺利
完成一整套交互, 因为**双方都遵守同一套惯例**.

技术里的协议一模一样, 只是把惯例写成了白纸黑字的文档:

| 餐厅里的惯例 | 协议里对应的东西 |
| :--- | :--- |
| 菜单的格式 | 请求该长什么样 |
| 圈菜表示点单 | 每个字段是什么意思 |
| 菜一道道上 | 回答分成几段, 按什么顺序发 |
| 说买单表示结账 | 有一个明确的结束标记 |
| 后厨怎么做菜 | **协议不管**. 那是实现的事 |

最后一行是协议最厉害的地方: **它只规定看得见的那一层, 完全不管两边内部怎么实现.**

所以这个项目的后端可以是 Python, 也可以换成 Go, 前端一个字都不用改 —— 只要新的后端
**同样照着这份协议说话**.

### 你每天都在用协议

顺便认几个, 你会发现这东西无处不在:

| 协议 | 它约定了什么 | 好处 |
| :--- | :--- | :--- |
| HTTP | 浏览器怎么向服务器要东西 | 任何浏览器能打开任何网站 |
| SMTP | 邮件怎么从一个服务器传到另一个 | Gmail 能给 Outlook 发信 |
| USB | 插头形状, 电压, 数据怎么传 | 一根线插所有设备 |
| **AI SDK 流式协议** | AI 的回答怎么一段段流回浏览器 | **这一篇要讲的** |

## 6. 这个项目用的那份协议

这个项目的前端用的是 Vercel 的 AI SDK, 而它定义了一份叫
**UI Message Stream Protocol** 的规范, 文档公开在
[ai-sdk.dev/docs/ai-sdk-ui/stream-protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol).

那份文档里对它的定位是这么说的 (原文):

> A text stream contains chunks in plain text, that are streamed to the frontend. Each chunk
> is then appended together to form a full text response.

那是它更简单的那一种, 叫 Text Stream Protocol. 而文档紧接着说明了它的局限:

> Text streams only support basic text data. If you need to stream other types of data such
> as tool calls, use data streams.

**这个项目用的是后一种**, 也就是那份更完整的 UI Message Stream Protocol. 因为这个 agent 要
传的不只是文字: 还有思考过程, 而将来可能还有工具调用记录.

### 它的形状: 一行一个事件

协议规定回答不是一次性返回, 而是**一行一行地流回去**. 每一行长这样:

```text
data: {"type": "text-delta", "id": "abc", "delta": "Grade C 的"}

```

一个 `data: ` 开头, 后面跟一段 JSON, 然后一个**空行**. 那个空行是格式规定的分隔符, 不能省.

而那段 JSON 里的 `type` 字段, 就是**这个事件是什么**. 协议规定了一大堆 type.

## 7. 协议里有什么, 这个项目用了哪些

这是这一篇信息量最大的一节. 下面这张表来自那份官方文档, 左边是协议定义的事件, 右边是这个
项目用没用.

| 事件类型 | 它是什么 | 这个项目 |
| :--- | :--- | :--- |
| `start` | 一条消息开始了 | 没用 |
| `text-start` / `text-delta` / `text-end` | 正文的开始, 内容, 结束 | **用了** |
| `reasoning-start` / `reasoning-delta` / `reasoning-end` | 思考过程的三段 | **用了** |
| `finish` | 整条消息说完了 | **用了** |
| `error` | 出错了 | 没用 |
| `source-url` / `source-document` | 引用了哪个网页或文档 | 没用 |
| `file` | 附带一个文件 | 没用 |
| `tool-input-start` / `tool-input-delta` / `tool-input-available` | 模型正在决定调哪个工具, 参数是什么 | 没用 |
| `tool-output-available` / `tool-output-denied` | 工具跑完了, 结果是什么 | 没用 |
| `tool-approval-request` / `tool-approval-response` | 这个工具要不要让用户先批准 | 没用 |
| `start-step` / `finish-step` / `reset-step` | agent 的一轮开始和结束 | 没用 |
| `data-*` | 你自己定义的任意数据 | 没用 |
| `abort` | 用户中途取消了 | 没用 |

**这个项目只用了那张表里的三行**, 数下来是三十来种事件里的七个.

这件事本身很值得说一句: **实现一份协议不等于实现它的全部.** 你可以只实现自己用得上的那
部分, 只要你发出去的那些是**合法的**. 前端那个库看到不认识的就跳过, 看到认识的就渲染.

### 三个没实现的, 各自解决什么问题

这三个特别值得看, 因为它们正好对应这个项目将来可能要做的三件事.

**第一个: 工具调用的可见性**

```json
{"type":"tool-input-start","toolCallId":"...","toolName":"..."}
{"type":"tool-input-delta","toolCallId":"...","inputTextDelta":"..."}
{"type":"tool-output-available","toolCallId":"...","output":{...}}
```

这三个连起来, 界面上就能实时显示**agent 正在调哪个工具, 参数是什么, 结果回来了没有**.

你现在在这个 app 里看不到这些. 你只看到一个思考块, 然后是答案. 而实际上 agent 在那几秒里
查了库结构, 写了 SQL, 跑了查询. **那个过程被压扁成一段文字了.**

想让界面显示正在查询数据库这样的实时状态, 就是实现这三个事件.

**第二个: 引用来源**

```json
{"type":"source-url","sourceId":"...","url":"..."}
```

一个 agent 如果引用了网页或者文档, 用这个事件把来源告诉前端, 界面就能显示可点击的引用标注.

这个项目的 agent 只查自己的数据库, 没有外部来源, 所以用不上. 但如果你以后给它加一个搜网页
的工具, 这就是把来源显示出来的标准做法.

**第三个: 让用户先批准**

```json
{"type":"tool-approval-request","toolCallId":"...","approvalId":"...","reason":"..."}
{"type":"tool-approval-response","approvalId":"...","approved":false,"reason":"..."}
```

这一对是给**危险操作** 用的: agent 想干一件事, 先停下来问用户同不同意, 用户点了同意才继续.

这个项目的 agent 是只读的, 只查不改, 所以不需要. 但第 27 篇 ([写操作](../27-write-operations/README-cn.md)) 会讲到, 一旦你给它
加上能改数据的工具, **这就是那道该有的闸门**. 而协议已经替你准备好了.

> **看协议的一个正确姿势**: 别只看你现在用的那几行. 扫一眼你没用的那些, 因为它们往往就是
> 你将来会遇到的问题的标准答案, 而且已经有人替你想过一遍了.

## 8. 这个项目发出去的那条流

现在看这个项目实际发的东西. 代码在
[`agent_app/ai_sdk_adapter.py`](../../agent_app/ai_sdk_adapter.py), 输出长这样:

```text
data: {"type": "reasoning-start", "id": "..."}

data: {"type": "reasoning-delta", "id": "...", "delta": "我需要先看一下风险等级表..."}

data: {"type": "reasoning-end", "id": "..."}

data: {"type": "text-start", "id": "..."}

data: {"type": "text-delta", "id": "...", "delta": "Grade C 的实际违约率是 9.9%..."}

data: {"type": "text-end", "id": "..."}

data: {"type": "finish", "finishReason": "stop"}

data: [DONE]

```

### 四个不能省的细节

| 细节 | 少了会怎样 |
| :--- | :--- |
| **三段式**: 每种内容都是 start, delta, end | 前端不知道一个块什么时候开始什么时候结束, 没法开一个折叠框再填它 |
| **每个块带一个 id** | 前端分不清同时到达的两个块, 也没法把每个 delta 匹配回它所属的块 |
| **那个 `finish` 事件** | **界面会一直转圈**, 因为它不知道说完了 |
| **最后那个 `[DONE]`** | 协议规定的流终止标记, 文档里写的就是 `data: [DONE]`, 不是这个项目发明的 |

还有一条: **思考为空时整段跳过**, 三个 reasoning 事件一个都不发. 因为一个空块在界面上是一个
点开什么都没有的折叠箭头.

### 一个 delta 装完了整个字符串

看代码你会发现, `text-delta` 只发了一次, 里面装着完整的答案.

原因很朴素: **走到这一步的时候 agent 早就写完了.** 后端拿到的是一个完整字符串, 没有什么
可以一点点吐的.

**但这不影响协议的正确性.** 真正的逐字流式会发很多个 delta, 而协议的其余部分一个字都不用改.
换句话说, 这一层已经为将来的逐字流式准备好了.

## 9. 那三个 HTTP 头

除了那些事件, 响应还必须带三个头. 文档里明确要求了第一个:

```text
x-vercel-ai-ui-message-stream: v1
Cache-Control: no-cache
Connection: keep-alive
```

第一个是前端用来识别这是一个 v5 消息流的. **少了它前端不会按这个协议解析**, 于是页面上什么
都不显示 —— 而且不报错.

后两个是让中间的代理和浏览器**别缓冲这个流**. 缓冲了的话, 用户会等到全部内容到齐才一次性
看到, 流式就白做了.

### 为什么它们不在调用处拼

代码里这三个头和那个产出事件的函数包在同一个地方, 调用方只写一行就能拿到一个完整的响应.

设想另一种写法: 每个要返回流的地方各自拼一次响应对象, 各自加三行头. 那等于
**把协议的一部分交给使用者保管**:

- 协议改了要同时改每一处
- 而漏掉一处的症状是**前端静默地不渲染**, 不报错

这个 app 里返回流的地方不止一处: 正常回答一处, 配额超了一处, 请求为空又一处. 三处都得对.

**这是一条通用的规矩**: 一个东西的正确性依赖好几个部分同时到位时, 把它们打包在一起, 别让
调用者去记.

## 10. 进来那一侧: 为什么要写得很宽松

出去的讲完了, 说说进来的.

前端每次发请求, 送上来的是这样一包东西 (简化过):

```json
{
  "messages": [
    {
      "role": "user",
      "parts": [{ "type": "text", "text": "Grade C 的定价对吗?" }]
    },
    {
      "role": "assistant",
      "parts": [
        { "type": "reasoning", "text": "我需要先看一下风险等级表..." },
        { "type": "text", "text": "Grade C 的实际违约率是 9.9%..." }
      ]
    }
  ]
}
```

描述这包东西形状的代码在
[`agent_app/vendor/vercel_ai_sdk.py`](../../agent_app/vendor/vercel_ai_sdk.py). 打开它你会
在几个地方看到一行配置, 意思是**多出来的字段一律接受并忽略, 不报错**.

### 这在防什么

前端那个 AI SDK 是一个跑得很快的库, 会不断加新字段, 加新的事件类型 (看第 7 节那张表就知道
它有多能长). 而后端是 Python 写的, 和它不在一个发布节奏上.

设想一个具体场景: 半年后有人跑了一次前端依赖升级, 于是前端开始送一种后端没见过的 part.

| 如果后端严格校验 | 如果后端宽松 |
| :--- | :--- |
| 请求解析失败, 后端报错 | 那个 part 被解析成一个通用的壳, 后端照常处理它认识的那些 |
| 用户看到聊天彻底不能用 | 用户什么都没察觉 |
| 报错在 Python 这边, 而**原因是一次前端升级** | 无事发生 |

最后一行是关键: **失败的地方和引发它的改动隔得非常远**, 而这类问题的排查成本极高.

### 判据: 对读的东西严格, 对不读的东西宽容

| 字段 | 处理 |
| :--- | :--- |
| 后端真正会读的 (`messages`, 每个 part 的 `type` 和 `text`) | **有类型, 缺了就报错** |
| 其余一切多出来的字段 | 接受并忽略 |
| 不认识的 part 类型 | 不炸, 解析成通用的壳 |

**这条判据不只适用于这里.** 你以后写任何对接别人系统的代码都该问一句: 这个字段我真的会读
吗? 不读的话, 我凭什么因为它变了而失败?

### 那个目录为什么叫 vendor

`vendor` 是一个约定俗成的名字, 意思是**从别处拷进来的第三方代码, 不是我们写的**.

拷而不是装依赖, 两个理由: 它只有一百来行, 不值得为它引入一个我们控制不了发版节奏的依赖;
而上面那个宽松行为是这个仓库加的, 不是原版的.

放进 `vendor/` 是给后来的人一个信号: **这里的规矩和别处不一样, 动它之前先想想上游.**

## 11. 翻译: 丢掉两样东西

[`agent_app/ai_sdk_adapter.py`](../../agent_app/ai_sdk_adapter.py) 里有两个函数负责把前端
的格式翻译成 agent 要的格式. 它们丢掉了两样东西, 而两次丢弃都是有理由的:

| 丢掉什么 | 为什么 |
| :--- | :--- |
| **所有思考 part** | agent 重读自己之前的思考没有好处, 而那些块很长. 留着的话每一轮都会重发一次, 并且**付一次钱** |
| **最后一条消息** | 那是现在要回答的问题. 它作为 agent 的输入进去, 不作为历史 |

第二条你在第 21 篇 ([多轮对话](../21-multi-turn-and-caching/README-cn.md)) 会亲手实现一次
了: 历史和当前问题是两个不同的参数, 不是一个列表.

还有一条防御: 一条消息如果一个文字 part 都没有, 就整条跳过, 因为**供应商会拒绝空内容**.

## 12. 练习

### 练习 1: 打开网络面板, 对着协议读一遍

**目标:** 把这一篇讲的东西和屏幕上真实的字节对上号.

**怎么做:**

1. 起开发服务器, 打开 agent 页
2. 打开浏览器的开发者工具, 切到网络那一栏
3. 点一个 kickstart 按钮
4. 在请求列表里找到 `chat` 那一条, 点开它
5. 先看**请求** 那一侧: 对照第 10 节那个形状, 认出 `messages` 和里面的 `parts`
6. 再看**响应** 那一侧: 从头读到尾, 逐个找出第 8 节那张流里的每一种事件
7. 数一数 `text-delta` 出现了几次, 想清楚为什么是这个数
8. 再点一个别的按钮, 找找有没有 `reasoning-start` 那三行; 什么情况下它们会整段消失

**你会观察到:**

响应那一侧和第 8 节那段示意几乎一模一样. 而请求那一侧, 如果你之前已经问过几轮, `messages`
里会有好几条 —— 前端每次都把整段历史送上来.

> **关键洞见:** 界面上那些看起来很高级的东西, 底下往往是一段格式很朴素的文本. 学会打开网络
> 面板看真实的请求和响应, 比读十篇文档都快.

### 练习 2: 挑一个没实现的事件, 想清楚它值多少

**目标:** 练一次读协议的正确姿势: 看你没用的那部分.

**怎么做:**

1. 打开那份官方文档:
   [ai-sdk.dev/docs/ai-sdk-ui/stream-protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol)
2. 对照第 7 节那张表, 找出三个这个项目没实现的事件
3. 挑其中一个, 回答三个问题:
   - 它解决的是什么问题
   - 这个 app 现在有没有这个问题
   - 如果要实现它, 除了后端多发一个事件, 前端那边还要做什么
4. 然后开一个叫 `17-the-ai-sdk-protocol` 的 branch, 加载
   `/about-ba-agent-app-scaffold-cn`, 问它:

```text
假设前端的 AI SDK 升级之后, 开始往后端送一种新的 message part, 类型叫 source,
而后端需要读它里面的一个字段. 请只告诉我要动哪些文件, 每个文件改什么. 先不要动手.
```

5. 检查两件事: 它有没有说清**只改两处** (加一个模型类, 在那张映射表里加一行), 以及它有没有
   顺手去改别的地方
6. 再问一个反向的: 换一家 LLM 供应商要不要动 vendor 那个文件? 正确答案是**不需要**

**你会观察到:**

第 3 步那个问题最有价值的是第三小问. 后端多发一个事件是容易的, 难的是
**前端要知道拿它干什么** —— 而这正是协议只解决一半问题的地方: 它规定了怎么说, 没规定
听懂之后做什么.

第 6 步在考 AI 知不知道这个文件的边界: 前端契约和 LLM 供应商是两件毫不相干的事.

> **关键洞见:** 判断一个人 (或者一个 AI) 是不是真懂一层代码, 最快的办法不是问它这一层是什么,
> 是问它**什么东西不该进这一层**.

## 13. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 协议解决什么问题 | 5 个前端配 10 个后端本来要 50 套对接, 有协议之后每边各实现一次就够 |
| 协议管什么不管什么 | 只规定看得见的那一层, 完全不管两边内部怎么实现 |
| 这个项目用的哪份 | AI SDK 的 UI Message Stream Protocol, 公开文档, 任何人都能实现 |
| 实现了多少 | 三十来种事件里的七个. **实现一份协议不等于实现它的全部** |
| 没实现的那些 | 工具调用可见性, 引用来源, 危险操作的批准. 都是将来可能要做的事的标准答案 |
| 流的形状 | 一行 `data:` 加一段 JSON, 后面一个空行. 最后一行是 `data: [DONE]` |
| 四个不能省 | 三段式, 每块带 id, `finish` 事件, 结束标记 |
| 那三个头 | 一个让前端认出协议, 两个防缓冲. 和产出事件的代码打包在一起 |
| 进来那一侧的判据 | 对读的东西严格, 对不读的东西宽容 |
| 翻译丢掉两样 | 所有思考 (重读没好处而且要重新付钱), 和最后一条消息 (它是问题不是历史) |

## 14. 导师寄语

**为什么协议这个概念值得你认真对待:**

你以后做的任何一个稍微大一点的东西, 都会遇到两个部分要对话的情况. 前端和后端, 你的服务和
别人的服务, 你的程序和一个数据库.

而每一次, 你都面临同一个选择: **是让这两边互相认识, 还是让它们都去认识一份中间的约定?**

前者短期更快, 因为你不用写文档, 也不用管别人. 后者长期便宜得多, 因为
**加第三个第四个的时候成本不涨**.

这一篇那张表 (50 对 15) 就是这件事的数学. 而现实里那个数字通常更悬殊, 因为还要算上每一对
组合的维护成本.

**关键洞见:**

- 协议让两个素不相识的程序对上话. 代价是双方都得严格照着它来
- 实现一份协议不等于实现它的全部. 但读的时候要读全, 因为没用的那些往往是你将来问题的答案
- 对读的东西严格, 对不读的东西宽容. 不读的字段变了, 你凭什么失败

**下一步:**

到这里, 一次提问在系统里怎么流动这条线走完了: 数据住在哪儿, 两个进程怎么接上, 它们之间说
什么话.

**但 agent 本身一直是个黑盒.** 接下来一整组把它拆开, 顺序就按那条数据链路走. 第 18 篇
([读懂这个库](../18-read-the-schema/README-cn.md)) 从最底下开始: agent 要查的那十张表, 到底
是怎么串起来的.
