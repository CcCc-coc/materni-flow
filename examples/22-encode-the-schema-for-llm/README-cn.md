# 把库结构压给模型看

> 你不能把整个数据库塞给模型. 那要塞什么? 这一篇讲怎么把十张表压成一百行, 以及压缩的时候
> 该丢掉什么.

## 1. 概览

数据在云上了, agent 也能用了. 接下来四篇拆开它, 看它到底是怎么造出来的:

| 篇 | 在这条线上是什么 |
| :--- | :--- |
| **第 22 篇 (这一篇)** | **眼睛** — 它看到的数据库长什么样 |
| 第 23 篇 ([你的第一个 agent](../23-your-first-agent/README-cn.md)) | **手** — 一个工具是怎么定义的 |
| 第 24 篇 ([SQL 工具](../24-the-sql-tool/README-cn.md)) | **那只最要紧的手** |
| 第 25 篇 ([系统提示词](../25-the-system-prompt/README-cn.md)) | **脑子** — 领域知识怎么灌进去 |

从这一篇开始你会一直看到同一个主题: **让模型看到正确的东西, 是这类应用绝大部分的工作量.**
这句话不是口号, 接下来四篇就是它的具体样子.

先跑一条命令, 看一眼这一篇的主角:

```bash
mise run cli-print-db-schema
```

打出来的那一坨东西, **就是 agent 对这个数据库的全部认识**. 它写任何一句 SQL 之前, 看到的
只有它.

### 卡住了怎么办

这一篇每一步都可能出错: 脚本报连不上库, 或者打印出来的东西和这里写的不一样.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/22-encode-the-schema-for-llm/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/22-encode-the-schema-for-llm/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

先问一个笨问题: **为什么不能把数据库原样给模型?**

这个问题值得认真回答, 因为它决定了后面所有的设计.

### 第一层: 数据给不了

十几万行数据塞不进任何一个模型的上下文, 而且**根本没必要** —— 模型不需要看见数据, 它需要
的是会写查数据的 SQL. 所以给的一定是**结构**, 不是内容.

这一层很好理解, 跳过.

### 第二层: 结构也不能原样给

那给 `CREATE TABLE` 语句总行了吧? 结构就那么点东西.

行, 但有两个代价:

**一, 它是钱.** 库结构在**每一次** 对话里都要重发一遍 —— 你在第 21 篇
([多轮对话和缓存](../21-multi-turn-and-caching/README-cn.md)) 已经知道模型什么都不记得.
一个大一点的库有上百张表, 那就是每问一句话都付一次这个钱.

**二, 它是噪音.** 原始 DDL 里有一大堆模型根本用不上的东西: 存储引擎, 字符集, 自增起始值,
约束的名字. 它们不帮助模型写出更好的 SQL, 只是让真正有用的那部分**更难被找到**.

第二条其实比第一条重要. 你在第 2 篇 (为什么是这个项目) 那句提示词写太长会被忽略, 讲的是
同一件事.

### 所以: 压缩, 而且是有损压缩

这一篇讲的那套编码, 干的就是这件事. 而**有损** 这个词是关键 —— 它故意扔掉了东西.

所以这一篇真正要教的不是那套记号怎么读 (十分钟就学会了), 是这个问题:

> **压缩的时候, 什么必须留, 什么可以扔?**

学完这个 Task, 你将能够:

1. 读懂那段编码, 说出一列的类型和它身上每一个标记是什么意思
2. 解释为什么主键后面不再标不为空和索引, 并说出背后那条通用规则
3. 描述反射, 建模, 编码这三步, 并说清为什么它只能单向走
4. 说出那条每个字段都要有读者的规矩, 以及违反它的代价
5. 亲手量一次压缩率, 并判断一个写在 docstring 里的百分比可不可信

## 5. 它长什么样

跑完那条命令, 开头是这样:

```text
postgresql Database fintech_smb_lending_pipeline_medium(
  Schema fintech_smb_lending_pipeline_medium(
    Table industry(
      id:int*PK,
      industry_code:str*NN,
      industry_name:str*NN,
      default_rate_baseline:float*NN,
    )
```

三层嵌套, 从外往里是**数据库, schema, 表**, 每张表里一列一行.

最外面那个 `postgresql` 不是装饰. 它是在告诉模型**该写哪种方言的 SQL** —— 第 19 篇和第 15 篇
反复讲的那件事, 在这里落成了一个单词.

再看一张有外键的表:

```text
Table loan(
  id:int*PK,
  loan_number:str*NN,
  application_id:int*NN*FK->application.id,
  customer_id:int*NN*FK->customer.id,
  risk_grade_id:int*NN*FK->risk_grade.id,
  approved_amount:dec*NN,
  disbursement_date:date*NN,
  current_status_id:int*NN*FK->loan_status.id,
)
```

**这就是第 18 篇那条业务主线, 换了一种写法.** 你在那一篇画的图, 现在是模型眼里的这几行.

## 6. 那套记号

一行的形状是 ` 列名: 类型` 后面跟若干个 `* 标记`.

**类型只有十二个词**, 因为数据库自己的类型名太多太啰嗦:

| 编码 | 它代表数据库里的什么 |
| :--- | :--- |
| `str` | 各种长度的文本: `VARCHAR(50)`, `TEXT`, `CHAR`, 还有 JSON 和 UUID |
| `int` | 整数: `INTEGER`, `SMALLINT`, `BIGINT` |
| `float` | 近似小数 |
| `dec` | **精确** 小数. 钱用这个 |
| `date` / `time` / `dt` / `ts` | 日期, 时间, 日期时间, 带时区的时间戳 |
| `bool` | 真假 |
| `blob` / `bin` | 二进制 |

`float` 和 `dec` 分开是有意的. 它们在数据库里是两种东西, 而**钱不能用 `float`** —— 这个区别
模型需要知道, 所以留着了.

标记有五个:

| 标记 | 意思 |
| :--- | :--- |
| `*PK` | 主键 |
| `*UQ` | 唯一 |
| `*NN` | 不为空 |
| `*IDX` | 有索引 |
| `*FK-> 表. 列` | 外键, 箭头指向它引用的那一列 |

**最后一个是最值钱的**, 因为它直接告诉模型怎么 join. 没有它, 模型只能靠列名猜
`customer_id` 大概对应 `customer.id` —— 猜通常是对的, 但通常不等于总是.

### 一个没有被编码的东西

对着看会发现: **注释没了, 默认值没了, 约束的名字也没了.**

这是有意的. 它们对写 SQL 没有帮助, 而每一样都要占位置.

## 7. 冗余的标记被丢掉了

这一节讲一个很小但很能说明设计品味的细节.

看 `id:int*PK` 这一行. 一个主键**一定** 不为空, 也**一定** 有索引 —— 数据库自己保证的.

那要不要写成 `id:int*PK*NN*IDX`?

**不要.** 编码器专门有两行代码把它们去掉:

| 已经有 | 就不再写 | 因为 |
| :--- | :--- | :--- |
| `*PK` | `*NN`, `*IDX` | 主键必然非空, 必然有索引 |
| `*UQ` | `*IDX` | 唯一列必然有索引 |

省下的字符其实不多. **真正的理由是另一个:**

> **不要让同一个事实被读到两遍.**

一个读者 (人或者模型) 看到 `*PK*NN`, 会花掉一点点注意力去确认这两个标记是不是在说不同的
事. 每一处这样的小停顿单独看都不值一提, 但一份文档里有几百处的时候, 它就是可读性本身.

**这条规则在写任何东西的时候都成立**, 包括你写文档和写提示词.

## 8. 三步, 单向

代码在 [`agent_app/db_schema/`](../../agent_app/db_schema) 下面, 一共三个文件, 是一条流水线:

```mermaid
flowchart LR
    S(["数据库"])
    A("反射")
    B("中间模型")
    C("编码")
    D(["交给模型的文本"])

    S --> A --> B --> C --> D

    classDef startNode fill:#D1F0DB,stroke:#1B7F4B,color:#0B3D24
    classDef finishNode fill:#FDE2E1,stroke:#C0392B,color:#5A1710

    class S startNode
    class D finishNode
```

**关键是这条线只能往一个方向走**, 没有任何一步会回头 —— 中间那个模型是唯一穿过这条线的
东西, 而它两头的代码谁也不认识谁:

| 文件 | 干什么 | 它不干什么 |
| :--- | :--- | :--- |
| `extractor.py` | 把 SQLAlchemy 给的东西变成中间模型 | **不拼字符串** |
| `model.py` | 就是一组数据类, 什么都不做 | **不碰数据库, 也不碰格式** |
| `encoder.py` | 把中间模型拼成字符串 | **完全不碰数据库** |

### 为什么中间要隔一层

一个很自然的疑问: 为什么不直接从数据库拼字符串? 中间那层看起来纯属多余.

因为**它把两个会各自变化的东西隔开了**:

- 左边会变: 换个数据库, 反射出来的东西不一样 (SQLite 没有 schema, PostgreSQL 有)
- 右边会变: 你想换一种编码格式, 比如改成 JSON 给别的工具用

中间隔一层之后, **改左边不用动右边, 改右边不用动左边**. 而且最实在的好处是:
`encoder.py` 完全不碰数据库, 所以**测它不需要一个数据库** —— 造几个中间模型对象就能测.

> **这是分层最朴素的价值**: 不是为了看起来整齐, 是让每一层能被单独替换和单独验证.

## 9. 一条不起眼但很硬的规矩

打开 [`agent_app/db_schema/model.py`](../../agent_app/db_schema/model.py), 文件开头写着一句:

> **这里每一个字段都必须有一个读者 (也就是编码器里那一行把它输出的代码).**

意思是: **不许提取一个没人输出的东西.**

这条规矩为什么值得写下来? 因为违反它的诱惑非常大 —— 反正都反射到了, 顺手存下来嘛, 说不定
以后用得上.

而代价有两层:

| 代价 | 说明 |
| :--- | :--- |
| 浅的 | 反射要花时间, 存一个没人读的字段是白花 |
| **深的** | **它是一个不兑现的承诺.** 后来的人看到模型里有这个字段, 会以为输出里有它 |

第二层才是真的. 一个中间模型是给后来的人看的一张说明书, 而说明书上写了输出里没有的东西,
就是在骗人.

**同类的规矩这个仓库里不止一处**: 没有读者的东西会安静地烂掉, 而它烂掉的时候不会有人
通知你. 它们是同一条: **没有读者的东西会烂掉, 而且烂得很安静.**

## 10. 那个 70% 的说法

最后这一节是这一篇最想让你带走的东西, 而它跟编码本身没关系.

打开 [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), 找到那个取库
结构的工具, 它的说明里有这么一句 (这句话是写给模型看的):

> The compact format reduces token usage by ~70% compared to verbose SQL DDL.

**这个 70% 是从哪儿来的?**

这一篇目录下有个脚本, 拿这个数据集实际量了一次 —— 编码后的字符串, 对上这个数据集自己那份
`CREATE TABLE` DDL:

```bash
.venv/bin/python examples/22-encode-the-schema-for-llm/01_measure_the_encoding.py
```

量出来是 **46%**, 不是 70%.

### 那这句话是错的吗

**不一定.** 它说的是对上 verbose DDL, 而这个数据集的 DDL 一点也不 verbose —— 没有注释,
没有约束命名, 没有表选项. 换一份真实生产库导出来的 schema, 省的可能真的有七成.

**但这恰恰是问题所在**: 这个数字**没有说清楚它在跟什么比**, 所以它既没法被证实, 也没法被
证伪. 它只是一个听起来很有说服力的数字.

而它现在还被写进了给模型看的工具说明里 —— 模型读到它, 也无从判断.

> **关键洞见:** 一个没有交代基准的百分比, 不是一个事实, 是一句广告词. 你以后在代码注释,
> 文档, 简历里写下任何一个百分比之前, 先问自己一句: **跟什么比?**

这类数字还有一个共同点: **它写下的那天可能是对的, 但没有任何东西会在它过期时提醒你.**
第 25 篇 ([系统提示词](../25-the-system-prompt/README-cn.md)) 会给你看两个更严重的例子,
那两个数字直接影响 agent 的答案.

## 11. 练习

### 练习 1: 对着输出把记号认全

**目标:** 确认你真的读得懂 agent 看到的东西, 而不是眼熟.

**怎么做:**

1. 开一个叫 `22-encode-the-schema-for-llm` 的 branch
2. 跑 `mise run cli-print-db-schema`, 把输出存下来慢慢看
3. 找出这几样, 每样至少一个例子:
   - 一个主键
   - 一个外键, 并说出它指向哪张表的哪一列
   - 一个 `dec` 类型的列, 想一想它为什么不是 `float`
   - 一个既不是主键也不是外键, 但标了 `*NN` 的列
4. 数一数一共有几张表, 和第 18 篇你画的那张主线图对一遍
5. 现在做一次反向翻译: 挑一张表, **不看 ER 文档**, 只根据这段编码, 用中文把这张表是干什么
   的写出来
6. 再打开 ER 文档对一下, 看你漏了什么

**你会观察到:**

第 5 步大部分表你都能猜个八九不离十, 靠的是列名和外键. 而第 6 步你会发现漏掉的都是同一类
东西: **那些列名看不出来的业务含义.**

比如 `loan_status` 那张表被两个实体共用, 而且各自只能用其中一部分状态码 —— 这件事编码里
一个字都没有, 因为**数据库自己也不知道**.

> **关键洞见:** 这段编码告诉模型的是**结构**, 不是**业务**. 那道空缺正是第 25 篇那份系统
> 提示词存在的理由.

### 练习 2: 量一次, 然后判断那个数字

**目标:** 练一次对数字的怀疑, 这比记住编码格式有用得多.

**怎么做:**

1. 跑一次那个测量脚本, 记下它给的百分比
2. 打开 [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), 找到那句
   `~70%`, 对比一下
3. 回答三个问题:
   - 这两个数字为什么不一样?
   - 要让那句 `~70%` 变成可检验的, 至少要补上什么?
   - 这句话是写给**模型** 读的. 模型读到一个它无法验证的数字, 有什么坏处?
4. 然后加载 `/about-ba-agent-app-scaffold-cn`, 问它:

```text
这个仓库里还有哪些地方写着一个没有交代对比基准的数字或者百分比?
请列出文件和原话, 先不要改任何东西.
```

5. 检查它找到的每一条: 哪些是真的问题, 哪些其实交代清楚了

**你会观察到:**

第 3 步第三小问最值得想. 模型没有办法去验证一句话, 它只能选择信或者不信 —— 而它通常会信.
所以**写进提示词和工具说明里的每一句话, 都是你替模型做的判断**.

> **关键洞见:** 你写给 AI 看的文字, 和你写给同事看的文字, 有一个根本区别: 同事会怀疑,
> 模型不会. 这让准确性的要求变高了, 而不是变低了.

## 12. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 给模型看什么 | 只给**结构**, 不给数据. 模型不需要看见数据, 它要写查数据的 SQL |
| 为什么还要压 | 结构每轮都重发一次, 所以它既是钱又是噪音. **噪音那一条更重要** |
| 压缩是有损的 | 注释, 默认值, 约束名都被扔了. 这一篇真正的问题是**什么该留什么该扔** |
| 那套记号 | ` 列名: 类型` 加 `*PK` `*UQ` `*NN` `*IDX` `*FK-> 表. 列`. 最值钱的是外键 |
| 最外层那个方言词 | 告诉模型写哪种 SQL. 第 19 篇和第 15 篇讲的那件事在这里落成一个单词 |
| 冗余标记被丢掉 | 主键不再标非空和索引. 理由不是省字符, 是**不让同一个事实被读两遍** |
| 三步单向 | 反射, 建模, 编码. 中间那层把两个各自会变的东西隔开, 顺便让编码器不用数据库也能测 |
| 每个字段要有读者 | 提取一个没人输出的字段, 是一个不兑现的承诺. **没有读者的东西会安静地烂掉** |
| 那个 70% | 实测这个数据集是 46%. 它没交代跟什么比, 所以既不能证实也不能证伪 |
| 那条判据 | **没有交代基准的百分比不是事实, 是广告词** |

## 13. 导师寄语

**为什么这一篇看起来最技术, 其实最不技术:**

那套记号你十分钟就学会了, 而且换个项目就用不上了. 真正带得走的是它背后那个动作:
**有人坐下来, 一项一项地判断了什么该给模型看, 什么不该.**

这件事没有标准答案, 也没有库可以帮你做. 外键留下来是因为它决定 join; 注释扔掉是因为它不
影响 SQL; `float` 和 `dec` 分开是因为钱不能算错. 每一条都是一次判断.

**而这正是 AI 应用里最缺的能力.** 接模型是容易的, 难的是想清楚它需要知道什么.

**最后那一节我特意放在最后**, 因为它是这一篇里唯一一个你明天上班就能用上的东西. 一个没有
基准的百分比, 在代码注释里, 在设计文档里, 在简历里, 到处都是. 它们不是谎话, 它们只是
**没法被检验** —— 而没法被检验的东西, 时间久了就等同于没说.

**关键洞见:**

- 只给结构不给数据; 结构还要再压, 因为噪音比成本更伤
- 压缩是取舍, 取舍要有判据: 影响写 SQL 的留, 不影响的扔
- 不要让同一个事实被读到两遍
- 没有读者的字段会安静地烂掉
- 没有交代基准的百分比是广告词. 你写给 AI 的文字尤其要小心, 因为**它不会怀疑你**

**下一步:**

眼睛讲完了, 该讲手. 第 23 篇 ([你的第一个 agent](../23-your-first-agent/README-cn.md)) 讲
一个工具是怎么定义的, 而那里有一件很反直觉的事:
**你写的那段函数说明, 就是给模型看的接口文档 —— 它读的不是你的代码, 是你的注释.**
