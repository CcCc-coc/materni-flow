# 花费上限: 谁在为这些对话付钱

> 这个功能默认是关着的. 这一篇一半的价值在于讲清它**什么时候才该打开**, 另一半在于它那几个
> 决定, 那几个判据换到任何一个功能上都成立.

## 1. 概览

到这里为止, 这门课里所有的模型调用花的都是**你自己的钱**, 而且是你自己按下的回车. 那种情况
不需要任何上限.

现在设想第 35 篇之后的那一刻: 这个 app 部署上线了, 你把链接发给了一个面试官.

**从那一秒起, 付钱的人和打字的人不再是同一个人.**

链接是公开的, 谁点开都能用, 每一条消息都在花你云账号里的钱. 一个好奇的人多聊两句是几美分;
一个爬虫发现了这个接口, 那就是另一回事了.

这一篇讲这个项目对付这件事的那道闸门. 它一共只有一百多行, 但里面有三个决定值得单独学,
因为它们和花费上限本身没什么关系, 它们是**任何一个可开关的功能** 都会遇到的问题.

### 卡住了怎么办

这一篇每一步都可能出错: 脚本跑不起来, 或者输出和这里贴的不一样.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/33-the-spend-cap/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/33-the-spend-cap/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

这一篇是主题 7 里最像一个普通功能的一篇, 它有一张表, 三个数字, 两个函数. 但它被放进这一组
是因为它的**形状**, 不是它的功能.

一个可开关的功能, 会逼着你回答三个问题, 而这三个问题在任何项目里都一样:

| 问题 | 答错的后果 |
| :--- | :--- |
| 那个开关**写在哪儿** | 写在使用者那里, 第二个使用者忘了写就是一个 bug, 而且默默地花钱 |
| 这个功能**自己坏了** 怎么办 | 处理错了, 一个记账系统能把整个应用拖下水 |
| 它要的那个标识符**从哪来** | 另起一个短名字, 就多了一样要同步维护的东西 |

这一篇讲这个项目对这三个问题的回答, 而且每一个都能直接搬到你自己的项目里.

学完这个 Task, 你将能够:

1. 说清为什么这道闸门必须拦在调模型之前, 而不是之后
2. 解释那个开关为什么住在拥有这个功能的模块里, 而不是住在调用它的地方
3. 说清为什么计量出故障时必须放行, 以及哪一种异常是例外
4. 说出那个三段式标识符各段是什么, 以及为什么不给它另起一个短名字
5. 亲手看一次计数器累加, 超限拒绝, 以及故障放行

## 5. 什么时候才需要它

先把边界划清楚, 因为**大多数时候你不需要这个功能**.

| 场景 | 需要上限吗 |
| :--- | :--- |
| 你在本地开发, 花自己的额度 | **不需要**. 上限只会碍事 |
| 你部署了, 但只发给几个认识的人 | 大概不需要, 但设一个很宽松的也不亏 |
| 你把链接放进简历, 谁都能点 | **需要** |
| 有人开始批量调你的接口 | 那时候再想就晚了 |

所以它**默认是关的**. 打开它要两步: 在配置里把开关打开, 外加一张你自己建的 DynamoDB 表,
而那张表在有人去建之前并不存在, 所以这个功能不可能默认可用.

这也是第 30 篇那个例子的来源: **开了开关却没给表名, 应用在启动时就炸.** 不这样的话, 一个
配错的公开部署会完全正常地起来, 直到有人打第一个字.

> 顺带说一句: 上限不是防超支的唯一手段, 也不是第一道. 第一道是第 13 篇让你在供应商控制台
> 里设的那个消费上限. **两道是不一样的东西**: 控制台那道是硬的, 花完就停; 这一道是软的,
> 它让你的 app 在到达那个硬边界之前先礼貌地说一句话.

## 6. 闸门拦在哪一步

回忆第 28 篇那条路. 查配额那一步的位置是挑过的:

```text
读请求 -> 解析 -> 取出问题 -> 灌历史 -> [查配额] -> 调模型 -> 记账 -> 挖答案 -> 编码返回
```

**它在调模型之前.** 这一点听起来是废话, 但反过来想一下就知道为什么必须如此: 拦在之后,
那笔钱已经花掉了, 你只是拒绝把结果给用户看, 花了钱又没服务, 两头都亏.

再往前挪也不行. 它需要解析完的请求才知道该记在哪个账上.

### 拒绝路径一分钱不花

超限的时候返回的是**一句写死的话**, 不是让模型生成一句道歉.

这个细节很容易被做反. 一个很自然的想法是让 agent 用友好的语气解释一下额度用完了, 而那
需要调一次模型, 也就是说**你的超限保护本身在花钱**, 而且越是被刷得厉害花得越多.

> **一条判据**: 一个用来省钱的路径, 自己必须是免费的. 一个用来防雪崩的路径, 自己必须不
> 依赖那个正在雪崩的东西.

## 7. 决定一: 开关住在拥有它的模块里

这是这一篇最值得带走的一条.

那两个入口 (查配额, 记账) **自己检查开关并提前返回**. 所以调用它们的地方长这样:

```text
check_quota(client, config)
```

而不是这样:

```text
if config.quota_enabled:
    check_quota(client, config)
```

差别看起来只是省了两行. 它不是.

**把 `if` 放在调用方, 那个开关就从一个机制退化成了一条纪律.**

今天只有一个调用方, 你写了那个 `if`, 一切正常. 明天有人加了第二个调用方, 比如一个批量
跑评测的脚本, 而他忘了写那个 `if`. 会发生什么?

**一个关着的配额, 照样发出了一次真实的 DynamoDB 请求.** 不报错, 不影响功能, 只是每次都白
花一点钱和一点延迟. 而且没有任何测试会红, 因为那行代码本来就没错.

> **判据**: 一个功能的开关, 应该由**拥有这个功能的那段代码** 保证,
> 而不是由**每一个想用它的人** 保证. 使用者会变多, 而模块只有一个.

这条你在第 30 篇见过一个同族的说法: 不变量应该由创建对象的那个动作保证, 而不是由几个恰好
调用了它的入口保证. **同一个思路: 把保证放在唯一的那个地方.**

## 8. 决定二: 计量坏了绝不能拒绝服务

第二条, 而且它比第一条更容易做反.

想一下这个场景: DynamoDB 那边出了点问题, 或者那张表被人误删了, 或者凭据过期了.

现在**记账坏了**. 那用户的请求该怎么办?

一个很自然的反应是: 不知道用了多少额度, 那就先拒绝, 安全第一.

**这个项目选的是相反的: 放行.**

理由是一句很朴素的比较: **少记一次数, 比让一个用户已经等了十几秒的回复失败要便宜得多.**
记账是你的内部事务, 而用户是来问问题的. 让一个记账故障变成一次用户可见的失败, 是把内部问题
的代价转嫁给了外面的人.

所以那两个入口都在内部把基础设施异常记一笔日志然后咽掉.

### 但有一种异常必须出去

这里有一个很关键的不对称, 值得看清楚:

| 是什么 | 怎么处理 |
| :--- | :--- |
| DynamoDB 连不上, 表不存在, 凭据过期 | **咽掉**, 记一条日志, 放行. 这是**故障** |
| 额度真的用完了 | **抛出去**, 让调用方返回那句写死的话. 这是**答案** |

**一个是故障, 一个是答案.** 故障不该让用户看见, 答案必须让用户看见.

实现上这件事靠位置保证: 那个表示超限的异常是在捕获块**之外** 抛出的, 所以它不可能被那个
兜底的 `except` 顺手吞掉.

> **判据**: 写兜底的 `except` 之前, 先分清楚哪些东西是**这个模块的故障**,
> 哪些是**它要表达的结论**. 一个吞掉了结论的兜底, 会让整个功能静默失效.

## 9. 决定三: 不给同一个东西起第二个名字

最后一条, 它很小, 但很典型.

计数器要按部署分开存, 所以需要一个标识符. 它长这样:

```text
learn-ba-agent-app-scaffold : fintech_smb_lending_pipeline_medium : 2026-09
```

三段, 各有各的来源:

| 段 | 是什么 | 从哪来 |
| :--- | :--- | :--- |
| 脚手架 | 标识**这个代码库** | 一个写死在代码里的常量. 换数据集不变, 所以它不是配置 |
| 数据集 | 标识**这一份数据** | 直接用那个 schema 名 |
| 月份 | 让新的一个月自动从零开始 | 当前时间 |

**第二段值得说.** 这里完全可以给这个功能另配一个短名字, 比如在配置里加一行
`QUOTA_APP_SLUG="smbll"`. 那样 key 会短一点, 好看一点.

**不要.** 那个数据集**已经有一个必须全局唯一的标识符了**, 就是 schema 名, 它不唯一就会撞
别的项目的表. 再配一个短名字, 就是同一个东西的第二个名字, 也就是
**第二个要记得同步维护的东西**: 换数据集的时候你要改两处, 而漏掉一处不会报错, 只会让这个月
的账记到上一个数据集头上.

第三段那个月份也值得一提: 它在 key 里, 所以**新的一个月自动是一行新数据, 从零开始**. 没有
任何人需要记得去重置什么, 也不需要一个定时任务.

> **判据**: 需要一个标识符的时候, 先看看现有的东西里有没有一个**已经必须唯一** 的. 有就用
> 它. 每多一个名字, 就多一处会漂移的地方.

## 10. 练习

### 练习 1: 看着计数器涨上去, 然后撞墙

**目标:** 亲眼看一遍累加, 超限拒绝, 和故障放行三种行为.

**这个练习不需要 AWS 账号, 不需要凭据, 也不需要联网.**

**怎么做:**

1. 跑这一篇自带的脚本:

```bash
.venv/bin/python examples/33-the-spend-cap/01_watch_the_counters.py
```

2. 看第 1 节打印出来的那个 key, 把三段各是什么念一遍
3. 看第 3 节: 三次记账之后计数器是多少, 想清楚**为什么这件事只有真实现能证明**
4. 看第 4 节那条超限报错, 注意它报的是哪一个上限, 以及那个 key
5. 看第 5 节: 表不存在的时候两个函数各返回了什么, **有没有任何一个抛异常**
6. 看第 6 节: 开关关掉之后, 那个一被调用就会炸的假 client **没有被调用过**

**你会观察到:**

第 3 步那三行是 `(1, 100, 40)`, `(2, 200, 80)`, `(3, 300, 120)`. 这正是第 31 篇讲的那件事:
**一个手写的假对象只能记录我被调用了, 而真实现会真的把数字加上去.** 于是不用先读再写这个
决定第一次可以被验证.

第 5 步两个都没抛. 它们咽掉的是那个库真正会抛的异常, 不是谁吩咐它抛的.

第 6 步那个假 client 是故意写成一碰就炸的. 它没炸, 就证明了开关确实在模块内部生效.

> **关键洞见:** 这三种行为里, 最容易被写错的是第 5 步. 一个记账功能把整个应用拖垮, 是真实
> 世界里反复发生过的事故.

### 练习 2: 判断五个功能的开关该住在哪儿

**目标:** 把第 7 节那条判据用起来.

**怎么做:**

对下面五个假想的功能, 各回答两个问题:

- **A. 开关该住在哪儿?** 住在那个功能自己的模块里, 还是住在调用它的地方
- **B. 它自己坏了的时候, 该放行还是该拒绝?**

| 功能 | A | B |
| :--- | :--- | :--- |
| 把每次对话写一条审计日志 | | |
| 检查这个用户有没有权限用这个 agent | | |
| 给回答加一段免责声明 | | |
| 把回答缓存起来, 下次同样的问题直接返回 | | |
| 对用户输入做一次敏感词过滤 | | |

然后回答一句总结: **A 那一列有没有例外? B 那一列呢?**

**你会观察到:**

**A 那一列五个答案一样**, 全都该住在功能自己的模块里. 这条判据没有例外, 因为它的理由和功能
是什么无关, 它只跟使用者会不会变多有关.

**B 那一列不一样, 而且分界线很清楚**: 权限检查和敏感词过滤坏了必须**拒绝**, 因为它们是
**安全边界**; 审计日志, 免责声明, 缓存坏了应该**放行**, 因为它们是**辅助功能**.

配额属于哪一类? 它像安全边界, 但这个项目把它归到了辅助那一边. 想清楚为什么, 提示: 想想
最坏情况下各自的代价是什么.

> **关键洞见:** 坏了该放行还是该拒绝, 取决于**这个功能失效的代价** 和**拒绝服务的代价** 哪个
> 大. 这是一个需要你自己判断的取舍, 而不是一条可以背下来的规则.

## 12. 导师寄语

**为什么这一篇讲的三个决定比这个功能本身重要:**

花费上限这个功能, 你以后大概率不会原样再写一遍. 但那三个问题你会反复遇到:
**开关放哪儿, 坏了怎么办, 标识符从哪来.**

这三个问题有一个共同点: **它们的错误答案在写代码的那一刻看起来完全合理.** 把 `if` 写在调用
处很自然; 记账坏了就拒绝听起来很负责; 给一个功能起一个短名字显得整洁. 三个都要等到很久以后
才露出代价, 而且露出来的时候通常不会有人把它和当初那个决定联系起来.

**这也是整个主题 7 的共同底色.** 这一组六篇讲的全是这类决定: 它们不影响功能, 只影响这个
项目半年后还好不好改.

**关键洞见:**

- 一个功能的开关应该由拥有它的模块保证, 不由每一个使用者保证
- 分清什么是这个模块的故障, 什么是它要表达的结论. 兜底的 `except` 只该吞前者
- 坏了该放行还是拒绝, 取决于失效的代价和拒绝服务的代价哪个大
- 需要标识符时先找现有的那个已经必须唯一的东西, 别另起名字
- 一个用来省钱的路径, 自己必须是免费的

**下一步:**

([渲染契约](../34-the-rendering-contract/README-cn.md)) 把三样你已经分头见过的东西合起来讲:

## 13. 速查

**一条命令:**

```bash
.venv/bin/python examples/33-the-spend-cap/01_watch_the_counters.py
```

**三条判据:**

| 问题 | 答案 |
| :--- | :--- |
| 开关住哪儿 | 拥有这个功能的模块里. 使用者会变多, 模块只有一个 |
| 自己坏了怎么办 | 看失效的代价和拒绝服务的代价哪个大. 记账属于前者小, 所以放行 |
| 标识符从哪来 | 找现有的那个已经必须唯一的东西, 不另起名字 |

**那个 key 的三段:**

```text
脚手架常量 : schema 名 : 年- 月
```

**打开它要两步:**

1. 配置里把开关打开
2. 建一张 DynamoDB 表, 分区键是 `app_id`, 类型 String, 然后把表名填进配置

只做第一步的话, **应用在启动时就会报错** (第 30 篇那个例子).

**关键文件:**

- [`agent_app/quota.py`](../../agent_app/quota.py): 全部在这里, 一百多行
