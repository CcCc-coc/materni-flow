# 看懂那道花费闸门

## 1. 目标

到这里为止, 这门课里所有的模型调用花的都是你自己的钱, 而且是你自己按下的回车. 那种情况
不需要任何上限.

但第 35 篇部署上线之后, **付钱的人和打字的人不再是同一个人**. 链接是公开的, 每一条消息都在
花你云账号里的钱.

这一篇讲那道闸门. 但它被放进这一组不是因为功能, 是因为**形状**: 任何一个可开关的功能都
要回答三个问题, 而这三个问题的错误答案在写代码那一刻看起来全都很合理:

| 问题 | 那个看起来合理的错误答案 |
| :--- | :--- |
| 开关写在哪儿 | 写在调用的地方. 于是第二个调用方忘了写, 关着的功能照样在发请求 |
| 自己坏了怎么办 | 拒绝服务, 安全第一. 于是一个记账故障变成一次用户可见的失败 |
| 标识符从哪来 | 另起一个好看的短名字. 于是同一个东西有了两个要同步维护的名字 |

**练习 1 那个脚本不需要 AWS 账号, 不需要凭据, 也不需要联网.** 它在一个跑在本进程里的真
DynamoDB 上跑, 所以计数器是真的在加, 表不存在时抛的是那个库真正会抛的异常.

**卡住了别硬扛.** 把三样东西一起给 AI: 你在读哪一篇的路径, 你敲的那条命令, 以及
**终端打出来的原文** (整段复制, 不要截图, 不要只说一句报错了).

---

## 2. 要做的事情

1. 读完 README, 重点是第 7 到第 9 节那三个决定.
2. 跑 `.venv/bin/python examples/33-the-spend-cap/01_watch_the_counters.py`.
3. 看第 1 节那个 key, 说出三段各是什么, 以及月份在里面带来了什么好处.
4. 看第 3 节三次记账之后的数字, 说清为什么这件事只有真实现能证明, 手写的假对象不能.
5. 看第 4 节那条超限报错, 说出它报的是三个上限里的哪一个.
6. 看第 5 节, 确认表不存在时两个函数**都没有抛异常**, 并说清这个选择的理由.
7. 看第 6 节, 说清那个一被调用就会炸的假 client 没炸, 证明了什么.
8. 打开 `agent_app/quota.py`, 找到那个表示超限的异常是在捕获块**里面** 还是**外面** 抛的,
   说清为什么必须是那个位置.
9. 打开 `api/index.py`, 找到查配额那一步, 确认它在调模型之前, 并找到超限时返回的那句写死
   的话.
10. 按 README 练习 2 那张表, 对五个假想功能各回答开关住哪儿和坏了怎么办.
11. 回答一句: 配额本身更像安全边界还是辅助功能, 为什么这个项目把它归到了放行那一边.

**预计用时:** 45 到 70 分钟

## 3. 检查清单

- [ ] **什么时候才需要**: 你能说清这个功能为什么默认关着, 以及它和供应商控制台那个消费上限
      是两道不一样的闸门.
- [ ] **闸门的位置**: 你能说清它为什么必须拦在调模型之前, 以及为什么拒绝路径要返回一句写死
      的话而不是让模型生成一句道歉.
- [ ] **开关住在哪**: 你能说清它为什么住在拥有这个功能的模块里, 并描述把 `if` 放在调用方
      之后第二个调用方会造成什么后果.
- [ ] **故障放行**: 你亲眼见过表不存在时两个入口都不抛异常, 也能说出这个选择背后那句比较.
- [ ] **那个不对称**: 你能说清故障和答案的区别, 并指出那个超限异常在源码里为什么必须抛在
      捕获块之外.
- [ ] **计数器真的在加**: 你能说清三次记账之后读回来是 3 这件事, 为什么手写的假对象证明不了.
- [ ] **标识符**: 你能说出那个 key 的三段各是什么, 并解释为什么不给数据集那一段另起一个短
      名字.
- [ ] **判据会用**: 对那五个假想功能你都给出了两个答案, 并能说清 A 那一列为什么没有例外,
      而 B 那一列的分界线在哪儿.
