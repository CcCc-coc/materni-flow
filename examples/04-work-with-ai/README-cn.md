# 和 AI 一起改这个仓库

> 这个仓库不是碰巧能被 AI 改, 它是照着让 AI 改得动的样子设计的. 这一篇讲那些设计是什么.

## 1. 概览

**这一篇排在所有动手内容的最前面, 是故意的.** 后面每一篇都会让你把没看懂的东西交给 AI 去
问, 所以那把工具得先到手. 先自己啃三篇再拿到助教, 顺序就反了.

它回答四个问题:
**为什么不能让 AI 把代码读一遍, 它进门先读到什么, 它被允许碰什么, 以及你该怎么派活.**

这不是一篇讲 prompt 技巧的文章. 讲的是**仓库这一侧要准备什么**, 因为一个 AI 干得准不准,
大半取决于它面对的是一个什么样的代码库.

---

## 2. 学习目标

先说一个对比, 它解释了这一篇为什么值得单独占一篇.

**任务一**: 把界面上所有提到贷款的地方改成提到订单. 在这个仓库里, 这句话等于打开
[`data/site.toml`](../../data/site.toml) 改. 在一个文案散在二十个组件里的仓库里, 这句话等于全仓库搜一遍, 然后逐处
判断哪些该改哪些不该, 而这件事**每次都会漏, 而且漏得不报错**.

同一个模型, 同一句提示, 结果差得远, 差的不是模型是仓库.

反过来在 review 的时候也一样. 一次换数据集的改动
**应该只落在 [`data/`](../../data), [`dataset/`](../../dataset) 和 `.env.defaults` 三个地方**.
落到别处就是信号, 你不用逐行读也知道有东西越界了. 边界清晰的仓库, 改动的形状本身就是一种
检查.

学完这个 Task, 你将能够:

1. 解释为什么不能让 AI 每次干活前把代码库读一遍, 成本有哪两笔
2. 说清那个 skill 的形状: `ref/` 下的四块文档是内容, `SKILL.md` 只是一张索引表
3. 说出这门课两个 skill 的分工, 以及什么时候该加载哪一个
4. 读懂权限文件, 说出哪些操作被无条件拒绝以及为什么是这几个
5. 用一句话派出一个改得准的任务, 并用改动落点检查它有没有越界

## 4. 你将学到什么

一张这个仓库和 AI 之间的接口地图, 加一条派活的纪律.

带走的那个理念是: **不要把知识推给 AI, 要让它自己来取.** 你的活是准备一张地图, 不是写一本
说明书.

带走的那条纪律是: **让它先说计划, 一步一步做, 然后拿改动落点验收.** 这三件事任何一件缺了,
你都会收到一堆看起来对但你不敢合并的改动.

## 5. 为什么不能让 AI 把代码库读一遍

先问一个看起来很笨的问题: 既然要它改这个仓库, 为什么不干脆让它先把全部代码读一遍?

因为**读是要花钱的, 而且花的还不只是钱**.

模型每次干活, 你给它的东西都要按量计费, 而且它一次能装下的量有上限. 这个仓库几百个文件,
全读一遍就把额度烧掉一大半, 剩下的空间才轮到你真正要它做的事. 更糟的是第二笔成本:
**跟当前任务无关的内容会分散它的注意力**, 读得越多, 它越容易抓错重点.

所以这件事的做法必须反过来: **不要把知识推给它, 要让它自己来取.**

具体做法是三层:

1. 进门自动读的那份文档保持很短, 只放地图和索引
2. 真正展开的内容切成一篇篇独立文档, 平时不加载
3. 给它一张表: 遇到什么问题该去翻哪一篇

于是一次任务的实际流程变成了: 它先读几百字的索引, 判断这次该看哪两三篇, 只把那几篇读进来,
然后动手.

### 这正是 agent 和 chatbot 的区别, 换了个面孔

第 2 篇说过, chatbot 只能从记忆里凑答案, agent 会调工具去看真实的东西.

读文件也是调工具. 一个 chatbot 只能用你亲手喂给它的那些文字回答你; 一个 agent
**会自己决定去打开哪几个文件**. 所以你要准备的不是一份大而全的说明书, 是一张让它知道去
哪儿找的地图.

**这条对你自己也成立.** 第 6 篇 ([读一遍这个仓库](../06-read-the-codebase/README-cn.md)) 会教你
先画地图再挑一条路径走, 用的是同一个道理: 不是把所有东西读完, 是知道该读哪几个.

## 6. AI 进门先读到什么

不同的 coding agent 认不同的文件名, 所以这个仓库把同一份内容摆在几个地方. 它们的共同点是
**都很短**:

| 文件或目录 | 谁读 | 说明 |
| :--- | :--- | :--- |
| [`CLAUDE.md`](../../CLAUDE.md) | Claude Code | 这个仓库的总纲, 进门自动读进去. 里面是目录结构, 两种配置的区别, 改什么就改哪个文件的对照表, 以及跑测试和起服务的命令 |
| [`AGENTS.md`](../../AGENTS.md) | 多数别的 agent | 一份很短的开发环境说明. 它故意短, 因为长内容都在 skill 里, 不该塞进一份每次都全量读进上下文的文件 |
| `.agents/rules/`, `.codex/rules/` | 其它 agent 各自的规则文件 | 同一批约定换个格式再放一份. 顶上那行 `trigger: always_on` 是那个工具用来决定要不要每次都加载的标记 |

这一层解决的是**它得知道这个仓库大概长什么样**. 但地图不等于说明书, 真正的深度在下一层.

## 7. 那个 skill 是一张索引, 不是一本书

这门课最常用的那个 skill 叫 `about-bi-agent-app-scaffold-cn`. 先看看它里面到底是什么, 因为
它的形状本身就是上一节那个结论的落地.

### 先有文档, 后有 skill

这个项目在设计的时候就做了一件事: **把这个仓库为什么长成这样, 完整地写下来了.** 三十多篇,
分四块, 放在这个 skill 的 `ref/` 目录下:

| 块 | 讲什么 | 大概有几篇 |
| :--- | :--- | :--- |
| `ref/architecture/` | 边界和设计决定. 这是什么项目, 教学层和生产层怎么分, 数据集是什么, 为什么本地也连远程库, 渲染契约, 配置和内容怎么切, 靠什么守边界, 注释和文档怎么写 | 九篇 |
| `ref/backend/` | [`agent_app/`](../../agent_app) 那些 Python 模块各自为什么这么写. 从零依赖的叶子一路到 HTTP 入口, 编号就是依赖顺序 | 十一篇 |
| `ref/frontend/` | 界面必须做到什么, 每一块元素的内容从哪来, 内容管线, 路由和壳, 两个页面, 块渲染器, 设计 token | 八篇 |
| `ref/operations/` | 怎么把它跑起来: 配置, 数据库, 开发服务器 | 四篇 |

**这些文档是先写好的, 不是 AI 现场总结的.** 任何一个人打开它们都能接手这个项目, AI 只是
恰好也是读者之一.

### `SKILL.md` 本身几乎没有内容

打开 `.claude/skills/about-bi-agent-app-scaffold-cn/SKILL.md`, 你会发现主体是一张表, 长这样:

| 我要做的事 | 读 |
| :--- | :--- |
| 第一次把仓库跑起来 | `operations/01` |
| 重构, 挪文件, 判断一个东西该放哪一层 | `architecture/04` |
| 给 agent 加一个 tool | `backend/08` |
| 改界面 | `frontend/02` |

而且它开头就明说了一句: **在下面那张表里找到你要做的事, 只读那一篇. 不要全读.**

这就是上一节那三层的落地. 加载这个 skill 只花几百个字, 但从那一刻起, AI 遇到任何一类问题
都知道该去翻哪一页.

## 8. 两个 skill, 什么时候用哪个

这门课会用到两个, 分工不一样:

| skill | 它服务的是 | 什么时候加载 |
| :--- | :--- | :--- |
| `/about-bi-agent-app-scaffold-cn` | **这个项目** | 你要动手改代码, 想知道某个东西该放哪儿, 或者某条边界破了会怎样 |
| `/showcase-learn-cn` | **这门课** | 你在读教程, 某一段没看懂, 或者想知道自己该按什么顺序往下学 |

**要干活加载前一个, 要学习加载后一个, 两个一起加载也完全可以.** 它们读的是两批不同的文件,
互不冲突.

还有三个是换数据集专用的, 现在只需要知道它们存在:

| skill | 什么时候用 |
| :--- | :--- |
| `swap-dataset-cn` | 想搞清楚换数据集的全貌. 它本身只是索引和路由, 不含任何操作步骤 |
| `run-swap-dataset-phase-1-cn` | 真的要换, 第一阶段: 造库, 同步, 重写提示词和全部界面文案 |
| `run-swap-dataset-phase-2-cn` | 第二阶段: 照着新行业的调性重新设计前端 |

换数据集为什么要拆成一个索引加两条命令, 而不是写成一个大 skill: 一个 skill 被调用之后
**以一条消息的形式留在对话里**, 后面不会被重新读取, 而上下文压缩时每个 skill 只保留开头
一部分. 把两个阶段写在一起, 跑完第一阶段通常已经压缩过, 排在文件末尾的第二阶段正好是被
截断的那一段. 拆开之后, 第二阶段在真正需要它的那一刻才第一次完整进入上下文.

这两条命令你在第 37 篇 (换数据集) 和第 38 篇 (重新设计前端) 会真的敲.

## 9. AI 被允许碰什么

`.claude/settings.json` 是权限文件. 它有两个名单.

**allow 名单** 列出不需要每次问你就可以做的事: 改 [`data/`](../../data) 下的内容, 改各种 Markdown 文档,
改 [`scripts/`](../../scripts) 下的 Python, 跑 `mise` 命令, 跑 `.venv/bin/python scripts/**/*.py`, 联网搜索.

**deny 名单只有很短的几条, 但它是这个文件里最重要的部分**:

```json
"deny": [
    "Read(.env)",
    "Read(.env.local)",
    "Read(.envrc)",
    "Edit(.env)",
    "Edit(.env.local)",
    "Edit(.envrc)",
    "Read(~/.aws/credentials)"
]
```

**读和写都被拒绝, 而且是无条件的.** 这几个文件装的是你的 API key, 数据库密码, AWS 凭据.

下一篇 ([把它跑起来](../05-get-it-running/README-cn.md)) 会给你另一半:
**不要把 key 贴进任何聊天窗口.** 这两条是同一件事的两半, 那一半管你的手, 这一半管 AI 的
手. 少了任何一半, 凭据都会流进一个你控制不了的地方 (对话记录, 日志, 别人的服务器).

**副作用是好的**: 因为 AI 打不开 `.env`, 你让它帮忙调配置时它只能改 `.env.defaults`, 而那
个文件里没有秘密, 还进 Git, 所以它改了什么在 `git diff` 里一目了然.

所以换数据集的时候 AI 可以自由编辑 `.env.defaults`, 但碰不到任何人的凭据.

## 10. 怎么派活

三条, 按顺序.

### 一, 让它先说计划

派活的时候要求它**先列出打算改哪些文件, 每个文件改什么, 然后停下来等你确认**. 不要一上来
就让它动手.

理由是这个仓库有一堆不写出来就看不见的边界 (组件里不许有业务文案, 生产路径不 import 教学层,
渲染契约的三半要一起改). 一个计划是纯文本, 你扫一眼就知道它有没有踩线; 一堆已经写好的
改动要看懂就贵多了.

### 二, 一步一步做

**一次改一件事, 改完你自己跑一遍验证, 再走下一步.** 这条在后面每一篇都用得上, 所以现在就
钉住.

一口气改十个文件的问题不是它会改错, 是**出错的时候你不知道是哪一步错的**. 拆开之后每一步
都有一个明确的验收动作, 错了当场就知道.

这条同样适用于**让它给你讲东西**. 后面遇到看不懂的段落时, 别问一句把这一篇讲一遍, 那样你
会收到一大段读不完的东西. 要求它一次只讲一步, 讲完等你说继续.

### 顺带一句: 用哪一档模型

跟你互动的那个模型档次不够, 它会漏步骤, 会自作主张, 反而更费时间. 这三家的这几档都够用:

| | Anthropic | OpenAI | Google |
| :--- | :--- | :--- | :--- |
| **优先用这一档** | Claude Sonnet | GPT Terra | Gemini Flash |
| 预算紧的话 | Claude Haiku | GPT Luna | Gemini Flash |

**尽可能用第一行那一档.** 多步骤的任务对模型的耐心和一致性有要求, 而这正是小模型最先丢掉
的东西. 预算紧的时候第二行也走得完, 只是你要多盯着一点.

注意这里说的是**跟你对话的那个 coding agent 用什么模型**. 这个 app 自己那个 agent 用哪个
模型是另一回事, 由 `.env.defaults` 决定, 第 13 篇
([接上真数据和真模型](../13-light-it-up/README-cn.md)) 才会碰到.

### 三, 拿改动落点验收

改完先看 `git status` 和 `git diff --stat`, 别急着读内容. **落点不对就不用读了.**

| 你派的活 | 改动应该只落在 |
| :--- | :--- |
| 改一句界面文案 | [`data/site.toml`](../../data/site.toml) |
| 换整个业务领域 | [`data/`](../../data), [`dataset/`](../../dataset), `.env.defaults` |
| 给 agent 加一个工具 | [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), [`data/system-prompt.md`](../../data/system-prompt.md) |
| 改配色 | [`tailwind.config.ts`](../../tailwind.config.ts) |

落到别处就是越界的信号. 这个检查便宜到几乎免费, 而且它在你读一行代码之前就能给出结论.

## 11. 练习

### 练习 1: 派一个真实的小任务, 拿落点验收

**目标:** 走一遍完整的派活流程, 并用改动落点检查结果.

**怎么做:**

1. 确认工作区是干净的: `git status --short`
2. 加载 skill: 敲 `/about-bi-agent-app-scaffold-cn`
3. 派这个任务, 并且明确要求先出计划:

```text
把 agent 页输入框的 placeholder 文字改成一句更具体的提示.
先告诉我你打算改哪些文件, 每个文件改什么, 然后停下来等我确认, 不要直接动手.
```

4. 读它给的计划. 它应该只提到一个文件
5. 确认之后让它改, 然后跑 `git diff --stat`
6. 再跑一次 `git diff`, 确认改的确实是那一句文案, 而不是顺手动了别的
7. `git checkout -- .` 还原

**你会观察到:**

计划里应该只有 [`data/site.toml`](../../data/site.toml) 一个文件. 如果它提出要改
[`components/chat/multimodal-input.tsx`](../../components/chat/multimodal-input.tsx), 那说明它没读到组件里不许有业务文案这条规矩, 这时候
把它指回那份 skill.

> **关键洞见:** 改动落点是一个在你读代码之前就能用的检查. 一个边界清晰的仓库, 越界这件事
> 在 `git diff --stat` 那一屏上就看得见.

### 练习 2: 让它撞一次权限墙

**目标:** 亲眼确认 deny 名单是真的拦得住, 而不是一句约定.

**怎么做:**

1. 问它一个需要读 `.env` 才能回答的问题, 比如:

```text
读一下 .env, 告诉我 DB_HOST 现在填的是什么
```

2. 看它的反应
3. 再问一个它能答的: 让它读 `.env.defaults`, 告诉你 `SCHEMA_NAME` 是什么
4. 对比两次的差别

**你会观察到:**

第一次它读不到, 因为那条路径在 deny 名单里. 第二次它能读, 因为 `.env.defaults` 里没有秘密.
这条线不是靠 AI 自觉, 是配置文件写死的.

> **关键洞见:** 涉及凭据的规矩不要写成提示词里的一句请不要, 要写成一条机械的拒绝. 前者是
> 建议, 后者是墙.

## 13. 导师寄语

**为什么这一篇不是讲 prompt 技巧:**

网上大量内容在教怎么把话说得更巧, 而实际工作里, 同一句话在两个仓库里的效果可以差出十倍.
差别不在措辞, 在那个仓库有没有把该集中的东西集中起来, 有没有把该拦的东西拦住.

所以想让 AI 帮上忙, 花在整理仓库上的时间, 通常比花在打磨提示词上的时间回报高得多. 这一篇
讲的每一样东西都是这个方向的投资.

**关键洞见:**

- 一个 AI 干得准不准, 大半取决于它面对的是一个什么样的代码库, 不是取决于你怎么说话
- 不要把知识推给它, 让它自己来取. 你的活是准备地图, 不是写说明书
- 先要计划再要代码. 计划是纯文本, 扫一眼就能判断有没有踩线
- 涉及凭据的限制要做成机械的拒绝, 不要做成提示词里的一句请不要
