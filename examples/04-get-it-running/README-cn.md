# 把它跑起来: 装依赖, 配密钥, 灌数据, 起服务

> 四步, 顺序不能换. 每一步跳过之后的失败方式都不一样, 而最阴的那一种根本不报错.

## 1. 概览

这一篇是这门课第一次动手. 目标很朴素: 浏览器里打开 `localhost:3000` 看到首页, 点进 agent
页问一个问题, 拿到一个基于真实数据的答案.

达到这个状态要走四步:

| 步 | 干什么 | 一条命令 |
| :--- | :--- | :--- |
| 1 | 装依赖 | `mise run inst` |
| 2 | 配密钥 | `cp .env.example .env`, 然后填 |
| 3 | 灌数据 | `gen-data` 然后 `sync-db` 然后 `verify-db` |
| 4 | 起服务 | `mise run dev` |

这四步看起来是任何项目都有的开场白, 但这个项目的第 2 步和第 3 步跟你熟悉的不太一样, 而且
**跳不过去**. 这一篇一半的篇幅在讲为什么.

### 读不懂的地方, 别跳过去

先说一条贯穿整个系列的读法, 因为从这一篇开始正文会变密.

这门课很长, 而且它的第一优先级是**让你先跑通**. 所以正文里很多东西只讲到你现在需要知道的
那个程度, 不会一路展开到底. 这是刻意的取舍: 每个点都写细一遍, 篇幅会长到没人读得完, 而且
每个人卡住的地方本来就不一样, 提前猜也猜不准.

补这个深度的办法是把 AI 拉进来:

1. 敲 `/showcase-learn-cn` 把这门课的助教加载起来

3. 追问到懂为止. 这句话什么意思, 为什么不能反过来做, 给我举个例子, 换个说法再讲一遍, 都行

**不要装作看懂了往下翻.** 这门课后面每一篇都长在前一篇之上, 一个含糊的地方会一路含糊下去,

## 2. 学习目标

大多数项目的 README 会告诉你装依赖然后跑起来, 中间那些配置步骤是可选的, 缺了顶多某个功能
用不了. 这个项目不是: 缺了第 2 步它连不上数据库,
**缺了第 3 步它会跑得好好的然后给你编造的答案.**

第二种失败值得你现在就记住, 因为它是这门课反复出现的一个模式: 这个项目里最贵的错误几乎
全都不报错. 一个报错的系统是好系统, 你至少知道该修哪儿. 一个连着空数据库还在自信作答的
agent, 你可能一个星期之后才发现.

学完这个 Task, 你将能够:

1. 用 mise 一条命令装齐 Python 和 Node 两套工具链, 并说清 mise, uv, pnpm 三者谁调谁
2. 分清哪些配置该进 `.env`, 哪些该进 `.env.defaults`, 判据是什么
3. 在三家 LLM 厂商里选一家拿到 API key, 给它设上花费上限, 并妥善保管
4. 把这门课的 AI skill 叫起来当助教, 而且知道怎么让它一步一步来
5. 走完造种子, 同步, 逐表核对这三条命令, 并说清它们为什么不是 mise 任务
6. 解释空 schema 和不存在的 schema 为什么在程序看来一模一样, 以及后果是什么

## 5. 一个入口: mise

打开 `mise.toml`, 它同时管两件事.

**第一件是钉住工具版本.** 顶上那个 `[tools]` 段声明这个项目要 Python 3.12, Node 24, 加上
uv, pnpm, ruff. 所以 clone 下来之后你不需要自己去装 Python 和 Node, mise 会按这张表准备好.
这也意味着你机器上装的是哪个版本的 Python 不重要.

**第二件是定义任务.** 剩下那一大堆 `[tasks.xxx]` 就是这个项目所有能敲的命令. 常用的是这些:

| 命令 | 干什么 |
| :--- | :--- |
| `mise run inst` | 装依赖 (Python 和 Node 一起) |
| `mise run dev` | 起两个开发服务器 (会先杀掉本 checkout 的旧进程) |
| `mise run kill` | 停掉本 checkout 的服务器 |
| `mise run test` | 内容检查加 Python 测试加 Node 测试 |
| `mise run check-content` | 只查 `data/` 里的内容一致性 |
| `mise run build-web` | 构建前端, 也是唯一会查 `site.toml` 必填 key 和图标名的地方 |

`mise run inst` 底下调的是两个包管理器: `uv sync --all-extras` 读 `pyproject.toml` 和
`uv.lock`, `pnpm install` 读 `package.json` 和 `pnpm-lock.yaml`. 你不需要分别记住它们的写法,
这正是 mise 存在的理由.

**任务名点的是它碰什么, 不是它属于哪一类.** 一个叫 `check` 的任务说不清它是这个仓库好几种
检查里的哪一种; `check-content` 和 `build-web` 摆在一起, 就看得出它们分管两边.

现在敲第一条:

```bash
mise run inst
```

## 6. 两个配置文件, 按是不是密钥切

第 2 步是配置. 这个项目有两个配置文件, 它们之间的那条线值得单独讲, 因为它决定的不只是
"值放哪儿", 而是**谁能打开这个文件**.

| | `.env` | `.env.defaults` |
| :--- | :--- | :--- |
| 装什么 | API key, AWS 密钥, 数据库 host, user, password, name | `SCHEMA_NAME`, `LLM_PROVIDER`, `AWS_REGION`, `DB_PORT`, 整块配额设置 |
| 是密钥吗 | 是 | 不是 |
| 进 Git 吗 | 不进 | **进** |
| AI 能打开吗 | **不能**, `.claude/settings.json` 里 deny 了读和写 | 能 |
| 加载顺序 | **先读, 所以它赢** | 后读, 补空缺 |

**判据只有一句: 它是密钥吗?** 另一条看起来也讲得通的切法是 "会不会因为换台机器而不同",
但那条线会把数据集的身份 (一个字符串) 切成第三个配置文件, 于是你要为它养一个格式和一个
读取模块. 按密钥切的这条线能挣回成本, 因为它管的是访问权限.

这条线带来的两个具体好处: 轮换一个 API key 不该碰到 schema 名; 把仓库指向一个新数据集不该
碰到任何人的凭据.

**注意 `.env.defaults` 是进 Git 的, 而且没有 `.env.defaults.example`.** 这是故意的: 那个
文件本身就是参考. 搞成 "gitignore 加模板" 的话, `SCHEMA_NAME` 就跑到版本控制外面去了, 每次
clone 都要重填一遍.

现在动手:

```bash
cp .env.example .env
```

然后在 `.env` 里填两样东西, 别的都留着注释:

- `DB_HOST`, `DB_USER`, `DB_PASS`, `DB_NAME`. 用 Neon 那个带 `-pooler` 的主机名
- **一个** LLM 凭据, 就是 `.env.defaults` 里 `LLM_PROVIDER` 指的那一家

### 三个填的时候会咬人的地方

**一, `"..."` 等于没设.** `.env.example` 里的占位符是 `"..."`, 而代码把这个值当成未设置.
所以从模板抄过来忘了注释掉的那一行, 不会变成一个 "已设置, 非空, 但没用" 的变量.

**二, 用 bedrock 的话本地不要设 AWS 那两个 key.** boto3 查环境变量**早于**
`~/.aws/credentials`, 所以 `.env` 里一个占位符就能遮蔽掉一个好好的本地 profile. 报出来的
错是 `UnrecognizedClientException`, 一条完全指不到原因的话.

**三, 换 `LLM_PROVIDER` 时记得 `LLM_MODEL_ID`.** 各家的 model ID 格式不通用. 要么一起改,
要么把它注释掉让它回退到那家的默认值.

## 7. 一把 LLM 的 API key

这个 app 的核心是一个大模型, 所以你得给它一把钥匙. 这一节讲的是**你需要做什么判断**, 不是
点哪个按钮, 因为三家厂商的控制台每隔几个月就改一次版, 写死步骤只会过期.

### 三选一

| 厂商 | 环境变量 | 说明 |
| :--- | :--- | :--- |
| OpenAI | `OPENAI_API_KEY` | **推荐**, 注册和拿 key 这条路最顺 |
| Anthropic | `ANTHROPIC_API_KEY` | Claude 系列 |
| Google | `GOOGLE_API_KEY` | Gemini 系列 |

**只填一家.** 每个进程只跟一个 LLM 后端说话, 由 `.env.defaults` 里的 `LLM_PROVIDER` 决定,
而只有被选中那家的凭证是必需的. 三把 key 都填不会更好, 只是多两个要保管的东西.

选好之后, 把 `.env.defaults` 里那行改成对应的值, 或者在自己的 `.env` 里写一行同名的盖掉它.
`.env` 先读, 所以它赢.

还有第四家 AWS Bedrock, 它不走 API key 而走 AWS 凭据, 配起来多几道手续. 第一次跑先别选它.

### 订阅和 API key 是两回事

这一点每年都要坑掉一批人.
**ChatGPT Plus, Claude Pro 这类月费订阅买的是网页版和客户端的使用权, 不带 API 额度.**
你已经付过订阅费, 不代表你的 API key 能用. API 是单独计费的另一条路, 在各家的开发者控制台
里, 通常叫 API keys 或者 Developer platform.

### 给它设一个花费上限

拿到 key 之后, **在控制台里给这个账号设一个消费上限, 5 美元或者 10 美元**. 这门课大概率
用不完, 一次对话的成本是零点几美分的量级.

这一步不是为了省那几美元, 是**防呆**:

- 一把不小心提交进公开仓库的 key, 会在几小时内被爬到并跑满
- 一段写错的循环可能在你去泡咖啡的时候调用几千次

设了上限, 这两件事的代价就是上限本身, 用完为止. 不设上限, 它是一张空白支票.

### 安全保管

- **存进密码管理器** (LastPass, 1Password, Bitwarden 这类), 不要存在便签或者聊天记录里
- **不要贴进任何聊天窗口**, 包括跟 AI 的对话
- **不要提交进 Git.** 这个仓库把它放在 `.env` 里, 那个文件被 `.gitignore` 排除, 而且
  `.claude/settings.json` 里 deny 了 AI 对它的读和写, 所以你让 AI 帮忙改配置时它碰不到这
  个文件
- **发现泄漏就当场吊销重发一把.** 不要试图评估影响, 吊销是几秒钟的事

## 9. 灌数据: 三条不在 mise 里的命令

第 3 步是这个项目最不常规的一步. **数据库文件不进 Git**, 所以一个新 clone 打开就用是不行的,
你得自己造一份.

```bash
CLI=.claude/skills/about-bi-agent-app-scaffold-cn/scripts/teaching_cli.py

.venv/bin/python $CLI gen-data      # 跑生成器, 造出 dataset/<name>.sqlite
.venv/bin/python $CLI sync-db       # 把种子发布进 PostgreSQL 的 SCHEMA_NAME
.venv/bin/python $CLI verify-db     # 逐表对行数, 不一致就 exit 1
```

数据是这么流动的:

| 阶段 | 产物 | 进 Git 吗 |
| :--- | :--- | :--- |
| `dataset/04-*_data_generator-cn.py` | 数据集自带的生成器 | 进 |
| `gen-data` 之后 | `dataset/<name>.sqlite`, 本地种子 | 不进 |
| `sync-db` 之后 | PostgreSQL 里 `SCHEMA_NAME` 那个 schema | 不适用 |
| `verify-db` | 逐表行数一致 | 不适用 |

**为什么产物不进 Git**: 它是二进制, 每次重新生成都是一次没人读得懂的 diff, 而仓库体积一去
不回. 更根本的理由是它可再生: 生成器是确定性的, 同一份代码跑两遍拿到同样的行.

`gen-data` 在 `.sqlite` 已经存在时**什么都不做**, 因为生成要几分钟而绝大多数时候它已经在
那儿了. 真要重来加 `--force`.

**为什么这三条不是 mise 任务.** `mise.toml` 跑的是**应用**: 装依赖, 起服务, 跑测试. 造数据
和同步数据库都不是应用. agent 通过一个数据库连接读 PostgreSQL, 数据怎么进去的不是它的事.
把这三条放在解释它们的那个 skill 旁边, 教学层就是删几个目录, 而不是从共用配置里一行行挑
出来删. 这条边界第 6 篇 (教学层和生产层) 会展开.

## 10. 为什么本地开发也连生产那个数据库

这里有一个看起来完全合理, 而且几乎所有人第一反应都会选的做法: **按运行环境自动选引擎**,
本地读那份现成的 SQLite, 线上读 PostgreSQL. 本地不用连网, 线上用真库, 两边都舒服.

这个做法在这个项目里行不通, 理由只有一条: **查这个数据库的不是人, 是模型.**

模型写 SQL 的依据是 `data/system-prompt.md` 里那十几段 SQL 例子, 它们是给模型照抄的模板.
如果这些例子是在本地对着 SQLite 写的, 那它们全都是 SQLite 方言. 发到线上以后:

| 写在提示词里的 (SQLite) | 在 PostgreSQL 上 |
| :--- | :--- |
| `strftime('%Y-%m', d)` | 不存在 |
| `JULIANDAY(a) - JULIANDAY(b)` | 不存在 |
| `DATE(d, '-90 days')` | 不存在 |
| `WHERE is_flag = 1` | 报 boolean 和 integer 不能比较 |

**而线上从来不会崩.** agent 的 SQL 工具把数据库报错转成字符串还给模型, 模型换个写法再试
或者干脆绕过去. 所以症状不是异常, 是**答案悄悄变差**, 没有任何监控会报这种事.

一句话: 人可以在两套方言之间切换, **一份提示词不能**. 提示词只有一份, 它必须对着一个确定
的数据库写.

代价要认: 本地开发现在需要 `DB_*` 环境变量, 而且第一次要跑一次同步才能工作. 这是一个安装
步骤, 换掉的是一个静默的错误答案.

SQLite 没有消失, 它退回到它擅长的位置: **种子和同步源**, 不是任何人查询的对象.

### 顺带一提: 隔离用 schema, 不用表名前缀

线上那个 Neon 实例是和别的项目共用的, 隔离靠 PostgreSQL schema, 也就是 `.env.defaults` 里
那行 `SCHEMA_NAME`. **两边的表名一模一样, 这是全部设计目标.**

不要用表名前缀去做隔离. 加了前缀之后, agent 看到的表名就取决于背后是哪个引擎, 于是提示词
里每一段 SQL 在一个环境对在另一个环境错, 而且没有任何东西会报错. 第 20 篇 (种子到
PostgreSQL) 会把这件事讲透.

## 11. `sync-db` 跳过之后会发生什么

这是这一篇最想让你记住的一件事.

不同步就等于没有数据库, 但失败方式很阴:
**空 schema 和不存在的 schema 在反射器看来一模一样.**
agent 的 schema 工具反射到一个空 schema, 拿到的结果是这个库里没有表. 然后它会凭空编出一些
看起来非常合理的表名来回答你的问题, 而且答得很自信.

代码里专门有一个检查挡这件事: 反射出零张表就当场抛异常, 并在错误信息里直接告诉你去跑同步.
这个检查不是防御性编程的洁癖, 它挡的正是上面那种失败.

同步是**幂等** 的: 每次都先倒着 drop 本项目 schema 里的表再重建, 跑几次结果一样.
**它只碰自己的 schema**, 共用实例上别的项目的表不会被动到.

## 12. 起服务

```bash
mise run dev
```

这一条底下绕了一圈: mise 先跑 `mise run kill` 清掉本 checkout 的旧进程, 然后调 pnpm 的
`concurrently`, 再由它调回 mise 去起两个子任务, 一个 `next dev --port 3000`, 一个
`uvicorn api.index:app --reload --port 8000`.

**mise 调 pnpm 再调回 mise**, 是因为并发跑两个进程这件事用 `concurrently` 最省事, 而它是
一个 node 包.

两件值得知道的事:

**前端端口钉死在 3000.** Next.js 默认在 3000 被占时会跳到 3001, 而 `next.config.js` 把
`/api/*` rewrite 到写死的 `127.0.0.1:8000`. 于是那个跳过去的前端仍然指着 8000, 而坐在那里的
可能是另一个 checkout 的后端. **起不来比静默接错好.**

**`package.json` 里那几个同名 script 不要用.** 它跑起来的东西看着一样, 但少了两件事: 没有
那个用来认出 "哪些进程是我的" 的环境变量标记, 也没有先 kill 那一步. 它留着是因为 Vercel 构建
要读 `package.json`, 日常一律用 `mise run dev`.

两个服务器都起来之后, 打开 `http://localhost:3000`, 你会看到首页. 点右上角进 agent 页, 点
任意一个 kickstart 按钮.

## 13. 练习

### 练习 1: 走完四步

**目标:** 在自己机器上得到一个能回答问题的 agent.

**怎么做:**

1. `mise run inst`
2. `cp .env.example .env`, 填 `DB_*` 和一个 LLM 凭据
3. 三条灌数据的命令, 一条一条跑, 每条都看完输出再跑下一条
4. `mise run dev`, 等两个服务器都打出就绪日志
5. 打开 `http://localhost:3000/chat`, 点一个 kickstart 按钮

**你会观察到:**

`gen-data` 要跑几分钟, `sync-db` 会一张表一张表地报进度, `verify-db` 输出一张对照表.
agent 回答时上面会先出现一个可以展开的思考块, 然后正文才一段段出来.

> **关键洞见:** 四步里有三步在处理数据和配置, 只有最后一步在跑代码. 这个比例不是偶然,
> 一个 AI 应用的绝大部分工作量都在 "让模型看到正确的东西" 上.

### 练习 2: 亲眼看一次静默失败

**目标:** 理解为什么跳过同步比连不上数据库更糟.

**怎么做:**

1. 在 `.env` 里加一行, 把 schema 指到一个不存在的地方: `SCHEMA_NAME="nowhere_at_all"`
2. 重启开发服务器, 在 agent 页问一个关于数据的问题
3. 读那条错误信息, 看它有没有告诉你该跑什么命令
4. 把那一行删掉, 重启, 确认恢复正常

**你会观察到:**

你拿到的是一条指名道姓的异常, 而不是一个编出来的答案. 这个检查就是为了把 "静默编造" 换成
"当场报错".

> **关键洞见:** 一个能被机械判断的错误状态, 值得写成一个当场抛出的检查, 而不是写进文档
> 等人记住.

## 15. 导师寄语

**为什么这一篇的顺序值得记住:**

装依赖, 配密钥, 灌数据, 起服务. 这四步在任何项目里都有, 但很少有项目会把为什么不能跳过第
3 步这件事写进文档. 大多数项目里第 3 步是可选的, 缺了顶多某个功能用不了.

这个项目不一样, 因为它的核心组件是一个模型, 而模型不会因为拿到坏输入就崩. 它会尽力给你
一个答案, 而且那个答案看起来和好答案毫无区别.

**关键洞见:**

- 这个项目里最贵的错误都不报错. 你的第一直觉应该从 "哪里崩了" 改成 "哪里悄悄错了"
- 一个配置值该放哪个文件, 只问它是不是密钥. 不要用 "会不会因机器而异" 那条线
- 一个能机械判断的坏状态, 应该在启动时抛异常, 而不是写进 README 等人记住
- 让 AI 一步一步来, 是这门课里你要反复用到的一条纪律. 它一次做完, 学到东西的是它不是你

**下一步:**

环境跑起来了, 但你现在对这个仓库的了解还停留在目录名. 第 5 篇 (读一遍这个仓库) 会带你从
上往下读一遍: 两个页面, 一个后端包, 以及一次提问从浏览器出发到底走过了哪些文件.
