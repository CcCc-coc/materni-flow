# 没有一个测试连网

> 这个仓库连着一个云数据库, 一个 AWS 服务, 和一个大模型. 整套测试跑完 269 个用例要两秒半,
> 而且一个包都没发出去.

## 1. 概览

先看一个数字, 因为它比任何论证都直接:

```text
269 passed in 2.60s
```

这是这个仓库全部 Python 测试跑完的样子. 而这个仓库是干什么的? 它连一个云上的 PostgreSQL,
调 AWS 的 DynamoDB, 还要跟一个大模型说话.

**这三样东西, 测试里一样都没碰.**

这一篇讲这是怎么做到的, 以及为什么值得这么做. 顺带回答两个你以后自己写测试时一定会遇到的
问题: 覆盖率到底该看什么, 以及一条架构规矩什么时候值得写成测试而不是写进文档.

### 卡住了怎么办

这一篇每一步都可能出错: 脚本跑不起来, 覆盖率报告打不出来, 或者你看到的数字和这里写的对不上.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/31-tests-without-network/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/31-tests-without-network/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

**这一篇不教你怎么写测试.** 网上教这个的东西比这门课好得多, 而且你多半已经会写一个断言了.

这一篇教的是一个更前面的问题: **当被测的东西依赖一个你控制不了的外部世界时, 你怎么办?**

这是真实工作里最常卡住人的地方. 一个新人写业务逻辑的测试都写得挺好, 一碰到这个函数要连
数据库就停住了, 然后走上那条最自然也最糟的路: **让测试真的去连**.

那条路会怎么烂掉, 值得先说清楚, 因为它烂得很慢:

| 一开始 | 三个月后 |
| :--- | :--- |
| 跑得慢一点, 能接受 | 跑一次要五分钟, 于是没人在提交前跑了 |
| 偶尔失败, 重跑一次就好 | 大家学会了忽略红色, 于是真的坏了也没人信 |
| 只有 CI 上要配数据库 | 新人 clone 下来跑不了测试, 第一天就卡住 |
| 测试之间互相看得见数据 | 单跑绿, 一起跑红, 而且顺序一换结果就变 |

**最后那一条最致命**: 它让测试从一个能给你信心的东西, 变成一个你要花时间去哄的东西.

所以这一篇真正的主题是: **怎么把外部世界换掉, 而且换得让测试仍然有意义.** 最后半句是重点,
因为换错了的话, 你测的就只是你自己的假设.

学完这个 Task, 你将能够:

1. 说出这个仓库对数据库, AWS, 大模型三类依赖分别用了什么手段
2. 解释为什么 DynamoDB 用 moto 而不是自己手写一个假对象, 这个区别为什么是实质性的
3. 说清覆盖率 100% 意味着什么, 以及它**不** 意味着什么
4. 用一条判据决定一行代码够不够格打上不计入覆盖率的标记
5. 说出这个仓库里有一条测试守着的架构规矩, 以及什么样的规矩值得这么干

## 5. 亲手掐一次网

先做, 再讲.

```bash
.venv/bin/python examples/31-tests-without-network/01_cut_the_network.py
```

这个脚本干的事很直接: 它先把 Python 里那个负责建立连接的函数换成一个**只会拒绝** 的版本,
然后在同一个进程里跑完整套测试.

于是逻辑变成了: 如果有任何一个测试试图连网, 它现在只能失败, 而且失败信息里会写清它想连
哪儿. 全绿, 就等于**没有一个测试连过网**.

你应该看到类似这样的结尾:

```text
269 passed in 2.60s

======================================================================
No test attempted a single outbound connection.
======================================================================
```

**这就是这一篇的立论**, 剩下的几节讲它是怎么办到的.

> 顺带说一句这个证明本身的性质: 它不是读代码读出来的结论, 是**造一个条件让谎言无法成立**.
> 你以后想确认任何一件我以为没有发生的事, 都可以用这个思路.

## 6. 三类依赖, 三种手段

外部世界不是一种东西, 所以也没有一个通用的换法. 这个仓库对三类依赖用了三个不同的手段, 而
选择的依据是**这个依赖的哪一部分是你真正想测的**.

### 数据库: 换一个真的数据库

测 `db_schema/` 那一层 (第 22 篇讲的那个把库结构压给模型看的东西) 时, 用的不是假对象,
是**一个真的数据库, 只不过它活在内存里**:

```text
sqlite://
```

SQLAlchemy 认这个地址, 建出来的库不落任何文件, 进程一退就没了.

**为什么这样可以?** 因为那一层要测的是它**怎么读一份库结构并编码**, 而不是它连的是哪个牌
子的数据库. 内存 SQLite 提供的是一份货真价实的库结构, 有表, 有列, 有类型, 有外键.

还有一部分测试更极端: 它**根本不建库**, 直接手搓一份 SQLAlchemy 的结构描述对象丢进去.
因为那一层压根不碰数据库, 它只碰那个描述对象.

> 这里的判据是: **看清楚被测的东西真正摸的是什么.** 它摸的是描述对象, 那你就给它一个描述
> 对象, 不用为了给它一个描述对象而先起一个数据库.

### AWS: 用一个真实现, 不用假对象

测那个月度花费上限 (下一篇的正题) 时, 要跟 DynamoDB 打交道. 这里用的是 **moto**, 一个
跑在你这个进程里的 DynamoDB 实现.

这个选择值得单独讲, 因为它和手写一个假对象的差别是**实质性的**.

DynamoDB 的低层接口有个特点: 数字不是数字, 是带类型标签的字典. 一个 42 写进去长这样:

```text
{"N": "42"}
```

现在假设你手写一个假对象. 你写它的时候, 脑子里对这个格式有一个印象. 如果那个印象是错的
(比如你以为直接写 `42` 就行), 会发生什么?

**你的代码和你的假对象会一起错.** 假对象不会挑剔, 因为它就是你写的; 于是测试全绿, 上线
才炸.

**手写的假对象断言的是作者对接口形状的信念, 不是接口本身.** 而 moto 是真实现, 格式写错了
它当场拒绝.

用真实现还白捡两件事, 都是假对象给不了的:

| 白捡什么 | 假对象为什么给不了 |
| :--- | :--- |
| **计数器真的在累加** | 假对象只能记录被调用过, 而真实现会真的把数字加上去. 于是累加三次读回来是 3 这件事第一次可以被断言 |
| **故障是真故障** | 让它指向一张不存在的表, 抛出来的是那个库真正会抛的异常, 而不是你吩咐假对象去抛的那个 |

第二条尤其要紧, 因为下一篇有一条重要的性质是**记账出故障绝不能拒绝服务**. 拿真异常去验它,
才算验过.

### 大模型: 根本不叫它

模型这一侧的手段最简单: **不叫它.**

这类测试要验的是**这个模型对象被怎么建出来的**, 用了哪个 provider, 传了哪个 model id,
该带的参数带了没有. 那些在**构造那一刻** 就已经确定了, 不需要真的发一次请求.

做法是把 `one.config` 换成一个你自己造的, 然后断言构造出来的东西长什么样. 上一篇讲的那个
用到才建的性质在这里帮了大忙: 你换掉 `config` 的时候, 模型还没被建出来.

> 三个手段, 一条共同的线: **先想清楚你要测的到底是什么, 再决定要替换掉多少东西.** 替换得
> 太少测试就慢又脆, 替换得太多就只是在测你自己的假设.

## 7. 那些真的需要外部世界的事怎么办

诚实一点: 有些事**没法在没有 PostgreSQL 的情况下验**.

比如第 15 篇讲的那个 `search_path` 到底钉不钉得住, 又比如同步是不是真的把每一行都搬过去
了. 这些东西的正确性只存在于一个真的 PostgreSQL 上.

**这个仓库的做法是: 不把它们塞进 pytest.**

它们由你手动跑的那几条命令覆盖: `mise run cli-test-db-conn`, `sync-db`, `verify-db`.
你在第 13 篇和第 15 篇已经跑过了.

**为什么不塞进去?** 因为塞进去就等于给整套测试加了一个前置条件: 你得先配好数据库凭据.
于是一个刚 clone 下来的人跑测试, 收到的是一片红色, 而那片红色和他的代码毫无关系.

> **一条判据**: 一个测试如果在一台干净的机器上必然失败,
> 那它不属于那套**每次改完都要跑一遍** 的测试. 它是一个验证步骤, 该有它自己的入口和自己的
> 时机.

这条线画在哪儿是有代价的, 要认: 这个仓库确实有一部分正确性不被自动检查, 只被人跑一次.
第 32 篇 (内容检查) 会接着讲这一类没有自动检查的东西还剩哪些.

## 8. 覆盖率: 它说了什么, 没说什么

跑一次带覆盖率的测试:

```bash
mise run cov
```

你会在最后看到一张表, 每个模块一行, 最后一行是总计. 现在这个仓库大概是这样:

```text
TOTAL                                879      4    99%
```

数字本身不重要, 重要的是**你该从它这里读出什么**.

### 它说的是: 这一行被执行过

仅此而已. 覆盖率是一个**执行过没有** 的统计, 不是**测对了没有** 的统计.

一个 100% 覆盖的模块, 完全可能:

- 每个函数都被调用过, 但一个断言都没写
- 断言写了, 但断言的是错的东西
- 正常路径全测了, 而所有出错的分支只是恰好被走到, 没人验它们的行为对不对

**所以 100% 不是目标, 它是一个下限.** 它能告诉你哪些代码**肯定** 没被测到, 但不能告诉你
被测到的那些**测得好不好**.

### 那它有什么用

它最有用的时刻不是看总数, 是**看那几行红的**.

一个模块突然掉到 80%, 意味着有一块代码没有任何测试碰过它. 这时候值得问一句: 是忘了写,
还是这块代码本来就走不到? 前者去补, 后者就轮到下一节那个标记了.

## 9. 什么时候可以说这行不算

有些行是真的测不了. Python 提供了一个标记, 打上它, 覆盖率统计就跳过这一行.

**这个标记很容易被滥用成懒得测的挡箭牌**, 所以要有判据. 这个仓库用的是这一条:

> **给这行写一个测试, 需要一台这里没有的机器, 还是根本写不出有意义的断言?**

两者之一才够格. 只是懒得写不够格.

现在这个仓库一共 24 处, 分四类:

| 类 | 大概几处 | 例子 |
| :--- | :--- | :--- |
| **真的够不到的外部依赖** | 九处 | 建 AWS session, 建真的模型, 往真的 PostgreSQL 写数据 |
| **走不到的防御分支** | 八处 | 那个为了将来加第三个部署目标而留着的 `else: raise` |
| 只为类型检查存在的 import | 五处 | 那几个 `if TYPE_CHECKING:` |
| 测试工具自己 | 两处 | 不是被测代码 |

**第二类值得多想一下**, 因为它反直觉: 那些分支不是测不了, 是**测了也没意义**.

拿第 30 篇提过的那个例子: 那个判断跑在哪个环境的函数, 最后有一个走不到的 `else: raise`.
今天它定义上就走不到 (本地被定义成不是 Vercel). 给它编一个测试, 测的是那句 `raise` 本身.

那为什么不干脆删掉它? 因为它是留给**将来加第三个部署目标却忘了改这里** 的那个人的. 那一天
它会响, 而不是静默地拿到本地配置.

> **配套判据**: 删掉这个分支会不会让代码更危险? 会 -> 留着并打标记; 不会 -> 那它是死代码,
> 删掉, 而不是打标记.

**打标记的时候顺手写一句为什么.** 这个仓库里有几处是这么写的:

```text
pragma: no cover - needs AWS
pragma: no cover - builds a real Agent
pragma: no cover - needs an unsynced schema
```

一眼就知道它属于哪一类. 没写的那些靠上下文自明, 新加的时候请写上.

## 10. 有一条测试守着一条架构规矩

最后一件事, 它和上面所有内容都不太一样.

第 7 篇 ([教学层和生产层](../07-teaching-and-production/README-cn.md)) 讲过一条边界:
**生产路径不许 import 教学层**. 因为教学层是要被整块删掉的, 一旦生产代码 import 了它,
删教学材料就会把应用一起弄坏.

这条规矩没有写成文档了事, 它被写成了一个测试.

那个测试不跑任何业务代码. 它把几个源文件当文本读进来, 解析成语法树, 然后
**看它们的 import 语句里有没有出现教学层那个模块**.

### 为什么这条值得写成测试

因为**靠人自觉守不住**.

想象半年后有人打开代码, 想着启动的时候顺手检查一下数据库有没有数据吧. 那个检查的代码正好
在教学层里, 于是他加了一行 import. 这一行:

- 不报错
- 不影响任何功能
- 所有别的测试照常绿
- 而它把整个应用钉死在了教学层上

**它只在有人真的去删教学层的那一天暴露**, 而那一天通常是交付前一小时.

一条能被机械判断的规矩, 加上一个不这么做会静默地坏的后果, 就够格写成测试.

> **一条可以带走的判据**: 你想写进文档的那条规矩, 先问一句 **它能不能被机械判断**. 能的话
> 写成测试, 因为文档挡不住任何人, 而一个红色的测试挡得住.

这个思路不止用在架构上. 你在第 32 篇会看到同一个思路用在**内容** 上: 提示词里的表名对不对,
界面上那 12 个按钮的配额齐不齐, 也都被写成了检查.

## 11. 练习

### 练习 1: 掐掉网络, 跑一遍全套

**目标:** 亲手证明那句一个测试都不连网, 而不是相信它.

**这个练习不需要任何凭据, 不需要数据库, 也不需要联网.**

**怎么做:**

1. 先正常跑一次, 记下用了多少秒:

```bash
mise run test-python
```

2. 再跑那个掐网络的脚本:

```bash
.venv/bin/python examples/31-tests-without-network/01_cut_the_network.py
```

3. 对比两次的用例数和耗时, 应该几乎一样
4. 打开这个脚本, 读它是怎么掐的, 一共就三行, 把负责建连接的那几个函数换掉
5. 现在跑一次带覆盖率的:

```bash
mise run cov
```

6. 看最后那张表, 找出**唯一一个不是 100% 的模块**, 想一想它为什么是例外

**你会观察到:**

第 3 步两次的耗时都在几秒的量级. 一套连数据库的测试不可能这么快, **速度本身就是证据**.

第 6 步那个不到 100% 的模块是那个命令行入口. 它的几行没被覆盖, 因为那几行只有在真的从终端
敲命令时才会走到.

> **关键洞见:** 一套跑得飞快的测试和一套跑得慢的测试, 差别不只是等待时间. 快到你会在每次
> 改动后顺手跑一遍的测试, 才真的在保护你; 慢到你要等的测试, 迟早会变成你提交前跳过的那一步.

### 练习 2: 给六行代码判一次该不该打标记

**目标:** 把那条判据用起来, 而不是记住.

**怎么做:**

1. 打开这几个文件, 找到带那个标记的行:

```bash
grep -rn "pragma: no cover" agent_app/
```

2. 挑出**三处**, 各判断它属于四类里的哪一类: 够不到的外部依赖, 走不到的防御分支,
   只为类型检查的 import, 还是测试工具自己
3. 然后判断下面六个假想的情况, 各回答一句该不该打这个标记, 理由用那条判据:

| 情况 | 该打吗 |
| :--- | :--- |
| 一个函数要往真的 S3 上传文件 | |
| 一个 `except Exception: pass`, 你想不出什么情况会走到 | |
| 一个函数逻辑很绕, 写测试要花两小时 | |
| 一个 `if __name__ == "__main__":` 下面的几行 | |
| 一个为了将来加第三种数据库而留的 `raise NotImplementedError` | |
| 一段刚写完还没来得及写测试的新功能 | |

4. 第二条和第五条长得很像, 但答案不一样. 说清差在哪

**你会观察到:**

第三条和第六条都是不该打. 它们的共同点是: 那行代码**能被测**, 只是你现在不想测. 判据里
那句这里没有的机器和写不出有意义的断言, 一条都不满足.

第二条和第五条的区别在于**删掉它会不会让代码更危险**. 那个想不出什么情况会走到的
`except`, 如果删掉之后一个真实的异常会直接冒到用户面前, 那它就该留着并打标记; 如果删掉
之后什么都不会变, 那它是死代码.

> **关键洞见:** 不计入覆盖率这个标记不是一句我测不了, 是一句**声明**: 这行代码的正确性
> 只能靠真跑一次来证明. 所以它后面该跟一个为什么.

## 12. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 三类依赖三种手段 | 数据库换成内存里的真库或者干脆手搓结构, AWS 用真实现 moto, 模型根本不叫只验它怎么建的 |
| 为什么不用手写假对象 | 手写的假对象断言的是作者对接口形状的信念. 信念错了, 代码和假对象一起错, 测试照样绿 |
| 真实现白捡两件事 | 计数器真的在累加可以被断言, 故障是那个库真正会抛的异常 |
| 需要真外部世界的事 | 不塞进 pytest. 它们由你手动跑的那几条命令覆盖, 有自己的入口和时机 |
| 判据 | 一个测试如果在一台干净的机器上必然失败, 它就不属于每次改完都跑一遍的那一套 |
| 覆盖率说了什么 | 只说这一行被执行过. 不说测对了没有. 100% 是下限不是目标 |
| 覆盖率最有用的时刻 | 不是看总数, 是看那几行红的, 然后问是忘了写还是本来走不到 |
| 打标记的判据 | 需要一台这里没有的机器, 或者根本写不出有意义的断言. 懒得测不算 |
| 配套判据 | 删掉这个分支会不会让代码更危险. 不会的话它是死代码, 该删不该打标记 |
| 什么规矩值得写成测试 | 能被机械判断, 而且破了会静默地坏. 文档挡不住人, 红色的测试挡得住 |

## 13. 导师寄语

**为什么这一篇讲的是判断而不是写法:**

写一个测试是很容易学会的事, 一个下午就够. 而真正区分人的是三个判断:
**这个东西值不值得测, 外部世界要换掉多少, 以及什么时候可以说这行不算.**

这三个判断都没有标准答案, 但它们都有判据. 这一篇给的就是判据, 不是模板.

**还有一件事想说.** 很多人把测试理解成一种交作业式的负担: 功能做完了, 再补一批测试.
那样写出来的测试确实是负担, 因为它们只在证明代码做了它已经做的事.

而这一篇里那条守着架构边界的测试是另一种东西: 它不验证任何功能, 它**保护一个决定**.
半年后那个想顺手加一行 import 的人, 会被它拦住, 而拦住他的成本是一次红色, 不是一次事故.

**你以后自己做项目时, 值得先问一句: 这个项目里有没有哪条规矩, 破了不会有任何人发现?**
有的话, 那就是最值得写测试的地方, 比任何一个业务函数都值得.

**关键洞见:**

- 换外部世界的分寸: 换得太少测试又慢又脆, 换得太多就只是在测你自己的假设
- 手写的假对象验的是你的信念, 真实现验的是接口本身
- 覆盖率是下限不是目标. 它能告诉你哪些肯定没测到, 不能告诉你测到的测得好不好
- 一条能被机械判断而且破了会静默坏掉的规矩, 值得写成测试而不是写进文档

**下一步:**

这一篇讲的是**代码** 的检查. 但这个项目里还有一大块东西不是代码: 提示词, 界面文案, 那 12
个按钮, 数据本身. 它们一样会错, 而且一样不报错. 第 32 篇
([内容检查](../32-content-checks/README-cn.md)) 讲那一半, 以及一条更难的判断:
**什么东西根本不该做成自动检查.**
