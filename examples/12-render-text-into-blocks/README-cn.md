# 一段纯文本怎么变成表格, 流程图和图表

> agent 从头到尾只交给前端一样东西: 一段 Markdown 字符串. 屏幕上那些图, 全是从这一段字里
> 长出来的.

## 1. 概览

这是前端那一组的最后一篇, 也是这一组里唯一一篇讲**动态内容** 的.

前面几篇里, 屏幕上的东西都能用第 8 篇那个三步法搜到源头: 你看到一句话, 搜一下, 找到
[`data/site.toml`](../../data/site.toml). 但 agent 的回答搜不到, 因为它**不在任何文件里**, 它是每次现生成的.

那么问题来了: agent 交回来的是一段纯文本, 屏幕上却出现了带边框的表格, 画好的流程图, 带坐标
轴的柱状图. **这个转换发生在哪儿?**

答案比你想的短: **一行代码.** 这一篇讲那一行, 以及围绕它的几个决定.

---

## 2. 学习目标

这一层有一个反直觉的性质, 而它是这一篇最值得带走的东西.

agent 的回答是**一个字一个字流过来的**. 所以在它写完之前,
页面上一定存在一个**没有闭合的代码围栏**: 一段写到一半的流程图语法, 一个被截断的 JSON.

对这一层来说, 这不是边缘情况, 是**每一次画图的必经状态**. 一次回答里可能有几十次渲染, 其中
前面几十次全都是失败的.

于是这一层的错误处理写法和你在别处见到的完全相反: **解析失败不是异常, 是正常路径.** 解析
不了就先显示原始代码, 等收尾的围栏到了再变成图.

理解了这一点, 你才看得懂这几个组件为什么长成那样, 也才知道流式界面该怎么设计.

学完这个 Task, 你将能够:

1. 指出那段文本变成表格和图的分发点在哪一行, 以及它靠什么区分行内代码和围栏块
2. 解释为什么这一层的失败路径是正常路径, 而不是异常处理
3. 说出那张查找表怎么控制支持哪几种块, 加一行和删一行各意味着什么
4. 说清两个渲染器各自的取舍: 一个按需加载近 1MB 的包, 一个手写 SVG 零依赖
5. 说出加一种新块要走哪三步, 以及为什么第三步在后端而且最常被忘

## 5. agent 交回来的只是一段文本

先把边界划清楚.

后端从模型那里拿到东西之后, 交给前端的只有两个字符串: 一段思考, 一段回答. 都是纯文本, 没有
任何结构.

那段回答里长这样:

```text
Grade C 的实际违约率比它的定价假设高了 3.9 个百分点.

| 等级 | 隐含违约率 | 实际违约率 | 缺口 |
| --- | --- | --- | --- |
| A | 3.0% | 3.9% | -0.9 |
| C | 6.0% | 9.9% | -3.9 |
```

也就是说, **表格是用 Markdown 的表格语法写出来的**, 只是一堆竖线和横线. 那些图也一样: 它们
是带语言标记的代码围栏, 里面装着流程图语法或者一段 JSON.

屏幕上那些漂亮的东西, 全部是前端把这段纯文本解释出来的结果.

**这个设计有一个很实际的好处**: 后端和模型之间不需要约定任何结构化的返回格式. 模型只要会
写 Markdown 就行, 而它本来就会.

## 6. 分发点只有一行

那段文本交给一个 Markdown 渲染库, 而这个项目给它传了一组自定义组件, 告诉它每一种元素该怎么
画: 段落怎么画, 表格怎么画, 链接怎么画.

其中管代码的那一个, 就是整个块渲染层的开关:

```tsx
code: ({ className, children }) => {
  if (!className) return <code className="...">{children}</code>
  const language = /language-(\w+)/.exec(className)?.[1] ?? ''
  const Block = getBlockRenderer(language)
  return <Block source={String(children).replace(/\n$/, '')} language={language} />
}
```

看不懂语法没关系, 它做的事只有两件:

**第一, 分清行内代码和围栏块.** 判据很简单: **行内代码没有语言标记, 围栏块有.** 一个用反引号
包起来的词是前者, 一个三个反引号加语言名开头的块是后者.

**第二, 拿语言名去查一张表**, 查到谁就用谁来渲染.

表格不走这条路, 它由那组自定义组件里管表格的那几个直接画. 所以**表格是免费的**: Markdown
本来就支持表格语法, 项目只是给它套了个好看的样式.

### 还有一个配套设置容易漏

那组自定义组件里, 管代码块外层容器的那一个是**直接透传的**, 什么都不做.

因为围栏块自己会渲染外层容器, 再包一层就会得到容器套容器, 或者一个块级元素被塞进一个不该
装它的标签里. 这类问题不会报错, 只会让页面排版莫名其妙地歪掉.

## 7. 那张查找表

```ts
const BLOCK_RENDERERS: Record<string, ComponentType<BlockProps>> = {
  mermaid: MermaidBlock,
  chart: ChartBlock,
}
```

整张表就这么长. 规则是一句话: **加一行支持一种块, 删一行关掉一种.**

没在表里的语言, 包括普通的 Python 代码块, 全部落到一个兜底的代码块渲染器, 显示成带语法高亮
的原始代码.

### 这张表为什么不放进文案文件

第 9 篇立了一条规矩: 会变的东西集中到 [`data/`](../../data). 那为什么这张表不在那儿?

因为它装的不是**这个数据集说什么**, 是**这个 app 能渲染什么**. 这两件事换的频率完全不同:
换一个业务领域, 文案全部重写, 而这个 app 能画哪几种图一点没变.

判据还是那条老规矩: **换个业务领域, 它要不要改?** 不改, 所以它归代码.

### 别和按钮上那个徽章搞混

第 11 篇讲的那个 `render` 字段和这张表长得有点像, 但它们是两件事:

| | 那 12 条的 `render` | 这张查找表 |
| :--- | :--- | :--- |
| 是什么 | 按钮对读者的**承诺**, 画在按钮上的小图标 | 真正决定一个围栏块怎么被渲染的**开关** |
| 谁读它 | 前端画徽章 | 前端选渲染器 |
| 它能让块出现吗 | **不能** | 能 |

**真正让块出现的是 agent 输出里那个围栏和它的语言名**, 而 agent 会不会输出, 取决于系统提示词
有没有教它. 这三方怎么对上是一份完整的契约, 第 34 篇 (渲染契约) 会一次讲完.

## 8. 失败是正常路径

这是这一篇最重要的一节.

再说一遍那个场景: 回答是流式到达的, 所以在写完之前, 页面上一定有一个**没闭合的围栏**.

假设 agent 正在写一张流程图, 那么这一层在半秒钟内会依次收到:

```text
第 1 次:  flowchart TD
第 2 次:  flowchart TD\n  A[申请]
第 3 次:  flowchart TD\n  A[申请] --> B[审
...
第 N 次:  完整的一张图
```

前面 N 减 1 次全都解析不了. 于是每个渲染器都这么写:

```text
解析不了  ->  退回显示原始代码
```

读者先看到原始代码, 收尾的围栏一到就变成图. **这不是错误处理, 是这个功能的正常工作方式.**

### 失败还必须是局部的

模型迟早会吐出一张语法非法的图. 这时候整个渲染被包在一个捕获里,
**一张坏图只损失它自己那一个块**, 不影响这条消息, 更不影响整个对话.

用户永远看得到内容, 最差也是一段可读的代码文本, 不会白屏.

**这两条合起来是一条通用的设计原则**: 一个持续接收不完整输入的界面, 它的降级形态必须比它的
完整形态只差一点点, 而不是差一整块. 这里那个降级形态是原始代码, 而原始代码本身就是可读的.

## 9. 两个渲染器, 两种取舍

这两个渲染器解决的是同一类问题, 选的路却相反, 对照着看很有意思.

| | 流程图 | 图表 |
| :--- | :--- | :--- |
| 用了什么 | 一个第三方库, 打包后接近 1MB | **零依赖, 手写 SVG** |
| 怎么加载 | **按需**. 页面遇到第一个流程图块时才去下载, 之后所有块复用同一次加载 | 不需要, 代码本来就很小 |
| 为什么这么选 | 画流程图这件事复杂到不值得自己写, 但大部分对话里一张图都没有, 所以不能让它拖慢首次加载 | 柱状图和折线图各自几十行就能写完, 而引一个图表库起步就是几百 KB |

### 流程图那边三个不能改的细节

**安全等级设成严格.** 图的源码来自模型, 而模型又在转述数据库内容. 严格模式会把输出过一遍
消毒并禁掉 HTML 标签, **这是那行直接插入 HTML 的代码唯一可以被接受的理由**.

**先解析再渲染.** 解析函数在源码不合法或者不完整时会抛异常, 这比让渲染失败再去收拾便宜.

**卸载时清理临时节点.** 一次失败的渲染会把库用来测量的临时节点留在页面上. 不清的话它们会
在整个页面生命周期里累积.

### 图表那边: 解析器假设输入是敌意的

生产这段 JSON 的是一个模型, 所以解析器对任何不严格符合形状的输入**一律返回空**, 调用方退回
显示原始 JSON.

硬性规则包括: 类型只能是柱状或折线; 最多四个数据系列, 最多二十四个分类;
**每个系列的值的数量必须等于分类的数量**; 值必须是有限的数字.

最后那条不是洁癖.
**少一格会画出一根高度是非数字的柱子, 它渲染出来什么都没有, 看起来就像一个真实的零值.**
一个看起来合理的错数字, 比一个明显的报错危险得多.

流式期间那半截 JSON 走的是同一条返回空的路径, **所以不需要另外一个是不是还在流的信号**.

## 10. 加一种新块: 三步, 第三步在后端

假设你想加一种时间线的块. 步骤是:

1. 在 [`components/chat/blocks/`](../../components/chat/blocks) 下写一个组件, 解析失败时退回那个兜底的代码块渲染器
2. 在那张查找表里加一行
3. **在 [`data/system-prompt.md`](../../data/system-prompt.md) 里告诉 agent 什么时候产出这种块**

**第三步是分界线, 也是最常被忘的一步.**

因为**前端认得一个格式, 不等于模型会输出它**. 跳过第三步的结果是: 你写的那个渲染器一行代码
都跑不到, 而前端测试全绿, 你会以为功能做完了.

这个坑值得单独记住, 因为它是一整类问题的代表: **一个功能横跨两侧, 而只有一侧有测试.**

如果这种块还要进 kickstart 那个橱窗, 那就是第四步: 在文案文件里分配配额, 在徽章组件里加图标.
完整规则第 34 篇讲.

## 13. 导师寄语

**为什么失败是正常路径这一条值得记一辈子:**

绝大多数人写代码时的默认假设是: 输入是完整的, 解析失败是异常. 这个假设在批处理的世界里没
问题, 但在任何**流式** 的场景里都是错的.

而 AI 应用几乎全是流式的. 模型一个字一个字地吐, 你的界面就必须在每一个中间状态下都是可用
的. 这时候你要设计的不是错误处理, 是**降级形态**: 东西还没到齐的时候, 用户看到的是什么.

这个项目的答案是原始代码, 因为它恰好本身就可读. 你以后做别的流式功能时, 第一个要想的问题
就是这个: 我的降级形态是什么, 它有多难看.

**关键洞见:**

- 流式界面里, 解析失败是每一次成功前的必经状态, 不是异常
- 降级形态要只比完整形态差一点点, 不能差一整块
- 一个功能横跨前后端而只有一侧有测试时, 写下来是唯一的保险

**下一步:**

前端这一组到此结束. 你已经把界面翻了个遍, 而且全程一个账号都没注册.

下一篇 ([接上真数据和真模型](../13-light-it-up/README-cn.md)) 要花钱了: 一把模型的 key,
一个云端数据库, 一份造出来的数据. 补完这三样, 第 5 篇那条报错就消失了, agent 会真的回答
你.

**这是整门课唯一一次真正的门槛**, 而它被放在这里, 是因为你现在已经清楚自己在给什么东西
付钱.

**图表的 JSON 形状:**

```json
{
  "type": "bar",
  "title": "Actual default rate by risk grade",
  "yLabel": "%",
  "categories": ["A", "B", "C", "D", "E"],
  "series": [{ "name": "actual", "values": [3.9, 6.23, 9.89, 15.16, 18.91] }]
}
```

硬性规则: 类型只能是 `bar` 或 `line`; 最多 4 个系列, 最多 24 个分类; 每个系列的值的数量
必须等于分类数量; 值是纯数字, 不带单位不带百分号.
