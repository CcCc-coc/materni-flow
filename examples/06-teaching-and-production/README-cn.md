# 教学层和生产层

> 这个仓库同时是一个能拿出去的应用和一门教你造出它的课. 交付前要把课擦掉, 而这个动作能
> 不能干净地做完, 从第一天就决定了.

## 1. 概览

第 5 篇 (读一遍这个仓库) 那张地图把顶层目录分成了两半: 一半属于应用, 一半属于教学. 当时
只说了这条线存在, 这一篇讲它为什么必须存在, 以及靠什么撑着.

起点是一个具体的时刻: 你学完这门课, 把这个仓库换成自己那个行业的样子, 部署上线, 放进简历,
然后面试官点开链接.
**那一刻读它的人不再是你, 是他.**
而他期待看到的是一个工程师写的生产代码库.

**这个终点从第一天就该在你脑子里.** 你现在做的每一个决定, 都是在决定那一刻他会看到什么.

如果他读到的是一份带练习题的课件, 目录里躺着 `TICKET.md` 和验收清单, docstring 里在讲什么
是 mixin, 测试文件里写着这一课的 TDD 练习, 那这个项目立刻从我做的产品降级成我上过的课.

所以这个仓库有一个动作叫**擦掉教学痕迹**. 这一篇讲的就是怎么让那个动作变得又快又安全.

---

## 2. 学习目标

擦除这件事表面上是最后一步的收尾工作, 实际上它是一条**从第一天就要守住的架构边界**.

理由很简单: 擦除的质量完全取决于两层分得有多开. 分得开, 擦除就是删几个目录, 一行代码都不
用改, 删完跑一遍测试就知道成没成. 分不开, 擦除就是打开每个文件逐行判断哪句话是教学的然后
删掉, 而这件事**改代码**, 所以有风险, 而且一定删漏, 因为没人能证明自己删干净了.

这条边界还有一个更日常的好处, 你在第 7 篇会直接用到: 一个层次分明的仓库, 你派给 AI 的任务
才写得成一句话.

学完这个 Task, 你将能够:

1. 说清你手上这个仓库为什么现在就已经是可交付状态, 以及这对你动手改它意味着什么
2. 从一个干净基线开出自己的 branch, 并知道搞砸之后有哪三条退路
3. 说清擦除教学痕迹的两种做法, 以及为什么只有一种能用
4. 列出这个仓库的教学层包含哪些路径, 以及删掉它们之后剩下什么
5. 复述支撑这条边界的四条约束, 并各说出破坏它之后会怎样
6. 找到那条用 AST 扫 import 的测试, 并亲手让它红一次

## 5. 你手上这个仓库已经是成品了

在讲怎么擦之前, 先说清楚一件很多人到很后面才反应过来的事.

**你 clone 下来的这个仓库, 灌完数据之后就是一个完整能跑的 app.** 不是半成品, 不是缺了几块
等你补的骨架. 首页能看, agent 能答, 部署上去就有一个公开网址. 你一行代码都不用改.

而擦掉教学痕迹这件事, 到最后那一步是一条命令的事. 换句话说: ** 这个仓库现在就已经处在一个
可以交付的状态**, 只是身上还穿着课程这层外衣.

这件事有两个推论, 第二个比第一个重要得多.

**推论一**: 这门课的起点是成品不是白纸. 你后面每一次改动, 都是在一个已经能用的东西上改.

**推论二**: **你搞砸了, 大不了从头再来.** 那个能跑的基线一直在那儿, 而且它在 Git 里.

### 所以从这一篇开始, 动手之前先开一个 branch

前面几篇你只是读和跑, 顶多改一句文案再改回去. 从这里往后你会真的动代码了, 所以定一条纪律:

```bash
git switch -c dev 01-showcase
```

`01-showcase` 是这门课住的那个 branch, 它就是那个随时能跑, 随时能发布的基线. 你在从它分出去
的 `dev` 上折腾, 基线一直原封不动.

搞砸了有三条退路, 从轻到重:

| 情况 | 怎么办 |
| :--- | :--- |
| 想看看自己到底改了什么 | `git diff 01-showcase` |
| 这一处改坏了, 想单独修 | 让 AI 干: 对比一下 `01-showcase` 这个 branch, 我把某某地方搞砸了, 帮我修回去. 它读得到 diff, 就修得了 |
| 整个乱了, 不想救了 | `git switch 01-showcase`, 然后重新分一个 branch. 之前那个 `dev` 扔掉就行 |

中间那条值得单独记住. **一个能跑的基线加一个 diff, 就是 AI 修复问题所需要的全部信息.** 没有
基线, 你只能描述症状; 有基线, 你可以直接把两个版本摆在它面前.

这条纪律和这一篇的主题是同一件事: **都是在保证一个动作可以安全地重来.** 擦除之所以要退化成
删几个目录, 分支之所以要从一个干净基线上开, 理由是同一个. 一件能重来的事, 你才敢放手做.

## 6. 两种分法, 只有一种能用

先把两种做法摆在一起看, 差别不在于哪个更整洁, 在于**擦除那一刻你要做什么动作**.

| | 混在一起 | 分层 |
| :--- | :--- | :--- |
| 教学内容在哪 | 散在 docstring 和注释里, 教学脚本混在 `mise.toml` 里, 教学依赖混在 `pyproject.toml` 里 | 整块住在自己的目录里 |
| 擦除的动作 | 打开每个文件逐行看哪句话是教学的然后删掉 | `rm -rf` 几个路径 |
| 会不会改代码 | **会**, 所以有风险 | **不会**, 所以零风险 |
| 能不能验证擦干净了 | 不能. 没人能证明自己删漏没删漏 | 能. 删完跑一遍测试和内容检查 |

这个仓库选第二种. 而这个选择反过来给代码提了一堆约束, 因为
**要让擦除退化成删目录, 教学层就不能在任何一个生产文件里留下残渣**.

## 7. 哪些是教学层

| 路径 | 是什么 | 说明 |
| :--- | :--- | :--- |
| `README.md` `README-cn.md` `TICKET.md` | 这一课教什么, 任务和验收清单 | 仓库根目录那几份课程文档. 一个交付出去的产品仓库不会有验收清单 |
| `docs/` | 教学正文和开发者走读 | 分章节的教程和面向开发者的代码走读, 都是写给学生的, 不是写给产品用户的 |
| `examples/` | 你正在读的这些 Task | 每个编号目录一课, 一份教学正文加一份验收清单 |
| `.claude/skills/` | 给 AI 和维护者看的规范 | 讲这个仓库为什么长成这样, 哪条边界不能破. 它是内部记录, 露出去只显得项目还在建设中 |
| `dataset/` | 数据集的源材料和生成器 | 四份领域文档加一个造假数据的脚本. 成品仓库连的是一个已经灌好的数据库, 不需要带着造数据的工具 |
| `agent_app/dataset.py` | 造数据加同步 PostgreSQL 的代码 | 唯一一个住在生产代码包里的教学文件. 它是那条边界最容易被破坏的地方, 所以专门有测试守着 |
| `tests_python/test_dataset.py` | 上面那个模块的测试 | 跟着它一起删 |
| `scripts/` | 编号的安装与连通性验证脚本 | 配置自检, 跑 SQL, 同步, 逐个 LLM 供应商探活. 都是搭环境时用的一次性工具 |

**删掉它们之后剩下的是**: `agent_app/` (除 `dataset.py`), `api/`, `app/`, `components/`,
`lib/`, `data/`, 加上 `.env.defaults`. 那正好是一个连着 PostgreSQL 的 agent 应用, 而且
**一行代码都不用改**.

### 一个值得单独说的细节

`mise run check-content` 看起来最像会被牵连的那个: 它检查的四项里有两项要读 SQLite 种子,
而种子属于教学层.

处理办法是把那个 import **放在函数体里** 并接住 `ImportError`, 拿不到就把那两项降级成 SKIP,
其余两项照常跑.

这不是为了少改一行配置. 是因为剩下那两项 (内容文件在不在, 12 条 kickstart 的渲染配额对不
对) 在一个交付出去的仓库里**仍然有意义**, 它们守的是 `data/` 和前端之间的契约, 和课程无关.
一个模块级的 import 会让整条命令在教学层消失的那一刻带着报错死掉, 于是连那两项一起陪葬.

## 8. 支撑这条边界的四条约束

### 一, 生产路径不 import 教学层

`agent_app/one/*.py` 和 `ai_sdk_adapter.py`, 也就是一个 HTTP 请求真正走过的代码, 一行都不
import `agent_app.dataset`.

agent 通过数据库连接读 PostgreSQL, **数据怎么进去的不是它的事**.

这一条靠人自觉守不住. 总有一天有人想顺手在启动时检查一下数据库有没有数据吧, 而那一行
import 就把整个应用钉死在了教学层上: 删教学材料会把 app 一起删坏. 所以它有测试守着, 下一节
讲.

### 二, 教学自动化不进 `mise.toml`

造数据集, 同步到 PostgreSQL, 逐表核对, 这三条命令在教学层自己的 `teaching_cli.py` 里, 不在
`mise.toml` 里.

理由就是上面那条: `mise.toml` 跑的是**应用** (装依赖, 起服务, 跑测试). 教学层要能靠删目录
擦掉, 不该在一个共用配置文件里留下需要一行行挑出来删的残渣.

### 三, 教学依赖不进 `pyproject.toml`

生成器要 Faker, polars, pandas, pyarrow 这几个包, 它们写在 `dataset/requirements.txt`, 装
进同一个虚拟环境, 但**不出现在 `pyproject.toml` 里**.

同一个理由: 一个文件删掉, 而不是从依赖列表里挑几行出来. 副作用是好的, 生产部署不会去装一个
造假数据的库.

### 四, 代码里不出现指向教学材料的指针

**这条是单向的**: 教学文档可以随便引用代码路径, 代码**一律不引用教学文档**.

不要这么写, 因为擦掉那个目录之后, 这句话指向一个不存在的文件:

```python
"""... full format spec: .claude/skills/xxx-cn/ref/backend/04-schema-encoding.md"""
```

这种指针擦除时既不报错也不失败, 只是变成一句死链躺在成品里, 而且它明明白白写着
**这个项目是从一门课里长出来的**.

代码里只留很短的工程原因, 展开的部分放在文档里, 靠内容自己站住, 不靠交叉引用.

**例外是功能性的命令提示**: `dataset.py` 里那个告诉你哪条命令能重建数据库的字符串, 是错误
信息的一部分, 不是文档指针. 而且它住在教学模块自己里, 一起删.

## 9. 有一条测试在守着这条边界

第一条约束不能靠自觉, 所以它被写成了一个测试. 在 `tests_python/test_dataset.py` 的最后:

```python
class TestNotOnTheProductionPath:
    def test_the_app_does_not_import_the_authoring_layer(self):
```

它做的事很直接: 用 Python 自带的 `ast` 模块把 `agent_app/one/` 下每个文件和
`ai_sdk_adapter.py` 解析成语法树, 遍历所有 import 语句, 只要有一句 import 了名字以
`dataset` 结尾的模块, 就把那个文件记进违规名单, 最后断言名单是空的.

**为什么用 AST 而不是搜字符串**: 搜字符串会把注释里, 字符串里提到 dataset 的地方一起算进来,
于是这个检查开始误报, 而一个会误报的检查比没有检查更糟, 因为它会训练人忽略输出.

这是一个**模式, 不是一次性的做法**: 一条能被机械判断的架构约束, 值得写成测试而不是写成文档.
哪些约束够格写成测试, 第 31 篇 (测试) 会给判据.

## 10. 一条落地的判断

要往仓库里加东西时, 问一句:

> **它是这个 app 的一部分, 还是教怎么造这个 app 的一部分?**

后者就找一个**整块能删掉的地方** 放, 不要塞进任何一个前者要用的文件.

拿不准的时候, 想象一下删除的那一刻: 你是 `rm -rf` 一个目录, 还是打开文件逐行看? 答案是后者,
说明位置放错了.

这条判据和第 5 篇那条**换个业务领域它要不要改** 是正交的两根轴. 两条一起用, 一个新文件的
位置基本就定了.

## 11. 练习

### 练习 1: 亲手把那条测试弄红

**目标:** 确认那条边界不是一句口号, 而是真的有东西在拦.

**怎么做:**

1. 先跑一次确认它是绿的: `.venv/bin/pytest tests_python/test_dataset.py -k ProductionPath`
2. 打开 `agent_app/one/one_02_db.py`, 在 import 区加一行 `from agent_app import dataset`
3. 再跑一次那条测试
4. 读失败信息, 看它报的是哪个文件
5. 把那一行删掉, 再跑一次确认恢复绿

**你会观察到:**

第 3 步会失败, 而且违规名单里正好是 `one_02_db.py`. 注意这一行 import 本身**完全合法**,
Python 不会报任何错, 应用也照常跑. 拦住它的只有这条测试.

> **关键洞见:** 一条架构约束如果只写在文档里, 它的寿命等于下一个人读不读文档. 写成测试之后,
> 它的寿命等于这个测试还在不在.

### 练习 2: 找出那两处指向教学材料的指针

**目标:** 用第四条约束去审真实代码, 并判断哪一处是例外, 哪一处不是.

**怎么做:**

1. 在仓库根目录跑一次搜索, 找生产代码里提到教学路径的地方:

```bash
grep -rn "\.claude/skills" agent_app/ api/ --include='*.py'
```

2. 你会找到两处. 逐一判断: 擦掉 `.claude/skills/` 之后, 这句话会变成死链吗
3. 对照第 7 节第四条那个例外的定义: 它是不是功能性的命令提示, 它住不住在教学模块自己里
4. 再看一眼 `mise.toml`, 确认没有任何一个 `run =` 指向 `scripts/`

**你会观察到:**

两处的性质不一样. 一处在 `agent_app/dataset.py` 里, 是错误信息里那条重建数据库的命令, 而且
那个文件本身就要被删掉, 属于规范说的例外. 另一处在 `agent_app/cli.py` 的模块文档里, 而
`cli.py` 是应用自己的命令行, **它会跟着成品一起交付出去**.

> **关键洞见:** 规矩和现实之间有出入是常态, 这一处出入本身就是这条约束为什么难守的证据:
> 它不报错, 不失败, 没有任何检查会提醒你, 只有人拿着规矩去读才发现得了.

## 13. 导师寄语

**为什么这条边界值得这么较真:**

大多数人第一次听到擦掉教学痕迹, 想的是最后花半天清理一遍. 真到那一天你会发现, 半天根本不
够, 而且你永远不确定删干净了没有. 于是最后要么留着一堆痕迹交付, 要么删过头把 app 弄坏.

这件事和写代码时的很多决定是同一类: **代价不在做的那一刻, 在很久以后**. 而一个好的架构选择,
就是把那个未来的代价提前压到接近零.

**关键洞见:**

- 一个动作能不能安全地做完, 取决于结构而不是取决于做的时候小不小心
- 一件能重来的事你才敢放手做. 干净的基线加一个 branch, 买的就是这个
- 能机械判断的约束写成测试, 判断不了的写成文档. 两者都比写在某个人脑子里强
- 会误报的检查比没有检查更糟, 因为它会训练人忽略输出

**下一步:**

这条边界还有一个副作用: 层次分明的仓库, 给 AI 派活时任务写得成一句话. 第 7 篇 (和 AI 一起
改这个仓库) 讲这件事, 以及这个仓库给 AI 准备了哪三套东西.

## 14. 速查

**动手之前:**

```bash
git switch -c dev 01-showcase
```

**搞砸了:**

```bash
git diff 01-showcase        # 看自己改了什么
git switch 01-showcase      # 整个不要了, 换回基线重开
```
