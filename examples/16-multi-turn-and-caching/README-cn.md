# 多轮对话和 prompt caching

> 模型没有记忆. 你每次都要把整段对话重新说一遍给它听, 而那正是账单增长的地方.

## 1. 概览

第 15 篇发了一次请求拿到一次回答. 这一篇加上记忆.

但这里有一件事和大多数人的直觉相反, 而且它是这一篇的全部基础:

> **模型本身完全不记得上一句话.**

每一次调用对它来说都是全新的. 你在网页版聊天工具里感受到的那种连贯, 不是模型记住了, 是
**那个产品每次都把整段历史重新发了一遍**.

所以这一篇讲两件事:

| 讲什么 | 因为 |
| :--- | :--- |
| 怎么把历史管起来 | 这是让对话成为对话的唯一机制, 而且它比你想的简单 |
| prompt caching | 每次重发历史意味着账单一路涨, 而缓存是各家给出的答案 |

这一篇的目录下有**五个能直接跑的脚本**, 和第 15 篇一样, 不用你改任何东西.

## 2. 学习目标

先算一笔很具体的账, 它解释了为什么这一篇后半段要讲缓存.

跑一下这一篇第一个脚本, 三轮对话下来你会看到输入 token 是这样的:

```text
Turn 1   in: 33
Turn 2   in: 58
Turn 3   in: 79
```

**你的问题长度几乎没变, 但输入一路涨.** 涨的部分就是被重新送了一遍的历史.

现在把这个放大到真实场景: 这个 app 的系统提示词有好几千 token, 而且
**每一次请求都要完整送一遍**. 一个用户聊十轮, 那份提示词就被送了十遍, 你付了十次钱, 而它
一个字都没变过.

缓存要解决的正是这一块. 而理解它的关键不在于怎么开, 在于**知道它省的是什么**.

学完这个 Task, 你将能够:

1. 解释模型没有记忆这件事, 以及对话的连贯感实际上是谁做的
2. 说清一段对话在代码里其实就是一个列表, 以及每一轮往里加了什么
3. 说清三家在历史结构上的差别, 尤其是系统提示词在不在历史里
4. 说清把那三步收进一个方法之后, 买到的到底是什么
5. 读懂一次缓存命中的数字, 并说出缓存省的到底是什么

## 6. 一段对话到底是怎么被记住的

好, 我们慢慢来看这件事.

你先想一下你平时用聊天工具的感觉. 你说一句, 它答一句; 你再说一句, 它好像还记得刚才那句.
所以你很自然地会以为, 那个记忆在模型那边 —— 你说过的话被它存下来了.

**不是的.** 模型那边什么都没存.

那要怎么办呢? 只有一个办法: **你自己存.** 你在自己的程序里开一个列表, 每说一句就往里塞一
条, 然后**每次提问都把这个列表整个交给模型**.

模型看到的不是你刚说的那一句, 它看到的是一整份对话记录, 从头到尾. 它读完这份记录, 顺着往下
接一句. 所以它看起来像是记得, 其实它只是**每次都重新读了一遍**.

### 那这个列表长什么样

就是一个普通的列表, 每一项是一条消息, 每条消息两件事: **谁说的**, 和**说了什么**.

打开 [`01_openai_multi_turn.py`](01_openai_multi_turn.py), 你会看到它一开始长这样:

```python
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},
]
```

一条. 里面那个 `role` 就是谁说的, `content` 就是说了什么. 这一条的角色叫 `system`, 是给
模型立规矩用的, 说完就不动了.

然后循环开始跑, 每一轮往这个列表里**加两条**: 你说的一条, 模型答的一条.

三轮之后它变成了七条:

```text
[0] system     你是一个助手, 回答简短一点
[1] user       我最喜欢的数字是 7
[2] assistant  好的, 记住了
[3] user       把它翻倍
[4] assistant  14
[5] user       翻倍之前是多少?
[6] assistant  7
```

**就这么简单.** 没有数据库, 没有魔法, 就是一个 Python 列表躺在你的程序里.

而第三轮那个问题之所以答得上来, 是因为**第 1 条还在列表里**, 而整个列表都被送上去了.

### 每一轮实际上做了三件事

现在看那个循环. 每一轮就三步, 而且这三步在任何一家供应商都一样:

**第一步, 把你要说的话塞进列表.**

```python
messages.append({"role": "user", "content": question})
```

注意是**塞进去**, 不是替换. 之前说过的全都留着.

**第二步, 把整个列表发上去.**

```python
response = client.chat.completions.create(model=MODEL_ID, messages=messages)
```

看清楚这里传的是 `messages`, 是**整个列表**, 不是刚才那一句. 到第三轮的时候, 这个列表已经
有六条了, 六条全都重新上传一遍.

**第三步, 把模型的回答也塞回列表里.**

```python
answer = response.choices[0].message.content
messages.append({"role": "assistant", "content": answer})
```

**这一步是新手最常漏的那一步**, 我们下一小节专门说它.

三步做完, 这一轮结束. 下一轮回到第一步, 列表又长了两条.

### 漏掉第三步会怎样

这件事值得单独讲, 因为它的失败方式特别阴.

漏掉第三步, 意味着列表里只有你说过的话, 没有模型说过的话. 那会怎样呢?

| 第几轮 | 表现 |
| :--- | :--- |
| 第一轮 | **完全正常**. 因为第一轮本来就没有历史 |
| 第二轮 | 看起来也还行, 因为你的问题里通常自己带着上下文 |
| 第三轮往后 | 模型开始丢线索, 前后矛盾. **但一个错都不报** |

它不崩溃, 它只是慢慢变笨. 而这种问题特别难被发现, 因为你不会去怀疑一个跑得好好的循环 ——
你只会觉得这个模型有点傻.

**所以那三个问题是特意设计成一个测试的.** 你回头看一眼:

```text
1. 我最喜欢的数字是 7. 记一下就行.
2. 把我最喜欢的数字翻倍.
3. 翻倍之前是多少?
```

第三个问题**只有在模型看得见第一句的时候才答得上来**. 答对了, 说明历史是完整的; 答不上来,
说明某一步漏了.

这是一个能**当场判真假** 的测试, 比你回头读代码可靠得多. 练习 2 会让你亲手把它弄坏一次.

## 7. 换一家供应商, 变的是什么

跑过两个以上的脚本, 你会发现最后那行统计对不上:

| 脚本 | 三轮之后列表里有几条 |
| :--- | :--- |
| OpenAI | **7** |
| Anthropic | 6 |
| Google | 6 |

差的那一条是**系统提示词**.

OpenAI 把它当成列表里的第一条消息, 所以它在列表里. 另外两家把它当成一个**独立的参数**,
每次调用单独传, 所以它不在列表里.

打开 [`02_anthropic_multi_turn.py`](02_anthropic_multi_turn.py) 对比一下就很清楚了. 它的
列表是空着开始的:

```python
messages = []
```

而系统提示词在发请求的时候单独给:

```python
response = client.messages.create(
    model=MODEL_ID,
    max_tokens=200,
    system=SYSTEM_PROMPT,      # 单独一个参数, 不在 messages 里
    messages=messages,
)
```

这正是第 15 篇 ([直接调模型](../15-call-the-model-directly/README-cn.md)) 那张对照表第一行
的后果. 那时候只是一个静态的差别, 现在你看到它**决定了历史列表的第一条是什么**.

还有一处小差别: 模型那一方的角色名, OpenAI 和 Anthropic 叫 `assistant`, Google 叫 `model`.
三家, 三套词汇, 同一个意思.

### 一个容易误会的地方

系统提示词在列表外面, **不代表它只发一次**.

它每次调用都要重新发. 它和历史一样不被记住. 看那段代码, `system=SYSTEM_PROMPT` 是写在循环
里面的, 每一轮都执行一次.

这一点等一下讲缓存的时候会变得很重要, 因为系统提示词恰好是**最长而且最不变** 的那一块.

## 8. 抽象: 把重复的三步收起来

好, 现在你已经知道那三步是什么了. 我们来看第四个脚本
[`04_chat_session.py`](04_chat_session.py), 它干的事听起来很简单: 把那三步塞进一个方法里.

但这件事背后的道理值得多说两句, 因为**它是编程里最基础也最重要的一个动作**.

### 先看用起来是什么样

```python
session = ChatSession()
print(session.ask("我最喜欢的数字是 7."))
print(session.ask("把它翻倍."))
```

就这样. 没有列表, 没有 append, 没有 `response.choices[0].message.content`.

你只说了要说的话, 剩下的它替你办了.

### 那三步去哪了

它们没消失, 只是搬进了 `ask` 这个方法里面. 打开那个文件, 你会看到 `ask` 里面还是那三步,
一个不少:

```python
def ask(self, question: str) -> str:
    # 第一步: 塞进列表
    self._messages.append({"role": "user", "content": question})

    # 第二步: 整个列表发上去
    response = self._client.chat.completions.create(
        model=self.model_id,
        messages=self._messages,
    )

    # 第三步: 回答也塞回列表
    answer = response.choices[0].message.content
    self._messages.append({"role": "assistant", "content": answer})

    return answer
```

一模一样的三步, 只是从循环里搬到了方法里.

### 那这么做买到了什么

**买到的是: 调用方再也没有机会做错.**

想一下上一节那个漏掉第三步的 bug. 在第一个脚本里, 那三步是摊开在循环里的, 谁都可能少写一
行, 或者顺序写反. 而在这里, **那三步在方法内部, 外面根本看不到**, 也就没法漏.

这就是封装最朴素的价值, 而且它常常被讲错:

> **封装不是为了少写代码, 是为了让一类错误变得不可能发生.**

少写代码只是顺带的. 真正值钱的是那个不可能.

**这个模式你会一直用到.** 凡是遇到一组必须按顺序做, 而且做完还要记录点什么的动作, 就把它
收进一个方法里. 让外面的人只需要说要什么, 不需要知道怎么做.

### 一个实例等于一段对话

那个脚本最后特意干了一件事: 建了**第二个** 会话, 拿同一个追问去问它.

结果它答不上来. 真实输出是这样的:

```text
A fresh session, asked the same follow-up:
AI: I can't determine it without knowing the number after it was doubled.
```

**这不是 bug, 这正是你要的.** 服务两个不同的用户时, 你要的就是两段互不相干的对话.

而这在代码里是靠一个很不起眼的写法保证的:

```python
_messages: list[dict] = dataclasses.field(init=False, default_factory=list)
```

那个 `default_factory=list` 的意思是: **每建一个实例, 就现给它做一个新的空列表.**

如果写成看起来更自然的 `_messages: list = []`, 会踩一个经典的 Python 陷阱:
**所有实例会共享同一个列表**. 后果是两个用户的对话会渗进彼此, 而且
**这个 bug 在只有一个用户的时候永远不会出现** —— 你本地测一百遍都是好的, 上线以后才炸.

### 换一家供应商要改几行

这个类是照 OpenAI 写的. 换成另一家要改的只有三处: 建客户端那一行, 发请求那一段, 挖回答那
一行.

**这正是这个 app 自己那一层在干的事**, 只不过它把这三处的差别一次性写好, 覆盖四家, 然后
用一个环境变量切换. 你现在知道那一层底下是什么了.

## 9. Prompt caching: 省的到底是什么

第五个脚本把同一个长系统提示词发两次, 然后打印缓存计数器. 真实输出长这样:

```text
--- call 1 ---
input tokens:  3214
written to cache: 3211
read from cache:  0

--- call 2 ---
input tokens:  3214
written to cache: 0
read from cache:  3211
```

**盯着第一行看**: 两次调用的输入 token 数**完全一样**.

这是理解缓存最关键的一点:

> **缓存不让请求变小, 它让同样大的请求变便宜.**

你还是把那三千多个 token 发上去了. 变的是它们的计价: 第一次是写入缓存 (正常价格), 第二次是
从缓存读 (通常是正常价格的四分之一左右, 各家不同).

### 三条会咬人的规则

| 规则 | 后果 |
| :--- | :--- |
| **有最低长度门槛**, 大约一千 token | 低于门槛**静默不生效**. 不报错, 不警告, 计数器就是零. 你会以为开了 |
| **缓存匹配的是前缀** | 靠前的地方改一个字符, 后面全部失效. 所以**不变的内容必须放最前面** |
| **缓存会过期** | 通常是分钟级. 一个很久没人用的部署, 每次都是第一次 |

第二条决定了提示词的组织方式:
**把不变的东西 (领域知识, 表结构, 例子) 放在最前面, 把每次都变的东西放在最后.**
顺序反了, 缓存等于没开.

### 三家的开法不一样

| 供应商 | 怎么开 |
| :--- | :--- |
| OpenAI | **自动**. 没有参数要设, 够长就会命中. 这也是这个脚本选它的原因 |
| Anthropic | **显式**. 在内容块上标一个缓存控制字段, 计数器叫另外两个名字 |
| Google | 有隐式的, 也有需要你提前建好的显式缓存 |

**概念完全一样, 只有语法不同.** 想给另外两家写一遍的话, 让 AI 帮你, 但记得让它先说清用的是
哪个字段名, 然后你去对一眼那家的官方文档, 因为这一块的 API 变得比别处快.

Bedrock 的写法又不一样: 它要你在内容里插一个显式的缓存断点标记, 明确指出从哪儿往前可以缓存.

## 10. 练习

### 练习 1: 五个脚本跑一遍, 盯住三个数字

**目标:** 把这一篇讲的三件事各看到一次真实输出.

**怎么做:**

1. 跑多轮对话那个脚本 (选你有 key 的那一家):

```bash
.venv/bin/python examples/16-multi-turn-and-caching/01_openai_multi_turn.py
```

2. **盯住每一轮的输入 token 数**, 三个数抄下来. 再看第三轮那个问题它答对了没有
3. 打开那个脚本, 在循环里逐个指出**那三步** 分别是哪几行: 塞进列表, 整个列表发上去,
   把回答塞回列表
4. 数一数三轮之后列表里有几条, 每一条是谁说的
5. 如果你有第二家的 key, 跑另一个脚本; 没有就直接读代码. 对比最后那行统计,
   **说清条数为什么不一样**
6. 跑封装那个:

```bash
.venv/bin/python examples/16-multi-turn-and-caching/04_chat_session.py
```

7. 看最后那个新建的会话怎么回答, 然后在代码里找到那行 `default_factory=list`, 想清楚它和
   刚才那个回答的关系
8. 跑缓存那个:

```bash
.venv/bin/python examples/16-multi-turn-and-caching/05_prompt_caching.py
```

9. 对比两次调用的三个数字: 输入 token, 写进缓存, 从缓存读. **特别注意输入 token 有没有变**

**你会观察到:**

第 2 步那三个数一路上涨, 而你的问题长度几乎没变 —— 涨的部分就是被重新送了一遍的历史.

第 7 步那个新会话会说它不知道, 因为它是一个全新的列表. **这不是 bug, 这正是你要的.**

第 9 步最反直觉: 两次调用的**输入 token 完全一样**, 变的只是那两个缓存计数器. 缓存不让请求
变小, 它让同样大的请求变便宜.

> **关键洞见:** 这三件事都只能靠**看数字** 发现, 光读代码看不出来. 而它们全都不会报错 ——
> token 涨了不报错, 缓存没命中也不报错.

### 练习 2: 亲手弄坏一次对话

**目标:** 亲眼看到漏掉第三步的后果, 因为它不报错.

**怎么做:**

1. 开一个叫 `16-multi-turn-and-caching` 的 branch
2. 跑一次 `01_openai_multi_turn.py` (或者你有 key 的那一家), 确认第三轮答对了
3. 把第三步那一行**注释掉**, 也就是把回答追加回历史那一行
4. 再跑一次. 看三轮各自答成什么样
5. 恢复那一行
6. 再改一处: 把第二步发送的历史从整段改成只发最后一条, 再跑一次
7. 恢复

**你会观察到:**

第 4 步里第一轮完全正常, 第三轮开始答不上来了, **而且全程没有任何报错**. 第 6 步会更彻底,
连第二轮都会失败.

> **关键洞见:** 一个不会报错只会慢慢变笨的 bug, 是最难被发现的那一种. 所以那三个问题被设计
> 成一个能当场判真假的测试. 有这种测试的时候, 别只靠读代码.

| :--- | :--- |
| 模型有没有记忆 | **没有**. 连贯感是产品每次重发整段历史做出来的 |
| 那三步 | 把问题塞进列表, 整个列表发上去, 把回答也塞回列表. 三步缺一不可 |
| 漏掉第三步 | 不报错, 只是从第三轮开始慢慢变笨. 最难发现的那一类 bug |
| 三家的历史结构 | OpenAI 把系统提示词放进历史 (三轮后七条), 另外两家放外面 (六条) |
| 系统提示词也重发 | 它不在历史里不代表只发一次. 它是最长而且最不变的那块, 缓存收益最大 |
| 封装的价值 | 不是少写代码, 是让一类错误不可能发生 |
| 一个实例一段对话 | 靠 `default_factory=list` 保证. 写成共享的默认值是经典陷阱 |
| 缓存省的是什么 | **不让请求变小, 让同样大的请求变便宜**. 输入 token 数一点不变 |
| 缓存三条规则 | 有最低门槛且静默失效, 匹配前缀所以不变的放最前, 会过期 |
| 三家的开法 | OpenAI 自动, Anthropic 显式标记, Google 两种都有. 概念一样, 语法不同 |

## 12. 导师寄语

**为什么模型没有记忆这件事值得反复强调:**

这是所有做 AI 应用的人最早形成, 也最难改掉的一个错觉. 因为你日常用的那些聊天产品
**表现得太像有记忆了**, 你会不自觉地假设那个能力在模型里.

一旦你接受了模型没有记忆, 很多事情立刻讲得通: 为什么账单随对话长度增长, 为什么长对话要裁剪
或者总结, 为什么后端可以是无状态的, 为什么第 28 篇里每次请求都要把 agent 的记忆清空重建.

**它们全都是同一件事的推论.**

**关键洞见:**

- 模型没有记忆. 你感受到的连贯是产品做的, 不是模型做的
- 不报错只是慢慢变差的 bug 最贵. 给自己设计一个能当场判真假的测试
- 缓存不让请求变小, 它让同样大的请求变便宜. 而且它可能在你以为开着的时候根本没开

**下一步:**

模型这一侧到此为止. 从第 17 篇 (一个数据集包含什么) 开始转向数据: 这个 agent 查的那个数据库
是从哪儿来的, 那四份描述这个行业的文档又是干什么用的.

```bash
.venv/bin/python examples/16-multi-turn-and-caching/05_prompt_caching.py
```

**每一轮那三步:**

1. 把你要说的话塞进列表
2. 把整个列表发上去
3. **把模型的回答也塞回列表**

**缓存三条规则:**

- 有最低长度门槛, 低于它静默不生效
- 匹配前缀. 不变的内容放最前面, 每次都变的放最后
- 会过期, 通常是分钟级

**那句要记住的话:**

缓存不让请求变小, 它让同样大的请求变便宜.
