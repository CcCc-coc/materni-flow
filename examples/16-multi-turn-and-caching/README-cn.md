# 多轮对话和 prompt caching

> 模型没有记忆. 你每次都要把整段对话重新说一遍给它听, 而那正是账单增长的地方.

## 1. 概览

第 15 篇发了一次请求拿到一次回答. 这一篇加上记忆.

但这里有一件事和大多数人的直觉相反, 而且它是这一篇的全部基础:

> **模型本身完全不记得上一句话.**

每一次调用对它来说都是全新的. 你在网页版聊天工具里感受到的那种连贯, 不是模型记住了, 是
**那个产品每次都把整段历史重新发了一遍**.

所以这一篇讲两件事:

| 讲什么 | 因为 |
| :--- | :--- |
| 怎么把历史管起来 | 这是让对话成为对话的唯一机制, 而且它比你想的简单 |
| prompt caching | 每次重发历史意味着账单一路涨, 而缓存是各家给出的答案 |

这一篇的目录下有**五个能直接跑的脚本**, 和第 15 篇一样, 不用你改任何东西.

---

## 2. 学习目标

先算一笔很具体的账, 它解释了为什么这一篇后半段要讲缓存.

跑一下这一篇第一个脚本, 三轮对话下来你会看到输入 token 是这样的:

```text
Turn 1   in: 33
Turn 2   in: 58
Turn 3   in: 79
```

**你的问题长度几乎没变, 但输入一路涨.** 涨的部分就是被重新送了一遍的历史.

现在把这个放大到真实场景: 这个 app 的系统提示词有好几千 token, 而且
**每一次请求都要完整送一遍**. 一个用户聊十轮, 那份提示词就被送了十遍, 你付了十次钱, 而它
一个字都没变过.

缓存要解决的正是这一块. 而理解它的关键不在于怎么开, 在于**知道它省的是什么**.

学完这个 Task, 你将能够:

1. 解释模型没有记忆这件事, 以及对话的连贯感实际上是谁做的
2. 亲手管一次对话历史, 说出那三步是什么, 以及漏掉哪一步会怎样
3. 说清三家在历史结构上的差别, 尤其是系统提示词在不在历史里
4. 把那套记账封装成一个类, 并说清它替调用方挡住了什么错误
5. 读懂一次缓存命中的数字, 并说出缓存省的到底是什么

## 6. 三步循环: 追加, 发送, 追加

打开第一个脚本, 那个 `for` 循环里就三步, 而且这三步在任何一家都一样:

| 步 | 干什么 | 说明 |
| :--- | :--- | :--- |
| 1 | **追加** 你要说的话 | 注意是追加不是替换. 之前说过的全都留着 |
| 2 | 把**整段历史** 发上去 | 不是只发新问题. 第三轮的时候这个列表已经有六条, 六条全都再上传一遍 |
| 3 | 把回答**追加** 回历史 | 这一步是新手最常漏的 |

### 漏掉第三步会怎样

这是这一节最值得记住的一件事, 因为**它的失败方式很隐蔽**.

漏掉第三步的话, 历史里只有你说过的话, 没有模型说过的话. 于是:

| 第几轮 | 表现 |
| :--- | :--- |
| 第一轮 | **完全正常** |
| 第二轮 | 看起来也还行, 因为你的问题里通常带着上下文 |
| 第三轮之后 | 模型开始丢线索, 前后矛盾, 但**不报任何错** |

它不崩溃, 只是慢慢变笨. 而这种 bug 很难被发现, 因为你不会怀疑一个跑得好好的循环.

**脚本里那三个问题就是为这件事设计的**: 第三个问题问的是 "翻倍之前是多少", 而它只有在模型
看得见第一轮的时候才答得上来. 这是一个**能当场判真假的测试**, 比读代码可靠得多.

## 7. 三家的历史结构不一样

跑过两个以上的脚本, 你会看到最后那行统计对不上:

| 脚本 | 三轮之后历史里有几条 | 为什么 |
| :--- | :--- | :--- |
| OpenAI | **7** | 系统提示词是历史里的第一条 |
| Anthropic | 6 | 系统提示词是一个独立参数, 不在历史里 |
| Google | 6 | 同上, 在配置对象里 |

这正是第 15 篇那张对照表里第一行的后果. **系统提示词放在哪, 决定了历史列表的第一条是什么.**

还有一处细节差别: 模型那一方的角色名, OpenAI 和 Anthropic 叫 `assistant`, Google 叫 `model`.
三家, 三套词汇, 同一个意思.

### 系统提示词也是每次重发的

一个容易误会的地方: 系统提示词在历史外面, 不代表它只发一次.

**它每次调用都要重新发.** 它和历史一样不被记住. 这一点在下半篇讲缓存时会变得很重要, 因为
系统提示词恰好是**最长而且最不变** 的那一块, 也就是缓存收益最大的地方.

## 8. 把它封装起来

第四个脚本 `04_chat_session.py` 干的事很简单: 把那三步塞进一个方法里.

```python
session = ChatSession()
print(session.ask("My favorite number is 7."))
print(session.ask("Double it."))
```

调用方现在**没有机会把顺序搞错, 也没有机会漏掉第三步**, 因为那三步在方法内部, 外面看不到.

这就是封装最朴素的价值: **不是为了少写代码, 是为了让一类错误不可能发生.**

### 一个实例等于一段对话

脚本最后特意建了第二个实例, 拿同一个追问去问它. 结果是它答不上来, 因为**它的历史是空的**.

这不是缺陷, 这正是你要的: 服务两个不同的用户时, 你要的就是两段互不相干的对话. 而这在代码里
是靠一个很不起眼的写法保证的:

```python
_messages: list[dict] = dataclasses.field(init=False, default_factory=list)
```

那个 `default_factory=list` 让**每个实例拿到自己的空列表**. 写成 `_messages: list = []` 是
一个经典的 Python 陷阱: 所有实例会共享同一个列表, 于是**每段对话都会渗进其它每一段**.

### 换一家供应商要改几行

这个类是照 OpenAI 写的. 换成另一家要改的只有三处: 建客户端那一行, 发请求那一段, 挖回答那
一行.

**这正是这个 app 自己那一层在干的事**, 只不过它把这三处的差别一次性写好, 覆盖四家, 然后
用一个环境变量切换. 你现在知道那一层底下是什么了.

## 9. Prompt caching: 省的到底是什么

第五个脚本把同一个长系统提示词发两次, 然后打印缓存计数器. 真实输出长这样:

```text
--- call 1 ---
input tokens:  3214
written to cache: 3211
read from cache:  0

--- call 2 ---
input tokens:  3214
written to cache: 0
read from cache:  3211
```

**盯着第一行看**: 两次调用的输入 token 数**完全一样**.

这是理解缓存最关键的一点:

> **缓存不让请求变小, 它让同样大的请求变便宜.**

你还是把那三千多个 token 发上去了. 变的是它们的计价: 第一次是写入缓存 (正常价格), 第二次是
从缓存读 (通常是正常价格的四分之一左右, 各家不同).

### 三条会咬人的规则

| 规则 | 后果 |
| :--- | :--- |
| **有最低长度门槛**, 大约一千 token | 低于门槛**静默不生效**. 不报错, 不警告, 计数器就是零. 你会以为开了 |
| **缓存匹配的是前缀** | 靠前的地方改一个字符, 后面全部失效. 所以**不变的内容必须放最前面** |
| **缓存会过期** | 通常是分钟级. 一个很久没人用的部署, 每次都是第一次 |

第二条决定了提示词的组织方式:
**把不变的东西 (领域知识, 表结构, 例子) 放在最前面, 把每次都变的东西放在最后.**
顺序反了, 缓存等于没开.

### 三家的开法不一样

| 供应商 | 怎么开 |
| :--- | :--- |
| OpenAI | **自动**. 没有参数要设, 够长就会命中. 这也是这个脚本选它的原因 |
| Anthropic | **显式**. 在内容块上标一个缓存控制字段, 计数器叫另外两个名字 |
| Google | 有隐式的, 也有需要你提前建好的显式缓存 |

**概念完全一样, 只有语法不同.** 想给另外两家写一遍的话, 让 AI 帮你, 但记得让它先说清用的是
哪个字段名, 然后你去对一眼那家的官方文档, 因为这一块的 API 变得比别处快.

这个仓库里还有一个真实的缓存例子: `scripts/test_12_ai_aws_bedrock_with_cached_prompt.py`,
那是 Bedrock 的写法, 用的是一个显式的缓存断点标记.

## 10. 练习

### 练习 1: 亲手弄坏一次对话

**目标:** 亲眼看到漏掉第三步的后果, 因为它不报错.

**怎么做:**

1. 开一个叫 `16-multi-turn-and-caching` 的 branch
2. 跑一次 `01_openai_multi_turn.py` (或者你有 key 的那一家), 确认第三轮答对了
3. 把第三步那一行**注释掉**, 也就是把回答追加回历史那一行
4. 再跑一次. 看三轮各自答成什么样
5. 恢复那一行
6. 再改一处: 把第二步发送的历史从整段改成只发最后一条, 再跑一次
7. 恢复

**你会观察到:**

第 4 步里第一轮完全正常, 第三轮开始答不上来了, **而且全程没有任何报错**. 第 6 步会更彻底,
连第二轮都会失败.

> **关键洞见:** 一个不会报错只会慢慢变笨的 bug, 是最难被发现的那一种. 所以那三个问题被设计
> 成一个能当场判真假的测试. 有这种测试的时候, 别只靠读代码.

### 练习 2: 把缓存弄成一次未命中

**目标:** 亲手验证缓存匹配的是前缀这条规则.

**怎么做:**

1. 跑一次 `05_prompt_caching.py`, 确认第二次调用读到了缓存
2. 现在在那个长系统提示词的**最前面** 加一个字符, 比如一个句号. 再跑
3. 观察两次调用的计数器
4. 把那个字符去掉, 改成加在**最后面**. 再跑, 再观察
5. 最后把长提示词那个重复次数从 200 改成 5, 让它远低于门槛. 再跑
6. 全部还原

**你会观察到:**

第 2 步之后, 第二次调用仍然会命中, 因为你改完之后连着发了两次, 新前缀自己也被缓存了. 想
看到未命中, 关键是**对比改之前和改之后第一次调用的计数器**.

第 5 步最值得看: 计数器**全是零, 而且没有任何提示告诉你为什么**. 这就是那条静默不生效.

> **关键洞见:** 一个功能可能在你以为开着的时候完全没开, 而且不给你任何信号. 判断它到底有没有
> 生效的唯一办法, 是去读它自己报告的数字.

## 12. 导师寄语

**为什么模型没有记忆这件事值得反复强调:**

这是所有做 AI 应用的人最早形成, 也最难改掉的一个错觉. 因为你日常用的那些聊天产品
**表现得太像有记忆了**, 你会不自觉地假设那个能力在模型里.

一旦你接受了模型没有记忆, 很多事情立刻讲得通: 为什么账单随对话长度增长, 为什么长对话要裁剪
或者总结, 为什么后端可以是无状态的, 为什么第 28 篇里每次请求都要把 agent 的记忆清空重建.

**它们全都是同一件事的推论.**

**关键洞见:**

- 模型没有记忆. 你感受到的连贯是产品做的, 不是模型做的
- 不报错只是慢慢变差的 bug 最贵. 给自己设计一个能当场判真假的测试
- 缓存不让请求变小, 它让同样大的请求变便宜. 而且它可能在你以为开着的时候根本没开

**下一步:**

模型这一侧到此为止. 从第 17 篇开始转向数据: 这个 agent 查的那个数据库是从哪儿来的, 那四份
描述这个行业的文档又是干什么用的.

**五个脚本:**

```bash
.venv/bin/python examples/16-multi-turn-and-caching/01_openai_multi_turn.py
.venv/bin/python examples/16-multi-turn-and-caching/02_anthropic_multi_turn.py

.venv/bin/python examples/16-multi-turn-and-caching/04_chat_session.py
.venv/bin/python examples/16-multi-turn-and-caching/05_prompt_caching.py
```

**三步循环:**

1. 追加你要说的话
2. 发送整段历史
3. **把回答追加回历史**

**缓存三条规则:**

- 有最低长度门槛, 低于它静默不生效
- 匹配前缀. 不变的内容放最前面, 每次都变的放最后
- 会过期, 通常是分钟级

**那句要记住的话:**

缓存不让请求变小, 它让同样大的请求变便宜.
