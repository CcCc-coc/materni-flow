# 把它送上公网

> 到现在为止它只活在你那台电脑上. 这一篇把它送出去, 而你会发现难的不是部署本身, 是那些你
> 从来没意识到自己在依赖的东西.

## 1. 概览

到上一篇为止, 这个项目每一层你都拆开看过了. 但它还只活在你自己那台电脑上: 关掉终端它就没了,
换一台电脑它就不在了, 想给别人看你只能录屏.

**这一篇把它送上公网.** 做完之后你会有一个任何人都能打开的地址, 里面跑着你自己的数据库和
你自己的模型调用.

这一篇是纯操作篇, 但它要讲清楚的东西只有一件:
**本地跑得起来和云上跑得起来, 差的不是代码, 是环境.**
你机器上那些你从来没意识到自己在依赖的东西 —— 一个 `.env` 文件, 一个
`~/.aws/credentials`, 一个一直开着的进程 —— 云上一个都没有.

**你可能已经部署过一个 Next.js 应用了.** 这门课的前身
(`learn_personal_portfolio_ai` 那门课) 里有两个 Task 专门讲这件事: `05-Deploy-Hello-World-NextJs-App-to-Vercel`
和 `13-Env-Vars-and-Deployment`. 如果你走过那一遍, 导入仓库, 触发构建, 看部署日志这些动作
你已经会了.

**所以这一篇不重教那些, 也不教怎么点界面.** 那些按钮每隔几个月就挪一次位置, 写死了就是一篇
过期文档.

**这一篇真正新的东西只有两件:**

- **这个仓库有两半.** 前面那门课部署的是一个纯前端应用, 而这个仓库里 Python 和 TypeScript
  并存, 一次部署会把它拆成两样完全不同的东西
- **环境变量在这里比在一个纯前端项目里麻烦得多.** 上一门课里它可能就是一两个值; 这里它是
  三层配置, 而且**其中一层在云上根本不存在**

第二件是这一篇的重心, 所以它单独占了第 7 和第 8 两节. 而**上线之后 agent 不答**, 十有八九
就是那两节里的某一条没做对.

### 卡住了怎么办

这一篇最容易卡的地方是构建失败和上线之后 agent 不答: 前者通常是依赖或者版本, 后者几乎总是
环境变量少填了一个.
**这些都很正常** —— 你的仓库, 你的账号, 你的供应商, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/35-deploy-to-vercel/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

部署这一篇还多两个来源, 而且这两个比终端更重要, 因为**这一篇一大半的状态不在你的终端里**:

| 多给这个 | 在哪儿拿 | 为什么它比终端值钱 |
| :--- | :--- | :--- |
| **构建日志** | 项目页面的部署列表, 点进失败的那一次 | 构建发生在云上, 你本地什么都看不见 |
| **界面截图** | 直接截你正看着的那个页面 | 环境变量配没配对, 配在了哪个环境, 光靠描述说不清 |

**截图这一条要特别强调一下.** 这一篇里最容易出错的那一步 (填环境变量) 完全发生在网页上:
一个值填错了, 一个变量名少了个下划线, 或者填到了预览环境而不是生产环境 —— 这三种在终端里
一模一样, **只有截图能一眼看出来**.

一段可以照抄的开场白:

```text
我在读 examples/35-deploy-to-vercel/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端或者 Vercel 构建日志打出来的是:
(把完整输出粘在这里)
我另外附了一张当前页面的截图.
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 构建日志和报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段.
截图里那个环境变量列表, 值也要打码 —— **变量名可以给, 值不行**. 那些东西不该出现在任何
聊天窗口里, 包括跟 AI 的对话.

**如果卡住的是部署这件事本身** (构建过不去, 项目导入不进来, 域名和路由的基础问题), 那不是
这一篇的内容, 回去翻前身那门课的 `05-Deploy-Hello-World-NextJs-App-to-Vercel` 和
`13-Env-Vars-and-Deployment`. 这一篇假设那些你已经会了.

## 5. 部署到底在做什么

先说一个容易误解的事: **部署不是把你的文件夹拷到一台服务器上.**

本地你跑 `mise run dev` 的时候, 起的是**两个长期活着的进程**: 一个 Next.js 开发服务器, 一个
uvicorn. 它们一直在那儿, 等着你的浏览器来敲门.

云上不是这样. Vercel 拿到你的仓库之后做的是三件事:

**第一, 它重新装一遍依赖.** 不是用你的 `.venv/` 和 `node_modules/`, 那两个目录根本不会上传.
它读 `pyproject.toml` 加 `uv.lock`, 读 `package.json` 加 `pnpm-lock.yaml`, 从头装一遍. 所以
**你本地手动装过但没写进依赖清单的东西, 云上不存在** —— 这是构建失败最常见的一类原因.

**第二, 它把前端整个编译成静态文件.** `next build` 跑完之后, 首页那些内容已经被烤进 HTML 了.
这就是为什么改 `data/site.toml` 需要重新构建才生效, 而不是刷新一下浏览器 —— 你在第 9 篇
([界面上每一句话](../09-copy-lives-in-one-file/README-cn.md)) 里已经见过这条规矩的本地版本,
云上它更绝对.

**第三, 它把 `api/` 下的 Python 变成按需启动的函数.** 注意这个词: **按需**. 没有请求的时候,
那边什么进程都不在跑. 有请求进来的时候才拉起来一个, 处理完可能就被回收掉.

**漏掉第三点会怎样**: 你会以为可以在模块顶层做一次很贵的初始化, 反正只做一次. 实际上它可能
每几个请求就重做一次. 这个仓库的 `one` 对象用的是 `cached_property` 而不是在导入时就建连接,
第 29 篇 ([那个叫 one 的东西](../29-the-one-object/README-cn.md)) 讲的那个用到才建, 在云上
的价值比在本地大得多.

## 6. Vercel 怎么认出这个仓库有两半

这个仓库里有 TypeScript 也有 Python, 而 Vercel 需要知道哪一半归谁管.

它靠的是**约定加一个很短的配置文件**:

- 根目录有 `package.json` 和 Next.js 的结构, 所以它知道这是一个 Next.js 项目, 直接用 Next
  的那套构建
- `api/` 这个目录名是约定. 里面的 Python 文件被当成函数入口
- 剩下的靠 [`vercel.json`](../../vercel.json) 补齐

打开那个文件看一眼, 它一共只说了三件事:

| 它说的 | 为什么要说 |
| :--- | :--- |
| `functions` 里 `api/**` 的 `excludeFiles` | 打包函数的时候别把 `.next`, `.git`, `node_modules` 塞进去. 函数有体积上限, 而这三个目录跟 Python 一点关系都没有 |
| `build.env` 里的 `PYTHON_VERSION` | 明确要 3.12. 不写就吃平台的默认值, 而默认值会变 |
| `build.env` 里的 `ENABLE_EXPERIMENTAL_COREPACK` | 让构建用仓库里锁定的那个 pnpm 版本, 而不是平台自带的 |

还有一个更短的文件: [`.vercelignore`](../../.vercelignore). 它只记了一条规矩 ——
**下划线开头的文件会被忽略**. 这条不是这个项目定的, 是平台的行为, 记下来是为了让下一个想把
`api/_helpers.py` 抽出去的人先看到它.

**这里值得记住的形状是**: 配置文件短到可以一眼看完, 是因为**其余的都靠约定**. 每多一行配置,
就多一样下一个人必须读过才能改对的东西.

## 7. 要手填的只有密钥

**这一节是这一篇的重心.** 如果你上线之后 agent 不答, 十有八九错在这里.

它同时也是这个项目和你上一门课里那个纯前端项目差别最大的地方. 那边的环境变量通常是一两个
值, 填错了页面当场就不对; 这边是**三层**, 而且**填错了首页照样好好的**.

你本地能跑, 靠的是三样东西凑齐了. 它们在云上各走各的路:

| 在本地 | 在云上 | 为什么 |
| :--- | :--- | :--- |
| [`.env.defaults`](../../.env.defaults) | **自动跟着 git 上去了** | 它是提交进仓库的. schema 名, 供应商, 区域, 端口, 配额上限, 一个都不用重填 |
| [`.env`](../../.env.example) | **必须在 Vercel 的网页上一条条手填** | 它是 gitignored 的. 云上根本没有这个文件 |
| `~/.aws/credentials` | **不存在** | 见下一节 |

**这就是那条按是不是密钥切的分界线在真实世界里的样子.** 第 30 篇
([两个配置文件](../30-configuration/README-cn.md)) 讲过为什么这么切; 部署是那个判断第一次
产生实际后果的地方 —— 换一个数据集, 你改的是 committed 的那个文件, 部署的时候一行都不用重填;
而轮换一把 key, 你动的是另一个, 跟数据集毫无关系.

要手填哪几条, 不用猜, [`.env.example`](../../.env.example) 就是那份清单. 按你的
`LLM_PROVIDER` 挑对应那一组, 再加上四条数据库的:

| 一定要填 | 备注 |
| :--- | :--- |
| `DB_HOST`, `DB_USER`, `DB_PASS`, `DB_NAME` | 用 Neon 那个带 `-pooler` 的主机名 |
| 你那家供应商的那一把 key | `LLM_PROVIDER` 是哪家就填哪家的, 别的不用填 |

**漏填会怎样, 值得先知道一下**: 前端照样部署成功, 首页照样打开, 因为首页根本不调后端. 只有
你点下第一个问题的时候才会失败. 这和第 5 篇 ([把它跑起来](../05-get-it-running/README-cn.md))
里那个占位符 `.env` 的现象是同一个 —— **前端和后端的健康状况是分开的**.

### 三种填错的方式, 在终端里长得一模一样

这一步全部发生在网页上, 而网页上有三种错法, 报出来的现象**完全相同** (点问题就失败):

| 错法 | 为什么难发现 |
| :--- | :--- |
| **值填错了** | 少一个字符, 多一个空格, 或者复制的时候把引号也带进去了 |
| **变量名拼错了** | `DB_PASS` 写成 `DB_PASSWORD`. 程序找不到就当没设, 不会告诉你有个名字很像的 |
| **填到了错的环境** | Vercel 分生产, 预览, 开发三种环境. 只勾了预览, 生产就是空的 |

**这三种用眼睛读自己的配置很难发现**, 因为你是照着自己的记忆在读, 而你的记忆正是错的来源.

### 所以这一步值得截图给 AI 看

这是这一篇里最该用上截图的地方. 步骤是:

1. 打开 Vercel 项目的环境变量页面, **把变量名那一列完整截下来** (值那一列是打码的星号,
   截图里本来就看不到, 所以是安全的)
2. 同时打开 [`.env.example`](../../.env.example) 和 [`.env.defaults`](../../.env.defaults)
3. 把下面这段连同截图一起发给 AI

```text
我在给一个部署在 Vercel 上的项目配环境变量, 附了一张环境变量页面的截图.
这个项目的配置分两个文件: .env.example 是密钥的清单, .env.defaults 是
committed 的非密钥配置, 它跟着 git 自动上去所以不用手填.

我贴上这两个文件的内容:
(把 .env.example 粘在这里)
(把 .env.defaults 粘在这里)

我用的 LLM_PROVIDER 是 (填你的那家).

请对着截图帮我核三件事:
1. 有没有该填的变量漏掉了
2. 有没有变量名和文件里的写法对不上 (比如少个下划线, 或者用了近义词)
3. 有没有本来跟着 git 走的东西被我多填了一遍

只看变量名, 不用管值. 一条一条列出来, 别给我一句看起来没问题.
```

**最后那句要求很重要.** 不加这一句, 模型很容易扫一眼说没什么问题; 要求它一条一条列, 它才会
真的去逐个比对.

**还有一件截图上看得见而描述里说不清的事**: 每个变量旁边标着它作用于哪几个环境. 检查的时候
顺手确认**生产那一栏是勾上的** —— 只勾了预览是这三种错法里最隐蔽的一种, 因为预览部署是好的,
只有正式地址不行.

## 8. 云上没有你的家目录

上一节那张表的第三行值得单独讲, 因为它是最反直觉的一条.

如果你的 `LLM_PROVIDER` 是 `bedrock`, 你本地很可能**从来没有在任何文件里写过 AWS 凭据**.
你只是某一天跑过一次 `aws configure`, 然后它就一直能用. 那把凭据躺在 `~/.aws/credentials`,
boto3 每次自己去读.

**云上没有那个文件, 也没有那个家目录.** 函数跑在一个临时的沙箱里, 里面除了你的代码和你设的
环境变量, 什么都没有.

所以 Bedrock 这一种在云上要走另一条路: 把 `AWS_ACCESS_KEY_ID` 和 `AWS_SECRET_ACCESS_KEY`
当成普通环境变量填进去.

而这里有一个漂亮的对称: [`.env.example`](../../.env.example) 里那两行是**注释掉的**, 而且
旁边写着本地开发千万别打开. 理由是 boto3 读环境变量的优先级**高于** 读家目录, 所以你在本地
填一个占位符, 等于把那把能用的凭据挡住了.

**同一个变量, 本地必须留空, 云上必须填满.** 这不是矛盾, 这是同一条优先级规则在两个环境里的
两个结果. 遇到这种规矩不要死记, 记那条规则就行: **环境变量赢过配置文件.**

## 9. 一个只在云上出现, 而且不报错的失败

这一节讲一行代码, 但它是这一篇里最值得记住的东西.

打开 [`agent_app/utils.py`](../../agent_app/utils.py), 看那个 `debug` 函数. 它只做一件事:
把一句话打出来. 但它打到的是 **stderr**, 不是 stdout, 而且函数的文档字符串专门解释了为什么.

理由是这样的: 在 Vercel 这类 serverless 环境里, **函数写到 stdout 的东西是响应流的一部分**.

慢慢想一下这句话意味着什么. 你的后端正在往浏览器推一串 SSE 事件 (第 17 篇
[那份协议](../17-the-ai-sdk-protocol/README-cn.md) 讲过它的格式). 这时候某个地方
`print("checking quota")` 了一句. 那句话会**混进那串事件里**, 从浏览器的角度看, 它就是协议
的一部分 —— 一段格式不对的协议.

**然后呢? 不报错.** 前端的解析器遇到一行认不出来的东西, 通常就跳过去了. 你看到的现象可能是
某一段回答莫名其妙少了一截, 或者一个块没渲染出来, 而所有日志都是绿的.

**而且它只在云上发生.** 你本地跑, stdout 是你的终端, 那句话就老老实实打在终端上, 一切正常.
这是最坏的一类 bug: 本地复现不出来, 线上不报错, 只是偶尔不太对.

所以这个项目的规矩很硬: **调试输出一律走 `debug`, 而 `debug` 一律走 stderr.** stderr 只会
进服务器日志, 到不了浏览器.

> **这条的可迁移版本是**: 在一个你不完全了解的运行环境里, 先搞清楚**标准输出通向哪里**.
> 本地它是你的终端; 在 serverless 里它可能是响应体; 在容器里它可能是日志采集器的输入; 在
> 一个被别的程序调用的 CLI 里, 它是那个程序要解析的数据.

## 10. 上线之后第一件事

到这里为止, 这门课里所有的模型调用都是你自己按下回车, 花你自己的钱. 那种情况不需要任何上限.

**上线改变了这件事.** 链接是公开的, 别人点一次, 花的是你的钱. 你把地址发到群里, 或者写进
简历, 就等于把你的账单交给了不认识的人.

第 33 篇 ([那道花费闸门](../33-the-spend-cap/README-cn.md)) 讲的就是这个功能, 而且讲过它
**默认是关着的**. 现在是打开它的时刻.

打开它要两样东西: 一张 DynamoDB 表 (分区键叫 `app_id`, 类型 String, 别的都无所谓), 和把
`QUOTA_ENABLED` 改成 `true`. 具体怎么配在第 33 篇里, 这里只说一句判断:

**判据不是这个 demo 会不会被滥用, 而是最坏情况你赔得起多少.** 一个没有上限的公开 agent,
它的成本上界是无穷大; 加了上限之后, 上界是你自己填的那个数字. 这两者的区别不是概率问题.

**另外一道闸门也别忘了**: 你那家供应商的控制台上通常有一个账号级别的消费上限. 那一道和这个
项目里的这一道是不同的东西 —— 前者是最后的保险丝, 后者能让用户看到一句人话而不是一个 500.
两道都设上.

## 11. 练习

### 练习 1: 把它送上去, 然后用一条命令验收

**目标:** 拿到一个公网地址, 并且用一条不依赖浏览器的命令确认两半都活着.

**怎么做:**

1. 把当前分支推到 GitHub. 如果你一直在按这门课的规矩开分支, 先确认你要部署的是哪一个
2. 在 Vercel 上从 GitHub 导入这个仓库. 界面细节交给 AI, 用上面那段开场白
3. 按第 7 节那张表, 把要手填的环境变量一条条填进去. **填完再触发第一次部署**, 顺序反了要重来
4. 等构建结束, 记下那个 `.vercel.app` 地址
5. 先验后端那一半, 把地址换成你自己的:

```bash
curl -s https://your-app.vercel.app/api/hello
```

6. 再打开首页, 点一个 kickstart 问题, 看它答不答

**你会观察到:**

第 5 步应该返回一小段 JSON, 里面有 `Hello from FastAPI!`.
**这一条通了, 说明 Python 那一半被正确识别成函数了**, 和数据库, 模型, 环境变量都无关.

这个顺序是有意的. 如果第 5 步就不通, 问题在构建或者路由; 如果第 5 步通了而第 6 步不通, 问题
几乎一定在环境变量. **一条命令把故障范围砍掉了一半.**

> **关键洞见:** 一个部署了但不知道怎么验的系统, 和一个没部署的系统区别不大. 上线之后第一件
> 要有的东西是一个**不依赖界面** 的健康检查, 因为界面会因为太多种原因坏掉.

### 练习 2: 判断每一条配置走哪条路

**目标:** 不靠试, 直接说出一个配置项在云上从哪来.

**怎么做:**

1. 打开 [`.env.defaults`](../../.env.defaults) 和 [`.env.example`](../../.env.example)
2. 对下面这六个变量, 各回答两个问题: 它在云上从哪来, 以及**漏了它会怎样**

| 变量 | 从哪来 | 漏了会怎样 |
| :--- | :--- | :--- |
| `SCHEMA_NAME` | ? | ? |
| `DB_PASS` | ? | ? |
| `LLM_PROVIDER` | ? | ? |
| `ANTHROPIC_API_KEY` | ? | ? |
| `AWS_REGION` | ? | ? |
| `QUOTA_ENABLED` | ? | ? |

3. 填完之后回到 Vercel 的环境变量页面对一遍: 你标成自动来的那几条, 那里应该一条都没有
4. 最后回答一句: 如果有人把 `SCHEMA_NAME` 也填进了 Vercel 的环境变量页面, 会发生什么

**你会观察到:**

六条里只有两条要手填 (`DB_PASS` 和你那家的 key), 有一条取决于你的供应商, 剩下的都跟着 git
走了. 而第 4 步那个问题的答案是: **它会生效, 而且会赢** —— 因为环境变量的优先级在最上面.
这不是 bug, 这正是第 30 篇讲的那条覆盖机制, 只是它在云上表现为一个**看不见的覆盖**: 仓库里
写着一个值, 线上跑的是另一个, 而 `git diff` 是干净的.

> **关键洞见:** 一份配置能被覆盖是好事, 但每多一处能覆盖它的地方, 就多一个下次排查时必须
> 想到的地方. 所以要覆盖的时候覆盖, 不要因为顺手就填两遍.

## 12. 回顾: 我们学到了什么

| 概念 | 一句话 |
| :--- | :--- |
| 部署不是拷文件 | 它是重装依赖, 重新构建, 再把后端变成按需启动的函数 |
| 按需启动 | 没请求的时候什么都不在跑, 所以用到才建在云上比在本地更值钱 |
| 两半怎么被认出来 | Next.js 靠结构, Python 靠 `api/` 这个目录名, 剩下的靠一个很短的 `vercel.json` |
| 三层配置在云上 | committed 的跟着 git 走, 密钥手填, 家目录里的那种根本不存在 |
| 环境变量赢过文件 | 同一条规则解释了本地为什么不能填 AWS 凭据, 和云上为什么必须填 |
| stdout 的去向 | serverless 上它是响应流的一部分, 所以调试输出必须走 stderr |
| 最坏的一类 bug | 本地复现不出来, 线上不报错, 只是偶尔不太对 |
| 上线改变了成本模型 | 付钱的人和打字的人不再是同一个人, 这时候上限才有意义 |

## 13. 导师寄语

**为什么这一篇值得认真读:**

因为它是这门课里第一次, 你的代码要在一个**你没法直接观察的地方** 运行.

在此之前, 出了问题你总能加一句打印, 总能开一个 REPL, 总能看着终端一行行滚. 上线之后这些
全没了: 你只有一份构建日志, 一份函数日志, 和一个用户说不太对.

**这个转变比任何一项具体技术都重要**, 因为它改变了你写代码时的默认假设. 那句 stdout 的
规矩不是一条 Vercel 的琐碎知识, 它是这个转变的一个具体例子: 在一个你不控制的环境里, 连
最基础的东西 —— 打印一句话 —— 都可能有你没想到的后果.

**还有一句想说.** 很多人第一次部署成功之后的感受是松了一口气, 然后就不再碰它了. 那是可惜的,
因为部署真正的价值不在于它跑起来了, 而在于**它现在会以你没预料的方式坏掉**, 而那些坏法是
你在本地永远学不到的.

**关键洞见:**

- 云上没有的东西比云上有的东西更值得列一遍: 没有你的 `.env`, 没有你的家目录, 没有一个常驻进程
- 一个健康检查的价值在于它**排除** 了什么, 而不在于它证明了什么
- 配置能被覆盖是好事, 但每一处覆盖点都是下次排查时的一个必查项
- 本地和线上表现不同的 bug, 根因几乎总是环境差异, 不是代码差异
- 公开一个会花钱的东西之前, 先想清楚最坏情况你赔得起多少

**下一步:**

现在你有了一个地址, 但那个地址是平台给你的, 长得像 `smb-lending-lens-xyz123.vercel.app`.
第 36 篇 ([挂上你自己的域名](../36-your-own-domain/README-cn.md)) 把它换成一个属于你自己的
名字 —— 而且那个名字以后可以挂你所有的作品.
