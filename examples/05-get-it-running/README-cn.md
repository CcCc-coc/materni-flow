# 把它跑起来: 装依赖, 复制配置, 起服务

> 三步, 一个账号都不用注册. 目标是尽快看到东西动起来, 而不是一次把所有事情做完.

## 1. 概览

这一篇是这门课第一次动手. 目标很朴素, 而且**故意定得比你以为的低**: 浏览器里打开
`localhost:3000` 看到首页, 点得动, 页面正常渲染.

达到这个状态要走三步:

| 步 | 干什么 | 一条命令 |
| :--- | :--- | :--- |
| 1 | 装依赖 | `mise run inst` |
| 2 | 复制一份配置 | `cp .env.example .env`, **什么都不用填** |
| 3 | 起服务 | `mise run dev` |

### 说清楚这一篇的终点在哪

走完这三步, **agent 页还不能用**. 界面会正常显示, 但你点 kickstart 按钮一定会拿到一条报错,
因为这台机器上既没有模型的凭据, 也没有数据.

**这是预期结果, 不是你哪儿做错了.**

这一篇刻意把门槛压到最低: **不注册任何账号, 不填任何真值, 不碰数据库.** 那些留到第 13 篇
([接上真数据和真模型](../13-light-it-up/README-cn.md)), 那时候你已经跟着走了九篇, 知道自己
在给什么东西付钱.

为什么这么切? 因为**第一次动手最重要的事情是尽快看到东西动起来**. 一上来就让你注册两个
账号再等几分钟造数据, 中间任何一步卡住, 你都搞不清是工具链的问题, 账号的问题, 还是数据的
问题.

先让界面亮起来, 你就有了一个能回头对照的正常状态.

### 读不懂的地方, 别跳过去

先说一条贯穿整个系列的读法, 因为从这一篇开始正文会变密.

这门课很长, 而且它的第一优先级是**让你先跑通**. 所以正文里很多东西只讲到你现在需要知道的
那个程度, 不会一路展开到底. 这是刻意的取舍: 每个点都写细一遍, 篇幅会长到没人读得完, 而且
每个人卡住的地方本来就不一样, 提前猜也猜不准.

补这个深度的办法是把 AI 拉进来:

1. 敲 `/showcase-learn-cn` 把这门课的助教加载起来
2. **把你没看懂的那段原样复制粘贴给它**, 不用自己转述
3. 追问到懂为止. 这句话什么意思, 为什么不能反过来做, 给我举个例子, 换个说法再讲一遍, 都行

**不要装作看懂了往下翻.** 这门课后面每一篇都长在前一篇之上, 一个含糊的地方会一路含糊下去,
而且通常要到很后面才以你说不清哪里不对的形式暴露出来.

这个 skill 怎么加载, 该配什么档次的模型, 上一篇
([和 AI 一起改这个仓库](../04-work-with-ai/README-cn.md)) 已经讲过了.

### 还有一条: 要改代码就先开一个 branch

从这一篇开始, **凡是练习让你改仓库里的文件, 都先从这门课那个基线 branch 分一个出来**:

```bash
git switch -c 05-get-it-running 01-showcase
```

`01-showcase` 是这门课住的那个 branch, 它随时都是能跑的.
**branch 的名字就用你正在做的那一篇的目录名**, 这样过两周回头看 `git branch`, 你一眼
就知道每个 branch 当时在试什么.

搞砸了就 `git switch 01-showcase` 换回去重开, 之前那个扔掉就行. 你手上这个仓库为什么可以
这么放心地折腾, 第 7 篇 ([教学层和生产层](../07-teaching-and-production/README-cn.md)) 会讲清楚.

### 卡住了怎么办

这一篇每一步都可能出错: 装依赖卡住, 端口被占, 两个服务器只起来一个, 或者输出和这里写的对不上.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/05-get-it-running/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/05-get-it-running/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

三步里有两步是配置, 只有最后一步在跑代码. 这个比例本身就是这一篇要讲的事.

而配置这件事在这个项目里有个特点, 现在就值得记住: **它的错误几乎都不报错.**

一个报错的系统其实是好系统, 你至少知道该修哪儿. 而配错了还能跑的系统才是麻烦: 你从
`.env.example` 抄了一行忘了注释掉, 于是一个变量已设置, 非空, 但完全没用; 或者你把一个值
填进了错的那个文件, 程序照跑, 只是读到的不是你以为的那个值.

这门课后面会反复撞见这个模式, 最典型的一次在第 15 篇
([把种子发布到 PostgreSQL](../15-seed-to-postgres/README-cn.md)): 一个连着空数据库的 agent
不会崩, 它会自信地把表名编出来回答你.

学完这个 Task, 你将能够:

1. 用 mise 一条命令装齐 Python 和 Node 两套工具链, 并说清 mise, uv, pnpm 三者谁调谁
2. 分清哪些配置该进 `.env`, 哪些该进 `.env.defaults`, 判据是什么
3. 一条命令起两个开发服务器, 并说清 mise, pnpm 和它们之间绕的那一圈
4. 解释为什么一个真值都没填的情况下, 首页照样渲染, 后端照样启动
5. 说清那条 kickstart 报错是在哪一步冒出来的, 以及它为什么现在不用修

## 5. 一个入口: mise

打开 [`mise.toml`](../../mise.toml), 它同时管两件事.

**第一件是钉住工具版本.** 顶上那个 `[tools]` 段声明这个项目要 Python 3.12, Node 24, 加上
uv, pnpm, ruff. 所以 clone 下来之后你不需要自己去装 Python 和 Node, mise 会按这张表准备好.
这也意味着你机器上装的是哪个版本的 Python 不重要.

**第二件是定义任务.** 剩下那一大堆 `[tasks.xxx]` 就是这个项目所有能敲的命令. 常用的是这些:

| 命令 | 干什么 |
| :--- | :--- |
| `mise run inst` | 装依赖 (Python 和 Node 一起) |
| `mise run dev` | 起两个开发服务器 (会先杀掉本 checkout 的旧进程) |
| `mise run kill` | 停掉本 checkout 的服务器 |
| `mise run test` | 内容检查加 Python 测试加 Node 测试 |
| `mise run cli-check-content` | 只查 [`data/`](../../data) 里的内容一致性 |
| `mise run build-web` | 构建前端, 也是唯一会查 `site.toml` 必填 key 和图标名的地方 |

`mise run inst` 底下调的是两个包管理器: `uv sync --all-extras` 读 [`pyproject.toml`](../../pyproject.toml) 和
`uv.lock`, `pnpm install` 读 [`package.json`](../../package.json) 和 `pnpm-lock.yaml`. 你不需要分别记住它们的写法,
这正是 mise 存在的理由.

**任务名点的是它碰什么, 不是它属于哪一类.** 一个叫 `check` 的任务说不清它是这个仓库好几种
检查里的哪一种; `check-content` 和 `build-web` 摆在一起, 就看得出它们分管两边.

现在敲第一条:

```bash
mise run inst
```

## 6. 两个配置文件, 按是不是密钥切

第 2 步是配置. 这个项目有两个配置文件, 它们之间的那条线值得单独讲, 因为它决定的不只是
值放哪儿, 而是**谁能打开这个文件**.

| | `.env` | `.env.defaults` |
| :--- | :--- | :--- |
| 装什么 | API key, AWS 密钥, 数据库 host, user, password, name | `SCHEMA_NAME`, `LLM_PROVIDER`, `AWS_REGION`, `DB_PORT`, 整块配额设置 |
| 是密钥吗 | 是 | 不是 |
| 进 Git 吗 | 不进 | **进** |
| AI 能打开吗 | **不能**, `.claude/settings.json` 里 deny 了读和写 | 能 |
| 加载顺序 | **先读, 所以它赢** | 后读, 补空缺 |

**判据只有一句: 它是密钥吗?** 另一条看起来也讲得通的切法是会不会因为换台机器而不同,
但那条线会把数据集的身份 (一个字符串) 切成第三个配置文件, 于是你要为它养一个格式和一个
读取模块. 按密钥切的这条线能挣回成本, 因为它管的是访问权限.

这条线带来的两个具体好处: 轮换一个 API key 不该碰到 schema 名; 把仓库指向一个新数据集不该
碰到任何人的凭据.

**注意 `.env.defaults` 是进 Git 的, 而且没有 `.env.defaults.example`.** 这是故意的: 那个
文件本身就是参考. 搞成 gitignore 加模板那一套的话, `SCHEMA_NAME` 就跑到版本控制外面去了, 每次
clone 都要重填一遍.

现在动手, 就一条命令:

```bash
cp .env.example .env
```

**然后就不管它了, 一个值都不用填.** 复制出来的那份里每一行都是注释掉的占位符, 这正是这一
篇要的状态. 真正要填什么, 第 13 篇 ([接上真数据和真模型](../13-light-it-up/README-cn.md))
会一项一项带你填.

那为什么现在还要复制这一份? 因为**它是那份清单本身**: 打开看一眼, 你就知道这个项目一共
需要哪几类外部东西 (一把模型的 key, 一组数据库连接信息), 心里有个数.

顺便记住一条现在还用不上, 但迟早会救你一次的纪律:
**API key 不要贴进任何聊天窗口, 包括跟 AI 的对话.** 上一篇讲过 `.claude/settings.json` 里
那条 deny 名单管住了 AI 的手, 这一条管的是你自己的手. 两条缺一不可.

### 三个填的时候会咬人的地方

**一, `"..."` 等于没设.** `.env.example` 里的占位符是 `"..."`, 而代码把这个值当成未设置.
所以从模板抄过来忘了注释掉的那一行, 不会变成一个已设置, 非空, 但没用的变量.

**二, 用 bedrock 的话本地不要设 AWS 那两个 key.** boto3 查环境变量**早于**
`~/.aws/credentials`, 所以 `.env` 里一个占位符就能遮蔽掉一个好好的本地 profile. 报出来的
错是 `UnrecognizedClientException`, 一条完全指不到原因的话.

**三, 换 `LLM_PROVIDER` 时记得 `LLM_MODEL_ID`.** 各家的 model ID 格式不通用. 要么一起改,
要么把它注释掉让它回退到那家的默认值.

## 7. 为什么现在什么都不填也能跑起来

上一节让你把 `.env` 复制出来就不管了. 这一节解释为什么这样也能跑, 因为这个解释顺带讲清了
这个后端是怎么组织的.

### 首页根本不碰配置

首页上那些字 (大标题, 四张能力卡, 页脚) 全都来自
[`data/site.toml`](../../data/site.toml), 那是一个躺在磁盘上的文本文件. Next.js 在渲染页面
的时候直接把它读进来. 这条路径上没有数据库, 没有模型, 也没有任何一把 key.

所以首页是**这个项目里唯一一块完全不依赖外部服务的东西**. 这也是它适合当第一个验收点的
原因: 它亮起来, 就说明你的工具链装对了.

### 后端起得来, 是因为它什么都还没建

Python 那一侧看起来该报错才对: 没有数据库地址, 没有 API key, 它凭什么能启动?

因为**那些东西都是等到第一次真的要用才建的**. 后端有一个总装配对象, 数据库连接, AWS 会话,
模型, agent 全挂在它身上, 但每一样都是用到才建. 启动的时候一样都没建, 所以一样都不缺.

这不是巧合, 是有意的设计, 而且它买到两样东西:

| 买到什么 | 为什么值钱 |
| :--- | :--- |
| 启动快 | 这个 app 最终跑在 serverless 上, 每次冷启动都要重来一遍. 启动时不连数据库, 冷启动就便宜 |
| 现在这一篇成立 | 你可以先把界面跑起来看见东西, 把注册账号推到后面 |

这个对象叫什么, 那四块怎么拼起来的, 第 29 篇 ([那一个对象](../29-the-one-object/README-cn.md))
会拆开讲. 现在只要记住这个性质: **导入这个后端是免费的.**

### 所以第一个真的要用它的动作, 就是第一个会失败的动作

你在 agent 页点下 kickstart 按钮的那一刻, 后端第一次真的需要一个模型, 于是它去建, 于是它
发现凭据不在.

**这条报错的具体文字, 取决于 [`.env.defaults`](../../.env.defaults) 里 `LLM_PROVIDER` 指的是哪一家.**
所以这里不贴一段让你逐字比对. 你要做的只有一件事:
**把它记下来, 别急着修.** 第 13 篇 ([接上真数据和真模型](../13-light-it-up/README-cn.md))
就是专门来消掉它的.

顺带认识一个模式, 后面还会见到:
**一个用到才建的东西, 它的配置错误会推迟到第一次使用时才暴露.** 好处是启动快, 代价是错误
离配置很远. 这个项目在几个真的会咬人的地方做了相反的选择, 让配置错误在启动的那一刻就炸,
第 30 篇 (配置) 会讲那条线画在哪.

## 8. 起服务

```bash
mise run dev
```

这一条底下绕了一圈: mise 先跑 `mise run kill` 清掉本 checkout 的旧进程, 然后调 pnpm 的
`concurrently`, 再由它调回 mise 去起两个子任务, 一个 `next dev --port 3000`, 一个
`uvicorn api.index:app --reload --port 8000`.

**mise 调 pnpm 再调回 mise**, 是因为并发跑两个进程这件事用 `concurrently` 最省事, 而它是
一个 node 包.

两件值得知道的事:

**前端端口钉死在 3000.** Next.js 默认在 3000 被占时会跳到 3001, 而 [`next.config.js`](../../next.config.js) 把
`/api/*` rewrite 到写死的 `127.0.0.1:8000`. 于是那个跳过去的前端仍然指着 8000, 而坐在那里的
可能是另一个 checkout 的后端. **起不来比静默接错好.**

**[`package.json`](../../package.json) 里那几个同名 script 不要用.** 它跑起来的东西看着一样, 但少了两件事: 没有
那个用来认出哪些进程是我的的环境变量标记, 也没有先 kill 那一步. 它留着是因为 Vercel 构建
要读 [`package.json`](../../package.json), 日常一律用 `mise run dev`.

两个服务器都起来之后, 打开 `http://localhost:3000`, 你会看到首页. 上下滚一遍, 点一点那
四张能力卡, 看看那个解释气泡.

然后点右上角进 agent 页. 界面会正常显示, 但**点 kickstart 按钮会失败**. 上一节解释了那是
为什么, 也说了它归第 13 篇 ([接上真数据和真模型](../13-light-it-up/README-cn.md)) 管.

到这里这一篇就算走完了.

## 9. 练习

### 练习 1: 走完三步, 停在首页

**目标:** 在自己机器上把界面跑起来, 并且亲眼看一次预期中的失败.

**怎么做:**

1. `mise run inst`
2. `cp .env.example .env`, **什么都不填**
3. `mise run dev`, 等两个服务器都打出就绪日志 (Next.js 打 `Ready in`, uvicorn 打
   `Application startup complete.`, **两条都出现才算起来了**)
4. 打开 `http://localhost:3000`, 首页应该完整渲染. 上下滚一遍, 点一点那四张能力卡
5. 点右上角进 agent 页, 确认空状态那四张卡和下面 12 个按钮都在
6. 点一个 kickstart 按钮, **看它怎么失败**
7. 回到终端看后端那一侧打了什么, 把那几行**抄下来存着**

**你会观察到:**

第 3 步要等一会儿, 两个服务器的日志会交错着打出来, 顺序每次都可能不一样.

第 4 步和第 5 步应该完全正常, 界面上一个字都不缺. 这一点值得停一秒: 你**什么都没配**, 而
这两个页面完整地渲染出来了.

第 6 步一定失败, 而且失败信息里会提到某一家供应商的凭据没设. **不要去修它.** 那正是第 13
篇要做的事, 抄下来是为了到时候能对照着确认它真的消失了.

> **关键洞见:** 一个说得清自己缺什么的失败, 比一个含糊的失败值钱得多. 你在第 30 篇 (配置)
> 会看到这条信息是被人特意写出来的, 不是碰巧.

### 练习 2: 给七个值分家

**目标:** 把这一篇那条判据用起来, 而不是记住.

**怎么做:**

   **它是密钥吗?**

| 值 | 你的判断 |
| :--- | :--- |
| 数据库的主机名 | |
| 数据库的端口 | |
| 这个数据集用的 schema 名 | |
| OpenAI 的 API key | |
| 用哪一家供应商 | |
| AWS 的区域 | |

2. 打开 [`.env.example`](../../.env.example) 和 [`.env.defaults`](../../.env.defaults),
   逐个对答案. 前者是密钥那一侧的模板, 后者是非密钥那一侧的真身
3. 挑一个你判断错了的 (或者最没把握的), 说清它为什么落在那一边
4. 最后回答一个问题: 数据库的**端口** 和数据库的**主机名** 分在了两个文件里, 为什么

**你会观察到:**

端口那一条最容易判错. 一个端口号看起来和主机名是一类东西, 但它不是密钥: 知道端口是 5432
这件事对任何人都没有价值, 而知道主机名等于知道那台机器在哪儿.

> **关键洞见:** 会不会因为换台机器而不同这条线看起来也讲得通, 但它切出来的边界没有用.

## 11. 导师寄语

**为什么这一篇的终点定得这么低:**

装依赖, 复制一份什么都没填的配置, 起服务, 看到首页. 就这么多. 你可能会觉得不过瘾, 最有
意思的那个 agent 还不能用.

这是有意的, 而且理由有两层.

**第一层是学习上的.** 第一次在一个陌生项目上动手, 最重要的事情是尽快拿到一个正常状态,
一个你以后每次出问题都能回头对照的基准. 一口气把所有东西都配完, 中间卡在哪一步都很难判断,
而且你会花两个小时却说不出自己到底走到了哪里.

**第二层是关于门槛的.** 注册供应商账号, 绑一张卡, 再注册一个云数据库, 这些事本身不难, 但
它们是**在你还没看见任何东西之前** 要求你付出的成本. 把它们推到第 13 篇, 那时候你已经跟着
走了九篇, 亲手翻过前端的每一层, 知道自己在给什么东西付钱.

先让一半亮起来, 剩下一半就变成一件有把握的事了.

**关键洞见:**

- 这个项目里最贵的错误都不报错. 你的第一直觉应该从哪里崩了改成哪里悄悄错了
- 一个配置值该放哪个文件, 只问它是不是密钥. 不要用会不会因机器而异那条线
- 一个能机械判断的坏状态, 应该在启动时抛异常, 而不是写进 README 等人记住
- 用到才建让启动变便宜, 代价是配置错误推迟到第一次使用时才暴露. 这个取舍到处都在
- 把一件大事切成两半分别验收, 比一次做完更容易做对, 也更容易看出自己卡在哪儿
- 一个要花钱, 要注册账号的门槛, 尽量往后推到读者已经看见价值的那一刻

**下一步:**

环境跑起来了, 但你现在对这个仓库的了解还停留在目录名. 第 6 篇
([读一遍这个仓库](../06-read-the-codebase/README-cn.md)) 会带你从上往下读一遍: 两个页面,
一个后端包, 以及一次提问从浏览器出发到底走过了哪些文件.

至于那个还不能用的 agent, 第 13 篇 ([接上真数据和真模型](../13-light-it-up/README-cn.md))
会把它补上.
