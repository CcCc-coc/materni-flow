# 你的第一个 agent: 工具是怎么长出来的

> 你写的函数说明不是注释, 是接口文档. 而读它的不是同事, 是模型.

## 1. 概览

上一篇讲眼睛, 这一篇讲**手**.

先把 agent 这个词拆开. 第 2 篇 ([为什么是这个项目](../02-why-this-project/README-cn.md))
说过它和 chatbot 差着一个东西: **工具**. 现在把那句话落到代码上.

打开 [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), 整个文件只有
两百来行, 干三件事:

| 这一段 | 干什么 |
| :--- | :--- |
| `model` | 按 `LLM_PROVIDER` 挑一家供应商, 建一个模型对象 |
| `agent` | 把模型, 系统提示词, 和一串工具**组装** 成一个 agent |
| 三个 `@tool` 方法 | 那三只手 |

这一篇要讲清楚的是最反直觉的那一件: **模型不读你的代码, 它读你的函数说明.**

---

## 2. 学习目标

先想一个问题: **模型怎么知道有哪些工具可以调?**

你可能会以为框架会去分析函数体, 或者要你另外写一份配置. 都不是.

**它把你写的函数说明原样发给模型.** 那段 docstring, 连同函数名和参数名, 拼进请求里一起
送上去. 模型读完之后自己决定要不要调, 调的时候填什么参数.

### 这件事的后果比听起来严重

在普通的代码里, 一段写得含糊的注释, 后果是同事多花两分钟去读函数体. 他有兜底手段.

**模型没有兜底手段.** 它看不见函数体, 它只有你那段说明. 所以:

| 你的说明写成什么样 | 后果 |
| :--- | :--- |
| 没写参数是什么格式 | 模型自己编一个格式, 试, 报错, 再试 |
| 没说什么时候该用它 | 该调的时候不调, 或者不该调的时候乱调 |
| 写得含糊 | 每一轮都多烧几次工具调用, 而且**不报错** |

于是有了这一篇的中心句:

> **在 agent 里, docstring 不是文档, 它是接口本身.**

这句话会让你重新看待写注释这件事. 你以前写注释是为了以后的自己和同事; 现在你写的是
**一段会被程序读取, 并且直接影响运行结果的东西**.

学完这个 Task, 你将能够:

1. 说清一个普通的 Python 方法怎么变成模型能调的工具
2. 解释为什么函数说明是接口而不是注释, 并说出写不好的三种后果
3. 读懂那个 agent 对象是由哪几样东西组装出来的
4. 说清换一家 LLM 供应商时要动的是哪一处, 不动的是哪些
5. 说出这三个工具为什么是这三个, 以及为什么没有第四个

## 5. 一个方法怎么变成工具

看最简单的那个, 取库结构的那只手. 去掉说明之后它只有这样:

```python
@tool(name="get_database_schema")
def tool_get_database_schema(self) -> str:
    """<一段说明>"""
    return self.database_schema_str
```

**函数体只有一行**, 返回上一篇那个字符串. 真正的工作全在那段说明里.

`@tool` 这个装饰器干的事, 用大白话说就是**贴一张标签**: 它告诉框架这个方法可以被模型调,
并且把三样东西收集起来 —— 名字, 参数, 和那段说明.

### 送上去的是什么

框架把这三样拼成一份工具清单, 跟着每一次请求发给模型. 模型收到的大致是:

```text
你可以调这些工具:

- get_database_schema()
  Retrieve the complete database schema information in LLM-optimized
  compact format. ... Use this tool FIRST to understand the database
  structure before writing SQL queries.

- execute_sql_query(sql: str)
  Execute a SQL SELECT query and return results as a Markdown table.
  sql: A valid SQL SELECT query string to execute.
  ...
```

**注意这里面没有一行是你的函数体.** 模型对 `return self.database_schema_str` 这句话一无所知.

所以再看一遍那句话: 你在 docstring 里写的每一句, 都是模型做决定时唯一的依据.

## 6. 一段好的工具说明长什么样

打开那三个工具的说明读一遍, 你会发现它们都在回答同样几个问题.

拿查 SQL 那个当例子, 拆开看:

| 说明里的这句 | 它在回答什么 |
| :--- | :--- |
| Execute a SQL SELECT query and return results as a Markdown table | **它是干什么的** |
| `sql`: A valid SQL SELECT query string to execute | **参数要什么** |
| On success: a Markdown table / If no rows match: `No result` / On error: an error message | **回来的可能是什么** |
| Only SELECT queries are supported | **它的边界在哪** |
| Use get_database_schema first to understand available tables | **什么时候用它** |

第三行和第五行是最容易被漏掉的两条, 而它们恰恰最影响行为.

**第三行 (回来的可能是什么)** 让模型知道拿到 `No result` 不等于出错了 —— 否则它会以为自己
SQL 写错了, 然后换个写法再试一遍, 白烧一轮.

**第五行 (什么时候用)** 是在给模型排顺序. 那句 `Use this tool FIRST` 是取库结构那个工具
说明里的原话, 它直接影响 agent 第一步干什么.

> **写工具说明的五问**: 它是干什么的, 参数要什么, 回来的可能是什么, 边界在哪, 什么时候用.
> 五个都答上, 模型就不用猜了.

### 一个很小的语言细节

这些说明全是英文写的. 不是因为规矩, 是因为**模型在英文技术文本上见得最多**, 而且这份说明
会被逐字发送 —— 中文同样长的一句话通常占更多 token.

而这个仓库里注释一律英文还有另一层理由, 第 6 篇 ([读一遍这个仓库](../06-read-the-codebase/README-cn.md))
讲过: 混着两种语言的代码库, 后来的人既读不顺也搜不着.

## 7. 组装: agent 是被拼出来的

现在看 `agent` 那一段. 它短得出奇:

```python
Agent(
    model=self.model,
    system_prompt=<那份提示词的全文>,
    tools=[
        self.tool_get_database_schema,
        self.tool_execute_sql_query,
        self.tool_write_debug_report,
    ],
)
```

**一个 agent 就是这三样东西拼起来的**:

| 拼进去的 | 是什么 | 哪一篇讲 |
| :--- | :--- | :--- |
| 模型 | 哪家供应商的哪个模型 | 第 20 篇 |
| 系统提示词 | 领域知识, 口径, 规矩 | 第 25 篇 |
| 工具清单 | 它能动的手 | 这一篇 |

**这个仓库里所有关于 agent 的东西, 就这一处组装点.** 想知道这个 agent 到底是什么, 读这
十几行就够了.

### 那个循环在哪儿

你可能会问: 第 2 篇讲的那个想一步, 动一次手, 看结果, 再想的循环, 代码在哪儿?

**不在这个仓库里.** 那是 `strands` 这个框架干的事: 它拿着你的工具清单去问模型, 模型说要调
哪个, 框架就替你调, 把结果送回去, 再问一次, 直到模型说我说完了.

这是一个很值得注意的分工:

| 谁 | 负责什么 |
| :--- | :--- |
| 框架 | 那个循环, 工具清单的传输, 结果的回填 |
| **你** | **模型看到什么** —— 提示词, 工具说明, 库结构 |

**你负责的全是内容, 不是机制.** 这也是为什么这个仓库里 agent 相关的代码这么少, 而
`data/` 目录那么重要.

## 8. 换一家供应商, 只动一处

`model` 那一段比 `agent` 长得多, 因为它要处理四家供应商的差别 —— 你在第 20 篇亲眼见过那些
差别有多琐碎.

但结构很简单: **看一眼 `LLM_PROVIDER`, 按它建对应的模型对象**, 完事.

| 会变的 | 不会变的 |
| :--- | :--- |
| 建哪个模型类, 传什么参数 | 三个工具, 一行不用改 |
| | 系统提示词, 一个字不用改 |
| | 组装那几行, 完全一样 |

**这就是第 2 篇讲的模块化在 agent 这一层的样子**: 会变的东西被关在一个地方, 其余部分承诺
不被碰.

### 两个踩出来的细节

代码里有两段注释很长, 值得读一读, 因为它们都是撞出来的:

**一, OpenAI 用的是另一个接口.** 那些带推理能力的新模型, 在老的那个接口上
**拒绝同时使用函数工具和推理**, 会直接报错说不支持. 而这个 agent 除了工具什么都没有,
所以这里换了个接口.

**二, Anthropic 必须给长度上限, 别家可以不给.** 你在第 20 篇那张三家对照表里已经见过这一条,
它在这里又出现了一次.

### 还有一处防呆

有一个小函数专门负责导入供应商的模型类, 它存在的唯一理由是**把报错换一句人话**.

不加它的话, 装漏了某家 SDK 的症状是一句
`ModuleNotFoundError: No module named 'anthropic'` —— 这句话技术上完全正确, 但
**它没告诉你该干什么**. 换过之后那条报错会直接告诉你跑哪条命令重装, 或者去哪儿换一家供应商.

> **这是一个反复出现的模式**: 一条报错的价值不在于它说了什么错, 在于
> **读的人接下来知不知道该做什么**. 第 14 篇那个找到好几个数据库的报错, 第 15 篇那个空
> schema 的报错, 都是同一个思路.

## 9. 为什么是这三个工具

最后聊聊工具清单本身. 现在是三个:

| 工具 | 干什么 |
| :--- | :--- |
| 取库结构 | 上一篇那段编码 |
| 跑 SQL | 下一篇整篇讲它 |
| 写调试报告 | 把推理过程写成一个文件, 供人事后核对 |

值得注意的是**没有的那些**. 比如没有一个叫取表关系的工具, 也没有一个叫解释业务概念的工具.

为什么? 因为那些信息**已经在提示词里了**, 模型随时看得见, 不需要花一次工具调用去拿.

> **一条判据**: 工具是用来在运行时取数据的; 领域知识属于提示词.
> 一个不需要访问外部世界就能回答的问题, 不该做成工具.

### 写操作一个都没有

三个工具全是只读的, 而且这不是忘了做.

**默认一个写操作都不带**, 是因为写操作天然是跟数据集绑定的 —— 放贷这个库该有什么写操作,
和物流那个库完全不同. 所以这里留的是一个位置: 代码里那个工具清单下面写着一句注释, 说数据集
需要写操作的时候, 在这里加.

怎么加, 加之前要想清楚什么, 是第 27 篇 (写操作) 的内容.

## 10. 练习

### 练习 1: 判断这三个该不该做成工具

**目标:** 练一次那条判据 —— 要在运行时去外面取东西的才做成工具.

**怎么做:**

1. 下面是三个有人提议给这个 agent 加的工具. **对每一个回答两个问题**: 它需要在运行时去外部
   取什么东西吗? 如果不需要, 它其实该住在哪儿?

| 提议的工具 | 它想干什么 |
| :--- | :--- |
| `explain_risk_grade` | 传入一个等级字母, 返回这个等级是什么意思, 分数区间是多少 |
| `get_loan_count_by_industry` | 返回每个行业有多少笔贷款 |
| `export_result_to_csv` | 把上一次查询的结果写成一个 csv 文件 |

2. 三个里**只有一个** 是真该做成工具的. 找出它, 并说清另外两个各自该去哪儿
3. 第二个有点绕: 它确实要查库, 但它和现有的哪个工具重了? 想清楚多这一个工具的代价是什么
4. 对那个真该做成工具的, 按第 6 节那五问写一段说明 (英文中文都行, 这里只练结构)
5. 然后加载 `/about-ba-agent-app-scaffold-cn`, 把你写的说明贴给它, 问:

```text
这是我打算加的一个 agent 工具的说明. 请只当作一个模型来读它, 告诉我:
哪些地方你会需要猜, 以及你会猜成什么样. 先不要帮我改写.
```

6. 它说需要猜的地方, 就是你说明里的漏洞

**你会观察到:**

第一个不需要查任何东西 —— 风险等级表**已经写在系统提示词里了**, 做成工具等于让模型花一次
调用去拿一个它早就看得见的东西.

第二个更微妙: 它确实要查库, 但**跑 SQL 那个工具已经能干这件事了**. 多一个专用工具的代价是
工具清单变长, 而清单每一条都在每次请求里重发, 还多一个让模型犹豫的选项.

第三个才是真的: 写文件是一个外部动作, 现有工具都做不到.

第 5 步那个问法值得记住: **让 AI 扮演读者而不是作者.** 让它改写, 你学不到东西; 让它指出
哪里要猜, 你才知道自己漏了什么.

> **关键洞见:** 加一个工具的成本不只是写它. 每多一条, 模型每次都要读一遍, 而且要多做一次
> 选择. **一个能用现有工具办到的事, 不值得再开一只手.**

### 练习 2: 把一段工具说明改坏, 看 agent 怎么变笨

**目标:** 亲眼确认那段说明真的在参与运行, 而不只是注释.

**怎么做:**

1. 开一个叫 `23-your-first-agent` 的 branch
2. 先跑通一次基线: 起开发服务器, 在 agent 页问一个要查数据的问题, 记下它答得怎么样
3. 打开 [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), 找到取库
   结构那个工具的说明
4. 把里面那句 `Use this tool FIRST ...` **删掉**, 别的都不动
5. 重启服务器 (Ctrl+C 退出, 再 `mise run dev`), 问同一个问题, 观察它的行为有没有变
6. 恢复那一句. 这次改另一个: 把跑 SQL 那个工具说明里交代返回值的那几行删掉, 特别是
   `If no rows match: "No result"` 那条
7. 重启, 故意问一个**查不到数据** 的问题, 比如某个不存在的行业的贷款数
8. 全部还原, 再跑一次确认恢复

**你会观察到:**

第 5 步的变化不一定每次都明显 —— 模型可能自己就想到要先看库结构. **这本身是个重要观察**:
提示词和说明的影响是**概率性** 的, 不是开关. 少一句话不会让它必然出错, 只会让它出错的概率
变高.

第 7 步更容易看出来: 模型拿到 `No result` 而说明里没交代过这个词, 它可能会当成一次失败,
于是换个写法再查一遍.

> **关键洞见:** 这类改动**不会让程序崩**, 它只让 agent 变笨一点. 而这就是这门课反复讲的那
> 类问题里最难缠的一种 —— 它没有报错, 没有测试会红, 只有你盯着看才发现.

## 12. 导师寄语

**为什么这一篇会改变你写注释的习惯:**

我们都被教过要写注释, 而且都知道注释会过期, 所以心里多少有点敷衍 —— 反正代码才是真的.

**在 agent 这一层, 这个假设翻过来了.** 模型看不到代码, 只看得到那段文字. 你写得含糊, 它就
猜; 猜错了不报错, 只是答得差一点, 而且慢一点贵一点.

第一次意识到这件事的时候我挺不适应的: 一段文字直接决定运行结果, 而且没有任何编译器会检查
它. 但这也是一个机会 —— **它把写清楚这件事, 从一种美德变成了一项功能.**

**顺带说一件更大的事.** 你在第 7 节看到那张分工表了: 框架负责机制, 你负责内容. 这个分工在
整个 AI 应用领域都成立, 而且分给你的那一半正在变重.

接模型这件事一年比一年容易, 框架帮你做的越来越多. 剩下那一半 ——
**想清楚模型需要知道什么, 然后把它准确地写下来** —— 没有任何框架能代劳,
因为那需要懂业务.

**关键洞见:**

- docstring 是接口, 读它的是模型, 而模型没有兜底手段
- 五问写清楚, 模型就不用猜
- 你负责内容, 框架负责机制. 内容那一半正在变重
- 工具用来取数据, 知识写进提示词
- 提示词的影响是概率性的, 不是开关 —— 所以坏掉的时候你看不见

**下一步:**

## 13. 速查

**一个工具的三个部分:**

```text
@tool(name="...")        <- 标签: 告诉框架这个方法能被模型调
def tool_xxx(self, ...): <- 名字和参数: 模型照着这个填
    """<说明>"""         <- 接口文档: 模型唯一的依据
    return ...           <- 函数体: 模型完全看不见
```

**写说明的五问:**

1. 它是干什么的
2. 参数要什么 (格式, 约束)
3. 回来的可能是什么 (成功, 空, 出错)
4. 边界在哪 (它不能做什么)
5. 什么时候该用它

**agent 的三样组装件:**

- 模型 (`LLM_PROVIDER` 挑的那个)
- 系统提示词 ([`data/system-prompt.md`](../../data/system-prompt.md) 全文)
- 工具清单 (那三个 `@tool` 方法)

**一条判据:**

要在运行时去外面取东西的, 做成工具; 不需要取东西的, 写进提示词.
