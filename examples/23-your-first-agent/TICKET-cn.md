# 你的第一个 agent: 工具是怎么长出来的

## 1. 目标

上一篇讲眼睛, 这一篇讲**手**: 一个普通的 Python 方法, 怎么变成模型能调的工具.

**这一篇只有一句话最要紧, 而且它很反直觉:**

> 模型看不见你的函数体. 它做决定的唯一依据, 是你写的那段函数说明.

框架把方法名, 参数名和 docstring 收集起来发给模型, 函数体一个字都不发. 所以在 agent 这一层,
**docstring 不是注释, 它就是接口本身**.

后果比听起来严重. 普通代码里一段含糊的注释, 同事读不懂还能去看函数体;
**模型没有这个兜底手段**, 它只能猜. 而猜错了**不报错** —— 只是多烧几轮工具调用, 或者答得
差一点.

练习 2 要你**亲手把一段说明改坏**, 然后看 agent 的行为怎么变. 一定要做, 因为你会观察到一件
重要的事: 这类改动的影响是**概率性** 的, 不是开关 —— 少一句话不会让它必然出错, 只会让它出错
的概率变高. 没有测试抓得住这种东西.

这一篇还有一条判据要带走: **要在运行时去外面取东西的才做成工具, 不需要取东西的写进提示词.**

---

## 2. 要做的事情

1. 读完 README, 重点是写说明的五问和那张组装表.
2. 打开 `agent_app/one/one_04_agent.py`, 把三个 `@tool` 方法的说明都读一遍.
3. 挑跑 SQL 那个, 按五问逐条对照: 干什么, 参数要什么, 回来的可能是什么, 边界在哪, 什么时候用.
4. 找到 `agent` 那一段, 数清楚它由哪三样东西组装出来.
5. 读 README 练习 1 那三个提议的工具, 对每一个判断它需不需要在运行时去外部取东西.
6. 找出三个里唯一真该做成工具的那个, 并说清另外两个各自该去哪儿.
7. 给真该做成工具的那个按五问写一段说明, 贴给 AI, 让它**只当读者** 指出哪里需要猜.
8. 开一个叫 `23-your-first-agent` 的 branch, 下面几步都在它上面做.
9. 起开发服务器, 在 agent 页问一个要查数据的问题, 记下基线表现.
10. 删掉取库结构那个工具说明里的 `Use this tool FIRST ...`, 重启, 问同一个问题, 观察变化.
11. 恢复. 再删掉跑 SQL 那个说明里交代返回值的几行, 特别是 `No result` 那条.
12. 重启, 故意问一个查不到数据的问题, 观察 agent 怎么反应.
13. 全部还原, 再跑一次确认恢复.

**预计用时:** 70 到 100 分钟

---

## 3. 检查清单

- [ ] **docstring 是接口**: 你能说清框架把哪三样东西发给了模型, 以及为什么函数体不在其中.
- [ ] **五问对得上**: 你能在跑 SQL 那个工具的说明里逐条指出五问各自答在哪一句.
- [ ] **两个最容易漏的**: 你能说清漏掉返回值说明和漏掉什么时候用, 各自会让 agent 怎么表现.
- [ ] **改坏过一次**: 你至少改坏过一段说明并重启观察过, 而且确认了全程没有任何报错.
- [ ] **概率性这件事**: 你能说清为什么这类影响不是开关, 以及为什么没有测试抓得住它.
- [ ] **agent 的三样组装件**: 你能说出模型, 系统提示词, 工具清单, 知道整个仓库只有一处
      组装点; 也能说清那个想一步动一次手的循环是框架的事, 而你负责的是模型看到什么.
- [ ] **换供应商动哪里**: 你能说出只动建模型那一段, 并说清工具和提示词为什么不用陪着改.
- [ ] **三个候选判断对了**: 你找出了唯一真该做成工具的那个, 也说得清另外两个分别该去哪儿,
      其中一个的理由要落在多一个工具本身就有成本上.
- [ ] **工作区干净**: 练习 2 删掉的那几行都还原了, `git status` 没有留下改动.
