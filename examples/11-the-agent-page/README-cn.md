# agent 页: 空状态不能是空的

> 首页把人带到了门口. 推门进去看到一个空输入框, 他还是不知道能问什么.

## 1. 概览

这是前端那一组的第三篇, 也是学生最熟悉的一页: 第 4 篇 (把它跑起来) 你就在这里点过按钮拿到
过回答.

那时候你是当用户在用它. 这一篇换个身份, 看看**这一页为什么摆成这个样子**.

核心问题只有一个, 而且它比看起来难: ** 一个聊天界面, 在用户还没打第一个字的时候, 该显示
什么?**

大多数人的答案是一个输入框加一句请输入你的问题. 那个答案在这里是不及格的, 因为这个 agent
背后是一个十张表的数据库, 而用户根本不知道里面有什么, 也不知道它能算什么.

**这一篇仍然不教前端.** 它讲的是几个界面决定和它们背后的理由, 以及换领域时你要动哪几段.

---

## 2. 学习目标

先说一个很多人做 AI 产品时会踩的坑.

模型很强, 所以做产品的人容易相信**用户会自己想出好问题**. 实际情况是反过来的: 面对一个
无所不能的输入框, 绝大多数人打出的第一句话是你好, 第二句是你能干什么, 然后就关掉了.

这不是用户懒, 是**空白输入框没有给任何线索**. 用户不知道边界在哪, 就没法开始.

所以这一页做了三件事来解决它: 让空状态显示四条业务主线, 给出 12 个可以直接点的问题, 并且
在按下之前就告诉你会画出什么形状的答案.

**这三件事你换任何一个领域都要重做一遍**, 而且它们的质量直接决定了面试官会不会多待两分钟.

学完这个 Task, 你将能够:

1. 说清一个空输入框为什么等于什么都没给
2. 解释那 12 个按钮为什么是橱窗而不是问题列表, 以及四类各三条这个配额在防什么
3. 说出按钮上那个小图标在向读者承诺什么, 以及为什么有一类故意不画图标
4. 说出对话开始之后消息气泡里有哪三种内容, 以及思考块为什么默认折叠
5. 说清换领域时这一页要重写哪几段

- 完成第 10 篇 (首页), 知道那四条业务主线的三层结构
- 完成第 4 篇 (把它跑起来), agent 能真的回答问题, 因为这一篇的练习要点按钮

## 4. 你将学到什么

一张 agent 页的设计说明, 加一次逐条点完 12 个按钮的验证.

带走的那句话是: **那 12 个按钮不是常见问题列表, 是橱窗.** 它们的作用不是回答问题, 是让人
知道这个东西能干什么, 以及答案长什么样.

---

## 5. 空状态不能是空的

`messages.length === 0` 的时候, 也就是还没有任何对话的时候, 这一页同时显示两样东西:

**一, 一张欢迎卡.** 里面是 agent 自称的名字, 一句副标题,
**和首页同一份数据同一个组件的四张能力卡**, 加一行示例提示. 只是卡片用了紧凑模式, 因为
这里地方小.

**二, 输入框上方 12 个可以直接点的问题.**

一旦发出第一条消息, 这两样都消失, 换成一条可以关掉的横幅. 所以
**它们和横幅永远不会同时在屏幕上**
. 这一点值得知道, 因为它们长得像同一个东西, 而在代码里它们分属两个组件.

### 为什么欢迎卡里还要再放一次那四张能力卡

因为**很多人是直接从别人分享的链接进到 agent 页的**, 根本没看过首页.

对这些人来说, 这四张卡是他们唯一一次机会知道这个 agent 是干什么的. 而它们和首页共用同一份
数据同一个组件, 所以这次复用零成本, 也不会漂移. 那条判断第 10 篇讲过.

---

## 6. 12 个按钮是橱窗, 不是问题列表

这一节是这一页最要紧的设计决定.

一个很自然的做法是: 想 12 个用户可能会问的问题, 写上去. 这么做出来的结果几乎必然是
**12 段纯文字回答**.

而这个 app 能画表格, 能画流程图, 能画柱状图. 如果 12 个按钮全都只出文字, 那些渲染器
**谁也看不见**
, 相当于做了不用.

所以这 12 条有一个配额: **四类各恰好三条.**

| 类别 | 三条各产出什么 |
| :--- | :--- |
| 表格 | 一张 Markdown 表格, 并且把用到的 SQL 也贴出来 |
| 流程图 | 一张流程图 |
| 图表 | 一张柱状图或折线图 |
| 纯文字 | 一段散文回答. 第 1 条固定是介绍这个 agent 能干什么 |

**这个配额是被机械检查着的**, 改错了 `mise run check-content` 会报. 它具体怎么校验, 以及
为什么这件事需要提示词, 文案文件和前端三方一起对上, 属于一份完整的契约, 第 29 篇 (渲染契约)
会一次讲完. 这一篇只讲你在屏幕上看得见的那一半.

### 选题比措辞更要紧

不是随便挑三条问题加上一句短语就行. 每一类都有它适合的问题形状:

| 类别 | 挑什么问题 | 挑错了会怎样 |
| :--- | :--- | :--- |
| 流程图 | **本来就是流程或状态迁移的**: 生命周期, 漏斗, 状态流转 | 给一个排名问题硬套流程图, 出来的是装饰 |
| 图表 | **形状就是答案的**: 排名, 趋势, 两个量之间的差距 | 给一个只有两个数字的问题画图, 不如直接说 |
| 表格加 SQL | **读者会想验算的**: 评分卡, 分档明细, 敞口清单 | 给一个一句话能答完的问题配一张表, 显得笨重 |
| 纯文字 | 解释性的, 判断性的 | |

还有两条很实用的:

**点名要哪几列.** 说清楚要 A B C D 四列, 比说给我一张表更能让模型真的吐出表格.

**问题问小.** 一条要连着调三次以上工具才能凑齐答案的问题, 直接拆小.
**这是给人现场点开看的按钮, 转很久的圈就等于坏了.**

---

## 7. 按钮上那个小图标是一句承诺

12 个按钮长得一模一样. 不给标记的话, 想知道按下去会得到什么, 唯一的办法是
**按一个然后等模型回答**
.

所以每条 kickstart 带一个 `render` 字段, 前端据它在按钮上画一个小图标:

| `render` 的值 | 画什么 | 读者读到的意思 |
| :--- | :--- | :--- |
| `table` | 一个表格图标 | 按下去会出一张表, 还带 SQL |
| `flowchart` | 一个流程图标 | 按下去会出一张流程图 |
| `chart` | 一个柱状图标 | 按下去会出一张图表 |
| `free` | **什么都不画** | 就是一段文字回答 |

**`free` 故意什么都不画**, 理由很简洁: **每个按钮都有徽章, 等于没有徽章.** 标记的价值来自
对比, 全都标上就没有信息量了.

还有一个容易忽略的点: **这三个图标不走文案文件里那张图标表.** 那张表是数据集作者可以在
`site.toml` 里点名的集合; 而这三个图标是渲染器固定的, 不是数据集作者能选的. 判据还是那条
老规矩: 换个业务领域, 它要不要改? 不改, 所以它归代码.

## 8. 对话开始之后

发出第一条消息, 空状态消失, 页面变成消息列表.

一条 agent 消息里可能有三种东西:

| 内容 | 从哪来 | 显示成什么 |
| :--- | :--- | :--- |
| 思考 | agent 每调一次工具产生的一段推理 | 一个**默认折叠** 的块, 折叠时显示前一百来个字符当预览 |
| 正文 | agent 最终的回答 | 交给 Markdown 渲染器, 于是表格, 流程图, 图表都从这里出来 |
| 别的类型 | AI SDK 将来可能送来的其它东西 | 直接跳过 |

**思考默认折叠是必要的.** 这个 agent 每调一次工具就产生一段思考, 一次回答里可能有三四段.
全部展开的话, 你真正要读的那段正文会被埋在下面.

但折叠状态下会显示前一百来个字符当预览, **让人知道里面是什么**. 完全藏起来和完全展开都不
对, 中间这个做法是折中.

正文那一路怎么从纯文本变成表格和图, 是第 12 篇 (一段文本怎么变成表格和图) 的内容.

### 对话状态存在哪儿

存在**浏览器内存里**, 刷新页面就没了.

这是设计不是缺陷: 这个 app 没有登录, 也就没有地方存. 而且后端是无状态的, 前端每次把完整
消息列表发上去, 所以任何一个服务器实例都能接任何一个请求.

唯一落盘的是**输入框里还没发出去的草稿**, 存在浏览器本地存储里, 刷新回来还在.

---

## 9. 输入框周围那些防呆

这几件小事单独看都不起眼, 但少了任何一件, 用起来都会别扭.

| 做法 | 少了会怎样 |
| :--- | :--- |
| 输入框高度随内容自适应 | 打长句子看不见前面的内容 |
| 回车发送, Shift 加回车换行 | 想换行只能用鼠标点 |
| 上一条还在跑的时候按回车, **弹一条提示** | 静默丢弃, 用户以为自己没按到 |
| 没发出去的草稿存进浏览器本地存储 | 手滑刷新一次, 打了半天的问题没了 |
| 宽屏发送后把焦点还给输入框, **窄屏不还** | 手机上抢焦点会把软键盘顶起来, 挡住刚发的消息 |

最后一条最值得记: **同一个行为在两种屏幕上一个是贴心一个是添乱**, 而这种事不真在手机上用
一次是想不到的.

第三条还有一个前置条件在别处: 那条提示需要一个容器挂在页面上, 而那个容器在 chat 那层壳里.
第 8 篇讲过, 少了它每一次弹提示都是静默的空操作.

## 10. 换领域时这一页要重写什么

| 段 | 屏幕上是什么 | 难度 |
| :--- | :--- | :--- |
| `[chat] agent` `welcomeSubtitle` | 欢迎卡的标题和副标题 | 容易 |
| `[chat] tryExamples` `suggestionsHint` `inputPlaceholder` | 示例提示, 按钮上方那条提示, 输入框占位文字 | 容易 |
| `[chat.messages]` | 横幅那句话, 上一条还在跑的提示 | 容易 |
| `[[chat.suggestedActions]]` **12 条** | 那 12 个按钮 | **最难的一块** |
| `[[capabilities]]` | 欢迎卡里那四张 | 已经在第 10 篇写完了 |

那 12 条难在两点: 既要问得**对** 这个行业 (选题), 又要凑齐**四类各三条** 的配额, 而且触发
短语要写准.

还有一条纪律要提前知道: ** 这 12 条要照着 agent 的系统提示词改写, 不要照着数据集的原始文档
自己现编.
**提示词定义了这个 agent 的能力边界, 现编出来的问题里会混进几条它根本不会答的, 而**
所有检查都会通过**, 只有用户点下去的时候才开始即兴发挥. 这条第 29 篇会展开.

**组件一行都不用改.**

## 11. 练习

### 练习 1: 逐条点完 12 个按钮

**目标:** 验证那个配额不只是配置里的数字, 而是屏幕上真的兑现了.

**怎么做:**

1. 起开发服务器, 打开 agent 页, 别打字
2. 先看那 12 个按钮上的小图标, 数一数各类各有几个, 记下来
3. 逐条点开. 每点一条, 记录**实际出了什么**: 表格加 SQL, 流程图, 图表, 还是纯文字
4. 每点完一条刷新页面回到空状态, 再点下一条
5. 全部点完之后, 拿实际结果和第 2 步记的图标对一遍

**你会观察到:**

图标数量应该是三三三三. 至于实际输出对不对得上, **这正是要你去验的**. 对不上的那几条不是
配置错了, 通常是模型没照做, 而这件事没有任何脚本能提前告诉你.

> **关键洞见:** 配额脚本只能证明**问法** 写对了, 证明不了**模型照做了**. 这两件事之间的差距
> 只能靠人手点一遍. 这个仓库里这类必须手工验证的边界一共三条, 第 32 篇会一起讲.

### 练习 2: 判断三条 kickstart 为什么被分到那一类

**目标:** 把选题的判据用起来, 为你以后自己写那 12 条做准备.

**怎么做:**

1. 打开 `data/site.toml`, 找到 `[[chat.suggestedActions]]`
2. 挑三条 `render` 不同的, 各回答两个问题:
   - 这个问题为什么适合这种形状? 用第 6 节那张表的判据
   - 如果把它换成另一种形状, 会变差在哪儿?
3. 然后挑一条你觉得**最弱** 的, 说清它弱在哪: 是选题不适合那种形状, 还是问得太大要转很久
4. 试着为你自己那个目标行业, 想出三个适合画流程图的问题

**你会观察到:**

第 4 步比想象的难. 适合画流程图的问题必须**本身就是一个流程或者状态迁移**, 而大多数业务
问题是聚合和排名, 硬画出来就是装饰.

> **关键洞见:** 挑对形状比把短语写对难得多. 短语写错了有脚本会报, 选题挑错了没有任何东西
> 会说一句, 它只是让那张图看起来毫无必要.

## 13. 导师寄语

**为什么这一页的设计比 agent 本身更影响第一印象:**

一个面试官打开你的链接, 停留时间大概是一到两分钟. 在这段时间里, 他不会自己去想一个好问题
来考你的 agent, 他会点一个按钮看看会发生什么.

所以那 12 个按钮基本决定了他对这个项目的判断. 点开出来一张漂亮的图表, 他会再点一个; 点开
转了二十秒然后回一段泛泛的文字, 他就走了.

**这就是为什么它们叫橱窗而不是问题列表.** 橱窗要陈列的是你最拿得出手的东西, 而不是最常见
的东西.

**关键洞见:**

- 面对无边界的输入框, 用户不会自己找到好问题. 给线索是产品的责任, 不是用户的
- 承诺要在按下之前给出, 不能让人按一个等半天才知道会得到什么
- 脚本能验证问法写对了, 验证不了模型照做了. 这个差距只能手点一遍

**下一步:**

这一页反复提到一件事: agent 交回来的只是一段纯文本, 而屏幕上出现了表格, 流程图和图表.
第 12 篇 (一段文本怎么变成表格和图) 讲那个翻译是怎么发生的, 以及为什么它的失败路径才是
正常路径.

## 14. 速查

**空状态显示什么:**

- 欢迎卡: agent 名字, 副标题, 四张能力卡 (和首页同一份), 一行示例
- 12 个 kickstart 按钮, 各带一个渲染徽章

**12 条的配额:**

```text
table      x3    出表格, 并且贴出 SQL
flowchart  x3    出流程图
chart      x3    出柱状图或折线图
free       x3    纯文字, 第 1 条固定是介绍
```

**选题判据:**

- 流程图: 本来就是流程或状态迁移的问题
- 图表: 形状就是答案的问题, 排名, 趋势, 差距
- 表格: 读者会想验算的问题
- 通用: 点名要哪几列; 问题问小, 别让它转很久

**关键文件:**

- `data/site.toml` 的 `[chat]` 与 `[[chat.suggestedActions]]`
- `components/chat/chat.tsx`: 整页的状态和布局
- `components/chat/overview.tsx`: 空状态那张欢迎卡
- `components/chat/multimodal-input.tsx`: 输入框和 12 个按钮
- `components/chat/RenderBadge.tsx`: 按钮上那个小图标
- `components/chat/message.tsx`: 消息气泡, 含思考块

**验配额:**

```bash
mise run check-content
```

脚本只验问法, 模型照没照做要自己点一遍.
