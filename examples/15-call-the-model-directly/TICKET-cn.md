# 脱掉框架, 直接和模型说一次话

## 1. 目标

到这一篇为止, 模型在这门课里一直是黑盒: 你知道 agent 会回答, 但不知道那个回答是怎么被要来
的. 这一篇把中间层全部拆掉, 用三家供应商最底层的 SDK 各发一次请求.

**这一篇不用你配任何东西.** 三个脚本从这个 app 自己的配置里拿 key 和模型 id, 所以只要你在
第 4 篇填过 `.env`, 直接跑就有结果. 手上有哪家的 key 就跑哪个, 三个都跑对照着看最好, 一个
也够.

**真正的收获不是那几十行代码, 是一个排查习惯.** 你以后一定会遇到 agent 不工作而你不知道问题
在哪一层的时候, 那时候唯一有效的动作是**往下拆**: 用最底层的方式发一次最简单的请求. 通了,
问题在上面; 不通, 范围就缩小到了一件很小的事.

练习 2 里有一步是**故意把模型 id 改成一个不存在的名字**. 记住那条报错长什么样, 因为供应商
下线模型的时候你收到的就是它.

---

## 2. 要做的事情

1. 读完 README, 重点是五步骨架那一节和三家差别那张表.
2. 开一个叫 `15-call-the-model-directly` 的 branch.
3. 跑一个你有 key 的脚本, 看到回答和最后那行 token 数字.
4. 打开那个脚本, 在代码里逐个指出五步骨架分别是哪几行.
5. 找到它从 `one.config` 拿 key 那两行, 想清楚为什么不直接读环境变量.
6. 把用户问题改成一个需要长回答的, 再跑, 看 out 那个数字怎么变.
7. 把系统提示词里那句要求简短删掉或者反过来, 再跑, 对比 out 的变化.
8. 把模型 id 改成一个不存在的名字, 再跑, 读那条报错.
9. 全部还原.
10. 如果你有第二家的 key, 跑一下另一个脚本, 对着 README 那张表找出至少三处结构差别.
11. 写下从你的 key 到界面上那个回答之间有哪几层, 想清楚这三个脚本验的是最底下哪一层.

**预计用时:** 40 到 60 分钟

---

## 3. 检查清单

- [ ] **跑通了至少一个**: 你在终端里看到过模型的回答和那行 token 统计.
- [ ] **五步骨架指得出**: 你能在脚本代码里逐个指出拿凭据, 建客户端, 准备内容, 发请求, 挖响应
      这五步分别是哪几行.
- [ ] **为什么借 app 的配置**: 你能说清脚本为什么从 `one.config` 拿 key, 而不是自己读环境
      变量; 也能说清它为什么不用 `one.config.model_id`.
- [ ] **系统提示词影响成本**: 你改过那句要求简短并对比过 out 数字, 能说清它为什么是成本控制
      而不只是风格.
- [ ] **见过模型不存在那条报错**: 你故意写错过模型 id, 记得那条报错大概长什么样.
- [ ] **三家的差别说得出**: 你至少能说出系统提示词的位置, 长度上限是否必填, 和挖回答的写法
      这三处差别.
- [ ] **in 那个数字**: 你能说清它包含什么, 以及为什么它会随对话变长而增长.
- [ ] **往下拆会用**: 你写出了从 key 到界面之间至少四层, 并能说清这三个脚本验的是哪一层,
      以及它跑通了意味着什么.
- [ ] **工作区干净**: 练习改的每一处都还原了.
