# 直接和模型说话: 三家 SDK 的最小调用

> 这一篇没有 agent, 没有工具, 没有框架. 只有一个请求和一个回答.

## 1. 概览

到目前为止, 模型在这门课里一直是一个黑盒: 你知道 agent 会回答, 但不知道那个回答是怎么被
要来的.

这一篇把所有中间层拆掉. 你会跑三个脚本, 各自用一家供应商**最底层的 SDK** 发一次请求, 拿到
一句回答, 打印出来. 每个脚本不到一百行, 而且**不用你改任何东西**.

为什么值得花一篇做这件事? 因为后面所有的复杂度都是从这里长出来的:

| 这一篇 | 后面变成什么 |
| :--- | :--- |
| 一次请求, 一个回答 | 第 16 篇: 多轮对话 |
| 你手写那个请求 | 第 22 篇: agent 框架替你发, 而且会连着发好几次 |
| 你读回答里的字符串 | 第 25 篇: 从一整串消息里挖出思考和答案 |

**看过最底层的形状, 上面每一层就都只是包装.** 反过来, 没看过的人会一直觉得 agent 是魔法.

---

## 2. 学习目标

先说一个很实际的理由.

你以后一定会遇到这种情况: agent 不工作, 或者答得很奇怪, 而你不知道问题出在哪一层. 是凭据
不对, 是模型不存在, 是提示词写坏了, 还是框架用错了?

**这时候唯一有效的动作是往下拆.** 把框架去掉, 用最底层的方式发一次最简单的请求. 通了, 说明
凭据和模型都没问题, 问题在上面; 不通, 你就把范围缩小到了一件很小的事.

**这一篇给你的三个脚本, 就是这条链路最底下那一层的验证工具.** 它们小到不可能出错, 所以它们
跑通了就意味着凭据和模型都没问题, 你可以把注意力搬到上面去.

学完这个 Task, 你将能够:

1. 说出这类调用的五步骨架, 并在三家的代码里各自指出这五步
2. 指出三家在系统提示词, 长度上限和返回结构上的具体差别
3. 解释为什么这个 app 要在中间加一层把这些差别抹平
4. 读懂响应里那两个 token 数字, 并说清哪一个会随对话变长而增长
5. 用往下拆这个方法, 想清楚一个不工作的问题该从哪一头开始查

## 5. 三个脚本, 直接跑

这一篇的目录下有三个 Python 文件:

| 文件 | 供应商 | 需要哪把 key |
| :--- | :--- | :--- |
| [`01_openai.py`](01_openai.py) | OpenAI | `OPENAI_API_KEY` |
| [`02_anthropic.py`](02_anthropic.py) | Anthropic Claude | `ANTHROPIC_API_KEY` |
| [`03_gemini.py`](03_gemini.py) | Google Gemini | `GOOGLE_API_KEY` |

跑法:

```bash
.venv/bin/python examples/15-call-the-model-directly/01_openai.py
```

**你手上有哪家的 key 就跑哪个.** 三个都跑当然更好, 因为对照着看差别最明显, 但一个也够用.

没有那把 key 的时候, 脚本会打印一句话告诉你去哪儿加, 而不是抛一段看不懂的异常.

### 为什么不用你配任何东西

三个脚本开头都有这两行:

```python
from agent_app.api import one
from agent_app.constants import DEFAULT_MODEL_ID, LlmProviderEnum
```

`one` 就是这个 app 的那个组装点 (第 5 篇的地图里见过). 脚本从它身上拿两样东西:

| 拿什么 | 从哪 | 为什么这样拿 |
| :--- | :--- | :--- |
| API key | `one.config.openai_api_key` 这类字段 | 它已经替你读过 `.env` 了. 脚本和真正跑着的 app **用的是同一套配置**, 不可能对不上 |
| 模型 id | `DEFAULT_MODEL_ID` 那张表 | 和 app 用同一份默认值. 供应商改名下线时改一处就够 |

注意脚本用的**不是** `one.config.model_id`. 那个字段跟着 `LLM_PROVIDER` 走, 而这三个脚本
各自认死一家, 不管 app 当前指向谁.

**这就是一个很小但很实用的复用**: 不重新造一套读配置的代码, 直接借 app 自己的.

## 6. 三家的共同骨架

三个脚本长得不一样, 但骨架是同一个五步. 打开任意一个对着找:

| 步 | 干什么 | 说明 |
| :--- | :--- | :--- |
| 1 | 拿到凭据 | 一把 API key. 这是你和账单之间唯一的东西 |
| 2 | 建一个客户端 | 它拿着 key 和连接设置. **建一次反复用**, 每次请求新建一个是在浪费握手时间 |
| 3 | 准备两样内容 | 系统提示词 (立规矩) 和用户消息 (这一轮的问题) |
| 4 | 发一次请求 | 一个普通的阻塞式 HTTP 请求. 它在模型把整个答案生成完之前不返回 |
| 5 | 从响应里挖出文字和用量 | 回答藏在一层嵌套结构里, 每家的挖法不同 |

**这五步在任何一家都成立**, 包括这门课后面用的 agent 框架. 它只是把第 3 到 5 步自动化了,
而且会重复很多次.

### 系统提示词为什么要求简短回答

三个脚本的系统提示词都是同一句: 用一句话回答.

这**不是** 为了排版好看. **你为模型生成的每一个 token 付钱**, 所以一句要求简短的指令是一条
直接的成本控制. 在学习阶段这一点尤其明显, 因为你会反复跑同一个脚本.

---

## 7. 三家的差别

同一件事, 三种写法. 这张表是这一篇最值得记住的东西:

| | OpenAI | Anthropic | Google |
| :--- | :--- | :--- | :--- |
| **系统提示词放哪** | **在消息列表里面**, 作为第一条 `role="system"` 的消息 | 在消息**外面**, 一个独立的顶层参数 | 在消息**外面**, 塞进一个配置对象 |
| **长度上限** | 可选, 而且新模型换了参数名 | **必填**, 不给它拒绝调用 | 可选, 在那个配置对象里 |
| **消息正文的类型** | 一个普通字符串 | 字符串 (回答则是块列表) | 一个问题可以直接传字符串 |
| **回答怎么挖** | `choices[0].message.content` | `content[0].text` | `.text` 这个快捷方式 |
| **用量字段叫什么** | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` | `prompt_token_count` / `candidates_token_count` |

最后一行值得停一下: **三家给同样两个数字起了三个不同的名字.** 这就是所有跨供应商代码要面对
的现实, 而且它不会变好.

### 所以这个 app 才要在中间加一层

看完这张表, 第 30 篇 (配置) 那个设计就变得很自然了: 这个 app 用一个环境变量在四家之间切换,
业务代码里一行都看不到上面这些差别.

抹平它们的是 agent 框架加这个仓库自己那一层薄封装. **而你现在知道了那一层底下藏着什么.**

**顺带记住一个结构性的观察**: OpenAI 把系统提示词放进消息列表, 另外两家放在外面. 这个差别
在第 16 篇 (多轮对话) 会变得更明显, 因为它决定了历史列表的第一条是什么.

## 8. 那两个 token 数字

每次响应都会告诉你这次花了多少. 三个脚本最后都打印它:

```text
Tokens -- in: 32, out: 16
```

| 数字 | 含义 | 会怎么变 |
| :--- | :--- | :--- |
| in | 你送上去的所有东西: 系统提示词加全部消息 | **随对话变长而增长**, 而且是每一轮都重新算一遍 |
| out | 模型生成的内容 | 由回答长度决定 |

**第一个数字的增长方式是这一篇最反直觉的一点.** 你在第 16 篇会亲眼看到: 三轮对话下来, 你的
问题长度没变, 但那个 in 数字一路涨上去. 涨的部分就是被重新送了一遍的历史.

这也解释了为什么真实产品最后都要做一件事: **裁剪或者总结旧的对话轮次**, 而不是无限攒着.

token 大致是四分之三个英文单词, 中文大约一个字一到两个 token. 不用记精确换算, 记住数量级
就行.

## 9. 练习

### 跑一遍, 然后改三个地方

**目标:** 确认这几行代码真的是全部, 没有藏着什么.

**怎么做:**

1. 开一个叫 `15-call-the-model-directly` 的 branch
2. 跑一个你有 key 的脚本, 看到回答
3. 把那个用户问题改成一个需要长回答的, 比如让它列举五件事. 再跑, **看 out 那个数字怎么变**
4. 把系统提示词那句用一句话回答删掉或者改成鼓励详细回答. 再跑, 对比 out 的变化
5. 把模型 id 改成一个不存在的名字, 比如 `not-a-real-model`. 再跑, **读那条报错**
6. 全部还原

**你会观察到:**

第 3 步和第 4 步都会让 out 涨上去, 而系统提示词那一句的影响可能比你以为的大. 第 5 步会给你
一条很明确的报错, 直接说这个模型不存在. **记住这条报错长什么样**, 因为供应商下线模型的时候
你收到的就是它.

> **关键洞见:** 系统提示词不只是设定语气, 它直接决定你花多少钱. 一句要求简短的指令是这一行
> 代码里性价比最高的东西.

| :--- | :--- |

## 11. 导师寄语

**为什么值得花一篇跑三个几十行的脚本:**

因为**抽象层是会骗人的**. 你用一个 agent 框架用得很顺手, 会自然地以为自己懂了这件事. 直到
某天它出问题, 你发现自己完全不知道它底下在干什么, 只能在文档和搜索之间来回跳.

看过最底层的形状之后, 感觉完全不同: agent 框架不再是魔法, 它只是把这五步自动化并重复了很多
次. 你不一定记得住每个参数, 但你知道**该去哪儿看**.

这个习惯对任何技术都成立: 用一个封装之前, 花半小时看看它封装的是什么. 这半小时会在第一次
出问题的时候全部赚回来.

**关键洞见:**

- 上面每一层都只是这一层的包装. 看过底下, 上面就都不是魔法
- 系统提示词直接决定成本, 不只是决定语气
- 排查多层链路从底往上查. 前提是你手上有能单独跑的最小脚本

**下一步:**

一次问答是最简单的情况. 第 16 篇
([多轮对话和缓存](../16-multi-turn-and-caching/README-cn.md)) 加上记忆: 模型本身完全不记得
上一句话, 那对话是怎么连起来的? 以及那个 in 数字一路上涨的时候, 有什么办法省钱.
