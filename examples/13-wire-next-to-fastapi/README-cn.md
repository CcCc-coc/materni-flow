# Next.js 和 FastAPI 怎么接成一个网站

> 你敲一条 `mise run dev`, 起来的是两个互不相干的进程. 浏览器却只认一个地址.

## 1. 概览

前端那一组结束了, 从这一篇开始往后端走. 但在讲后端代码之前, 得先回答一个你从第 4 篇起就
一直在用, 却从没被解释过的事:

**你敲 `mise run dev`, 到底起来了什么?**

答案是两个完全独立的进程:

| 进程 | 是什么 | 端口 |
| :--- | :--- | :--- |
| Next.js | 前端开发服务器, 负责把页面渲染出来送给浏览器 | 3000 |
| uvicorn | 跑 FastAPI 的那个服务器, 负责 `/api/chat` 这类请求 | 8000 |

而你在浏览器里只打开过 3000, 从来没打开过 8000.
**那 agent 的回答是怎么从 8000 那个进程流到 3000 这个页面上的?**

这一篇讲那条通路, 以及围绕它的两个工程决定.

---

## 2. 学习目标

先说这一篇为什么值得单独占一篇, 而不是一句 "跑起来就行".

**第一, 这是本地和线上唯一一处结构不同的地方.** 上线之后没有 8000 这个端口, 也没有两个
进程, `/api/*` 直接由平台的 serverless 函数接管. 也就是说
**本地这套接线是一个只在开发时存在的临时结构**.
不知道这件事的人, 在线上遇到问题时会去找一个根本不存在的东西.

**第二, 它是这门课后面最容易浪费时间的一个坑.** 端口被占, 服务器起不来, 或者更糟, 起来了
但接到了别的项目的后端. 这几种情况的症状都很像程序坏了, 而实际上和代码一点关系没有.

学完这个 Task, 你将能够:

1. 说清 `mise run dev` 起了哪两个进程, 以及它们各自听哪个端口
2. 描述那条转发规则怎么把 `/api/*` 从 3000 送到 8000, 以及线上它变成了什么
3. 解释前端端口为什么被钉死在 3000, 而不是被占了就自动换一个
4. 说出那个杀服务器的脚本凭哪三种证据判定一个进程属于你这个 checkout
5. 说清 `package.json` 里那几个同名命令为什么不能用

## 5. 两个进程, 一条转发规则

浏览器打开 `localhost:3000`, 拿到页面. 页面上按下发送键, 前端往 `/api/chat` 发一个请求.

**注意这个地址没有写主机名**, 所以浏览器把它当成 `localhost:3000/api/chat`. 也就是说, 这个
请求是发给 Next.js 那个进程的, 不是发给 FastAPI 的.

接住它的是 `next.config.js` 里那段转发规则:

```js
rewrites: async () => {
  return [
    {
      source: "/api/:path*",
      destination:
        process.env.NODE_ENV === "development"
          ? "http://127.0.0.1:8000/api/:path*"
          : "/api/",
    },
    // ...
  ]
}
```

读法很简单:
**任何以 `/api/` 开头的请求, 开发环境下转发到 8000 那个进程, 生产环境下走另一条路.**

于是整条通路是:

| 步 | 谁在做 |
| :--- | :--- |
| 1 | 浏览器往 `localhost:3000/api/chat` 发请求 |
| 2 | Next.js 收到, 发现路径匹配 `/api/:path*` |
| 3 | Next.js 把这个请求原样转发到 `127.0.0.1:8000/api/chat` |
| 4 | FastAPI 处理, 调 agent, 把回答流回给 Next.js |
| 5 | Next.js 再流回浏览器 |

**浏览器全程不知道 8000 的存在.** 从它的角度看, 这就是一个普通网站.

### 这个词叫 rewrite, 不叫 redirect

两者很容易混, 但差别很大:

| | rewrite (转发) | redirect (重定向) |
| :--- | :--- | :--- |
| 浏览器知道吗 | **不知道**, 地址栏不变 | 知道, 地址栏会变 |
| 请求走几趟 | 一趟, 服务器内部转 | 两趟, 浏览器再发一次 |
| 这里用哪个 | **rewrite** | 用它的话前端代码里要写死 8000, 上线就崩 |

## 6. 线上没有这套东西

这是这一篇最要紧的一句话.

看那段转发规则里的三元判断: **只有开发环境才转发到 8000**. 生产环境下目的地是 `/api/`,
而那个路径由部署平台自己接管: 它扫描仓库里的 `api/` 目录, 把里面的 Python 变成一个
serverless 函数.

对照一下:

| | 本地开发 | 线上 |
| :--- | :--- | :--- |
| 有几个进程 | **两个**, Next.js 加 uvicorn | 前端是静态产物, 后端是按需拉起的函数 |
| 8000 端口 | 有 | **不存在** |
| 谁接住 `/api/chat` | Next.js 转发给 uvicorn | 平台直接路由到那个函数 |
| 有没有常驻的后端 | 有 | **没有**, 请求来了才拉起 |

这个差异解释了后面很多事. 最直接的一个: **后端不能有任何跨请求的记忆**, 因为线上两次请求
可能落在两个完全不同的函数实例上. 第 28 篇 (一次 chat 请求) 会讲那个每次清空 agent 记忆的
决定, 根子就在这儿.

## 7. 端口为什么被钉死

`mise.toml` 里前端那个任务写的是 `next dev --port 3000`, 而且这个 3000 是钉死的.

**Next.js 默认的行为是: 3000 被占了就自动跳到 3001.** 听起来很贴心, 在这个项目里却是个陷阱.

因为 `next.config.js` 里那个转发目的地 `127.0.0.1:8000` 是**写死的**. 于是:

| 情况 | 会发生什么 |
| :--- | :--- |
| 3000 空着 | 一切正常 |
| 3000 被另一个 checkout 占着, 允许自动跳 | 你的前端跑在 3001, 但它仍然把 `/api/*` 转发到 8000, 而**坐在 8000 上的是另一个 checkout 的后端** |

第二种情况最阴: 页面能打开, 按钮能点, agent 也会回答, 只是它回答的是**另一个项目的数据**.
不报错, 不崩溃, 你要盯着答案看很久才会觉得不对劲.

所以这里选了另一边: **起不来比静默接错好.** 端口钉死之后, 3000 被占的结果是一条明确的报错,
而不是一次安静的串线.

**这是这个仓库反复出现的一个取舍**: 在 "能跑但可能是错的" 和 "当场失败" 之间, 一律选后者.

## 8. 杀服务器凭什么判定是我的

`mise run dev` 第一件事是先跑 `mise run kill`, 而那背后是一个专门写的脚本
`kill-dev-servers.py`. 一个杀进程的小工具值得几百行代码, 理由是三件事叠在一起.

**一, 开发服务器永远不会自己退出.** 它们会一直跑到被杀.

**二, 一台机器上常常有好几个 checkout.** 这个脚手架的全部意义就是长出很多个项目, 于是同一
台笔记本上同时躺着好几个同构的仓库.

**三, 它们用同一对端口**, 因为它们是同一个脚手架.

所以 "关掉我的服务器" 这句话里的**我的**, 需要被精确定义. 定义错了就会杀掉别人的.

### 两种想当然的做法都会误杀

| 做法 | 为什么不行 |
| :--- | :--- |
| 扫进程列表, 命令行里含 `uvicorn` 或 `next dev` 就杀 | 完全不看进程属于哪个目录. 机器上任何一个 Node 项目的开发服务器都会中枪 |
| 对 3000 和 8000 无条件查出占用者然后杀 | 查端口的命令**不区分在监听还是只是连着**. 一个浏览器标签页, 任何一个远端端口恰好是 3000 的进程, 都会被返回并杀掉 |

### 这个脚本用的规矩

> **一个进程只有能被证明属于这个 checkout, 才会被杀.**

证明有三种, 满足任意一种即可:

| 证据 | 说明 |
| :--- | :--- |
| 环境变量里带着这个 checkout 的标记 | `mise.toml` 给两个 dev 任务都设了一个环境变量, 值是**这个 checkout 的绝对路径**. 子进程自动继承, 所以给树顶打标就等于给整棵树打标 |
| 工作目录就是项目根目录, 或者命令行里含项目根路径 | 手工起的服务器的兜底 |
| 它是满足上面两条之一的进程的后代 | 顺着进程树往下找 |

其余一律不动, 只报告, 并且**退出码非零**, 于是依赖它的 `mise run dev` 会停下来, 而不是在
别人的端口上搭起半套东西.

### 那个标记的名字是通用的, 身份在值里

标记的名字对所有从这个脚手架长出来的项目是**一样的**, 而脚本匹配的是整串 "名字等于路径".

这带来一个不直观但很有用的性质: **第二个第三个项目可以用同一个变量名**, 各自的脚本靠路径
区分, 谁也杀不到谁.

## 9. `package.json` 里那几个同名命令不要用

打开 `package.json`, 你会看到 `dev`, `next-dev`, `fastapi-dev` 这几个名字, 和 mise 里的任务
一模一样.

**别用它们.** 它们跑起来的东西看着一样, 但少了两件事:

| 少了什么 | 后果 |
| :--- | :--- |
| 那个用来认出 "哪些进程是我的" 的环境变量标记 | `mise run kill` 认不出它们, 于是杀不掉 |
| 先 kill 那一步 | 端口可能还被上一次的进程占着 |

那它们为什么还留着? 因为**部署平台的构建过程要读 `package.json` 的 `build`**. 那一条必须
在, 而其余几条是顺带留下的.

**日常一律用 `mise run dev`.**

## 10. 排查清单

这一节是拿来用的, 不是拿来读的. 起不来的时候按顺序过一遍.

| 症状 | 大概率是什么 | 怎么办 |
| :--- | :--- | :--- |
| `mise run dev` 报端口被占, 而且 kill 那一步退出码非零 | 有另一个 checkout 或者别的软件占着端口, 而且脚本证明不了它是你的 | 找出那个进程自己停掉; 确定要抢的话, 那个脚本有一个强制参数 |
| 页面能开, 但按钮点了没反应 | 后端那个进程没起来, 或者挂了 | 看终端里 uvicorn 那一路的输出 |
| 页面能开, agent 也答, 但答的东西不像你的数据 | 你的前端不在 3000 上, 转发接到了别人的后端 | 确认前端到底跑在哪个端口 |
| 改了 `data/` 下的文件页面没变 | 那几个文件是构建时读的 | 终端里 Ctrl+C, 再 `mise run dev` |
| 改了组件页面没变 | 少见, 通常是热更新卡了 | 同上, 重启一次 |

**卡住了就把这一节连同你看到的报错一起复制给 AI.** 这类问题的信息量全在报错的具体措辞里,
而那正是它擅长读的东西.

## 11. 练习

### 练习 1: 亲眼看那条转发规则在工作

**目标:** 确认 8000 那个进程真的存在, 而且浏览器确实不知道它.

**怎么做:**

1. 起开发服务器, 保持它跑着
2. 浏览器打开 `http://localhost:3000`, 正常
3. 现在直接打开 `http://localhost:8000/api/hello`. **这是后端的健康检查端点**, 你应该看到
   一小段 JSON
4. 再打开 `http://localhost:3000/api/hello`. 你应该看到**同样的 JSON**, 而地址栏还停在 3000
5. 打开 `http://localhost:8000`, 看看会发生什么

**你会观察到:**

第 3 步和第 4 步的内容一样, 但走的路不一样: 前者你直接敲了后端, 后者是 Next.js 替你转发的.
而第 5 步大概率什么都没有, 因为**后端只管 `/api/` 那几个路径**, 页面全在 Next.js 那边.

> **关键洞见:** 这两个端口在开发时是两个真实存在的服务器, 而线上只有一个入口. 本地这套接线
> 是临时结构, 别把它当成这个 app 的架构.

### 练习 2: 让那个 kill 脚本报告一次

**目标:** 看清它凭什么判定一个进程是你的.

**怎么做:**

1. 保持开发服务器跑着, 另开一个终端
2. 跑一次**只报告不动手** 的模式:

```bash
.venv/bin/python kill-dev-servers.py --dry-run
```

3. 读输出: 它列出了哪些进程, 每个是凭哪条证据被认领的
4. 现在换一种起法, 手工在项目根目录起一个前端: `pnpm exec next dev --port 3000`
   (先把原来的停掉). 再跑一次 `--dry-run`, 看它还认不认得出来
5. 停掉一切, 回到 `mise run dev`

**你会观察到:**

第 3 步里每个进程后面都跟着一条理由. 第 4 步那个手工起的进程**没有那个环境变量标记**, 但
它的工作目录是项目根, 所以第二条证据接住了它.

> **关键洞见:** 一个安全的批量操作, 靠的不是把匹配条件写得更严, 是要求每个目标都能被证明
> 属于这次操作的范围. 证明不了就不动, 并且说出来.

| 东西 | 一句话 |
| :--- | :--- |
| `mise run dev` 起了什么 | 两个独立进程: Next.js 在 3000, uvicorn 在 8000 |

## 13. 导师寄语

**为什么一个杀进程的脚本值得写几百行:**

这件事表面上很小: 关掉我自己起的服务器. 但它有一个性质, 让它值得认真对待:
**它是破坏性的, 而且错了没法撤销.**

大多数工具在这种场合会选择 "宁可多杀不可漏杀", 因为漏杀的症状很明显 (端口还被占着), 而误杀
的症状发生在别人身上. 这个脚本反过来: **证明不了就不动, 并且退出码非零让上游停下**.

这个取舍值得记住, 因为你以后会反复遇到它: 批量删除, 批量改名, 批量清理. 判据是一样的:
**这个操作错了能撤销吗?** 不能的话, 就该要求每个目标都被证明, 而不是被匹配.

**关键洞见:**

- 本地开发的结构不等于线上的架构. 分不清这一点, 线上出问题时你会去找一个不存在的东西
- 在 "能跑但可能是错的" 和 "当场失败" 之间, 一律选后者
- 破坏性操作要求证明, 不要求匹配. 证明不了就不动, 并且说出来

**下一步:**

请求已经从 3000 转到 8000 了, 但前端和 agent 说的是两种不同的语言. 第 14 篇
(AI SDK 协议) 讲那个翻译: 进来的请求体长什么样, 出去的回答又是按什么格式一段段流回浏览器的.

## 14. 速查

**两个端口:**

```text
3000   Next.js 前端开发服务器
8000   uvicorn, 跑 FastAPI
```

**转发规则在哪:**

`next.config.js` 的 `rewrites`. 开发环境把 `/api/*` 转到 `127.0.0.1:8000`, 生产环境走平台
自己的路由.

**日常命令:**

```bash
mise run dev     # 先 kill, 再并发起两个服务器
mise run kill    # 只停掉本 checkout 的服务器
```

**排查:**

```bash
.venv/bin/python kill-dev-servers.py --dry-run    # 只报告, 不动手
```

**两条不要:**

- 不要用 `package.json` 里那几个同名命令
- 不要让前端自动跳端口
