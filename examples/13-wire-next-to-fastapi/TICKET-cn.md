# 看懂本地那两个服务器怎么接在一起

## 1. 目标

从第 4 篇起你就一直在敲 `mise run dev`, 但从没人告诉你它到底起了什么.
**答案是两个完全独立的进程**: 一个 Next.js 在 3000, 一个 uvicorn 在 8000.
而你在浏览器里只打开过 3000.

这一篇讲那条把它们接起来的转发规则, 以及围绕它的两个工程决定.

**最要紧的一句话是: 本地这套接线是临时结构, 线上没有它.** 线上只有一个入口, 没有 8000, 也
没有常驻的后端进程. 不知道这件事的人, 在线上遇到问题时会去找一个根本不存在的东西.

**第二要紧的是那份排查清单.** 这一篇讲的东西是这门课后面最容易浪费时间的坑: 端口被占, 服务
器起不来, 或者更糟, 起来了但接到了别的项目的后端. 这几种情况的症状都很像程序坏了, 而实际上
和代码一点关系没有. 读到第 11 节那张排查表时, 把它记在手边.

---

## 2. 要做的事情

1. 读完 README, 重点是前后端分离那三节, 那条转发规则, 和第 11 节那张排查表.
2. 打开 `next.config.js`, 找到 `rewrites`, 认出那个三元判断在开发和生产各指向哪儿.
3. 打开 `mise.toml`, 找到起前端那个任务, 确认端口是写死的 3000, 并想清楚不写死会怎样.
4. 起开发服务器, 在浏览器里打开 3000 端口上的首页, 确认正常.
5. 直接打开 8000 端口上的 `/api/hello`, 看到那段 JSON.
6. 再打开 3000 端口上的 `/api/hello`, 确认内容一样而地址栏还在 3000.
7. 打开 8000 端口的根路径, 看看会不会有页面, 想清楚为什么.
8. 另开一个终端, 跑 `kill-dev-servers.py` 的 `--dry-run` 模式, 读它列出了哪些进程, 每个是
   凭哪条证据被认领的.
9. 停掉服务器, 在项目根目录手工起一个前端, 再跑一次 `--dry-run`, 看它还认不认得出来.
10. 停掉一切, 回到 `mise run dev`.
11. 打开 `package.json` 看那几个同名 script, 说清它们比 mise 任务少了哪两样东西.

**预计用时:** 45 到 70 分钟

---

## 3. 检查清单

- [ ] **两个进程说得出**: 你能说出 `mise run dev` 起了哪两个进程, 各听哪个端口, 各负责什么.
- [ ] **转发规则读懂了**: 你能描述 `/api/chat` 这个请求从浏览器到后端走过的五步, 并说清浏览器
      全程知不知道 8000 的存在.
- [ ] **两次访问验过**: 你分别在 8000 和 3000 上打开过健康检查端点, 看到了同样的内容, 也在
      8000 根路径上确认过没有页面.
- [ ] **线上的差别**: 你能说清线上有几个进程, 有没有 8000, 谁接住 `/api/chat`, 以及这个差别
      对后端的记忆意味着什么.
- [ ] **端口为什么钉死**: 你能说清允许自动跳端口之后最坏会发生什么, 以及为什么起不来比那个
      结果好.
- [ ] **kill 的三种证据**: 你跑过只报告模式, 能说出它凭哪三种证据认领一个进程, 以及认不出来
      的进程会被怎么处理.
- [ ] **标记的设计**: 你能说清那个环境变量为什么名字可以对所有项目通用, 身份藏在哪里.
- [ ] **那几个 script 不能用**: 你能说出 `package.json` 里那几条比 mise 任务少了什么, 以及
      它们为什么还留着.
