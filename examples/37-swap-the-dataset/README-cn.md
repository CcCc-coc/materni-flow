# 换一个行业

> 前面三十几篇讲的每一条边界, 都是在为这一刻做准备. 现在真的换一次, 然后数一数后端被改了
> 几个文件.

## 1. 概览

这门课从第 2 篇开始就在说同一句话: 这个项目值钱的地方不是它本身,
是**它能被反复换成别的行业**. 前面三十几篇讲的每一条边界, 都是在为这一刻做准备.

**这一篇就是那一刻.** 你要把这个应用从一家给小微企业放贷的公司, 整个换成一家医院的产科
病房排班系统 —— 数据换掉, agent 的领域知识换掉, 网站上每一句话换掉.

而这件事的重点不在于它能做到, 在于**它要动多少东西**. 换完之后你会发现:
`agent_app/` 下面**一行都没改**.

素材已经在仓库里了. [`dataset-for-swap/`](../../dataset-for-swap) 下面躺着一份完整的产科
病房排班数据集, 五份源文档, 和现在这份放贷数据集同构.

**这一篇也不是操作手册.** 具体每一步由两条 skill 命令驱动, 它们各自带着完整的剧本. 这一篇
讲的是**为什么是这个流程**, 以及流程里那几个地方为什么不能颠倒.

### 操作其实只有三步

**先把这件事的操作面说清楚, 因为它比这一篇的篇幅看起来简单得多:**

1. 把 `dataset/` 里旧的那几份文档和产物清掉
2. 把新数据集那几份文档放进去
3. 敲 `/run-swap-dataset-phase-1-cn`

**就这三步.** 剩下的全是 AI 在做, 而且**它会主动问你**: 品牌名叫什么, agent 叫什么, 有些
它拿不准的地方也会停下来确认. 你回答就行.

这一篇篇幅长, 是因为它要讲清楚**为什么是这个流程**, 不是因为操作复杂.

### 卡住了怎么办

**这一篇没有一段专门的求助提示词, 而且这是有意的.** 你已经在一个跟 AI 的对话里了, 所以
**卡住了就直接在那个 session 里跟它说**. 它手上有整份剧本, 也有你刚才做过的每一步; 另开
一个对话等于把这些全丢掉, 反而是退步.

说的时候还是那三样, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你卡在哪一步** | 换数据集是一个十步的流程, 说清第几步比描述现象省事 |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

**粘贴之前先打码.** 同步那一步的报错里常常带着完整的数据库连接串.

### 用一个够强的模型

这一篇是这门课里对模型能力要求最高的一次: AI 要通读几万字的数据集文档, 保持一条五步的推导
链不漂移, 还要写出一整套领域提示词.

**弱模型在这里会以一种很难发现的方式失败** —— 它不会报错, 它会写出一份看起来很像样但覆盖
不全的提示词, 然后下游全部跟着不全. 这正是第 6 节说的那个状态.

**建议用 Sonnet, Terra, Gemini Flash 这个级别或者更强的模型.** 更小更快的那一档用来做别的
事情很好, 但不适合这一篇.

## 2. 学习目标

学完这个 Task, 你将能够:

1. 说出换数据集要同时换的是哪三样, 以及只换其中两样会产生什么现象
2. 说清一个 skill 是什么, 以及一件事什么时候值得写成 skill 而不是写成给人读的文档
3. 解释为什么这件事被拆成两条命令, 而不是一条
4. 复述阶段一那条串行推导链的五步, 并说清每一步的输入为什么只能是上一步的产物
5. 说出那条铁律, 并判断一个想加的功能该从哪里开始加
6. 说清换完之后两个检查各自抓得住什么, 以及哪些东西两个都抓不住

## 5. 换的到底是哪三样

这个应用的本质是三样东西: **一个提示词, 一个数据库, 一个网站.**

| 这一样 | 住在哪 | 它决定什么 |
| :--- | :--- | :--- |
| **数据库** | [`dataset/`](../../dataset) 里那五份文档, 加上跑出来的库 | agent 能查到什么 |
| **提示词** | [`data/system-prompt.md`](../../data/system-prompt.md) | agent 懂什么, 以及它能做什么 |
| **网站** | [`data/site.toml`](../../data/site.toml) 和 [`data/business-context.md`](../../data/business-context.md) | 用户看到什么, 以及他会问什么 |

**这三样必须同时换, 而且必须换得一致.** 这就是为什么 `data/` 这个目录存在, 也是为什么这门课
从第 9 篇起就在反复说界面上的每一句话都在那一个文件里 —— 一个散落在二十个组件里的文案, 换
一次数据集就是二十处漏改的机会.

**除了这三样, 还有一个值:** `SCHEMA_NAME`, 在 [`.env.defaults`](../../.env.defaults) 里.
它是一次换数据集**唯一要改的配置**, 而且它改完之后新数据会落在一个新的 PostgreSQL schema
里, 旧的那一套还在.

**而 `agent_app/` 下面一行都不用改.** 这是这个项目最硬的那条承诺, 前面很多篇讲的边界都是在
守这一条: 文件名靠发现而不是写死, 表名两边一致, 库结构靠反射, 配置只有一个家.

---

## 6. 那个不报错的失败

现在讲这件事最危险的地方.

想象一个换到一半的状态: 网站上写着小微企业放贷分析, 提示词里教的是医院排班, 而数据库里躺着
产科病房的数据.

**这个状态是能跑起来的.** 构建成功, 测试全绿, 页面正常打开, agent 正常回答.

**它只是全程在撒谎.**

用户看到首页说这是一个贷款分析工具, 点了一个关于放贷的问题, 而 agent 拿着一份排班的提示词
去查一个排班的数据库, 然后编一段听起来很像回事的话回来.

**没有任何一个环节会报错**, 因为每一个环节单独看都是自洽的: 网站的文案是合法的 TOML, 提示词
是合法的 Markdown, 数据库里的表都在. 坏掉的是**它们之间的一致性**, 而一致性不属于任何一个
文件.

> 你在第 34 篇见过这个句式. 这一篇是它规模最大的一次: 不是三个文件的一个约定, 是整个应用
> 的所有内容都必须讲同一个故事.

**这就是整套流程存在的理由.** 如果换数据集可以一步一步随便改, 那么中途停下, 改错顺序, 或者
漏掉一个文件, 结果都是这个状态. 而这个状态**你验收的时候看不出来** —— 除非你恰好懂那个行业,
并且恰好问了一个正确答案你知道的问题.

## 7. 那两条命令是什么

这一篇要你敲两条斜杠命令. 在动手之前, 先花两分钟搞清楚它们到底是什么,
因为**这件事本身就是这一篇最值得带走的东西之一**.

### 一个 skill 是一份写给 AI 的操作手册

它不是脚本, 它自己什么都不执行. 它就是一份 Markdown 文档, 写着**这件事该怎么做**: 分几步,
每一步要改哪个文件, 改成什么样, 什么情况下要停下来问人, 做完怎么验.

这份文档躺在仓库里. 你敲那条斜杠命令的时候, 发生的事情非常朴素:
**整份文档被塞进当前这轮对话**, 然后 AI 照着它做.

跟换数据集有关的一共三条命令, 加六篇参考文档, 全部在 `.claude/skills/` 下面:

| 命令 | 它是什么 |
| :--- | :--- |
| `/swap-dataset-cn` | 索引与路由. **不含任何步骤**, 只回答这件事的全貌和现在该敲哪条 |
| `/run-swap-dataset-phase-1-cn` | 阶段一的完整剧本, 十步 |
| `/run-swap-dataset-phase-2-cn` | 阶段二的完整剧本 |

**它们是提交进仓库的**, 和代码一样会被 review, 也一样会随着项目演进. 这一点很关键: 一份写在
某个人聊天记录里的操作经验, 下一个人拿不到; 一份提交进仓库的, 下一个人敲一条命令就有了.

### 为什么这件事值得做成 skill, 而不是写成一篇给人读的文档

因为**换一次数据集要保持一致的点有三十几个**.

提示词里的分析索引要覆盖源文档每一条查询, 那 12 个问题要从分析索引里挑, 四张能力卡要对应
提示词里的四条主线, 首页那句几张表几行数据要现场从库里数, 渲染配额四类各要恰好三条, 外键
顺序要能排出来, 旧领域的词要清干净, `SCHEMA_NAME` 要改, 测试里的硬编码要改...

**一个人读一遍这样的清单, 能记住五条.** 然后他会漏掉第六条, 而第六条漏了不报错 —— 这正是
第 6 节讲的那个状态.

**而 skill 把这份清单交给了一个不会累也不会跳着读的执行者.** 你的角色因此变了: 你不再是那个
对着清单一条条改一条条查的人, 你变成**给输入和做验收** 的人.

### 所以你实际要做的只有三件事

| 你做什么 | 什么时候 |
| :--- | :--- |
| **给输入** | 把新数据集那五份文档放进 `dataset/` |
| **回答几个问题** | 阶段一中途会问品牌名, agent 叫什么 —— 这些任何业务文档里都没有 |
| **验收** | 阶段一走到闸门之后, 你自己点开网站看一遍 |

**第三件不能交出去**, 而且这不是因为 AI 不够好. 是因为**内容对不对这件事没有机械判据** ——
第 6 节说过, 一个换到一半的状态每个环节单独看都自洽. 判断它是不是在撒谎, 需要一个知道这个
网站应该说什么的人, 而那个人只能是你.

> **一句话概括这一节**: skill 能保证**每一处都被改到**, 不能保证**改得对**. 前者是人最容易
> 漏的, 后者是人最擅长的.

## 8. 两个阶段, 中间夹一道人工闸门

换数据集被拆成两条命令:

| 阶段 | 命令 | 做什么 |
| :--- | :--- | :--- |
| 一 | `/run-swap-dataset-phase-1-cn` | 造库, 同步 PostgreSQL, 重写提示词, 全部界面文案, 业务说明 |
| 二 | `/run-swap-dataset-phase-2-cn` | 结合新行业的调性重新设计前端: 布局, 配色, 字体, 图表色板 |

**阶段一做完, 页面还穿着上一个行业的衣服.** 那是预期结果, 不是没做完. 内容已经全换了, 视觉
还是旧的.

### 为什么是两条命令而不是一个大 skill

理由和模型的工作方式直接相关, 值得记住, 因为它适用于任何一个长流程:

**一个被加载进来的 skill, 是对话里的一条消息.** 它不会被重新读取. 而当对话变长触发自动
压缩时, 每个 skill 只保留开头一部分.

于是一个把两个阶段写在一起的长 skill, 跑完阶段一通常已经压缩过了 —— 而排在文件末尾的阶段二
正好是被截掉的那一段. 你说开始改前端的时候, 模型手里可能只剩阶段一的残影.

**拆开之后, 阶段二在真正需要它的那一刻第一次完整进入上下文.**

同一个理由让阶段二值得 `/clear` 之后再敲: 阶段一结束时上下文已经被内容工作塞满了, 清空之后
视觉设计能拿到一个干净的注意力. 该知道的东西全在文件里, 清掉不丢任何东西.

### 中间那道闸门是人

两个阶段之间必须有一次**你自己点开网站看一遍**. 上一节说了为什么: 内容一致性这件事没有任何
自动检查能替你确认.

## 9. 推导链: 阶段一为什么必须串行

这一节是整个流程最重要的部分.

阶段一要产出六样东西: 提示词, 12 个 kickstart 问题, 4 张能力卡, 首页文案, 概念气泡, 业务
说明. 它们描述的是**同一份领域知识**.

**如果它们各自去读源文档, 并行地写出来, 就一定会漂移.** 不是可能, 是一定.

漂移长这样, 而且没有任何东西会报错: 提示词只覆盖了源文档 20 条查询里的 13 条, 而 12 个
kickstart 问题是另起炉灶从源文档写的, 于是首页多出两个按钮, 问的是提示词根本没教的分析.
测试全过, 构建成功, 只有用户点下去的时候模型才开始即兴发挥.

**根治办法不是加校验, 是改顺序.**

> 这个手法你在第 32 篇 ([内容那一半的检查](../32-content-checks/README-cn.md)) 见过它的
> 名字: **用顺序代替检查**. 那一篇讲它为什么成立, 这一篇是它被真正用上的地方.

具体是五步, 严格按顺序, **每一步只从上一步的产物推导, 不回头读源文档**:

**第一步, 写提示词.** 这是**唯一允许通读全部源文档** 的一步. 源文档里每一条查询都要在
分析索引里占一行, 一条都不能漏.

**第二步, 写那 12 个 kickstart 问题.** 输入**只有第一步产出的提示词**, 不许回头翻源文档.
逐条对着分析索引挑出来, 改写成用户的口吻.

**第三步, 写 `site.toml` 的其余部分.** 4 张能力卡就是提示词里最重要的四条主线. 首页那个表数
和行数**此刻现场从数据库数出来**, 不抄旧值也不估.

**第四步, 写业务说明.** 输入是提示词加源文档里的业务背景.

**第五步, 清掉脚本和测试里残留的旧领域词.**

### 那条铁律

> **提示词定义能力边界. 下游只能换措辞, 不能新增一项提示词没教的能力.**

这一句是整条链的支点. 它意味着**想让首页出现某个分析, 唯一的合法路径是先把它写进提示词**.

**为什么第二步那个不许回头翻是有牙的**: 12 条里第 1 条固定是介绍这个 agent 能干什么, 所以
真正要从提示词里挑的是 11 条. 如果挑不出这 11 个问题, 说明提示词覆盖得不够, 那就回
第一步去补 —— 而不是在这里现编一个. 现编的那个, 就是上面说的那两个多出来的按钮.

## 10. 换完怎么验

两个检查, 各抓一半, 谁也替不了谁.

**第一个, 内容检查:**

```bash
mise run cli-check-content
```

你从第 5 篇起见过它好几次了. 换完数据集它抓的是: 新库的外键有没有成环, 提示词里点名的表在
不在, 该有的内容文件在不在, 以及那 12 个问题的渲染配额对不对.

**第二个, 构建:**

```bash
mise run build-web
```

它抓的是 `site.toml` 缺了必填的 key, 或者写了一个图标名字不存在. 这两样内容检查一个都不管,
因为它根本不解析 TOML 的图标字段.

> 第 32 篇讲过这两个是**换数据集落没落地的两半**, 谁也不覆盖谁. 两个都要跑.

**第三样, 只在换完之后跑一次:**

```bash
mise run cli-check-content -- --retired "loan,borrower,underwriting,delinquency"
```

这个参数的意思是: 上一个行业的这几个词, 现在全仓库应该一个都搜不到了. 它是一次性的, 不进
committed 的配置 —— 因为**下一次换数据集的时候, 要退休的是另外一批词**.

**这三样都过了, 还有一样只能人做**: 点开网站, 随便问几个问题, 看它答得像不像那个行业的人在
说话. 第 6 节说过为什么这一步没法自动化.

## 11. 练习

### 练习 1: 真的换一次

**目标:** 把这个应用从放贷换成产科病房排班, 并且用两个检查加一次人工验收确认它落地了.

**怎么做:**

1. 确认你在一个新分支上, 不在 `main` 上
2. 把 [`dataset-for-swap/`](../../dataset-for-swap) 里那五份文档复制进 `dataset/`, 然后
   **删掉旧的那五份** (`0*-fintech_*`). `requirements.txt` 留着
3. 删掉旧的产物: `dataset/` 下那个 `.sqlite` 文件和 `dataset/data/` 下的 `.tsv`.
   **这一步不能省** —— 文件名是被发现出来的, 留着两个库会直接抛异常
4. 敲 `/run-swap-dataset-phase-1-cn`, 跟着它走. 它会在中途问你几件文档里不会有的事
   (品牌名, agent 叫什么), 想好了再答
5. 它停在闸门那里之后, 跑那三条检查命令
6. **然后自己点开网站看一遍.** 首页说的是不是排班, 点两个问题, 看 agent 答得对不对
7. 最后跑一次 `git diff --stat`, 看看 `agent_app/` 下面有几个文件被改了

**你会观察到:**

第 7 步的答案应该是 **零**. 改动全部落在 `data/`, `dataset/` 和 `.env.defaults` 那一行. 这
就是前面三十几篇讲的那些边界买到的东西 —— 而它只有在这一刻才变得具体.

第 5 步里那个 `--retired` 参数大概率会**报出几处**. 那很正常: 旧领域的词经常残留在测试的
注释, 脚本的示例, 或者某一段没人注意到的文案里. 逐个看一眼, 该改的改掉.

第 6 步是唯一没有绿色对勾的一步, 也是唯一能发现全程撒谎那种状态的一步.

> **关键洞见:** 一次成功的换数据集, 它的 `git diff` 应该是一个很整齐的形状 —— 全部落在
> 内容, 一点不落在代码. 如果你发现自己在改 `agent_app/`, 那不是这次换数据集的需求, 那是
> 一条边界被破了.

### 练习 2: 逐条追溯那 12 个问题的出处

**目标:** 亲手验证那条串行推导链有没有被真正执行, 而不是听 AI 说它执行了.

**怎么做:**

1. 打开换完之后的 [`data/site.toml`](../../data/site.toml), 找到那 12 条 kickstart 问题
2. **挑其中 4 条**, 挑的时候有意挑那种听起来最具体的
3. 对每一条, 打开新的 [`data/system-prompt.md`](../../data/system-prompt.md), 到分析索引
   那一节里去找它的出处
4. 按下面这张表给每一条打个结果:

| 结果 | 意思 |
| :--- | :--- |
| **找到了** | 这一条是从提示词推出来的, 链条成立 |
| **意思对得上但措辞不同** | 正常. 第二步允许换措辞 |
| **提示词里根本没有这个分析** | **这就是即兴发挥**, 链条在这一条上断了 |

5. 如果出现第三种, 回答一句: 用户点了这个按钮会发生什么, 以及**有没有任何检查会告诉你**
6. 最后回答一句: 那条铁律说下游不能新增能力. 假设你现在真的很想让首页多一个分析, 正确的
   做法是什么

**你会观察到:**

如果流程被正确执行了, 四条应该全部落在前两种. 出现第三种也不用慌 —— 找出来就是这个练习的
目的, 而且修法很简单: 要么把那个分析补进提示词, 要么把那个问题换掉.

第 5 步的答案是: agent 会去查数据库, 然后**编一段听起来很专业的话**. 而** 没有任何检查会
告诉你**, 因为那个问题的渲染配额是对的, 表名是对的, 文件都在 —— 第 32 篇讲的那四项检查
一项都不管这件事.

第 6 步的答案是: **先改提示词, 再回来改这里.** 顺序反过来就等于在链条上打了一个洞.

> **关键洞见:** 一个流程说自己是串行的, 和它真的串行了, 是两回事. 而检验的办法永远是同一个:
> **拿下游的产物, 回上游去找它的出处.** 找不到出处的那一条, 就是凭空长出来的.

## 12. 回顾: 我们学到了什么

| 概念 | 一句话 |
| :--- | :--- |
| 换的是哪三样 | 一个提示词, 一个数据库, 一个网站. 必须同时换, 而且必须一致 |
| skill 是什么 | 一份提交进仓库的, 写给 AI 的操作手册. 敲一条命令就整份塞进对话 |
| 什么时候值得写成 skill | 要保持一致的点多到人读一遍记不住的时候. 这件事有三十几个 |
| 它换掉了你的角色 | 你不再是对着清单一条条改的人, 你是给输入和做验收的人 |
| 它保证不了什么 | 它保证每一处都被改到, 保证不了改得对. 后者只能人验 |
| 唯一要改的配置 | `SCHEMA_NAME`. 新数据落在新 schema 里, 旧的那套原封不动 |
| 那条最硬的承诺 | `agent_app/` 一行不改. 一次正确的换数据集, diff 里不该有它 |
| 全程撒谎 | 换到一半的状态能跑, 能构建, 测试全绿, 只是每句话都不对 |
| 为什么两条命令 | 一个长 skill 跑到后半段常常已经被压缩掉了, 而阶段二正好在末尾 |
| 中间那道闸门 | 是人. 内容一致性没有任何自动检查能替你确认 |
| 串行推导 | 每一步只从上一步的产物推导, 于是漂移根本没有机会发生 |
| 那条铁律 | 提示词定义能力边界. 想加一个分析, 唯一的合法起点是提示词 |
| 两个检查 | 内容检查管外键提示词和配额, 构建管 key 和图标名. 谁也不覆盖谁 |
| 那个只用一次的参数 | 退休词表是一次性的, 因为下次要退休的是另一批词 |

## 13. 导师寄语

**为什么这一篇值得认真读:**

因为它是这门课的兑现时刻.

前面三十几篇讲的每一条边界, 听起来都有点抽象: 文件名为什么要靠发现, 表名为什么两边必须一样,
文案为什么不能写在组件里, 配置为什么只能有一个家. 每一条单独看都像是洁癖.

**这一篇把账一次算清.** 你跑完 `git diff --stat`, 看到 `agent_app/` 下面零个文件被改, 那个
数字就是前面所有洁癖的收益. 换一个没守这些边界的项目做同一件事, 你会在几十个组件里搜字符串,
在几个地方各改一遍表名, 然后在三天后发现有一处没改到.

**还有一句想说.** 这一篇最值得带走的其实不是换数据集这个技能, 是**串行推导那个手法**. 你以后
一定会遇到这种局面: 好几样东西必须讲同一个故事, 而没有任何编译器管得着它们. 那时候大多数人
的第一反应是加检查. 而这一篇给的答案是: **先看看能不能改成一条链.** 检查只能发现漂移, 顺序
能让漂移不发生, 而且顺序是免费的.

**关键洞见:**

- 一致性不属于任何一个文件, 所以它坏掉的时候不属于任何一个文件报错
- 一个能跑但每句话都不对的系统, 比一个崩掉的系统危险得多
- 加检查是发现问题, 改顺序是消灭问题. 能改顺序的时候不要先想检查
- 验证一条链有没有真被执行, 就拿下游的产物回上游找出处
- 一次改动的 diff 的**形状**, 比它的行数更能说明设计好不好

**下一步:**

阶段一做完, 内容全换了, 但页面还穿着上一个行业的衣服. 第 38 篇
([换完内容, 再换衣服](../38-redesign-the-frontend/README-cn.md)) 讲阶段二: 为什么视觉要
单独一个阶段, 以及在重新设计的时候, 哪三样东西碰了会不报错地坏掉.
