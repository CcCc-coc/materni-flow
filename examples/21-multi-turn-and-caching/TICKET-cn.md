# 让对话有记忆, 并让重复的部分变便宜

## 1. 目标

第 20 篇发了一次请求拿到一次回答. 这一篇加上记忆, 而这里有一件反直觉的事:

**模型本身完全不记得上一句话.** 每一次调用对它来说都是全新的. 你在聊天产品里感受到的连贯,
是那个产品每次都把整段历史重新发了一遍.

接受了这一点, 后面很多事情才讲得通: 为什么账单随对话变长而增长, 为什么长对话要裁剪, 为什么
后端可以是无状态的.

**这一篇最容易糊弄过去的是练习 2.** 那里要你亲手注释掉每一轮那三步里的第三步, 然后看对话
怎么慢慢变笨. 之所以必须动手, 是因为**这个 bug 不报错**: 第一轮完全正常, 第二轮看起来也还行, 第三轮
才开始丢线索. 读代码是看不出这种东西的.

后半篇讲 prompt caching, 而理解它的关键不是怎么开, 是**知道它省的是什么**. 提前说一句结论:
缓存不让请求变小, 它让同样大的请求变便宜.

---

## 2. 要做的事情

1. 读完 README, 重点是一段对话到底是怎么被记住的那一节, 抽象那一节, 和缓存省的到底是什么
   那一节.
2. 跑一个你有 key 的多轮对话脚本, 确认第三轮答对了, 并**记下三轮各自的输入 token 数**.
3. 打开那个脚本, 在循环里逐个指出那三步分别是哪几行, 并数一数三轮之后列表里有几条.
4. 有第二家 key 的话跑另一个脚本, 对比最后那行统计, 说清条数为什么不一样.
5. 跑 `04_chat_session.py`, 注意最后那个新建的会话为什么答不上来.
6. 在那个类里找到给每个实例分配独立列表的那一行, 想清楚写成共享默认值会怎样.
7. 跑 `05_prompt_caching.py`, 对比两次调用的缓存计数器, **特别确认输入 token 数没有变**.
8. 开一个叫 `21-multi-turn-and-caching` 的 branch, 下面几步都在它上面做.
9. 把第三步那一行注释掉, 再跑一次, 看三轮各自答成什么样.
10. 恢复那一行; 再把第二步发送的历史改成只发最后一条, 再跑一次.
11. 还原所有改动, 确认工作区干净.

**预计用时:** 60 到 90 分钟

## 3. 检查清单

- [ ] **模型没有记忆**: 你能解释对话的连贯感实际上是谁做出来的, 并举出至少两个由这件事推出来
      的结论.
- [ ] **那三步指得出**: 你能在脚本里指出把问题塞进列表, 把整个列表发上去, 把回答塞回列表
      这三步分别是哪几行; 也能说出三轮之后列表里有几条, 每条是谁说的.
- [ ] **弄坏过一次**: 你注释掉第三步跑过一遍, 见过前两轮正常而第三轮丢线索, 并且确认全程
      没有报错.
- [ ] **token 增长看到了**: 你记下了三轮的输入 token 数, 能说清涨的部分是什么.
- [ ] **三家的历史结构**: 你能说清为什么 OpenAI 三轮之后是七条而另外两家是六条.
- [ ] **系统提示词也重发**: 你能说清它不在历史里为什么不代表只发一次.
- [ ] **抽象买到了什么**: 你能说清把那三步收进一个方法之后, 买到的不是少写代码而是让一类
      错误不可能发生; 也能说清新建一个会话为什么答不上来.
- [ ] **缓存这件事**: 你跑过缓存脚本, 能说清两次调用的输入 token 数为什么完全一样, 变的
      是哪个数字; 也能说出最低长度门槛, 匹配的是前缀, 会过期这三条脾气.
- [ ] **工作区干净**: 练习 2 注释掉的那几行都还原了, `git status` 没有留下改动.
