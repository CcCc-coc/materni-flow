# 看懂一个配置值是怎么走到代码里的

## 1. 目标

从第 5 篇开始你已经用了那两个配置文件好几次. 这一篇讲它们**是怎么做出来的**, 而重点不在
读文件那几行, 在三个决定: 优先级怎么实现, 校验放在哪一刻, 以及为什么没有一个模块级的单例.

**这一篇要抓住的那条线是: 配置错误是这个项目里唯一一类会静默生效的错误.** 代码错了会报错,
SQL 错了会报错, 而配置填错了程序照常跑, 只是读到的不是你以为的那个值. 三个决定的形状因此
完全一样: 把一个会在很远的地方冒出来的失败, 往前挪到离原因很近的地方.

**练习 1 那个脚本不需要任何凭据, 不需要数据库, 也不需要联网.** 它手搓 Config 对象, 跑的却
是真代码, 而这本身就是这一篇一个决定的直接结果, 读到第 6 节你会明白为什么.

**卡住了别硬扛.** 把三样东西一起给 AI: 你在读哪一篇的路径, 你敲的那条命令, 以及
**终端打出来的原文** (整段复制, 不要截图, 不要只说一句报错了).
粘贴前先把连接串和 key 的片段打码.

---

## 2. 要做的事情

1. 读完 README, 重点是第 6 节校验放在构造那一刻, 和第 7 节它为什么和 `validate()` 分开.
2. 打开 `agent_app/config.py`, 找到 `load_env_files`, 数清它一共几行, 说清优先级是怎么从
   这几行里出来的.
3. 在同一个文件里找到 `__post_init__`, 列出它做的四件事, 并把前三件和第四件分成拒绝和
   归一化两类.
4. 找到 `validate`, 说清它和 `__post_init__` 查的东西性质上差在哪.
5. 跑 `.venv/bin/python examples/30-configuration/01_when_does_it_complain.py`.
6. 对照脚本的输出和 `agent_app/config.py` 的源码, 确认那四条报错逐字来自 `__post_init__`.
7. 在整个 `agent_app/` 里搜一次 `Config.new()`, 确认它没有出现在任何模块的顶层.
8. 按 README 练习 2 那张表, 给五个假想的配置项各回答两个问题: 进哪个文件, 什么时候校验.
9. 打开 `.env.defaults` 和 `.env.example`, 拿现有的值检验你上一步的判断.

**预计用时:** 45 到 70 分钟

## 3. 检查清单

- [ ] **三层优先级**: 你能说出那三层各是什么, 并解释它只靠 `load_dotenv` 不覆盖已设值这一个
      性质就成立了, 不需要任何叫优先级的函数.
- [ ] **本机覆盖会用**: 你能说出怎么让自己这一个 checkout 指向另一个 schema, 而且不碰任何
      committed 的文件.
- [ ] **构造时校验**: 你能列出 `__post_init__` 做的四件事, 并分清哪三件是拒绝, 哪一件是
      归一化.
- [ ] **为什么不放工厂里**: 你能说清校验如果写在两个工厂方法里, 测试会出什么问题.
- [ ] **两个校验的分工**: 你能说清 `__post_init__` 查形状, `validate` 查在不在, 以及为什么
      一个没有凭据的 Config 必须是合法的.
- [ ] **脚本跑过**: 你跑过那个脚本, 见过四种错误各自的报错, 并能指出每一条报错里那句告诉你
      下一步该干什么的话.
- [ ] **没有模块级单例**: 你搜过 `Config.new()`, 确认它不在任何模块顶层, 并能说清写在顶层
      会让测试失去什么机会.
- [ ] **两条判据分得清**: 对那五个假想配置项, 你能分别用是不是密钥和能不能脱离外部世界判断
      这两条判据给出答案, 并说清它们是两件不同的事.
