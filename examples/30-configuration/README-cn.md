# 配置: 一个值是怎么走到代码里的

> 这个仓库最贵的几个错误都和配置有关, 而它们的共同点是: 你要么在启动那一刻知道, 要么在
> 一个用户面前才知道.

## 1. 概览

从第 5 篇 ([把它跑起来](../05-get-it-running/README-cn.md)) 开始, 你已经用了两个配置文件
好几次了: `.env` 装密钥, `.env.defaults` 装其余一切, 判据是它是不是密钥.

那是**怎么用**. 这一篇讲**怎么做出来的**, 而且重点不在读文件这件事上, 那部分很短. 重点在
三个决定:

| 决定 | 一句话 |
| :--- | :--- |
| 优先级是三层 | Vercel 面板 > `.env` > `.env.defaults`, 而实现它只用了一个性质 |
| 校验放在构造那一刻 | 于是一个拼错的 schema 名在启动时就炸, 而不是在某个用户的第一次提问里 |
| 没有模块级的单例 | 一个写在文件底部的 `config = Config.new()`, 会让测试永远拿不到它想要的环境 |

**这一篇是主题 7 的第二篇.** 从这一组开始, 问的问题从 agent 在干什么变成了
**这些代码为什么这么摆**. 上一篇讲那个把所有东西挂起来的对象, 这一篇讲挂在它上面的第一样
东西.

### 卡住了怎么办

这一篇每一步都可能出错: 脚本跑不起来, 或者打印出来的东西和这里写的不一样.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/30-configuration/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/30-configuration/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

先说这一篇为什么值得单独占一篇, 因为读配置听起来实在不像一件需要设计的事.

**因为配置错误是这个仓库里唯一一类会静默生效的错误.**

代码写错了会报错, SQL 写错了会报错, 提示词写歪了至少答案看起来怪. 而一个配置值填错了,
程序会**完全正常地跑起来**, 只是它读到的不是你以为的那个值. 你在第 5 篇撞过一次这个模式
(那个 `"..."` 占位符), 在第 13 篇又撞过一次 (改完 `.env` 没重启).

这一篇讲的是这个仓库为了对付这件事做的几个选择. 每一个的形状都一样:
**把一个会在很远的地方冒出来的失败, 挪到一个离原因很近的地方.**

学完这个 Task, 你将能够:

1. 说清那三层优先级是怎么实现的, 以及它靠的是一个什么性质
2. 解释为什么校验写在 `__post_init__` 里而不是写在两个工厂方法里
3. 说清 `__post_init__` 和 `validate()` 分别管什么, 为什么不能合成一个
4. 解释这个后端为什么没有一个模块级的 `config` 单例
5. 亲手让四种配置错误各炸一次, 并说出它们各自在什么时候炸

## 4. 你将学到什么

一条判据, 和一个可以照搬的形状.

判据是: **一个错误应该在离它的原因多近的地方暴露?** 这个问题没有免费的答案, 越早暴露就
越要在启动时做更多工作, 而有些事在启动时根本无从知道.

形状是这个仓库给出的那个答案: **能在构造那一刻判断的, 就在构造那一刻判断**;
判断不了的, 挪到第一次真的要用它的时候, 并且**给一条说得清缺什么的报错**.

## 5. 三层优先级, 靠的是一个性质

先看要解决什么问题. 同一个值可能来自三个地方:

| 来源 | 什么时候用它 |
| :--- | :--- |
| Vercel 面板里设的环境变量 | 线上. 密钥只能在这里填, 因为 `.env` 不进 Git |
| 你自己的 `.env` | 本机. 密钥, 加上你想临时盖掉的任何值 |
| committed 的 `.env.defaults` | 兜底. 非密钥的默认值, 跟着代码一起走 |

要的效果是**上面的盖住下面的**. 一般人会怎么实现? 大概会写一个函数, 依次去三个地方找, 找到
就返回. 那样要维护一个查找顺序, 而且每加一个来源就要改那个函数.

这个仓库没有那么做. 打开 [`agent_app/config.py`](../../agent_app/config.py), 那段代码一共
四行:

```python
def load_env_files() -> None:
    load_dotenv(path_enum.path_env)
    load_dotenv(path_enum.path_env_defaults)
```

**它先读 `.env`, 后读 `.env.defaults`.** 就这样, 优先级就成立了.

### 为什么先读的那个赢

因为 `load_dotenv` 有一个性质: **它不覆盖已经设过的变量.**

所以第一行跑完, `.env` 里的值已经进了环境; 第二行再跑, `.env.defaults` 里凡是重名的都被
跳过, 只有 `.env` 没管的那些才被填进去. 结果就是先读的赢.

**那 Vercel 那一层呢?** 它根本不需要代码参与. Vercel 在进程启动之前就把面板里的变量注入
进环境了, 所以上面两行跑的时候, 它们已经是已经设过的变量, 两个文件谁也盖不住它.

一层免费, 一层靠读取顺序. 整件事没有一个叫优先级的函数.

> **这个思路值得记住**: 当你想实现一个覆盖顺序时, 先看看你用的那个工具有没有自带的
> 不覆盖已存在的值这种语义. 有的话, 顺序就是实现.

### 一个推论: 任何一行都能被本机盖掉

`.env.defaults` 是 committed 的, 你不该随便改它. 但你想让自己这一个 checkout 指向一个别的
schema, 只要在 `.env` 里写一行同名的:

```text
SCHEMA_NAME="acme_widgets_staging"
```

`.env` 先读, 所以它赢. 你不用碰任何 committed 的文件, `git diff` 也是干净的.

## 6. 校验放在构造那一刻

现在看这一篇最核心的决定.

一个 `Config` 是个 dataclass. dataclass 有一个钩子叫 `__post_init__`,
它在**对象被造出来的那一瞬间** 跑. 这个仓库在那里面放了四件事:

| 它检查什么 | 不检查的话会怎样 |
| :--- | :--- |
| schema 名是不是合法的 PostgreSQL 标识符 | 拼错的名字会被拼进一条 SQL, 报出一条离原因好几层远的数据库错误 |
| provider 名字是不是认识的那四个之一 | 一个拼错的 provider 会一路走到建模型那里才炸 |
| 开了花费上限却没给表名 | 部署会**完全正常地启动**, 直到有人打第一个字 |
| 没给 model id 就填上这家的默认值 | 每个用到 model id 的地方都要自己判断一次空值 |

前三条是**拒绝**, 第四条是**归一化**. 两者放在同一个地方, 因为它们是同一件事的两面:
**让一个 Config 对象一旦存在, 就一定是可用的.**

### 为什么不放在两个工厂方法里

这个仓库有两个建 Config 的入口, 一个给本地一个给 Vercel. 校验完全可以写在它们里面, 而且
那样看起来更自然, 毕竟校验的是从环境读来的值.

**不行, 而且理由很实际: 测试.**

测试里的 Config 不是从环境读的, 是手搓的. 如果校验住在工厂里, 那么手搓出来的那个对象
**没经过任何校验**. 于是你的测试对着一个不可能在生产出现的对象跑, 全绿, 然后线上炸.

**校验放在 `__post_init__` 里, 手搓的和从环境建的走的是同一条路.** 这一篇的脚本就是靠这个
性质写出来的: 它一个环境变量都不读, 却验的是真代码.

> **一条可以带走的判据**: 一个不变量, 应该由**创建这个对象的那个动作** 保证, 而不是由某几个
> 恰好调用了它的入口保证. 入口会变多, 而对象只有一个.

## 7. 但有一样东西构造时查不了

`__post_init__` 不检查凭据. 检查凭据的是另一个方法, 叫 `validate()`, 而它是被单独调用的.

为什么要分开? 因为**一个没有凭据的 Config 是合法的**.

想想第 5 篇: 那时候你的 `.env` 一个真值都没填, 而整个后端照常启动. 如果构造时就要求凭据,
那一篇根本不成立, 你会在起服务器那一刻就被拦住, 连首页都看不到.

所以这两个检查的性质不一样:

| | `__post_init__` | `validate()` |
| :--- | :--- | :--- |
| 什么时候跑 | 对象一造出来 | 建模型之前, 由用到它的地方调 |
| 检查什么 | 这个值的**形状** 对不对 | 这个值**在不在** |
| 不通过意味着 | 你配错了, 任何情况下都跑不了 | 你还没配, 但别的功能照样能用 |

`validate()` 由建模型那段代码调用, 所以缺凭据是在**你第一次真的要用模型的时候** 炸, 也就是
你在第 5 篇点 kickstart 看到的那条报错.

**这个位置也是挑过的.** 它可以更晚, 等 SDK 自己去抛认证错误. 那样你收到的是供应商的
原始报错, 完全指不到是哪个环境变量没设. 早一步, 换来的是一条说得清缺什么的话.

## 8. 为什么没有一个模块级的单例

最后一个决定, 它看起来是个小事, 但踩过的人都记得.

很自然的写法是在 `config.py` 底部加一行:

```python
config = Config.new()
```

然后各处从这个模块 import 那个 `config`. 这个仓库**没有** 这么写.

**因为那一行在 import 的时候就跑了.**

Python 的 import 发生在任何测试代码之前. 于是一个想测试不同配置的测试, 拿不到任何机会:
等它开始布置环境变量的时候, 那个 `config` 早就建好了, 而且是拿当时那份环境建的.

这个仓库的做法是把它挂在上一篇那个对象上, 用到才建:

```python
one.config
```

于是它在**第一次被读到** 的时候才建, 而那时候测试已经把环境布置好了.

> **同一个道理换个说法**: 一个在 import 时就产生副作用的模块, 是没法被测试的. 而
> import 时读环境, 是这类副作用里最常见的一种.

## 9. 练习

### 练习 1: 让四种配置错误各炸一次

**目标:** 亲眼分清哪些错误在构造时炸, 哪些要等到用的时候才炸.

**这个练习不需要任何凭据, 不需要数据库, 也不需要联网.**

**怎么做:**

1. 跑这一篇自带的脚本:

```bash
.venv/bin/python examples/30-configuration/01_when_does_it_complain.py
```

2. 读第 1 节那四条报错, 每一条问自己一句: **它告诉我该去改哪个文件了吗**
3. 对比第 1 节和第 3 节: 同样是配置不对, 为什么 schema 名那一条在构造时就炸, 而缺 key
   那一条要等到 `validate()`
4. 读第 4 节那个占位符的演示, 回想第 5 篇你复制 `.env.example` 的那一刻
5. 打开 [`agent_app/config.py`](../../agent_app/config.py), 找到 `__post_init__`, 确认脚本
   里那四条报错逐字来自它

**你会观察到:**

四条报错**每一条都点名了要去改哪个文件**, 甚至给了备选做法 (比如把上限关掉). 这不是碰巧,
是有人一条条写的.

而 `validate()` 那条更进一步: 它直接告诉你该加哪个环境变量名.

> **关键洞见:** 一条报错的价值不在于它说了出错了, 在于它有没有把**下一个动作** 告诉你.
> 这个仓库里凡是能预料到的失败, 报错里都带着修法.

### 练习 2: 判断五个新配置项该走哪条路

**目标:** 把这一篇那两条判据用起来, 是不是密钥, 以及能不能在构造时检查.

**怎么做:**

假设要往这个项目里加下面五个配置项. 对每一个回答两个问题:

- **A. 它进 `.env` 还是 `.env.defaults`?** 判据: 它是密钥吗
- **B. 它的校验放 `__post_init__` 还是 `validate()`, 还是不校验?** 判据: 它的形状能不能在
  没有外部世界的情况下判断

| 要加的东西 | A | B |
| :--- | :--- | :--- |
| 一个控制回答最多多少字的上限 | | |
| 一个用来发报警邮件的 SMTP 密码 | | |
| agent 一次最多调几次工具 | | |
| 一个 Sentry 的错误上报地址, 里面带一段 key | | |
| 界面上要不要显示那个思考块 | | |

然后打开 [`.env.defaults`](../../.env.defaults) 和 [`.env.example`](../../.env.example),
看现有的值是怎么分的, 检验你的判断和它们一致不一致.

**你会观察到:**

B 那一列比 A 难. 一次最多调几次工具是个正整数, 形状能查, 所以可以在构造时查; 而那个 SMTP
密码对不对, 只有真的连上去才知道, 那是 `validate()` 那一类, 甚至是不该查的那一类.

Sentry 那一条最有意思: 它**既是密钥又有形状**. 进 `.env`, 但形状 (是不是一个合法 URL)
仍然可以在构造时查.

> **关键洞见:** 是不是密钥决定它住哪个文件, 能不能脱离外部世界判断决定它什么时候被检查.
> 这是两条正交的判据, 别用一条去回答另一条的问题.

## 10. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 三层优先级 | Vercel 面板 > `.env` > `.env.defaults`. 实现它只靠 `load_dotenv` 不覆盖已设值这一个性质 |
| 顺序就是实现 | 想要覆盖语义时, 先看工具有没有自带的不覆盖语义, 有就用读取顺序表达 |
| 构造时校验 | 能靠值本身判断的错, 在对象造出来那一刻就拒绝. 于是手搓的和从环境建的走同一条路 |
| 为什么不放工厂里 | 放工厂里, 测试手搓的对象就绕过了校验, 于是测试绿而线上炸 |
| `validate()` 是另一件事 | 它查凭据在不在, 而一个没有凭据的 Config 是合法的 (第 5 篇整篇都靠这个) |
| 没有模块级单例 | 写在模块底部的那一行会在 import 时读环境, 测试永远来不及布置 |
| 报错要带修法 | 这个仓库里能预料到的失败, 报错里都写着去改哪个文件或者哪个变量 |

## 11. 导师寄语

**为什么读配置这件小事值得一整篇:**

因为它是这个项目里**唯一一类不会自己暴露的错误**. 别的地方错了都会响, 只有配置错了会安静
地生效.

而这一篇讲的三个决定, 形状完全一样: 把一个会在很远的地方冒出来的失败, 往前挪到一个离原因
很近的地方. schema 名从查询深处挪到启动; 缺凭据从 SDK 的原始异常挪到一条人话; 配置对象从
import 时挪到第一次被读到.

**这个动作有一个通用的名字叫 fail fast**, 但名字不重要, 重要的是那个问题:
**这个错误最早能在什么时候被发现?** 你在自己的项目里每加一个配置项, 都值得问一遍.

**关键洞见:**

- 配置错误是唯一一类会静默生效的错误, 所以它值得被特殊对待
- 不变量应该由创建对象的那个动作保证, 而不是由某几个恰好调用了它的入口保证
- 一个在 import 时读环境的模块是没法被测试的
- 报错的价值不在于说出错了, 在于说出下一个动作

**下一步:**

配置讲完了, 但上面反复提到测试: 手搓的 Config, 布置环境的时机, 绕过校验的风险. 第 31 篇
([没有一个测试连网](../31-tests-without-network/README-cn.md)) 讲这个仓库的测试是怎么组织
的, 以及它凭什么做到一个连数据库, 连 AWS, 连大模型的应用, 整套测试跑起来一个网络请求都不发.

## 12. 速查

**两个文件, 一条判据:**

| | `.env` | `.env.defaults` |
| :--- | :--- | :--- |
| 装什么 | 密钥 | 其余一切 |
| 进 Git | 不进 | 进 |
| 加载顺序 | 先, 所以它赢 | 后, 补空缺 |

**两个校验, 两种性质:**

| | 什么时候 | 查什么 |
| :--- | :--- | :--- |
| `__post_init__` | 对象一造出来 | 值的形状 |
| `validate()` | 建模型之前 | 凭据在不在 |

**跑一次那四种错误:**

```bash
.venv/bin/python examples/30-configuration/01_when_does_it_complain.py
```
