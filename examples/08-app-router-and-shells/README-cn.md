# 从你看得见的东西, 找到看不见的代码

> 你已经把界面跑起来了, 屏幕上那些东西你都认得. 这一篇就从它们出发, 反向摸清底下的代码
> 是怎么组织的.

## 1. 概览

先把话说清楚, 免得你用错力气.

**这一篇不是要教你前端.** 你不需要会写 React, 不需要记住 Next.js 的 API, 不需要看懂任何一
段 JSX 的语法. 这门课的学生来自各种背景, 有人做分析, 有人做数据, 有人根本没碰过前端, 而
这门课的终点也不是把你变成前端工程师.

那这一篇要干什么?

**建立方位感.** 你以后要改这个界面: 换掉文案, 换掉配色, 换一个业务领域. 到那时候你需要
知道的不是这段代码怎么写的, 而是**这样东西住在哪儿**. 这是两件完全不同的事, 而后者便宜
得多, 也有用得多.

而摸清一个陌生代码库最好的抓手, 恰好就在你眼前: **屏幕上那些你已经看得懂的东西.**

### 读不懂的地方, 别跳过去

再提醒一次这条读法, 因为这一篇会第一次密集出现前端的名词.

这门课很长, 第一优先级是**让你先跑通**, 所以正文里很多东西只讲到你现在需要知道的那个程度.
遇到不懂的, 敲 `/showcase-learn-cn`, 把那一段原样复制给它, 追问到懂为止.

**尤其是这一篇, 你会看到 JSX, props, 组件这些词.** 看不懂一行代码不用自责, 那不是这一篇要
考你的东西. 但也不要装作看懂了往下翻.

---

## 2. 学习目标

大多数人打开一个陌生项目, 第一反应是从第一个文件开始读. 这个做法在小项目里勉强能用, 在
一个几百个文件的项目里必然失败: 读了两百个文件, 脑子里一条线都没有, 因为你不知道哪些重要,
也不知道它们之间是什么关系.

**从看得见的东西倒推, 是一个完全不同的路子.** 它的好处是每一步都有一个明确的目标:

- 你指着屏幕上那句话, 问它是从哪儿来的. 这个问题有唯一答案
- 找到之后, 你顺手就知道了这一类东西都住在哪儿
- 重复几次, 那张地图就自己长出来了

这个方法不只对前端有用. 你接手任何一个别人写的系统, 只要它有一个你能观察的输出 (一个页面,
一份报表, 一条日志, 一个接口返回值), 都可以这么倒推.

学完这个 Task, 你将能够:

1. 用三步法从屏幕上任意一块内容, 倒推到画出它的那个文件
2. 说出这个界面分成哪几层, 每一层归哪个目录管
3. 认出网址和目录之间的对应关系, 包括两个不进网址的特殊目录
4. 说出有哪几样东西是肉眼看不见的, 以及怎么发现它们的存在
5. 把一个你不懂的改动交给 AI 拆解, 并自己验证它说得对不对

## 3. 前置知识

- 完成第 4 篇 (把它跑起来), 界面已经能在本地打开
- 完成第 5 篇 (读一遍这个仓库), 知道 `app/` 和 `components/` 大致归谁管
- 会用编辑器的全局搜索. 这一篇一半的动作是搜索

**不需要** 会 React, 不需要用过 Next.js, 不需要看懂 JSX.

---

## 4. 你将学到什么

一个方法, 一张地图, 和一次让 AI 帮你拆问题的经历.

那个方法是三步, 而且它比这一篇讲的任何一个具体知识都耐用:

> **看见一块东西, 搜它身上的文字, 顺着找到的文件看它属于哪一层.**

---

## 5. 三步法

把开发服务器起起来, 浏览器打开本地 3000 端口, 然后跟着做一次.

### 第一步: 指着一块东西

随便挑一块你在屏幕上看得见的内容. 一句话, 一个按钮, 一张卡片都行.

比如首页那个大按钮上写的字, 或者 agent 页输入框里那句灰色提示.

### 第二步: 搜它身上的文字

把那句话复制出来, 在编辑器里全局搜索. **绝大多数情况下你会直接搜到一个文件.**

这一步能成立, 靠的是一个很朴素的事实: 屏幕上显示的字, 一定在某个文件里存在着. 它可能被
拆开了, 被拼接了, 但只要你搜一个足够长的片段, 通常一搜一个准.

搜不到就换个更短的片段, 或者换一句更独特的话. 如果一句话在整个仓库里都搜不到, 那本身就是
一条信息: 它可能是拼出来的, 或者来自数据库.

### 第三步: 看它属于哪一层

搜到的文件不是终点, 是起点. 现在看这个文件在哪个目录下, 那个目录说明了它是什么角色:

| 你搜到的文件在 | 说明它是 |
| :--- | :--- |
| `data/` | **一句文案**. 界面上说的话住在这里, 不在代码里 |
| `app/` | **页面或者壳**. 决定一个网址渲染什么, 或者一组页面外面套什么 |
| `components/` | **一块界面积木**. 可以在多个地方复用的那种 |
| `lib/` | **后勤**. 不直接画界面, 但界面需要的东西, 比如读配置和图标表 |
| `tailwind.config.ts` 或 `app/globals.css` | **样式**. 配色, 圆角这类跨全站的视觉设定 |

三步做完, 你不但知道了这一块在哪, 还知道了**和它同类的东西都在哪**.

## 6. 拿首页练一遍

下面这张表就是三步法的结果. 每一行都是你在首页上真的能看见的东西.

**读法**: 先在屏幕上找到那一块, 再看它的文字来自哪儿, 最后看谁把它画出来.

| 屏幕上这一块 | 文字来自 | 谁画的 | 说明 |
| :--- | :--- | :--- | :--- |
| 顶上那条导航栏, 左边两截不同颜色的名字 | `data/site.toml` 的 `[brand]` | `app/_components/layouts/Navigation.tsx` | 两个页面共用同一条导航栏. 名字被拆成两截, 是为了给后半截上一个不同的颜色 |
| 中间那个大标题 | `[home.headline]` | `Hero.tsx` | 同样拆成两截着色. 这是首页最先被读到的一行 |
| 大标题底下那句副标题和那段介绍 | `[home] tagline` 与 `description` | `Hero.tsx` | 三层递进: 名字, 一句话, 一段话 |
| 那个打开长说明的按钮 | `[home.businessContext] triggerLabel` | `Hero.tsx` | 按钮上的字在文案里, 按下之后弹出的那一整篇正文在 `data/business-context.md` |
| 四张能力卡 | `[[capabilities]]` 那四条 | `components/CapabilityCard.tsx` | **同一份数据在 agent 页还会再渲染一次**, 用的是同一个组件 |
| 鼠标停在卡片上弹出的解释气泡 | 上面那四条里的 `tooltip` 字段 | `components/ConceptTooltip.tsx` | 卡片标题对内行精确, 对外行等于没写, 所以配了一段白话解释 |
| 底下那排技术栈标签 | `[home] techStack` | `Hero.tsx` | 一个字符串列表 |
| 最下面那个大的行动召唤 | `[home.cta]` | `Hero.tsx` | 点它就去 agent 页 |
| 页脚那行版权 | `[brand] footerName` | `HomePageContent.tsx` | |

看完这张表, 有两件事应该跳出来.

**第一, 文字和画它的代码是分开的.** 每一行左边都是 `data/site.toml` 里的某个位置, 右边才是
组件. 这不是巧合, 是这个项目的一条硬规矩, 第 9 篇 (文案住在一个文件里) 专门讲它.

**第二, 首页的内容几乎全挤在一个叫 `Hero.tsx` 的文件里.** 所以你要改首页的布局, 打开那一个
文件就够了.

## 7. 拿 agent 页练一遍

agent 页复杂一点, 因为它有两副面孔: 你还没开始对话时是一副样子, 发出第一条消息之后是另一副.

| 屏幕上这一块 | 什么时候看得见 | 谁画的 | 说明 |
| :--- | :--- | :--- | :--- |
| 中间那张欢迎卡, 里面又是四张能力卡 | 只在还没对话时 | `components/chat/overview.tsx` | 四张卡和首页**是同一份数据同一个组件**, 只是换了个紧凑的样子 |
| 输入框上方那 12 个可以直接点的问题 | 只在还没对话时 | `components/chat/multimodal-input.tsx` | 文字来自 `[[chat.suggestedActions]]` 那 12 条 |
| 每个按钮上那个小图标 | 同上 | `components/chat/RenderBadge.tsx` | 它在告诉你按下去会画出表格, 流程图还是柱状图 |
| 底下那个输入框和右边的发送键 | 一直都在 | `multimodal-input.tsx` | 提示文字来自 `[chat] inputPlaceholder` |
| 对话开始后顶上那条可关闭的横幅 | 只在对话开始后 | `components/chat/chat.tsx` | 和上面那张欢迎卡**永远不会同时出现** |
| agent 回答上面那个可以展开的思考块 | 对话中 | `components/chat/message.tsx` | 默认折叠, 因为 agent 每调一次工具就产生一段思考 |
| 回答正文里的表格, 流程图, 柱状图 | 对话中 | `components/chat/markdown.tsx` 和 `blocks/` | agent 交回来的只是一段纯文本, 这里把它翻译成屏幕上的东西 |
| 左边那个方形头像 | 对话中 | `components/chat/AssistantAvatar.tsx` | 里面那两个字母是写死的, 不在文案文件里 |

最后一行值得停一下. **为什么头像里那两个字母写死, 而 agent 的名字在文案文件里?** 因为那个
方块很小, 而数据集可以给 agent 起一个很长的名字. 这类判断第 9 篇会给出统一的判据.

## 8. 为什么每个页面外面都套着同一条导航栏

上面两张表里有一个共同点: 导航栏两个页面都有, 但它既不属于首页也不属于 agent 页.

答案是这个界面被套了**三层壳**, 从外到内:

| 层 | 文件 | 你在屏幕上看到的是 |
| :--- | :--- | :--- |
| 最外层 | `app/layout.tsx` | 看不见的东西: 整个网页的字体, 浏览器标签上的标题和小图标, 分享链接时的预览 |
| 中间层 | `app/(marketing)/layout.tsx` 与 `app/chat/layout.tsx` | 顶上那条导航栏. 两个页面各有一份 |
| 最里层 | 两个 `page.tsx` | 页面自己的内容 |

一个页面被画出来之前, 要先穿过外面两层. 所以你新建一个页面放进同一个分组, 它自动就带上了
导航栏, 你什么都不用做.

### 有一行东西缺了不报错

`app/chat/layout.tsx` 比另一个 layout 多挂了一样东西: 那种一闪而过的提示条的容器.

少了它, chat 界面里每一次弹提示的调用都会
**静默地什么都不做**, 包括上一条还在跑的时候你又按了回车那条提示. 不报错, 只是提示永远
不出现.

**记住这个模式, 不是记住这一行.** 这类东西的共同点是: 它是别人的功能依赖的一个前置条件,
缺了不崩, 只是功能悄悄消失. 这个仓库里这种坑不止一处.

## 9. 网址和目录的对应关系

这是这一层最后一个约定, 而且它是纯记忆性的, 记住就行.

**`app/` 下面的目录层级就是网址的层级, 目录里那个 `page.tsx` 就是这个网址渲染的东西.**

| 路径 | 对应网址 |
| :--- | :--- |
| `app/chat/page.tsx` | `/chat` |
| `app/(marketing)/page.tsx` | `/` |
| `app/_components/` | 不是网址 |

两个特殊符号:

- **带括号的目录不进网址.** `(marketing)` 存在的唯一理由, 是让首页能有一个属于自己的中间层
  壳, 同时网址上看不出任何痕迹
- **下划线开头的目录不当路由.** Next.js 完全不把它当网址看, 所以可以拿它把组件放在离用它的
  页面最近的地方

想亲眼确认的话, 跑一次 `mise run build-web`, 输出里有一张路由表, 你会看到 `/` 和 `/chat`
两行, 而 marketing 这个词一次都不出现.

## 10. 有些东西肉眼看不见

到这里为止, 所有东西都能从屏幕倒推回去. 但有几样不行, 因为它们**没有对应的可见元素**.

| 看不见的东西 | 它在决定什么 | 怎么发现它 |
| :--- | :--- | :--- |
| 一段代码跑在服务器上还是浏览器里 | 它能不能读文件, 能不能记住状态, 能不能响应点击 | 看文件顶部有没有 `"use client"` 这一行 |
| 页面是构建时生成的还是每次请求现算的 | 改完文案要不要重新构建才看得到 | 跑 `mise run build-web`, 看路由表里的标记 |
| 页面的标题和分享预览 | 浏览器标签上显示什么, 发到聊天软件里长什么样 | 看浏览器标签, 或者在页面上右键查看源代码 |

**第一条是这一层里最要紧的**, 值得用一句话记住:

> **读盘的往上放, 有状态的往下放, 中间用 props 连.**

翻译成人话: 需要读文件的代码放在外层的页面里, 因为它跑在服务器上, 碰得到文件; 需要记住
东西或者响应点击的组件放在里层, 因为它要被送到浏览器里跑; 中间靠传参数连起来.

`app/chat/page.tsx` 全文就三行, 干的就是这件事: 读一次文案, 传下去.

**你现在不需要能自己判断该放哪边.** 你需要的是知道这条线存在, 以及当 AI 告诉你某个改动
要加或者去掉 `"use client"` 时, 你知道它在说什么.

## 11. 卡住了, 让 AI 帮你拆

这一篇的方法有一个明确的边界: **它只能带你找到入口, 带不了你穿过实现.**

你搜到了 `Hero.tsx`, 打开一看两百行. 这时候硬读是最差的选择. 正确的做法是把它变成一个问题
交出去.

### 好用的问法有三种

**一, 指着一块东西问它在哪:**

```text
首页上四张卡片鼠标悬停时会弹出解释气泡. 这个气泡的文字来自哪个文件, 由哪个组件画出来?
不用解释代码, 告诉我文件路径和它们之间的关系就行.
```

**二, 问一个改动要动哪些文件:**

```text
我想把 agent 页那 12 个建议问题改成 6 个. 请只告诉我要改哪些文件, 每个文件改什么,
以及有没有什么地方改了这里就必须跟着改的. 先不要动手.
```

**三, 把一段看不懂的代码丢给它, 但限定问题:**

```text
下面这段代码我看不懂. 我不需要学 React, 只需要知道它在页面上对应的是哪一块东西.
```

### 三种问法有一个共同点

**它们都限定了答案的形状.** 第一种要文件路径, 第二种要改动清单, 第三种要对应关系.

不限定的话, 你会收到一篇关于 React 组件生命周期的教程, 而那不是你要的.
**你要的是方位, 不是知识.**

第二种问法尤其值得练, 因为它正是你以后真正会做的事: 你想改一样东西, 但不知道从哪儿下手.
而它的答案你**可以自己验证**: 拿三步法去搜一遍它说的那几个文件, 看它说得对不对.

## 12. 练习

### 练习 1: 倒推三次

**目标:** 把三步法变成肌肉记忆.

**怎么做:**

起开发服务器, 打开浏览器, 然后对下面三样东西各走一遍三步法. 每一样都要写下两件事:
**它的文字来自哪个文件, 由哪个文件画出来.**

1. agent 页输入框里那句灰色提示文字
2. 首页顶上导航栏右边那个按钮上的字
3. agent 页那 12 个建议问题里的任意一个

搜不到就换个片段再搜. 三样都做完之后, 对着第 6 节和第 7 节那两张表核对.

**你会观察到:**

第 1 和第 3 样都能搜到 `data/site.toml`, 但第 2 样搜到的是一个组件文件, 文案文件里根本没有.
这个差别不是疏忽, 它是有理由的, 而理由第 9 篇会讲.

> **关键洞见:** 搜索的结果落在哪个目录, 本身就是答案的一半. 落在 `data/` 说明它是文案,
> 落在 `components/` 说明有人决定它不该被换掉.

### 练习 2: 让 AI 拆一个改动, 然后自己验它

**目标:** 练一次真正的用法, 并养成不轻信的习惯.

**怎么做:**

1. 开一个叫 `08-app-router-and-shells` 的 branch, 确认工作区干净
2. 加载 `/about-bi-agent-app-scaffold-cn`
3. 问它这个问题, 明确要求它先不要动手:

```text
我想把首页四张能力卡改成三张. 请只告诉我要改哪些文件, 每个文件改什么,
以及有没有什么地方改了这里就必须跟着改的. 先不要动手.
```

4. **不要直接照做.** 拿三步法去验证它说的每一个文件: 那个文件真的存在吗, 那里真的有它说的
   东西吗
5. 特别留意它有没有提到一件事: 这四张卡在两个页面上都被渲染. 如果它没提, 追问一句
6. 验证完再决定要不要让它动手

**你会观察到:**

它给的清单里应该有 `data/site.toml`. 至于要不要改组件, 答案取决于它有没有意识到那四张卡是
**一份数据渲染两次** 的. 这正是你该自己去验的地方.

> **关键洞见:** AI 给的答案是一个待验证的假设, 不是结论. 而三步法正好给了你一个几分钟就能
> 验完的手段. 有验证手段的信任, 和没有验证手段的信任, 是两回事.

## 13. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 这一篇不教什么 | 不教前端, 不教框架, 不要求你看懂任何一行代码 |
| 三步法 | 看见一块东西, 搜它身上的文字, 看搜到的文件属于哪一层 |
| 搜索落点就是答案的一半 | 落在 `data/` 是文案, `app/` 是页面或壳, `components/` 是积木, `lib/` 是后勤 |
| 三层壳 | 最外层管字体和标签页, 中间层管导航栏, 最里层是页面自己的内容 |
| 网址怎么来的 | 目录层级就是网址层级. 带括号的不进网址, 下划线开头的不当路由 |
| 看不见的三样 | 代码跑在哪一侧, 页面是不是构建时生成的, 页面的标题和分享预览 |
| 那条最要紧的线 | 读盘的往上放, 有状态的往下放, 中间用 props 连 |
| 问 AI 的正确姿势 | 限定答案的形状: 要文件路径, 要改动清单, 要对应关系. 不要一篇教程 |
| 拿到答案之后 | 用三步法自己验一遍. AI 给的是假设不是结论 |

## 14. 导师寄语

**为什么这一篇不教前端:**

这门课的学生里, 有人以后往数据方向走, 有人往分析方向走, 有人往 AI 工程走. 让所有人都先去
学一遍 React, 是一件性价比极低的事, 而且学完大概率会忘.

但**所有人都需要知道东西在哪儿**. 因为你迟早要改这个界面, 而改的时候你需要的不是写代码的
能力, 是定位的能力, 加上一个能帮你写的 AI.

这两件事的差距比大多数人以为的大. 一个知道东西在哪的人, 可以把改动准确地交给 AI 并验收它;
一个不知道的人, 只能描述症状然后祈祷.

**关键洞见:**

- 面对陌生系统, 从你能观察到的输出倒推, 比从第一个文件开始读有效得多
- 你要的是方位, 不是知识. 问 AI 的时候把这一点写进问题里
- AI 给的答案是待验证的假设. 三步法就是那个验证手段, 几分钟就能跑完

第 9 篇 (文案住在一个文件里) 讲这条规矩背后的设计, 以及它和把这个 app 换成另一个 app 这件
事的关系.

## 15. 速查

**三步法:**

```text
1. 指着屏幕上一块东西
2. 复制它的文字, 全局搜索
3. 看搜到的文件在哪个目录下
```

**目录说明它是什么:**

- `data/`: 文案, 界面上说的话
- `app/`: 页面和壳, 决定网址渲染什么
- `components/`: 界面积木, 可复用
- `lib/`: 后勤, 读配置和图标表
- `tailwind.config.ts` 与 `app/globals.css`: 样式

**网址约定:**

```text
app/xxx/page.tsx      ->  /xxx
app/(xxx)/page.tsx    ->  括号不进网址
app/_xxx/             ->  下划线不当路由
layout.tsx            ->  壳, 包住这一层下面所有页面
```

**问 AI 的三种问法:**

- 这块东西的文字来自哪个文件, 由哪个组件画出来
- 我想改某某, 要动哪些文件, 有没有必须跟着改的地方. 先不要动手
- 这段代码对应页面上的哪一块. 我不需要学 React

```bash
mise run build-web
```
