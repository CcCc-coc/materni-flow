# 渲染契约: 三样东西必须同时对上

> 这是主题 7 的最后一篇, 也是这门课里唯一一个横跨前后端的话题. 三样东西住在三个文件, 三种
> 语言里, 而没有任何东西保证它们一致.

## 1. 概览

你已经分头见过这三样东西了:

| 你在哪一篇见过 | 见到的是什么 |
| :--- | :--- |
| 第 11 篇 ([agent 页](../11-the-agent-page/README-cn.md)) | 那 12 个按钮, 每个带一个 `render` 徽章和一句触发短语 |
| 第 12 篇 ([一段文本怎么变成表格和图](../12-render-text-into-blocks/README-cn.md)) | 前端那张查找表: 围栏语言到渲染器 |
| 第 25 篇 ([系统提示词](../25-the-system-prompt/README-cn.md)) | 提示词里那五节, 当时明说了留给这一篇 |

**这一篇把它们合起来.** 因为让 agent 画出一张图这件事, 不是任何一个地方能单独办到的:

```text
data/system-prompt.md            告诉模型: 看到这句话, 就吐一个 chart 围栏
        |
data/site.toml                   那 12 个按钮里, 有 3 个真的写了那句话
        |
components/chat/blocks/index.ts  前端认得 chart 这个围栏标签, 有渲染器
```

**三样缺一样, 图就出不来. 而三种缺席方式, 一个都不报错.**

这就是这一篇存在的理由, 也是它被排在主题 7 最后的理由: 它是这一组里最典型的那种东西,
一个不影响任何单元测试, 却决定读者看到什么的约定.

### 卡住了怎么办

这一篇每一步都可能出错: 脚本跑不起来, 或者你看到的输出和这里贴的不一样.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/34-the-rendering-contract/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/34-the-rendering-contract/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

这一篇讲的东西有一个专门的名字: **跨越边界的约定**.

在一个只有一种语言的项目里, 这类约定通常被编译器管着. 你改了一个函数的参数, 所有调用它的
地方立刻标红. 那是最好的情况: **约定被表达成了代码, 所以违反它是一个语法错误.**

而这个契约横跨三种语言 (Markdown 散文, TOML 配置, TypeScript 代码), 中间还夹着一个**大模型**.
没有任何编译器能看见它的全貌.

**这种约定在真实项目里到处都是.** 前端和后端约好的字段名, 两个服务约好的消息格式, 代码和
运维脚本约好的目录结构, 只要跨过一个边界, 编译器就管不着了.

所以这一篇真正的问题是: **当编译器帮不上忙的时候, 你怎么保住一个约定?**

学完这个 Task, 你将能够:

1. 说出这个契约的三半各住在哪个文件, 各负责什么
2. 描述三半各自缺席时的症状, 并说清为什么三种都不报错
3. 说出加一种新块要动的四处, 以及最常被漏掉的是哪一处
4. 解释那个把尖括号标签改写成围栏的补丁在替谁擦屁股, 以及为什么不靠改提示词解决
5. 说清哪一部分能被自动检查, 哪一部分只能手点

## 4. 你将学到什么

一张三方对照表, 和一条关于跨边界约定的通用做法.

那条做法是这样的:
**编译器管不着的约定, 要么写一个专门读全部相关文件的检查, 要么改变产生它们的顺序.**
第 32 篇讲过后者, 这一篇给你前者的一个完整例子, 而且你会看到它盖不住的那一部分在哪儿.

## 5. 三半, 各管什么

### 第一半: 提示词告诉模型什么时候吐块

`data/system-prompt.md` 里有一张触发表, 大意是:

| 用户说了这句 | 你就产出 |
| :--- | :--- |
| `as a Markdown table` | 一张 Markdown 表格 |
| `show the SQL` | 一个 sql 围栏块 |
| `as a flowchart` / `as a diagram` | 一个 mermaid 围栏块 |
| `as a bar chart` / `as a line chart` | 一个 chart 围栏块 |

**这是契约本体.** 模型不会自己知道这个 app 能画图, 是这张表告诉它的.

提示词里还有四节配套的: 围栏怎么写 (以及**绝不能** 用尖括号包起来), 什么时候该给出 SQL,
什么时候值得画图, 以及那个 chart 的 JSON 长什么样.

**这五节在换数据集的时候是逐字抄的, 只换例子.** 因为它们描述的是**前端能渲染什么**,
和哪个行业没有关系.

### 第二半: 那 12 个按钮真的说了那句话

`data/site.toml` 里那 12 条, 四类各三条. 第 11 篇和第 32 篇都讲过它, 这里只补一句它在这个
契约里的角色:

**它是那张触发表的唯一使用者.**

提示词说了看到这句话就画图, 但如果没有任何一个入口真的说那句话, 那张表就是一纸空文. 那 12
个按钮是**保证这些短语真的会被说出来** 的地方.

这也解释了为什么要有配额: 12 条全是自由问答的话, 流程图渲染器和图表渲染器谁也看不见.

### 第三半: 前端认得这个围栏标签

`components/chat/blocks/index.ts` 里那张查找表, 现在两行:

```text
mermaid -> MermaidBlock
chart   -> ChartBlock
```

没在表里的语言 (包括普通的 `python`) 全都落到那个显示原始代码的兜底渲染器.

**加一行支持一种块, 删一行关掉一种.**

## 6. 三种缺席, 三种症状, 零个报错

现在看这一篇的核心. 把上面三半各拿掉一个:

| 缺哪一半 | 症状 | 谁会发现 |
| :--- | :--- | :--- |
| **提示词那节被精简了** | 模型不知道那句话意味着什么, 用户点了按钮, 回来一段散文 | 只有点开看的人 |
| **按钮里那句短语写错一个词** | 触发不稳定, 尤其在小模型上. 有时出图有时不出 | 只有多点几次的人 |
| **查找表里没有这个语言** | 块落到兜底渲染器, 用户看到一坨原始 JSON | 只有点开看的人 |

**三种都不报错.** 没有测试会红, 没有构建会失败, 没有日志会有异常.

更麻烦的是第二种: 它**时好时坏**. 一个措辞不精确的问题, 强一点的模型能领会意图, 弱一点的
不能. 于是你在自己机器上试是好的, 换个更便宜的模型上线就坏了.

亲手看一次这三半现在的状态:

```bash
.venv/bin/python examples/34-the-rendering-contract/01_check_all_three_halves.py
```

这个脚本把三个文件都读了一遍, 分别列出各自声明了什么, 然后对一遍. 它最后那一段值得读:
**只看任何一个文件, 你能发现的问题是哪些, 发现不了的又是哪些.**

## 7. 那个检查盖住了多少

第 32 篇讲的那个内容检查里, 有一项就是查这个契约的:

```bash
mise run cli-check-content
```

它的渲染配额那一项**两个方向都查**: `render` 声明的和措辞产生的对不对得上, 以及四类是不是
各三条.

**但它只盖住了第二半.**

| 哪一半 | 有自动检查吗 |
| :--- | :--- |
| 提示词里那张触发表还在不在 | **没有** |
| 12 个按钮的 `render` 和措辞一致吗 | **有**, 两个方向 |
| 前端查找表里有没有这个语言 | **没有** |

而且还有一件比这三样都难的事:

> **模型真的照做了吗?**

配额检查能证明**问法写对了**, 证明不了**模型照做了**. 这两件事之间的差距只有人点一次才看
得见, 这正是第 32 篇结尾说的那三件完全没有自动检查的事之一.

所以换完数据集之后, 那 12 个按钮**必须手点一遍**: 3 条出表格加 SQL, 3 条出流程图, 3 条出
图表. 出不来最常见的原因就是提示词那一节被当成冗余精简掉了.

> **一条判据**: 当一个约定的最后一环是一个**概率性的东西** (一个模型, 一个用户, 一个网络),
> 那么无论前面几环检查得多严, 最后都必须有一次人工验证. 检查能保证输入是对的, 保证不了
> 输出.

## 8. 加一种新块: 四处, 第三处最常漏

假设你想加一种新的块, 比如让 agent 画时间线. 要动的地方是:

| 第几处 | 动什么 | 漏了会怎样 |
| :--- | :--- | :--- |
| 一 | 在 `components/chat/blocks/` 下写一个渲染器组件 | 没得画 |
| 二 | 在那张查找表里加一行 | 块落到兜底渲染器, 用户看到原始文本 |
| 三 | **在提示词里告诉模型什么时候产出这种块** | **渲染器一行代码都跑不到, 而前端测试全绿** |
| 四 | 如果它也要进那 12 个按钮: 配额, 短语, 加一个徽章图标 | 功能有, 但没有入口, 没人会用到它 |

**第三处是分界线**, 而且它最容易被漏, 理由很好理解: 前面两处是写代码, 第三处是
**改一份散文文档**, 而它躺在另一个目录, 属于另一个心智模型.

漏掉它的症状特别有欺骗性: 你写完组件, 跑测试全绿, 甚至可以手动构造一段带那个围栏的文本
喂进去看到它画出来了. **一切看起来都对.** 只有当你意识到没有任何东西会产出那个围栏时,
才会发现这个功能等于不存在.

> **一句话记住**: **前端认得一个格式, 不等于模型会输出它.**

## 9. 一个专门给小模型擦屁股的补丁

最后讲一个细节, 因为它示范了当契约的一端是模型时会发生什么.

这个项目要跑得起很小的模型. 而小模型有一个毛病: 它们本来就在输出 `<thinking>` 这样的
尖括号标签, 于是**把这个习惯泛化了**, 它会把一段完好的图表内容包进 `<chart>` 标签里,
而不是用围栏.

后果很阴: Markdown 渲染器把未知的尖括号标签**静默丢弃**. 于是回答里写着这是图表, 下面
什么都没有, 而且没有任何报错解释为什么.

提示词里已经明确写了绝不能用尖括号标签. **但对那么小的模型, 调措辞救不了.**

所以后端加了一个补丁: 在把回答交给前端之前, 把那种独占一行的标签**机械地改写成围栏**.
你在第 26 篇 ([最后一条消息不一定是答案](../26-explain-the-reasoning/README-cn.md)) 见过
它, 当时它是三小步里的第三步.

这里值得学的是那个**取舍的判据**:

| 什么时候调提示词 | 什么时候写补丁 |
| :--- | :--- |
| 模型有能力理解你的意图, 只是没做对 | 模型能力不够, 说多少遍都没用 |
| 那个映射有歧义, 需要判断 | 那个映射**无歧义**, 机械可做 |

`<chart>` 改成 chart 围栏, 属于第二类: 它无歧义, 所以机械地做掉比反复调措辞可靠得多.

> 但要注意一个副作用: **这个补丁让提示词那一节看起来更像是可以精简的了**, 反正有东西
> 兜底嘛. 不是的. 补丁只处理已经产出了内容但包错了壳的情况; 提示词那一节管的是模型愿不愿意
> 产出内容. 少了它, 补丁没有东西可以修.

## 10. 练习

### 练习 1: 把三半摆在一起看一遍

**目标:** 亲眼确认这三样东西住在三个不同的文件里, 而且没有任何东西保证它们一致.

**这个练习只读文件, 不改任何东西, 不需要凭据也不需要联网.**

**怎么做:**

1. 跑这一篇的脚本:

```bash
.venv/bin/python examples/34-the-rendering-contract/01_check_all_three_halves.py
```

2. 对着输出, 把三个文件各打开一次, 找到脚本读的那一段:
   - 提示词里那张触发表
   - `data/site.toml` 里 12 条中任意一条的 `render` 和 `action`
   - `components/chat/blocks/index.ts` 里那张两行的查找表
3. 读脚本最后那一段 (每一半单独看会漏掉什么), 对每一条问一句:
   **这种情况下有没有任何东西会红?**
4. 再跑一次内容检查, 看它这一项报的是什么:

```bash
mise run cli-check-content
```

5. 回答一句: 那个检查盖住了三半里的哪一半, 另外两半为什么没盖

**你会观察到:**

三半住在三种不同的语言里: 散文, 配置, 代码. 这就是为什么没有编译器能管它们,
**它们之间不存在任何一种共同的语法.**

而那个内容检查只盖住了中间那一半. 另外两半没盖不是疏忽, 是因为一个字符串在提示词散文里
出现或者不出现, 判据没那么机械 (回想第 32 篇那条判据).

> **关键洞见:** 编译器能保护的约定, 是那些能被表达成同一种语言里的类型的约定. 一旦跨过
> 语言边界, 你就得自己造一个检查, 或者自己造一个顺序.

### 练习 2: 让 AI 拆一个加块的改动, 看它记不记得第三处

**目标:** 用第 4 篇那套派活方法, 验证一个横跨前后端的改动.

**这个练习不改任何代码.**

**怎么做:**

1. 加载 `/about-ba-agent-app-scaffold-cn`
2. 派这个任务, 明确要求先出计划:

```text
我想让这个 agent 能画时间线, 用一种新的 timeline 围栏块.
先告诉我要改哪些文件, 每个文件改什么, 然后停下来等我确认, 不要动手.
```

3. 读它给的清单, **重点看有没有 `data/system-prompt.md`**
4. 如果它只说了前端那两步, 追问一句:

```text
只改前端的话, 这个渲染器会被调用到吗?
```

5. 再追问一句, 看它答不答得上来:

```text
如果我还想让它出现在那 12 个按钮里, 还要动什么?
```

6. 拿第 8 篇那个三步法, 验证它说的每个文件路径真的存在

**你会观察到:**

漏掉第三处是很常见的, 因为前两处在同一个目录里, 而第三处在 `data/` 下, 是一份散文文档.
一个只看代码的思路很自然会停在第二处.

第 5 步那个追问的答案有三样: 配额, 触发短语, 加一个徽章图标. 少一样功能就有但没人用得到.

> **关键洞见:** 一个横跨多个文件的改动, 最容易漏掉的是**换了一种语言的那一处**. 派活的
> 时候把这句话直接写进要求里 (这个改动会不会涉及提示词?), 比事后 review 便宜得多.

| 东西 | 一句话 |
| :--- | :--- |
| 三半各是什么 | 提示词告诉模型什么时候吐块, 12 个按钮真的说那句话, 前端认得那个围栏标签 |

## 12. 导师寄语

**为什么这一篇被放在主题 7 的最后:**

因为它把这一组六篇的主题推到了最远的地方.

这一组从头到尾在讲同一件事: **有些正确性不属于任何一个模块.** 配置的正确性不属于任何一个
读它的地方; 那条守边界的测试不验证任何功能; 内容检查读的是散文; 而这一篇讲的东西, 连一个
共同的语言都没有.

**这类正确性有一个共同的性质: 它们坏了都不报错.** 这也是为什么这一组每一篇你都会看到同一
句话反复出现.

**还有一句想说.** 你以后做的任何一个稍微复杂点的系统, 都会长出这种跨边界的约定: 前端和
后端约好的字段名, 你的代码和某个云服务约好的目录结构, 两个团队约好的消息格式. 编译器一个
都管不着.

那时候你有三条路: 造一个检查, 造一个顺序, 或者**把它写下来并且指望别人会读**. 前两条这门课
都给了具体例子, 第三条基本不管用, 而大多数项目选的就是第三条.

**关键洞见:**

- 编译器只能保护那些能被表达成同一种语言里的类型的约定
- 跨过语言边界之后, 你得自己造检查, 或者自己造顺序
- 一个约定的最后一环如果是概率性的, 那无论前面查得多严, 最后都要人验一次
- 一个横跨多文件的改动, 最容易漏的是换了一种语言的那一处
- 前端认得一个格式, 不等于模型会输出它

**下一步:**

主题 7 到这里讲完了. **这个项目的每一层你现在都拆开看过了**: 界面, 数据, agent, 以及这一组
讲的那些让它不烂掉的东西.

接下来是这门课的落点. 第 35 篇 ([把它送上公网](../35-deploy-to-vercel/README-cn.md))
把它送上公网, 从那一刻起, 这个项目才真的存在于你自己电脑之外.
