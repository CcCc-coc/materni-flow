# SQL 工具: 只读是怎么保证的

## 1. 目标

三只手里最要紧的那只. 它的处境特殊: ** 这是整个 app 里唯一一个把外部来的字符串直接送进数据库
的地方**, 而那个字符串不是人写的, 是模型现编的.

**这一篇的核心问题是: 怎么保证模型改不了数据?**

大多数人的第一反应是拦住危险的词 —— 看到 `UPDATE` `DELETE` `DROP` 就拒绝. 这条路有两个问题,
第二个致命: 它**分不清代码和数据** (一条 `WHERE note = 'do not delete'` 会被误伤), 而且它
**永远漏得掉** —— 一个黑名单的可靠性等于写它的人当时的想象力, 那不是保证, 是运气.

这个项目换了个层次: **让所有 SQL 都跑在一个永远不会被提交的事务里.** 不管模型写出什么,
它都留不下来, 因为没有人会去提交那笔事务.

**练习 1 要你亲手当一次攻击者**, 往那个脚本里加语句试着改掉数据. **试不出来才是目的** ——
花十分钟找不到出口, 比读十遍代码更信得过这个设计.

带走的判据是: **能建立在机制上的安全性, 不要建立在规则清单上.** 清单要靠人想全, 机制不用.

## 2. 要做的事情

1. 读完 README, 重点是第 2 节那两个黑名单的问题, 和第 7 节抛还是返回那一段.
2. 开一个叫 `23-the-sql-tool` 的 branch.
3. 跑 `01_rollback_proves_it.py`, 三条结果逐条读懂.
4. 想清楚第三条为什么能通过关键词检查, 以及你**怎么知道** 它真的执行了.
5. 在 `CASES` 列表里加第四条, 自己写一条试图真正改掉数据的 SQL, 跑, 看那个数字动没动.
6. 至少试三种不同思路: 换一种写操作, 分号拼两条, 或者别的你想到的.
7. 全部还原.
8. 打开 `agent_app/sql_utils.py`, 找到那句说关键词检查不是安全边界的注释.
9. 找到那个显式写出来的回滚, 想清楚为什么不靠上下文管理器自己回滚就完了.
10. 找到处理数据库报错那一段, 想清楚为什么只取那一句话而不用完整文本.
11. 对三处代码各判断一次该抛还是该返回: 这个 SQL 工具, 第 17 篇找数据集文件的函数,
    第 20 篇发现零张表的地方.
12. 想清楚为什么后两个是抛, 以及如果第 20 篇那处改成返回文字会发生什么.

**预计用时:** 60 到 90 分钟

      住在同一个文件里.
