# SQL 工具: 只读是怎么保证的

> 你要让一个模型去查你的生产数据库. 怎么保证它改不了东西?
> 直觉的答案是拦住危险的词. 这一篇讲为什么那条路走不通.

## 1. 概览

上一篇讲了工具是怎么定义的, 这一篇拆开其中最要紧的那一只: **跑 SQL 的那只**.

它的处境有点特殊: **它是这个 app 里唯一一个把外部来的字符串直接送进数据库的地方.** 而且那个
字符串不是人写的, 是模型现编的.

所以它要同时做到三件事:

| 要做到 | 难在哪 |
| :--- | :--- |
| **改不了数据** | 模型可能写出任何东西, 包括你没想到的写法 |
| **失败了 agent 还能继续** | 一个异常会直接结束这一轮对话 |
| **结果模型读得懂** | 而且要便宜 |

代码在 [`agent_app/sql_utils.py`](../../agent_app/sql_utils.py), 一共一百二十行, 一个类都
没有, 全是普通函数.

## 2. 学习目标

先把第一件事拿出来单说, 因为它是这一篇的核心, 而且大多数人的第一反应是错的.

### 直觉答案: 拦住危险的词

你要防模型改数据, 最自然的想法是**检查它写的 SQL, 看到危险的词就拒绝**:

```text
如果 SQL 里出现 UPDATE / DELETE / DROP / INSERT / TRUNCATE ... 就拒绝
```

这个做法有个名字叫**黑名单**, 而它在这里有两个问题, 一个比一个致命.

### 问题一: 它分不清代码和数据

看这条完全正常的查询:

```sql
SELECT * FROM note WHERE content = 'do not delete this record'
```

里面有 `delete` 这个词, 但它在一个字符串里, 是**数据**, 不是命令. 黑名单看不出这个区别,
于是它拒绝一条合法查询.

**而这个误伤是有代价的**: 模型收到一句被拒绝, 它不知道为什么, 于是换一种写法再试 —— 通常
是更绕更奇怪的写法. 你不但没保护到什么, 还把 agent 逼笨了.

### 问题二: 它永远漏得掉

这才是真正致命的. 黑名单要求你**事先想到所有危险的写法**, 而这是做不到的:

- SQL 有一堆你可能没想到的写法能改数据
- 每种数据库还有自己的扩展
- 而模型很擅长写出你没见过的 SQL

**一个黑名单的可靠性, 取决于写它的人当时想到了多少.** 那不是保证, 那是运气.

### 这个项目的答案

它不去猜哪些 SQL 危险, 它换了个层次:

> **让所有 SQL 都跑在一个永远不会被提交的事务里.**

数据库的事务有个性质: **在你说提交之前, 你做的一切都是临时的**, 一旦回滚就像没发生过.

于是不管模型写出什么 —— 你想到的, 没想到的, 明天新发明的 ——
**它都改不了数据, 因为没有人会去提交那笔事务**.

| | 黑名单 | **永远回滚** |
| :--- | :--- | :--- |
| 要不要预判危险写法 | 要, 而且要全 | **不要** |
| 漏一个会怎样 | 数据被改了 | **漏不了, 因为不靠预判** |
| 会不会误伤合法查询 | 会 | 不会 |
| 保证来自 | 写规则的人的想象力 | **数据库自己的机制** |

> **一条很通用的判断**: 能把安全性建立在**机制** 上, 就不要建立在**规则清单** 上.
> 清单要靠人想全, 机制不用.

学完这个 Task, 你将能够:

1. 说清黑名单式防护的两个问题, 并解释为什么第二个更致命
2. 解释永远回滚的事务为什么是一个真正的保证
3. 说出那个开头关键词检查还留着的原因, 以及它**不是** 安全边界这件事
4. 解释为什么每一个失败都被返回成文字, 而不是抛出异常
5. 说清结果为什么拼成 Markdown 表格

## 5. 亲手验证一次

这一篇目录下有个脚本, 拿三条语句走一遍这只手, 每条前后都直接去文件里读一个数字:

```bash
.venv/bin/python examples/23-the-sql-tool/01_rollback_proves_it.py
```

它跑的是**本地那份种子**, 不碰云端. 输出是这样:

```text
--- a plain SELECT
    tool said: | grade_code   |   interest_rate |
    grade A interest_rate: 5.5 -> 5.5   UNCHANGED

--- a bare UPDATE
    tool said: Error: Invalid query: this agent is read-only, start with SELECT or WI
    grade A interest_rate: 5.5 -> 5.5   UNCHANGED

--- an UPDATE hidden behind a CTE
    tool said: Error formatting result: This result object does not return rows.
    grade A interest_rate: 5.5 -> 5.5   UNCHANGED
```

**三条的意义完全不同, 值得一条一条看.**

**第一条** 是正常查询, 没什么好说的.

**第二条** 是一条光秃秃的 `UPDATE`. 它连数据库都没到 —— 开头那个关键词检查直接拦了.

**第三条才是重点.** 它长这样:

```sql
WITH victim AS (SELECT id FROM risk_grade)
UPDATE risk_grade SET interest_rate = 99.0 WHERE id IN (SELECT id FROM victim)
```

它以 `WITH` 开头, 而 `WITH` 是**允许** 的 —— 一个只读的 agent 天天在写 CTE, 不可能禁掉它.
所以这条**顺利通过了检查, 真的送进了数据库, 真的执行了**.

你怎么知道它真的执行了? 看那句报错: 结果对象不返回行 —— 那是拼 Markdown 表格的时候才发现
的, 说明语句本身**跑成功了**.

**而那个数字一动没动.**

### 这条语句真的有杀伤力吗

值得确认一下, 否则上面的演示可能只是那条 SQL 本身写错了.

拿一份种子的副本, 把**同一条语句** 放进一个会提交的事务里跑一次:

```text
before: 5.5
after commit: 99.0
```

**同一条 SQL, 唯一的差别是有没有提交.** 所以第三条演示里那个 UNCHANGED, 完全是回滚挣来的.

## 6. 那个关键词检查还留着, 但它不是安全边界

既然回滚才是保证, 那开头那个只允许 `SELECT` 和 `WITH` 的检查还留着干什么?

**它是为了给模型一个又快又清楚的答复**, 不是为了安全.

对比一下没有它会怎样:

| | 有这个检查 | 没有这个检查 |
| :--- | :--- | :--- |
| 模型写了 `UPDATE ...` | 立刻拿到一句这个 agent 是只读的, 请用 SELECT 开头 | 送到数据库, 跑一遍, 回滚, 然后拿到一句数据库方言的报错 |
| 花了什么 | 几乎为零 | 一次数据库往返 |
| 模型读到什么 | **一句它能照做的话** | 一句它要猜的话 |

所以它是一个**效率和体验** 的东西, 不是一道防线.

**这个区分特别值得记住**, 因为把它当成防线是很自然的误会 —— 它看起来太像一道防线了. 而
误会的代价是: 有人以为安全靠它, 于是哪天为了兼容某个写法把它放宽了, 却不知道真正在承重的
是别的东西.

代码里专门写了一句话讲这件事, 说这个检查**不是** 安全边界, 回滚才是.
**一个安全保证如果在代码里看不出来, 下一次重构就会把它删掉.**

### 顺带: SQLite 需要额外一道手脚

这条只有在本地才用得上, 但它很有意思.

Python 那个 SQLite 驱动有个老毛病: 它**靠猜第一个关键词** 来决定要不要开事务,
而它**不认识 `WITH`**. 于是一条 CTE 打头的写操作会走在自动提交模式下 ——
**落盘了, 没有事务可以回滚**.

所以这个仓库开 SQLite 的时候关掉了那个猜测, 自己显式地发起事务. 代码就住在
[`sql_utils.py`](../../agent_app/sql_utils.py) 里, 和它保护的那个函数在同一个文件, 理由和
上面那句一样: **一个安全设置放得离它保护的东西太远, 下一次重构就会把它弄丢.**

## 7. 失败一律返回文字, 从不抛出

这是这只手的第二个设计, 而且它和你写普通代码的直觉是反的.

看代码你会发现每一处可能出错的地方, 都被包起来, 变成一句话返回:

| 出了什么事 | 返回的字符串 |
| :--- | :--- |
| 不是 SELECT 开头 | `Error: Invalid query: this agent is read-only, ...` |
| SQL 语法错, 表名写错 | `Error executing query: <数据库的原话>` |
| 结果拼不出表格 | `Error formatting result: ...` |
| 查出来零行 | `No result` |

**为什么不直接抛异常?**

因为**调用它的是一个模型**, 不是你的代码.

| | 抛异常 | **返回一句话** |
| :--- | :--- | :--- |
| 谁收到 | 框架, 然后这一轮对话结束 | 模型 |
| 模型能做什么 | 什么都做不了, 它已经出局了 | **看懂, 改一下 SQL, 再试一次** |
| 用户看到 | 一个失败 | 一个正确答案, 只是慢了一秒 |

这就是第 2 篇讲的那个循环 —— 想一步, 动一次手, **看结果**, 再想 —— 能转起来的前提.
**一个抛异常的工具, 会把这个循环打断.**

> **关键洞见:** 一个函数该抛异常还是该返回错误, 取决于**谁在接**. 接的是代码就抛,
> 接的是一个能自己想办法的东西, 就把话说给它听.

### 有一处很小的抠门

数据库报错的时候, 代码没有直接用那个异常的完整文本, 而是取了里面**只有那句话** 的部分.

因为完整文本会把你的整条 SQL, 所有绑定参数, 再加一个文档链接全都附上 —— 那是每条写错的
查询都要多烧的几百个 token, 而模型需要的只有那一句原因.

代码注释里还写了: 这个取法用的是一个私有属性, 万一将来的版本没有了, 退回用完整文本就行 ——
**工具会变啰嗦, 但不会坏**. 这是一个挺好的取舍写法: 用一点脆弱换一点省钱, 而且
**明确写下了脆的时候怎么办**.

## 8. 为什么结果是 Markdown 表格

第三个设计, 最短的一个.

查询结果可以拼成很多种样子, 这里选了 Markdown 表格:

| 选项 | 为什么不是它 |
| :--- | :--- |
| JSON | 每一行都要重复一遍所有列名, 明显更费 token |
| CSV | 便宜, 但列一多人就读不出来了 |
| **Markdown 表格** | 便宜, 而且**模型在训练时见过海量这种表格** |

最后那条是关键. 你给模型一种它极其熟悉的格式, 它解析出错的概率就低.

**还有一个顺带的好处**: 你打开日志的时候, 看到的是一张人也读得懂的表. 一个既省钱又让人能
读的格式, 不用犹豫.

而查出零行的时候返回的是 `No result` 这三个字 —— 上一篇讲过, 这句话**必须写进工具说明里**,
否则模型会把它当成一次失败.

## 9. 练习

### 练习 1: 跑那个证明, 然后试着自己绕过它

**目标:** 亲眼确认回滚是真的在承重, 并且试图打破它.

**怎么做:**

1. 开一个叫 `23-the-sql-tool` 的 branch
2. 跑一次 [`01_rollback_proves_it.py`](01_rollback_proves_it.py), 三条结果都读一遍
3. 想清楚第三条为什么能通过检查, 以及你怎么知道它真的执行了
4. 现在**你来当攻击者**: 在 `CASES` 那个列表里加第四条, 试着写一条能真正改掉数据的 SQL
5. 每加一条就跑一次, 看那个数字动没动
6. 至少试三种不同的思路, 比如: 换一种写操作 (DELETE, INSERT), 或者用分号拼两条语句
7. 全部还原

**你会观察到:**

那个数字不会动. 分号拼两条通常会被驱动直接拒绝 (一次只让执行一条); 而任何一条真的跑起来的
写操作, 结局都一样 —— 跑了, 然后被扔掉.

**试不出来才是这个练习的目的.** 你花十分钟没找到出口, 就比读十遍那段代码更信得过这个设计.

> **关键洞见:** 一个好的安全设计, 特征是**你想不出绕过它的角度**, 而不是你数得清它拦了
> 多少种情况. 后者说明它是个清单.

### 练习 2: 判断三处该抛还是该返回

**目标:** 把该抛异常还是该返回错误这条判据用到别处.

**怎么做:**

1. 对下面三个函数, 各回答一句该抛异常还是该返回一句话, **理由必须落在谁在接上**:
   - 那个跑 SQL 的工具 (已知答案, 当热身)
   - 第 17 篇那个找数据集文件的函数, 找到好几个的时候
   - 第 20 篇那个反射库结构的地方, 发现零张表的时候
2. 后两个都是**抛** 的. 想清楚它们和第一个的区别在哪儿
3. 然后想一个反例: 如果第 20 篇那个零张表的检查改成返回一句话给模型, 会发生什么
4. 加载 `/about-bi-agent-app-scaffold-cn`, 问它:

```text
这个仓库里有哪些地方是把失败返回成文字而不是抛异常的? 每一处的调用方是谁?
请列出来, 先不要改任何代码.
```

5. 看它有没有找到那条共同的判据

**你会观察到:**

第 3 步的答案很有意思: 模型会拿到一句这个库里没有表, 然后**它照样会努力回答** —— 编几个
表名出来. 所以那个地方必须抛, 因为**这不是模型能自己解决的问题**.

于是判据可以再说细一点: **返回一句话给模型, 前提是它真的有办法改.** 它改不了的事, 就该
当场炸给人看.

> **关键洞见:** 同一个仓库里两种相反的做法同时是对的, 靠的不是风格统一, 是
> **每一处都想清楚了谁在接, 以及那个接的人能做什么**.

## 11. 导师寄语

**为什么这一篇值得认真读:**

这一百二十行代码里有一个我很喜欢的思路转换, 而它在很多地方都用得上.

面对让模型查库但别改坏东西这个需求, 大多数人会往**枚举** 的方向走: 列出危险的操作, 一个个
拦. 这条路的问题不在于它拦不住第一个, 在于**你永远不知道自己漏了第几个** —— 而且漏掉的
那天你不会知道.

这个项目往**层次** 的方向走了一步: 不去管跑的是什么, 而是让跑完的东西**没有办法留下来**.
一步之差, 从需要想全, 变成了不需要想.

**这个转换值得你以后遇到安全问题时先试一次**: 与其问哪些输入是危险的, 不如问
**有没有一个层次, 让危险与否不再重要**. 沙箱, 只读副本, 权限最小化, 都是同一个思路的不同
样子.

**还有一件小事我想让你注意.** 这段代码里有好几句注释是在解释某个东西**不是** 什么 —— 那个
检查不是安全边界, 那个私有属性坏了怎么办, 那个 rollback 为什么要显式写出来. 这类注释的
共同点是: **它们防的不是读不懂, 是读懂了但理解反了.**

**关键洞见:**

- 安全性建立在机制上, 不要建立在规则清单上
- 一个看不出来的安全保证, 下一次重构就会被删掉 —— 所以要写出来, 而且要放在旁边
- 一个函数该抛还是该返回, 看谁在接, 以及那个接的人能不能自己解决
- 好的安全设计的特征是你想不出绕过的角度, 不是它拦了多少种情况

## 12. 速查

**亲手验证回滚:**

```bash
.venv/bin/python examples/23-the-sql-tool/01_rollback_proves_it.py
```

**三个设计:**

| 要解决什么 | 怎么解决的 |
| :--- | :--- |
| 改不了数据 | **事务永远回滚**. 不是黑名单 |
| 失败了循环还能转 | **一律返回一句话**, 从不抛异常 |
| 结果又便宜又好读 | **Markdown 表格**, 零行时返回 `No result` |

**两条判据:**

- 能建立在机制上的安全性, 不要建立在规则清单上
- 该抛还是该返回, 看谁在接以及那个接的人能不能自己解决

**这个文件里的四个函数:**

- `new_sqlite_engine`: 关掉驱动的猜测, 让回滚在 SQLite 上也成立
- `ensure_valid_select_query`: 快速答复, **不是安全边界**
- `execute_sql_query`: 跑, 然后**一定回滚**
- `format_result`: 拼成 Markdown 表格, 零行返回 `No result`
