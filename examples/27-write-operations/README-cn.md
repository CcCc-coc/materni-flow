# 写操作: 为什么默认一个都没有

> 让 AI 读你的数据库已经要想清楚不少事. 让它**改** 你的数据库, 是另一个量级的问题.

## 1. 概览

到这一篇为止, 这个 agent 做过的所有事情都是**只读** 的: 看库结构, 跑 SELECT, 写一份调试报告
到本地文件.

**它一个改数据的工具都没有.** 而这不是还没来得及做, 是一个决定.

这一篇讲三件事:

| 问题 | 在第几节 |
| :--- | :--- |
| 为什么默认一个都不带 | 第 5 节 |
| 真要加的时候, 三条约束各自在防什么 | 第 6 到 8 节 |
| 协议里早就准备好的那道闸门 | 第 9 节 |

**这一篇没有代码可读**, 因为那部分代码不存在. 它读的是**留下来的位置**: 代码里那句注释,
和它周围的几条约定.

---

## 2. 学习目标

先说清楚只读这个词在这个仓库里已经被认真对待到什么程度.

第 24 篇 ([SQL 工具](../24-the-sql-tool/README-cn.md)) 里你亲手验过: 那只手把所有 SQL 都跑在
一个**永远不提交的事务** 里, 所以你写一条藏在 CTE 后面的 UPDATE, 它照样执行, 照样一个字节都
改不了.

那是一道很硬的机制. 而**加一个写工具, 等于在这道机制旁边开一扇门.**

### 为什么这件事值得单独一篇

因为一旦能写, 前面几篇建立的很多东西就不再成立了:

| 只读的时候 | 能写之后 |
| :--- | :--- |
| 模型写错 SQL, 最坏是答案不对 | 模型写错, **数据坏了** |
| 出了问题重跑一次就行 | 有些事**重跑不回来** |
| 提示词写含糊一点只是浪费 token | 提示词含糊可能触发一个不该做的动作 |
| 那个循环可以自己试错 (第 23 篇) | **自己试错正是最危险的部分** |

最后一行最要命. agent 的整个价值来自它能**想一步, 动一次手, 看结果, 再想** —— 而当动手意味着
改数据的时候, 那个再试一次就成了一个你不想要的性质.

学完这个 Task, 你将能够:

1. 说清写操作为什么天然和数据集绑定, 而不是脚手架的一部分
2. 指出代码里给写工具留的那个位置在哪
3. 说出加写工具时的三条约束, 以及每一条各自在防什么
4. 解释为什么一个写工具的说明比读工具的说明更要紧
5. 说清 AI SDK 协议里那对批准事件为什么存在, 以及它在这个 app 里为什么还没用上

## 5. 为什么默认一个都不带

理由不是写操作危险所以我们不做 —— 那太笼统了. 真正的理由更具体:

> **写操作天然是跟数据集绑定的, 而这个仓库的其余部分承诺跟数据集无关.**

想一想: 一个放贷的库, 合理的写操作可能是**给一份申请打上已复核**, 或者**记一条催收备注**.
换成一个物流的库呢? 那是完全不同的几个动作. 换成排班的库, 又是另外一套.

**没有一个写操作是所有行业通用的.**

而这个仓库的核心承诺 (第 2 篇立的) 是: 换一个业务领域,
[`agent_app/`](../../agent_app) 下面一行都不改.

如果它带一个默认的写工具, 那个工具必然引用某张表的某几列 ——
**那就是把一个数据集的痕迹刻进了那个承诺不变的包里**.

### 所以它留的是位置, 不是实现

打开 [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), 找到组装 agent
那一段的工具清单. 三个只读工具下面有一句注释, 意思是:

> 写操作的工具是数据集特有的. 某个数据集需要它们的时候, 把 `@tool` 方法加在这个文件里,
> 然后在这个清单里登记.

**这就是那个位置.** 一句注释, 没有代码.

> **这是一种值得学的留白方式**: 与其提供一个通用的写工具让每个人去改, 不如把这里空着, 并
> 用一句话说清楚该怎么填. 前者是一个所有人都要绕开的默认值, 后者是一个明确的接口.

## 6. 约束一: 底下那层要保持纯函数

真要加的时候, 第一条约束和安全无关, 和**这段代码摆在哪儿** 有关.

这个仓库对这类底层 helper 有一个固定的形状, 你在
[`agent_app/sql_utils.py`](../../agent_app/sql_utils.py) 见过:

| 这个形状 | 具体是什么 |
| :--- | :--- |
| 第一个参数是那个数据库连接 | 不去 `self` 上摸一个全局的连接 |
| 返回一个普通的字典 | 不返回一个只有界面看得懂的东西 |
| 不碰任何全局状态 | 给什么就用什么 |

**写工具的底层逻辑要跟着这个形状写.** 那个 `@tool` 方法则很薄: 它只负责接住模型给的参数,
调这个纯函数, 把结果变成一句给模型看的话.

这个形状为什么值钱, 第 29 篇 ([那一个对象](../29-the-one-object/README-cn.md)) 会讲 —— 那里
是这个仓库怎么组织代码的地盘. 现在你只需要照着它写.

---

## 7. 约束二: 说明要写清楚它会改什么

第 23 篇讲过, 一个工具的说明就是模型唯一的依据. 对写工具, 这件事的分量完全不同.

对比一下同一个问题在两类工具上的后果:

| 说明里没写清楚 | 读工具的后果 | **写工具的后果** |
| :--- | :--- | :--- |
| 参数格式 | 模型试错几次 | 模型可能**改错一行数据** |
| 边界在哪 | 它查了不该查的, 浪费一次调用 | 它**改了不该改的** |
| 什么时候用 | 该调没调 | **不该调的时候调了** |

所以写工具的说明要多回答两个读工具不用回答的问题:

- **它到底会改什么?** 哪张表的哪些行, 一次改一行还是可能改很多行
- **它是不是可逆的?** 改错了能不能撤回来

第二个问题尤其值得写进说明里, 因为**模型不会自己去想这件事**. 你在提示词里告诉它这个动作
不可逆, 请先确认清楚, 它才有可能停下来问一句.

---

## 8. 约束三: 想清楚谁来兜底

前两条是怎么写, 这一条是**先想清楚再动手**.

一个写工具上线之前, 至少要有三个问题的答案:

| 问题 | 为什么必须先回答 |
| :--- | :--- |
| **改错了怎么发现?** | 只读的时候答案错了用户会觉得不对劲; 数据被改错了**可能没有人看得见** |
| **改错了怎么回退?** | 有没有备份, 有没有操作记录, 能不能只回退这一条 |
| **谁被允许触发它?** | 这个 app 没有登录 (第 11 篇讲过), 所以**任何一个打开链接的人都能让它写** |

第三个问题在这个项目上是决定性的. 它是一个**公开的作品集网站**, 谁都能打开. 在这个前提下,
任何一个写工具都等于把改数据的能力交给了整个互联网.

> **所以这一篇真正的结论不是写操作很危险**, 而是:
> **加写操作之前, 先得有一个能回答上面三个问题的场景.**
> 一个公开 demo 通常回答不上来 —— 那它就不该有写工具.

## 9. 协议里那道闸门

第 17 篇 ([AI SDK 协议](../17-the-ai-sdk-protocol/README-cn.md)) 那张事件表里, 有一对事件当时
只是扫了一眼:

```json
{"type":"tool-approval-request","toolCallId":"...","approvalId":"...","reason":"..."}
{"type":"tool-approval-response","approvalId":"...","approved":false,"reason":"..."}
```

翻译成人话: **agent 想干一件事, 先停下来问用户同不同意; 用户点了同意, 它才继续.**

这就是给写操作准备的那道闸门, 而且**它是协议自带的, 不用你自己发明**.

### 这里有个更大的道理

回想第 17 篇那句话: 读协议的时候别只看你现在用的那几行, 扫一眼你没用的那些, 因为它们往往是
你将来问题的标准答案.

**这一对事件就是那句话的兑现.** 你今天要给这个 agent 加写操作, 需要一个人工确认的机制 ——
而定义这份协议的人早就遇到过这个需求, 并且把它写进去了.

前端那半也已经实现了: 你后端发出批准请求, 界面就会显示一个确认按钮.

### 那这个 app 为什么还不用它

因为**它现在一个写工具都没有**, 那道闸门没有东西可拦.

这也是这一篇的形状: 前面八节讲的都是**在开门之前该想清楚什么**, 而这一节告诉你门框已经在
那儿了.

## 10. 练习

### 练习 1: 找到那个留白, 并顺着它读一遍约束

**目标:** 确认默认不带写工具是一个写下来的决定, 不是一个遗漏.

**怎么做:**

1. 开一个叫 `27-write-operations` 的 branch
2. 打开 [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), 找到组装
   agent 那一段的工具清单, **读三个工具下面那句注释**
3. 数一数清单里有几个工具, 确认它们**全都是只读的**
4. 打开 [`agent_app/sql_utils.py`](../../agent_app/sql_utils.py), 看那几个函数的签名,
   确认第一个参数都是那个数据库连接
5. 先做一次严格的搜索, 只找真正的写语句:

```bash
grep -rn "UPDATE \|INSERT INTO\|DELETE FROM" agent_app/ --include="*.py"
```

6. **它一条都搜不到.** 现在把范围放宽, 把建表和删表也算上:

```bash
grep -rniE "drop table|drop_all|\.insert\(" agent_app/ --include="*.py"
```

7. 这次会搜到几条, **全都在同一个文件里**. 看那个文件是哪个, 想清楚它为什么可以写
8. 最后打开 [`api/index.py`](../../api/index.py), 读它最上面那段模块说明的第二句

**你会观察到:**

第 5 步零结果. 第 7 步搜到的全在 [`agent_app/dataset.py`](../../agent_app/dataset.py) 里 ——
那是第 7 篇讲的**教学层**, 干的是把种子灌进 PostgreSQL 那件事 (第 15 篇), 而且
**它会在交付前被整个删掉**. 换句话说: 这个仓库里唯一会写数据库的代码, 是一段活不到上线
的代码.

第 8 步会让你意外: 那段说明写着这个后端连接的是**带写操作能力的** agent —— 而你刚刚确认了
它一个写工具都没有. **那是一句过期的话**, 大概率是这个脚手架早期版本留下来的.

> **关键洞见:** 又一次. 第 22 篇那个 70%, 第 25 篇那两个数字, 这里这句带写操作能力 ——
> **散文没有编译器**, 而这个仓库自己也一样会中招.

### 练习 2: 拿三条约束去审一个提议

**目标:** 把这一篇的三条约束当成一张检查表用一次.

**怎么做:**

1. 假设有人提议给这个 agent 加一个工具, 叫标记申请为已复核: 传入一个申请编号, 把那条申请的
   状态改成已复核
2. 用第 8 节那三个问题审它, **逐条写下答案**:
   - 改错了怎么发现?
   - 改错了怎么回退?
   - 谁被允许触发它?
3. 特别想清楚第三个: 这个 app 有登录吗? 那么在一个公开的作品集网站上, 谁能触发它?
4. 然后按第 7 节的要求, 给这个工具写一段说明, 必须回答那两个额外的问题: 它会改什么,
   以及可不可逆
5. 最后加载 `/about-bi-agent-app-scaffold-cn`, 问它:

```text
假设要给这个 agent 加一个会修改数据库的工具, 按这个仓库现有的约定,
底层 helper 应该写成什么形状, 放在哪个文件, @tool 方法又该放哪里?
只告诉我文件和形状, 先不要写代码.
```

6. 检查它说的形状对不对: 第一个参数是不是那个数据库连接, 返回的是不是一个普通字典

**你会观察到:**

第 3 步是这个练习的重点. 这个 app 没有任何登录机制, 所以答案是**任何一个知道链接的人**.
在这个前提下, 那三个问题里至少有一个是答不上来的 —— 而**答不上来就意味着现在还不该加**.

> **关键洞见:** 一份检查表最大的价值不是帮你通过, 是帮你**发现自己通不过**. 这三个问题里
> 有一个答不上来, 就是一个明确的停下来的信号.

## 11. 回顾: 我们学到了什么

| 东西 | 一句话 |
| :--- | :--- |
| 为什么默认一个都不带 | 写操作**天然和数据集绑定**, 而 `agent_app/` 承诺跟数据集无关 |
| 留下来的是什么 | **一个位置加一句注释**, 不是一个通用实现 |
| 能写之后什么变了 | 写错 SQL 从答案不对变成数据坏了; **agent 自己试错成了最危险的部分** |
| 约束一 | 底层 helper 保持纯函数: 连接当第一个参数, 返回普通字典, 跟 `sql_utils.py` 一个形状 |
| 约束二 | 说明要多答两个问题: **它会改什么**, 以及**可不可逆** |
| 约束三 | 先回答: 改错了怎么发现, 怎么回退, 谁被允许触发 |
| 第三条为什么决定性 | 这个 app **没有登录**, 所以任何一个打开链接的人都能触发 |
| 协议里那道闸门 | `tool-approval-request` 那一对. **协议自带的, 不用自己发明** |
| 那条判据 | **默认不给, 比给了再限制安全得多** |

## 12. 导师寄语

**为什么一篇讲不存在的代码的课值得写:**

因为**决定不做某件事, 和决定做某件事, 是同等分量的工程判断** —— 只是前者在代码里几乎看不见.

你打开这个仓库, 看到三个只读工具, 很容易以为写操作只是还没做. 而实际上有人坐下来想过, 得出
的结论是不做, 并且留了一句注释说明该怎么做.

**这类留白在真实代码库里到处都是**, 而且它们通常没有那句注释 —— 于是后来的人会把一个决定
当成一个待办事项, 顺手就填上了.

**顺带说一句这一篇的形状.** 它是这门课里唯一一篇你读完之后**什么都不用做** 的. 第 8 节那三个
问题, 在这个项目上的答案是答不上来, 所以正确的行动就是不加.

这本身是一个值得练的动作: **一个技术上完全可行的功能, 因为场景不成立而不做.** 这比做出来
难, 因为做出来是有成就感的, 而不做只有一句注释.

**关键洞见:**

- 写操作天然和数据集绑定, 所以它属于数据集那一侧, 不属于脚手架
- 能写之后, agent 自己试错这个优点变成了最危险的部分
- 一个写工具的说明要回答它改什么, 以及可不可逆
- 加之前先回答: 怎么发现, 怎么回退, 谁能触发. **答不上来就是停下来的信号**
- 默认不给, 比给了再限制安全得多

**下一步:**

agent 的每个零件都拆过了. 第 28 篇 ([一次 chat 请求](../28-one-chat-request/README-cn.md))
把它们串起来走一遍完整的路, 也就是第 6 篇那张九步表的展开版, 这次要把里面几个换个顺序就
会静默出错或者多花钱的决定逐个讲透.

那是这一组的收尾.
