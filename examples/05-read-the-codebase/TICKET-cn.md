# 建立这个仓库的地图

## 1. 目标

上一篇你把它跑起来了, 这一篇要看懂它. 产出是一张地图: 每个顶层目录归谁管, 前端两个页面
各自服务谁, 后端怎么分层, 以及一次提问从浏览器出发走过哪些文件.

**这一篇最容易走偏的地方是陷进实现细节.** 读一个陌生代码库时, 你的目标不是读懂每个函数,
是知道下次要改某个东西该打开哪个文件. 遇到看不懂的实现就跳过去, 把注意力留给这个文件属于
哪一层, 以及它的上下游是谁.

这张地图会在后面每一篇里被用到, 所以现在花的时间不会白花. 更直接的好处是: 边界清晰的仓库,
改动的形状本身就是一种检查, 而这件事只有先知道每一层归谁管才看得出来.

---

## 2. 要做的事情

1. 列出仓库的顶层目录, 给每一个标上它属于应用还是教学, 一共不超过十五个.
2. 打开 `app/(marketing)/page.tsx` 和 `app/chat/page.tsx`, 对比两个页面各自读了什么, 又把
   什么传给了下层组件.
3. 按依赖顺序从下往上扫一遍 `agent_app/` 里的模块, 先看零依赖的那几个叶子, 最后看 `one/`.
4. 打开 `agent_app/one/one_00_main.py`, 数清 `One` 这个类由哪几个 mixin 拼成, 各自提供什么.
5. 打开 `api/index.py`, 从 `handle_chat_data` 这个函数从上往下读一遍, 每遇到一个外部调用就
   跳去看那个函数的签名和 docstring, 然后跳回来.
6. 按顺序写下你在第 5 步里经过的每个文件名, 和 README 第 8 节那张九步表对一遍.
7. 用换领域要不要改这条判据, 给 README 练习 2 里那五样东西各找一个位置, 然后去仓库里对答案.

**预计用时:** 70 到 100 分钟

---

## 3. 检查清单

- [ ] **目录归属**: 你能说出至少十个顶层目录各自管什么, 并正确指出其中哪几个属于教学层.
- [ ] **判据会用**: 给你一个新东西, 你能用换领域要不要改这条判据说清它该放哪一层, 而不是
      凭感觉找一个看起来能放的地方.
- [ ] **两个页面的分工**: 你能说清首页服务的是谁, agent 页服务的是谁, 以及为什么首页的职责
      是把外行带到能提出第一个问题的位置.
- [ ] **server 和 client 的线**: 你能复述读盘的往上放, 有状态的往下放这条规矩, 并说出违反
      它会怎样.
- [ ] **后端分层**: 你能按依赖顺序说出后端从叶子到入口大致有哪几层, 并指出 `one` 在其中的
      位置和作用.
- [ ] **九步路径**: 不看文档, 你能复述一次 chat 请求的九步, 并说出至少五步分别落在哪个文件.
- [ ] **入口的性质**: 你能解释为什么 `api/index.py` 里几乎没有逻辑, 以及一段代码符合什么
      条件就不该待在那里.
- [ ] **三条规矩**: 你能复述组件里不出现业务文案, 通用代码里不出现真实表名, 代码不引用教学
      文档这三条, 并各说出破坏它之后的症状.
