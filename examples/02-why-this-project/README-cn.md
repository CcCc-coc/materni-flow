# 一个可以换领域, 也能往任何方向深挖的项目

> 在写第一行代码之前, 先搞清楚我们要造的到底是什么, 以及为什么这件事值得花时间.

## 1. 概览

这门课最后交到你手上的, 是一个部署在公网上的 AI Agent 应用: 一个表很多的 PostgreSQL
数据库, 一个能用自然语言查它的 agent, 一个把这在解决什么问题讲清楚给外行听的网站.

先说结论, 因为这句话决定了你该怎么读后面所有内容:

> **这个项目本身已经够硬了.** 拿它去面试, 作为一个作品集项目是够用的.
> **但更值钱的是它故意留了很多口子.**

### 够硬是什么意思

它不是一个玩具. 它有真实的数据库和真实的表关系, 有跑在云上的数据库实例, 有前后端两个
进程, 有部署上线的完整链路, 有一个真的会调工具, 会读结果, 会改一遍再试的 agent. 这些
东西任何一样单拿出来, 都够你在面试里聊二十分钟.

### 留了口子又是什么意思

意思是**不管你是哪个方向的人, 你都能在这个项目里找到属于你的那一块**, 而且那一块是可以
一直往下挖的:

| 你是哪一类人 | 项目里现成的那一块 | 你可以把它挖成什么 |
| :--- | :--- | :--- |
| **软件工程 / CS** | 前后端分开的两个进程, 一整套本地到线上的部署 | 上云, 拆服务, 加缓存加队列, 把系统做完整 |
| **AI / agent** | 一个会调工具, 会看结果再想一步的 agent | 加工具, 加多轮规划, 加评测, 换模型对比效果 |
| **数据工程** | 一个多表数据库, 一条本地到云端的同步链路 | 做成数据仓库, 加调度, 加数据质量检查 |
| **数据分析** | 一整套业务指标和它们各自的口径 | 加指标层, 加看板, 把这门生意的分析做深 |
| **机器学习** | 一份干净的, 带标签的业务数据集 | 把后端换成一个模型, 让 agent 去问那个模型 |

**每一块现在都只有一丢丢.** 这是有意的. 这个项目不追求任何一块做到底, 它追求的是每一块
都通到能跑, 然后**把继续挖下去的口子留在那儿**.

这一篇不写代码, 也不装任何东西. 它交代的是这套设计背后的底层逻辑: 为什么是这个形态,
为什么每一块都只做一丢丢, 以及为什么这样反而更有用.

### 卡住了怎么办

这一篇每一步都可能出错: 搜索命令在你的编辑器或者终端里的写法可能和这里不一样.
**这些都很正常** —— 你的机器, 你的账号, 你的网络, 和写这一篇时用的那一套不可能完全一样.

**别自己硬猜, 也别只把报错扫一眼就跳过去.** 把下面三样东西一起给 AI, 一样都别少:

| 给什么 | 怎么给 |
| :--- | :--- |
| **你在读哪一篇** | 原样给路径: `examples/02-why-this-project/README-cn.md` |
| **你敲了哪条命令** | 原样复制那一行, 不要凭记忆转述 |
| **终端打了什么** | **把终端里的文字整段复制粘贴给它**, 不要截图, 也不要只说了一句报错了 |

第三样最重要, 也最常被省掉. 一句报错了对 AI 来说和没说一样; 而那几十行原始输出里, 通常有
一行直接写着缺什么.

一段可以照抄的开场白:

```text
我在读 examples/02-why-this-project/README-cn.md 这一篇.
我敲的命令是:
(把命令粘在这里)
终端打出来的是:
(把完整输出粘在这里)
帮我判断是哪一步出了问题. 一步一步来, 每一步等我做完再往下.
```

**粘贴之前先打码.** 报错信息里有时会带上完整的数据库连接串, 或者一把 key 的片段. 那些东西
不该出现在任何聊天窗口里, 包括跟 AI 的对话.

## 2. 学习目标

这一节比通常的长, 因为它讲的是**你为什么要花时间做这个项目**. 想不清这件事, 后面三十几
篇你会一直觉得在学一堆零碎的东西.

三个理由, 一个一个说.

### 理由一: 它逼你碰到你不懂的东西, 而那正是要练的

先做一个诚实的预判: **这个项目一定会涉及到你不懂的部分.**

你要是写前端的, 那 SQL 和数据库设计对你就是新的. 你要是做数据的, 那前端组件, 部署,
流式响应对你就是新的. 你要是做算法的, 那这一整套工程链路对你都是新的. **没有人是全会的**,
这不是你的问题, 这是这个项目被设计成这样的结果.

那这有什么好处呢? 好处是它逼你练一件在真实工作里最值钱的事:

> **快速把一个陌生领域捡起来用到能干活的程度.**

注意这里的判据是**能干活**, 不是精通. 你不需要成为数据库专家, 你需要的是在两小时内搞清楚
这张表和那张表怎么连, 然后把活干了.

这跟很多人想的正好相反. 很多人的策略是挖一个洞挖到底, 把一样东西做到极致. 那当然也是一条
路, 但它有个前提: 你得赌对那个洞. 而这个项目走的是另一条路 ——
**广度优先, 会的东西越广越好**, 因为:

| | 挖一个洞挖到底 | 广度优先 |
| :--- | :--- | :--- |
| 遇到没见过的技术栈 | 从零开始, 心里发慌 | 见过类似的结构, 知道从哪下手 |
| 换一个方向 | 沉没成本很大 | 本来就是这么干的 |
| 和别的岗位的人合作 | 听不懂对方在说什么 | 大概知道对方那一侧长什么样 |

**这个能力本身就是产物**, 而且它比项目本身活得久. 项目会过时, 框架会换代, 但
把陌生东西捡起来用的能力, 你下一份工作还在用.

所以这门课里每遇到一个你不懂的点, 正确的动作不是跳过去, 是**当场把它捡起来**. 后面每一篇
都会教你怎么把不懂的东西交给 AI 去问 —— 那也是这个能力的一部分.

### 理由二: 有了脚手架, 你想往哪个方向深挖都行

刚才说每一块都只做了一丢丢. 那如果我就想在某一块上做深呢?

**可以, 而且改动量比你想的小得多.** 因为这个项目是**模块化** 设计的.

模块化这个词听起来很抽象, 说白了就一件事:
**会变的东西被集中放在一起, 不变的东西承诺不被碰.**
于是你想改哪一块, 就只动那一块, 别的地方不用陪着改.

具体到三个方向:

| 你想往哪深挖 | 大概要动什么 | 不用动什么 |
| :--- | :--- | :--- |
| **机器学习** | 换掉数据集, 在后端加一个模型, 再加一个查这个模型的工具 | 前端一行不改, 后端其余部分不改 |
| **业务 / 财务建模** | 换掉 [`dataset/`](../../dataset) 和 [`data/`](../../data) 里那几份文档, 数据换成你那门生意的 | 后端全部代码不改 |
| **软件工程** | 后端往复杂里做: 上云, 拆服务, 加缓存, 加监控 | 数据和前端那两侧不用陪着改 |

这就是脚手架这个词的意思: **它不替你决定往哪走, 它保证你往哪走都不用推倒重来.**

而这个保证不是白来的. 它是靠一堆边界撑住的, 而这门课后面绝大部分篇幅, 讲的就是每一条边界
具体在哪, 破了会怎样, 以及为什么破了通常**不报错**, 只是悄悄变坏.

### 理由三: 做完了要能给别人看

这一条听起来最不技术, 但它是最多人栽跟头的地方.

**很多人辛辛苦苦做完一个项目, 结果它只在自己电脑上躺着.** 简历上写了一行字, 面试官问起来
只能说我本地跑过. 那个项目对找工作的实际帮助, 接近于零 —— 因为**没人看得见它**.

这个项目从第一天就把这件事考虑进去了:

- 它是一个**网站**, 有公网地址, 面试官点开链接就能用
- 它有一个**讲人话的首页**, 外行也能看懂这在解决什么问题
- 发布出去**几乎不花力气**, 不是最后要做的一个大工程

再往前一步: 因为换领域的成本被压得很低, 你可以**针对每一次投递做一个专属的版本**. 面试官
打开链接看到的不是一个通用 demo, 是他自己每天在处理的那类问题.

> 别人准备一个像样的作品集项目要三个月, 而且只能投一次.
> 有这个脚手架, 你可以针对每一家公司长出一个新的, 一到两小时走完.

学完这个 Task, 你将能够:

1. 说清这个项目为什么每一块都只做一丢丢, 以及这样做换来了什么
2. 指出你自己那个方向对应项目里的哪一块, 以及往下挖大概要动什么
3. 解释这门课真正的产品为什么是脚手架, 而不是它当前长成的那个样子
4. 用一句话讲清 chatbot 和 agent 的区别, 并指出这个区别落在代码的哪一处
5. 在这个项目里找到你自己那一类人对应的那几个文件

## 4. 你将学到什么

这一节回答一个很自然的疑问: **为什么偏偏是一个报表 agent? 换个别的项目不行吗?**

答案值得展开讲, 因为它是这个项目全部设计的出发点.

### 一个项目, 怎么可能适配所有行业

先看我们想要什么: 我们想要一个项目, 它能跟着你要投的公司变, 投放贷公司就是放贷的项目,
投物流公司就是物流的项目.

那问题就变成了: **一个项目跟一个行业绑定得最紧的东西, 到底是什么?**

不是界面, 界面换个颜色换句文案就行. 也不是技术栈, 放贷公司和物流公司可能用一样的框架.

**是数据.**

一家公司是干什么的, 它靠什么赚钱, 它每天在为哪几个数字发愁, 全都写在它的数据里. 放贷公司
的库里有贷款, 有风险等级, 有还款记录, 有违约事件; 物流公司的库里是完全不同的一批表. 你把
一家公司的数据摸清楚了, 你就基本摸清楚了这门生意.

所以这个项目的设计是**从数据出发** 的: 先有一个行业的数据, 再有一个能读懂这些数据的 agent,
再有一个把这门生意讲给外行听的网站. 换行业的时候,
**换的是最底下那份数据, 上面的东西跟着变**.

### 为什么这个形态叫报表 agent

顺着上面那条思路, 你需要一个能把数据摆在正中间的项目形态. 报表和分析恰好就是那个形态:

- 它**必须** 接一个真实的多表数据库, 假数据糊弄不过去
- 它回答的问题**必须** 是这门生意真的会问的问题
- 它的好坏**一眼能看出来**: 答得对不对, 业务方一看就知道

换句话说, 这个形态没法搞虚的. 你要是没真的理解这门生意, 做出来的东西立刻就露馅了.

> **理解了业务, 才算真正理解他们.** 这句话是这门课的底色.
> 技术那部分脚手架已经替你做完了, 剩下要你自己补的就是这一块.

### 顺带说一句你的目标行业

这门课最后会让你把整个项目换成另一个行业的样子 —— 第 37 篇 (换数据集) 和第 38 篇
(重新设计前端) 干的就是这件事, 第 39 篇 (那个打法) 再告诉你怎么把它变成一次真实投递.

**但现在不用想那么远, 也不用现在就选定.** 你读这门课的时候心里可以装着一个方向 (你想投的
那类公司, 或者你自己熟的那个行业), 读到某一篇的时候顺手想一想换成它会怎么样, 就够了.

真正要把它定下来是第 39 篇的事, 而且到那时候你已经完整看过一个数据集长什么样, 也亲手换过
一次了 —— 那时候再选, 比现在瞎猜靠谱得多.

**这一篇结束时你真正会有的, 是一张地图**: 这个项目是什么, 为什么长成这样, 以及它每一块
分别通向哪儿.

## 5. 从报表到问一句话

让不懂 SQL 的人也能查数据这个念头, 比 LLM 老得多. 它走过三代.

**第一代是报表.** 分析师写好 SQL, 做成固定的报表, 业务方每周打开看一次. 好处是数字一定
是对的, 坏处是任何一个报表上没有的问题, 都得回头排队找分析师. 而业务方的问题恰恰大多数
都不在报表上, 因为报表是上个季度设计的.

**第二代是自助式 BI.** Tableau 和 Power BI 这类工具把 SQL 换成拖拽: 把字段拖进行, 拖进列,
选一个聚合方式. 它确实把简单问题从分析师手里拿走了. 但拖拽只是给 SQL 换了个界面, 那些
需要跨五张表才能回答的问题, 在拖拽界面里同样需要你先知道要跨哪五张表.

**第三代一直失败到最近.** 自然语言查数据的产品早就有人做, 做法是写一个语义解析器, 把
上个季度西部的销售额这类句子映射成 SQL 模板. 它在演示里效果很好, 一旦换个说法就崩,
因为那个解析器是一堆手写规则, 而人说话的方式是无穷的.

LLM 解开的就是这一处. 它不需要谁去枚举句式, 而且它本来就见过海量的 SQL. 剩下的问题变成
了一个完全不同的问题: **怎么让它知道你这个库长什么样, 你这行的黑话是什么意思.** 这门课
后面那些篇, 大半在回答这个问题.

## 6. Chatbot 会说, Agent 会动手

这两个词经常被混着用, 但它们差着一个具体的东西: **工具**.

一个 chatbot 拿到你的问题, 只能从它训练时记住的东西里凑一个答案出来. 你问它上个月违约率
是多少, 它会给你一个格式完美, 语气自信, 而且完全是编的数字, 因为它没有任何办法去看你的
数据库.

一个 agent 拿到同一个问题, 会先停下来做一件事: **调一个工具**. 它先调看库结构这个工具
弄清楚有哪些表, 再调跑 SQL 这个工具把查询发出去, 拿到真实结果之后才开口回答. 中间它可能
写错一次 SQL, 收到数据库的报错, 改一下再试. 这个想一步, 动一次手, 看结果, 再想的循环,
就是 agent 这个词的全部含义.

落到这个仓库里, 那个循环是三个 Python 函数, 都在
[`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py) 里:

| 工具 | 干什么 |
| :--- | :--- |
| `tool_get_database_schema` | 把整个库的结构压成一段紧凑文本交给模型 |
| `tool_execute_sql_query` | 跑一条只读查询, 把结果作为 Markdown 表格还回去 |
| `tool_write_debug_report` | 让 agent 把自己的推理过程写成文件, 供人事后核对 |

**这也解释了为什么这类应用一定挂着一个表很多的数据库.** 如果你的数据只有一张表, 那业务
方自己在 Excel 里透视一下就够了, 用不着 agent. Agent 的价值来自人问不出来的跨表关联: 把
贷款, 风险等级, 还款记录和违约事件四张表拼在一起, 才能回答哪个风险等级定价定低了, 低多少.
这种问题没有一张现成的报表, 而人手写这条 SQL 要半小时.

## 7. 换领域到底要改哪些文件

第 2 节说了模块化和脚手架, 这一节把它落到具体文件上, 因为一个承诺只有能被检查才算数.

你在屏幕上看到的这个应用, 有一个当前的样子: 它现在是一家中小企业放贷机构的风险与定价分析.
**但那个样子不是产品.** 产品是它底下那套东西: 会变的内容集中在一个目录里, 不变的代码承诺
一行都不用改.

换一个业务领域要动的地方一共只有这些:

| 换什么 | 在哪 |
| :--- | :--- |
| 数据本身, 以及描述这个领域的四份源文档 | [`dataset/`](../../dataset) |
| 界面上说的每一句话 | [`data/site.toml`](../../data/site.toml) |
| 首页那个这解决什么问题的长说明 | [`data/business-context.md`](../../data/business-context.md) |
| agent 的领域大脑 | [`data/system-prompt.md`](../../data/system-prompt.md) |
| 数据库 schema 的名字 | [`.env.defaults`](../../.env.defaults) 里的一行 |

**[`agent_app/`](../../agent_app) 下面一行都不改.** 这个 Python 包的名字被故意起得这么
通用, 就是为了兑现这句承诺. 前端也一样: 组件里不许出现任何一句业务文案, 所以换领域不需要
打开任何一个 `.tsx` 文件.

代价是这些边界必须一直被守住. 每一次就这一次, 先在组件里写死一个字符串, 都是在把下一次
替换的时间从两小时推向两天.

## 8. 会写代码不再是差异

值得把话说透一点, 因为它决定了你该怎么花这门课的时间.

写代码这件事本身正在快速贬值. 一个能生成整个 CRUD 应用的模型, 现在人人都有. 所以简历上
我做了一个全栈项目这句话的信息量, 比三年前低得多, 因为面试官知道那可能是一个下午的产物.

那么剩下什么还稀缺? 两样.

**第一样是判断力.** 同样一个功能, 为什么这么切而不是那么切, 哪条边界破了会静默地坏, 一个
显而易见的写法为什么是陷阱. 这些东西模型给不了你, 因为它给的通常正是那个显而易见的写法.
这门课里每一处不要这么做, 因为它不报错只是答案变差, 都是在训练这个.

**第二样是针对性.** 一个通用 demo 和一个我照着你们公司的业务做了一个之间, 隔着的不是
技术难度, 是有没有真的去理解那门生意.

所以这门课的正确用法不是学会怎么写.
**它是学会哪些地方不能凑合, 然后把省下来的时间花在理解一个具体行业上.**

## 9. 一个仓库, 既是应用也是课

最后一件需要提前知道的事, 否则你打开目录会觉得奇怪.

这个仓库里同时装着两样东西: 那个应用, 和教你怎么造出那个应用的课. 你正在读的这份文件,
[`examples/`](../../examples) 下面所有 Task, `.claude/skills/` 里给 AI 看的规范, [`dataset/`](../../dataset)
里造假数据的那一整套流水线, 全都属于后者.

学完之后, 你要把这个仓库当自己的作品拿出去给人看. 那一刻读它的人不再是你, 是面试官. 而
面试官期待看到的是一个工程师写的生产代码库, 不是一份带练习题的课件. 一个 docstring 里在
讲什么是 mixin 的仓库, 立刻会把这个项目从我做的产品降级成我上过的课.

所以这个仓库有一个动作叫**擦掉教学痕迹**, 而它被设计成删几个目录就完事, 一行代码都不用
改. 这件事能不能干净地做完, 取决于教学层和生产层在目录上分得有多开, 而那是从第一天就要
守住的边界, 不是最后一步的收尾工作.

第 7 篇 ([教学层和生产层](../07-teaching-and-production/README-cn.md)) 会专门讲这条边界.
现在你只需要知道: 目录里那些看起来不属于一个正经项目的东西, 是故意放在那儿的, 而且它们
知道自己迟早要被删掉.

## 10. 练习

这两个练习都不需要装任何东西, 也不需要改任何代码. 它们只要求你打开几个文件对着看.

### 练习 1: 用两分钟证实那句一行都不改

**目标:** 亲眼确认第 7 节那张表说的是真的, 而不是一句宣传.

**怎么做:**

1. 先看会变的那一侧. 打开 [`data/site.toml`](../../data/site.toml), 从头翻到尾,
   **数一数你能找到多少句只有放贷这行才会说的话** (风险等级, 违约, 贷款, 借款人 ...)
2. 再打开 [`data/system-prompt.md`](../../data/system-prompt.md), 同样翻一遍
3. 现在看不变的那一侧. 在仓库根目录跑这条搜索:

```bash
grep -rn "loan\|borrower\|default_event\|risk_grade" agent_app/ app/ components/ lib/ --include="*.py" --include="*.tsx" --include="*.ts"
```

4. 看它返回了什么
5. 最后随便打开 [`components/chat/chat.tsx`](../../components/chat/chat.tsx) 和
   [`agent_app/one/one_02_db.py`](../../agent_app/one/one_02_db.py), 自己扫一眼, 确认里面
   一句放贷的话都没有

**你会观察到:**

第 1 到 2 步几乎每一段都是行业特有的. 第 3 步那条搜索**应该什么都搜不到** —— 后端和前端的
代码里, 一个业务名词都没有.

这条线不是自然长成的. 它是被一堆纪律和检查撑住的, 而这门课后面大半在讲那些纪律具体在哪.

> **关键洞见:** 一个承诺能不能信, 看它**能不能被一条命令检验**. 这一条可以, 所以它是真的.

### 练习 2: 在这个项目里找到你自己那一块

**目标:** 把第 1 节那张表从一张表变成你真的看过的几个文件.

**怎么做:**

1. 对照第 1 节那张表, 找出你属于哪一类人 (软件工程 / AI / 数据工程 / 数据分析 / 机器学习)
2. 按下面这张表, 打开你那一行对应的那几个文件, **每个都扫一眼就行, 不要求读懂**:

| 你是哪一类 | 打开这几个 |
| :--- | :--- |
| 软件工程 | [`next.config.js`](../../next.config.js), [`mise.toml`](../../mise.toml), [`api/index.py`](../../api/index.py) |
| AI / agent | [`agent_app/one/one_04_agent.py`](../../agent_app/one/one_04_agent.py), [`data/system-prompt.md`](../../data/system-prompt.md) |
| 数据工程 | [`agent_app/dataset.py`](../../agent_app/dataset.py), [`dataset/`](../../dataset) 里那五个文件 |
| 数据分析 | [`dataset/`](../../dataset) 里 `03-` 开头那份 SQL 文档 |
| 机器学习 | [`dataset/`](../../dataset) 里 `02-` 开头那份 ER 文档 |

3. 挑其中**一个** 文件, 用一句话写下它大概在干什么 —— 猜的也行
4. 然后加载 `/showcase-learn-cn` (这是这门课的助教, 第 4 篇会讲它是什么, 现在照着敲就行),
   把那个文件名贴给它, 问:

```text
用两三句话告诉我这个文件在这个项目里是干什么的, 以及它属于哪一层.
不要贴代码, 我只是想知道它的位置.
```

5. 对比它的回答和你第 3 步猜的

**你会观察到:**

你大概率猜得八九不离十, 因为**文件名和目录名本身就在告诉你**. 这不是巧合 —— 第 6 篇
([读一遍这个仓库](../06-read-the-codebase/README-cn.md)) 会讲这个仓库怎么让目录结构自己说话.

第 4 步那个问法值得记住: **问位置, 不问细节.** 一上来就让 AI 讲代码, 你会淹在里面; 先问它
在哪一层, 你才有地方挂后面的知识.

## 11. 回顾: 我们学到了什么

| 概念 | 一句话 |
| :--- | :--- |
| 这个项目硬不硬 | 够硬, 拿去面试够用了. 但更值钱的是它每个方向都留了往下挖的口子 |
| 每一块只做一丢丢 | 有意的. 不追求任何一块做到底, 追求每一块都通到能跑 |
| 广度优先 | 项目一定涉及你不懂的部分, 而把陌生领域快速捡起来用, 本身就是要练的能力 |
| 脚手架是什么 | 它不替你决定往哪走, 它保证你往哪走都不用推倒重来 |
| 为什么必须能发布 | 只在自己电脑上躺着的项目, 在面试里等于不存在 |
| 为什么是报表 agent | 一个项目跟行业绑得最紧的是数据, 而这个形态把数据摆在正中间, 搞不了虚的 |
| chatbot 和 agent 的区别 | 前者只能凭记忆说话, 后者会调工具去看真实数据, 并根据结果再想一步 |
| 为什么一定要多表数据库 | 单表的问题用不着 agent, 它的价值来自人问不出来的跨表关联 |
| 为什么仓库里有一堆教学材料 | 它同时是课和作品. 教学层整块住在自己的目录里, 交付前删掉, 一行代码不用改 |

## 12. 导师寄语

**为什么这一篇值得认真读:**

我见过太多人把作品集项目做成技术展示: 用了多少个时髦框架, 部署在几朵云上, 代码有多少行.
然后在面试里被问一句你为什么做这个, 答不上来. 也见过更可惜的: 项目做得不错, 但只在自己
电脑上跑过, 从来没人看见过它.

一个项目真正的说服力, 来自它解决的问题是不是真的. 而真的这件事无法靠技术弥补, 只能靠
你花时间去理解一门生意. 这门课把技术成本压到几乎为零, 就是为了逼你把时间花在那个地方.

**关键洞见:**

- 每一块只做一丢丢不是偷懒, 是为了让每个方向的人都能接着往下挖
- 广度优先换来的是把陌生领域快速捡起来用的能力, 那个能力比项目本身活得久
- 一个作品只能投一次, 一个脚手架每次投递都能长出一个新作品
- 会写代码不再是差异, 判断力和针对性才是
- 这个仓库里所有看起来多余的纪律, 都是在保护那个一到两小时

**下一步:**

接下来的第 3 篇 ([开工之前的四门前置课](../03-prerequisites/README-cn.md)) 不教新东西,
它是一道闸门: 这门课默认你已经会用 mise, Vercel, DBeaver 和一个云端 Postgres, 那一篇把
这四样各指向一门课, 会的跳过, 不会的先去补.

## 13. 速查

**这门课的落点:**

一个部署在公网上, 针对某个具体岗位的 AI Agent 应用, 加上一套能反复换领域, 也能往任何
方向深挖的脚手架.

**五个方向各自的入口:**

| 方向 | 从哪块入手 |
| :--- | :--- |
| 软件工程 | 前后端两个进程, 部署链路 |
| AI / agent | 那三个 `@tool` 方法和它们的循环 |
| 数据工程 | 多表数据库和本地到云端的同步 |
| 数据分析 | 业务指标和它们的口径 |
| 机器学习 | 那份带标签的业务数据集 |

**换领域要动的文件:**

- [`dataset/`](../../dataset): 数据本身与描述这个领域的源文档
- [`data/site.toml`](../../data/site.toml): 界面上说的每一句话
- [`data/business-context.md`](../../data/business-context.md): 首页那个长说明
- [`data/system-prompt.md`](../../data/system-prompt.md): agent 的领域大脑
- [`.env.defaults`](../../.env.defaults): 一行 `SCHEMA_NAME`

**换领域不动的地方:**

- [`agent_app/`](../../agent_app): 后端全部代码
- [`app/`](../../app), [`components/`](../../components), [`lib/`](../../lib): 前端全部代码
