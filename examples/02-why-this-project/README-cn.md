# 一个可以换掉整个业务领域的 AI Agent 应用

> 在写第一行代码之前, 先搞清楚我们要造的到底是什么, 以及为什么这件事值得花时间.

## 1. 概览

这门课最后交到你手上的, 是一个部署在公网上的 AI Agent 应用: 一个表很多的 PostgreSQL
数据库, 一个能用自然语言查它的 agent, 一个把 "这在解决什么问题" 讲清楚给外行听的网站.

但这只是表面上那一层. 真正值钱的东西藏在下面: 这三样东西被设计成**可以整体换掉**. 今天
它是一个中小企业放贷机构的风险与定价分析工具, 明天可以变成一个供应链的库存分析工具,
后天变成一个医院排班的分析工具. 换的过程一到两小时, 换完直接部署上线.

这一篇不写代码, 也不装任何东西. 它交代的是背景: 这类应用是怎么长出来的, 它和你见过的
chatbot 差在哪, 以及为什么 "能换领域" 这件事比 "做出来了" 重要得多.

---

## 2. 学习目标

绝大多数人做作品集项目的方式是这样的: 花三个月做一个自己觉得酷的东西, 放进简历, 然后投
一百家公司. 这一百家公司里, 真正会对这个项目感兴趣的可能有五家, 因为剩下九十五家做的是
完全不同的生意.

这门课要教的是另一种打法. 你手上有一个脚手架,
**每投一家公司就用它长出一个那家公司真正会做的项目.**
面试官打开链接看到的不是一个通用 demo, 是他自己每天在处理的那类问题.

这个打法成不成立, 完全取决于 "换领域" 的成本能不能被压到足够低. 而那件事不是靠聪明, 是靠
一整套架构边界. 这门课的每一篇, 归根到底都在守其中一条边界. 所以在动手之前, 你得先知道
这些边界是为了什么存在.

学完这个 Task, 你将能够:

1. 说清 BI 这条路从报表工具走到自然语言查询, 中间卡住的是什么, LLM 解开的又是什么
2. 用一句话讲清 chatbot 和 agent 的区别, 并指出这个区别落在代码的哪一处
3. 解释为什么这门课真正的产品是脚手架, 而不是它当前长成的那个样子
4. 挑定你自己要投的岗位和行业, 并写下那个行业真正会问的三个业务问题

## 5. 从报表到问一句话

"让不懂 SQL 的人也能查数据" 这个念头, 比 LLM 老得多. 它走过三代.

**第一代是报表.** 分析师写好 SQL, 做成固定的报表, 业务方每周打开看一次. 好处是数字一定
是对的, 坏处是任何一个报表上没有的问题, 都得回头排队找分析师. 而业务方的问题恰恰大多数
都不在报表上, 因为报表是上个季度设计的.

**第二代是自助式 BI.** Tableau 和 Power BI 这类工具把 SQL 换成拖拽: 把字段拖进行, 拖进列,
选一个聚合方式. 它确实把简单问题从分析师手里拿走了. 但拖拽只是给 SQL 换了个界面, 那些
需要跨五张表才能回答的问题, 在拖拽界面里同样需要你先知道要跨哪五张表.

**第三代一直失败到最近.** 自然语言查数据的产品早就有人做, 做法是写一个语义解析器, 把
"上个季度西部的销售额" 这类句子映射成 SQL 模板. 它在演示里效果很好, 一旦换个说法就崩,
因为那个解析器是一堆手写规则, 而人说话的方式是无穷的.

LLM 解开的就是这一处. 它不需要谁去枚举句式, 而且它本来就见过海量的 SQL. 剩下的问题变成
了一个完全不同的问题: **怎么让它知道你这个库长什么样, 你这行的黑话是什么意思.** 这门课
后面那些篇, 大半在回答这个问题.

## 6. Chatbot 会说, Agent 会动手

这两个词经常被混着用, 但它们差着一个具体的东西: **工具**.

一个 chatbot 拿到你的问题, 只能从它训练时记住的东西里凑一个答案出来. 你问它上个月违约率
是多少, 它会给你一个格式完美, 语气自信, 而且完全是编的数字, 因为它没有任何办法去看你的
数据库.

一个 agent 拿到同一个问题, 会先停下来做一件事: **调一个工具**. 它先调 "看库结构" 这个工具
弄清楚有哪些表, 再调 "跑 SQL" 这个工具把查询发出去, 拿到真实结果之后才开口回答. 中间它可能
写错一次 SQL, 收到数据库的报错, 改一下再试. 这个 "想一步, 动一次手, 看结果, 再想" 的循环,
就是 agent 这个词的全部含义.

落到这个仓库里, 那个循环是三个 Python 函数, 都在 `agent_app/one/one_04_agent.py` 里:

| 工具 | 干什么 |
| :--- | :--- |
| `tool_get_database_schema` | 把整个库的结构压成一段紧凑文本交给模型 |
| `tool_execute_sql_query` | 跑一条只读查询, 把结果作为 Markdown 表格还回去 |
| `tool_write_debug_report` | 让 agent 把自己的推理过程写成文件, 供人事后核对 |

**这也解释了为什么这类应用一定挂着一个表很多的数据库.** 如果你的数据只有一张表, 那业务
方自己在 Excel 里透视一下就够了, 用不着 agent. Agent 的价值来自人问不出来的跨表关联: 把
贷款, 风险等级, 还款记录和违约事件四张表拼在一起, 才能回答哪个风险等级定价定低了, 低多少.
这种问题没有一张现成的报表, 而人手写这条 SQL 要半小时.

## 7. 真正的产品是那个脚手架

现在说这门课最核心的一件事.

你在屏幕上看到的这个应用, 有一个当前的样子: 它现在是一家中小企业放贷机构的风险与定价分析.
**但那个样子不是产品.**
产品是它底下那套东西: 会变的内容集中在一个目录里, 不变的代码承诺一行都不用改.

具体到文件上, 换一个业务领域要动的地方一共只有这些:

| 换什么 | 在哪 |
| :--- | :--- |
| 数据本身, 以及描述这个领域的四份源文档 | `dataset/` |
| 界面上说的每一句话 | `data/site.toml` |
| 首页那个 "这解决什么问题" 的长说明 | `data/business-context.md` |
| agent 的领域大脑 | `data/system-prompt.md` |
| 数据库 schema 的名字 | `.env.defaults` 里的一行 |

**`agent_app/` 下面一行都不改.** 这个 Python 包的名字被故意起得这么通用, 就是为了兑现这句
承诺. 前端也一样: 组件里不许出现任何一句业务文案, 所以换领域不需要打开任何一个 `.tsx`
文件.

这带来的是一个别人做不到的打法:

> 针对某个具体岗位, 做出那个岗位所在行业和公司真正会做的项目. 从做出来, 到部署上线, 到
> 进作品集, 到改简历, 一到两小时走完.

别人准备一个像样的作品集项目要三个月. 有这个脚手架, 你可以针对每一次投递做一个专属的.

代价是这些边界必须一直被守住. 每一次 "就这一次, 先在组件里写死一个字符串", 都是在把下一次
替换的时间从两小时推向两天. 这门课后面绝大部分篇幅, 讲的就是每一条边界具体在哪, 破了会
怎样, 以及为什么破了通常**不报错**, 只是悄悄变坏.

## 8. 会写代码不再是差异

值得把话说透一点, 因为它决定了你该怎么花这门课的时间.

写代码这件事本身正在快速贬值. 一个能生成整个 CRUD 应用的模型, 现在人人都有. 所以简历上
"我做了一个全栈项目" 这句话的信息量, 比三年前低得多, 因为面试官知道那可能是一个下午的
产物.

那么剩下什么还稀缺? 两样.

**第一样是判断力.** 同样一个功能, 为什么这么切而不是那么切, 哪条边界破了会静默地坏, 一个
显而易见的写法为什么是陷阱. 这些东西模型给不了你, 因为它给的通常正是那个显而易见的写法.
这门课里每一处 "不要这么做, 因为它不报错只是答案变差", 都是在训练这个.

**第二样是针对性.** 一个通用 demo 和一个 "我照着你们公司的业务做了一个" 之间, 隔着的不是
技术难度, 是有没有真的去理解那门生意. 脚手架的价值就在于它把技术成本压到接近零之后, 你
剩下的全部精力可以花在那门生意上.

所以这门课的正确用法不是学会怎么写.
**它是学会哪些地方不能凑合, 然后把省下来的时间花在理解一个具体行业上.**

---

## 9. 一个仓库, 既是应用也是课

最后一件需要提前知道的事, 否则你打开目录会觉得奇怪.

这个仓库里同时装着两样东西: 那个应用, 和教你怎么造出那个应用的课. 你正在读的这份文件,
`examples/` 下面所有 Task, `.claude/skills/` 里给 AI 看的规范, `dataset/` 里造假数据的
那一整套流水线, 全都属于后者.

学完之后, 你要把这个仓库当自己的作品拿出去给人看. 那一刻读它的人不再是你, 是面试官. 而
面试官期待看到的是一个工程师写的生产代码库, 不是一份带练习题的课件. 一个 docstring 里在
讲 "什么是 mixin" 的仓库, 立刻会把这个项目从 "我做的产品" 降级成 "我上过的课".

所以这个仓库有一个动作叫**擦掉教学痕迹**, 而它被设计成删几个目录就完事, 一行代码都不用
改. 这件事能不能干净地做完, 取决于教学层和生产层在目录上分得有多开, 而那是从第一天就要
守住的边界, 不是最后一步的收尾工作.

第 6 篇 (教学层和生产层) 会专门讲这条边界. 现在你只需要知道: 目录里那些看起来不属于一个
正经项目的东西, 是故意放在那儿的, 而且它们知道自己迟早要被删掉.

## 10. 练习

这两个练习都不需要装任何东西, 但第一个的产物会一直跟到这门课的最后一篇.

### 练习 1: 挑定你的目标岗位和行业

**目标:** 选好这门课最后要把整个项目换过去的那个领域.

**怎么做:**

1. 打开你正在投或者想投的招聘网站, 挑一个你真的会申请的岗位. 具体到公司, 不要写成某家
   科技公司这种说法.
2. 回答一句话: **这家公司靠什么赚钱?** 不是它的产品叫什么, 是钱从哪儿进来.
3. 写下这家公司里做分析的人**每周真的会问的三个问题**. 判据是这个问题必须要跨至少两类
   数据才回答得了. "上个月卖了多少" 不合格, "哪个渠道进来的客户续约率最低, 低多少" 合格.
4. 把这四样东西存成一个文件, 放在仓库的 `tmp/` 目录下 (那个目录不进 Git), 叫
   `my-target-domain.md`.

**你会观察到:**

第三步比前两步难得多. 大多数人写到这里会发现自己对这个行业的了解, 停留在 "它是做什么的"
这一层, 说不出它每天在为哪几个数字发愁.

> **关键洞见:** 这个卡住的地方, 正是这门课真正的价值所在. 技术那部分脚手架已经替你做完
> 了, 剩下要你自己补的就是这三个问题背后的东西.

### 练习 2: 数一数换领域要重写多少字

**目标:** 亲眼确认 "会变的东西集中在一个目录" 这句话是真的.

**怎么做:**

1. 打开 `data/site.toml`, 从头扫到尾. 每看到一句只有放贷这行才会说的话, 就在心里记一笔.
2. 打开 `data/business-context.md` 和 `data/system-prompt.md`, 同样扫一遍.
3. 然后随便打开 `components/chat/chat.tsx` 和 `agent_app/one/one_02_db.py`, 在里面找一句
   跟放贷有关的话.

**你会观察到:**

前三个文件里几乎每一段都是行业特有的, 后两个文件里一句都找不到. 这条线不是自然形成的,
是被一堆检查和纪律撑住的.

| 概念 | 一句话 |
| :--- | :--- |

## 12. 导师寄语

**为什么这一篇值得认真读:**

我见过太多人把作品集项目做成技术展示: 用了多少个时髦框架, 部署在几朵云上, 代码有多少行.
然后在面试里被问一句 "你为什么做这个", 答不上来.

一个项目真正的说服力, 来自它解决的问题是不是真的. 而 "真的" 这件事无法靠技术弥补, 只能靠
你花时间去理解一门生意. 这门课把技术成本压到几乎为零, 就是为了逼你把时间花在那个地方.

**关键洞见:**

- 会写代码不再是差异, 判断力和针对性才是. 判断力体现在你知道哪些地方不能凑合
- 一个作品只能投一次, 一个脚手架每次投递都能长出一个新作品
- 这个仓库里所有看起来 "多余" 的纪律, 都是在保护那个一到两小时

**下一步:**

接下来的第 3 篇 (开工之前的四门前置课) 不教新东西, 它是一道闸门: 这门课默认你已经会用
mise, Vercel, DBeaver 和一个云端 Postgres, 那一篇把这四样各指向一门课, 会的跳过, 不会的
先去补.

## 13. 速查

**这门课的落点:**

一个部署在公网上, 针对某个具体岗位的 AI Agent 应用, 加上一套能反复换领域的脚手架.

**换领域要动的文件:**

- `dataset/`: 数据本身与描述这个领域的源文档
- `data/site.toml`: 界面上说的每一句话
- `data/business-context.md`: 首页那个长说明
- `data/system-prompt.md`: agent 的领域大脑
- `.env.defaults`: 一行 `SCHEMA_NAME`

**换领域不动的地方:**

- `agent_app/`: 后端全部代码
- `app/`, `components/`, `lib/`: 前端全部代码
