# 模块化设计

> 这篇讲这个仓库被切成了什么样, 每条边界划在哪, 以及破了会怎样. 路径会随重构变动,
> **理由基本不变** —— 读的时候记理由, 别记路径.

## 模块化在这里要同时办四件事

模块化本身不是目的. 这个仓库把边界划得比一般项目更硬, 是因为有四件事同时压在这些边界上,
而它们恰好指向同一种切法.

**一, 换领域.** 最核心的一件, [01](01-what-this-project-is.md) 里那个"1 到 2 小时换掉
整个业务领域"就是它. 会变的东西必须能被整体替换, 不变的部分在替换时一行都不该动.

**二, 学生往一个方向深挖时只动一层.** [01](01-what-this-project-is.md) 列了六个深化方向:
BA 加分析框架, SWE 补 Ops, DE 做数据管道, DS 上模型, AIE 拆 MCP, UX 深化交互. 这六件事
落在六个不同的层上. 层与层之间接口清楚, 一个人才能在自己那层里放开改, 而不需要先读懂整个
仓库 —— 复用 80% 的现成代码, 精力全花在那 20% 的增量上, 前提就是这 80% 不会被碰到.

**三, 教学.** 一层可以单独拿出来讲, 单独练. 而且教学材料本身也是一层: 它整块住在自己的
目录里, 交付前能被干净擦掉, 见 [02](02-teaching-and-production.md).

**四, 让 AI 改东西时有明确边界.** 这条最容易被低估, 但它在这个仓库里是日常.

给 AI 一个任务, 它的成败很大程度上取决于"要改的地方是不是一句话能说清". 界面上所有文案
都在 `data/site.toml` 一个文件里, 任务就是"打开这个文件改"; 文案散在二十个组件里, 任务
就变成"全仓库搜一遍, 判断哪些该改哪些不该", 而这件事**每次都会漏, 而且漏得不报错**.

同一件事在 review 时反过来起作用: 一次换数据集的 diff **应该只落在 `data/`, `dataset/`
和 `.env.defaults` 里**. 落到别处就是信号 —— 不用逐行读也知道有东西越界了. 边界清晰的
仓库, 改动的形状本身就是一种检查.

`CLAUDE.md` 里那张"改什么就改哪个文件"的表, 存在的理由就是这一条.

## 0. 一条总原则

> **随数据集变的东西, 和随脚手架不变的东西, 必须分开存放.**

变的部分要能被整体替换, 不变的部分在替换时一行都不该动. 下面几节是这条原则在几个地方
的具体落法.

判断一个新东西该放哪, 就问一句: **换个业务领域, 它要不要改?** 要改 -> 归数据集; 不改 ->
归脚手架. 答案是"看情况"的, 说明它其实是两个东西粘在一起了, 先拆开再放.

**还有一条正交的轴**: 它是这个 app 的一部分, 还是教怎么造这个 app 的一部分? 那条轴单独
一篇, 见 [02](02-teaching-and-production.md). 两条轴一起看, 一个新文件的位置基本就定了.

---

## 1. 数据分离: 所有会变的内容, 一个目录

```
data/
├── site.toml             前端读: 界面上说的每一句话
├── business-context.md   首页那个"这解决什么问题"弹窗的正文
├── system-prompt.md      agent 的领域大脑
```

**换数据集 = 重写这一个目录, 外加 `dataset/` 和 `.env.defaults` 里的一行 `SCHEMA_NAME`.**

数据本体不在 `data/` 里: 它在 `dataset/`, 由那个目录里的生成器造出来, 而且不进 Git
(见 [03](03-the-dataset.md)). 这是整个设计里最重要的一条边界.

`data/` 里**没有配置**, 全是人写的内容: 文案, 提示词, 解释. 那唯一一行配置留在
`.env.defaults` 而不是搬进来, 是因为那个文件是按"是不是密钥"切的, 而这条边界还管着另一件
事: AI 能不能改它. 详见第 5 节.

**不要按类型把它们分开放** —— 配置一个目录, 提示词一个目录, 文案一个目录, 种子在仓库根.
那种布局下每样东西都待在"和它同类的东西"旁边, 代价是一次替换变成散落全仓库的 diff, 没有人
能一眼确认"改全了没有".

唯一的例外是**写操作的 `@tool`**: 它在 `agent_app/one/one_04_agent.py` 里, 因为那是代码
不是内容. 一个数据集需要写操作时, 在那里加方法.

### 按读者切, 不按主题切

`site.toml` 只有 TypeScript 读, 后端一个字节都不碰它; 后端的配置在 `.env.defaults`.
**不要把它们合成一个文件**: 两个运行时读的 key 集合完全不重叠, 合起来只是两份不相关的配置
钉在一起, 而且会逼着其中一个运行时去解析它根本不需要的格式.

所以规矩是: **加一个值之前, 先问哪个运行时消费它.** 如果答案是"两个都要", 把这件事说
出来, 因为今天没有任何一个值是这样.

## 2. 前端配置: 一份契约, 加载时校验

`site.toml` 是 TOML 而不是 TypeScript, 这是一个**有代价的选择**, 值得说清楚.

写成 `.ts` 字面量的话编译器会免费帮你查字段和图标名, TOML 没有这个. 换来的是"数据集的全部
产出集中在一个目录", 而后者更值: 编译期检查是在**写的时候**帮你一次, 目录集中是在**每一次
替换和每一次 review** 时帮你.

编译器不查, 就由加载时来查 (`lib/site/`):

| 文件 | 干什么 |
| :--- | :--- |
| `lib/site/schema.ts` | `SiteConfig` 类型 + `REQUIRED_SITE_KEYS` 必填清单 |
| `lib/site/load.ts` | 解析 TOML, 查必填 key, 查图标名, 两者都 throw |

**两个检查都在 `next build` 时真的会拦住构建** —— 少一个 key 会报出 key 名, 图标名拼错会
报出坏名字和全部合法名字. 所以换完数据集必须跑一次 `mise run build-web`, 光跑
`mise run cli-check-content` 查不到这两样.

`load.ts` 是 **server only** (读文件系统), 所以 `site` 是在 server component 里加载, 然后
**当 props 传进 client component** 的. 这不是麻烦, 是边界: client 组件不许自己去读配置,
它只能接收.

## 3. 首页模块化: 同一份内容, 两处渲染

首页和 agent 页展示的是**同一组四条业务主线**, 来自 `site.toml` 里唯一的一份
`[[capabilities]]`, 由共享组件渲染:

```
components/CapabilityCard.tsx     一条业务主线, 首页和 chat 页共用
components/ConceptTooltip.tsx     概念名背后那段白话解释的气泡
components/BusinessContextModal.tsx  把 business-context.md 渲染成弹窗
```

**不要给"这个页面稍微不一样"复制一份配置.** 两份配置描述同一组东西, 迟早会各走各的: 同一
条主线在两个页面上起了不同的名字, 配了不同的图标, 只有一边有说明 —— 而这种漂移不会有任何
测试失败, 因为两边各自都是合法的配置.

**一份数据两处渲染, 漂移在结构上就不可能发生.** 一份数据两份配置, 漂移是迟早的事.

`BusinessContextModal` 走的是 chat 页那个同一个 Markdown 渲染器, 所以
`business-context.md` 里写 ` ```mermaid ` 围栏就真的会画出图, 而且自动享有懒加载和
`securityLevel: "strict"`. 弹窗组件本身完全不知道"图"这个概念的存在.

## 4. chat 模块化: 围栏块的查找表

agent 说的每句话都是流式文本, 页面上看到的几乎所有东西 —— 表格, 流程图, 图表, 高亮的
SQL —— 都是从那段文本渲染出来的. 开关是一张查找表:

```typescript
// components/chat/blocks/index.ts
const BLOCK_RENDERERS: Record<string, ComponentType<BlockProps>> = {
  mermaid: MermaidBlock,
  chart: ChartBlock,
}
```

**加一行支持一种块, 删一行关掉一种.** 没在表里的语言全部落到 `CodeBlock` 兜底.

这里的模块边界有一个容易被忽略的部分: **前端认得一个格式, 不等于模型会输出它.** 所以
"加一种块"是三步, 第三步在后端:

1. 写渲染器组件
2. 在查找表里加一行
3. **在 `data/system-prompt.md` 里告诉 agent 什么时候产出这种块**

跳过第三步的结果是渲染器一行代码都跑不到, 而前端测试全绿.

同一份契约还有第三半: `site.toml` 里那 12 条 kickstart 问题, 每条带一个 `render` 字段和
一句触发短语. `mise run cli-check-content` 双向校验它们. 细节见 [06-rendering-contract.md](06-rendering-contract.md).

## 5. 后端模块化: 包名本身就是承诺

Python 包叫 `agent_app`, 不叫 `smb_lending_anything`. 这个名字是故意起得通用的, 它的含义
是一句承诺: **换数据集时, `agent_app/` 下面一行都不用改.**

支撑这句承诺的是几层拆分:

| 位置 | 职责 |
| :--- | :--- |
| `agent_app/paths.py` | 所有路径, 集中一处. 路径是源码树的事实, 所以不进配置 |
| `agent_app/config.py` | 读 `.env` 和 `.env.defaults`, 是后端唯一的配置入口 |
| `agent_app/one/one_0*.py` | 按关注点切开的 mixin: 配置, 数据库, boto3, agent |
| `agent_app/sql_utils.py` | 纯函数, 拿 `engine` 当第一个参数, 不依赖类 |
| `agent_app/db_schema/` | 把库结构编码成 LLM 好读的紧凑格式 |

### 两种"config"绝不能混

后端的配置分两个文件, 判据是一句话: **它是密钥吗?**

- `.env` 装密钥, 不进 Git. Claude Code 里由 `.claude/settings.json` 的 deny 强制; Antigravity 没有项目级 settings 文件, 这条只能靠纪律
- `.env.defaults` 装其余一切 (含 `SCHEMA_NAME`), 进 Git, AI 可以自由编辑

这条线之所以值得, 是因为它决定的是**谁能打开这个文件** —— 轮换 API key 不该碰到 schema 名,
换数据集不该碰到任何人的凭据. 完整的表, 加载优先级, 以及部署到 Vercel 之后的形态,
见 [07](07-config-and-content.md).

### 通用代码里不许出现本数据集的例子

在 `agent_app/` 或 `scripts/` 里写注释举例时, 不要用当前数据集的表名. 写
`# e.g. the "loan" table` 这种例子, 等于把这个数据集焊进了通用代码 —— 换数据集之后它
不报错, 不失败, 只是变成一句谎话躺在那里.

用永远虚构的占位领域 (`acme` / `widget` / `part`), 它们不属于任何真实数据集, 所以永远
不会过期.

## 6. 数据: 源材料一个目录, agent 只读一个地方

数据这一侧被切成两段, 各自一篇:

- **数据怎么造出来** —— `dataset/` 装一个数据集的全部源材料和生成器, 产物不进 Git,
  靠命令重建. 见 [03](03-the-dataset.md)
- **agent 从哪读** —— 任何环境下都是同一个 PostgreSQL, 本地也一样; 隔离靠 schema 而不是
  表名前缀, 所以**表名两边一模一样**. 见 [05](05-why-postgres-everywhere.md)

这里只留一句在模块化语境下最要紧的: **表名一致是全部设计目标.** 隔离用 schema, **不要给表
加前缀** (`smbll_loan` 那种) —— 加了之后 agent 看到的表名就取决于背后是哪个引擎, 于是提示词
里每段 SQL 例子在一个环境对在另一个环境错, 而且没有任何东西会报错.

## 7. 边界靠什么守住

模块化设计不会自己维持, 它要么被机械检查守住, 要么慢慢烂掉. 现在守着的是三条命令:

```bash
mise run cli-check-content     # 建表顺序 / 提示词表名 / 内容文件 / kickstart 渲染配额
mise run test      # Python 单元测试
mise run build-web     # site.toml 的必填 key 和图标名, 只有这里查得到
```

每一项具体拦住什么, 机械检查盖不住的部分怎么人工验, 以及"什么该自动检查什么不该"的判据,
全在 [08-what-guards-the-boundaries.md](08-what-guards-the-boundaries.md).

## 8. 重构时请守住的东西

这一节是给**接下来那次重构**看的. 路径可以改, 下面这些边界不要破:

1. **`data/` 是一个整体.** 别把某个数据集相关的文件挪回代码树, 也别把脚手架代码放进 `data/`.
2. **`agent_app/` 换数据集时一行不改.** 任何让它需要改的设计, 都是把数据集焊进了代码.
3. **两种 config 不合并.** 密钥和数据集身份是两件事.
4. **一份数据, 多处渲染.** 别为了"这个页面稍微不一样"复制一份配置.
5. **渲染契约的三半要一起动.** 渲染器 / 提示词 / kickstart 配额, 改一个就得改另外两个.
6. **通用代码里不出现真实表名.**
7. **教学层和生产层不混.** 教学的东西整块放, 别塞进生产路径要用的文件. 见 [02](02-teaching-and-production.md).
8. **代码不引用教学文档.** 单向: 文档可以引代码路径, 代码不能引文档路径.
9. **改了结构就改这篇文档**, 在同一个 commit 里.
