# SQL 怎么执行, 只读怎么保证

> 一组纯函数, 拿 `engine` 当第一个参数, 不依赖任何类. 它只守一个承诺: **经过这里的查询
> 改不了数据库** —— 而守住它的不是那个字符串检查, 是事务永远回滚.

**对应代码**: `agent_app/sql_utils.py`

**依赖**: 无, 只用 SQLAlchemy. 使用者是 [08](08-the-one-object.md) 的 `DbMixin` 和
[11](11-dataset-pipeline.md) 的同步.

---

## 这个模块只有一个承诺

> **经过 `execute_sql_query` 的查询改不了数据库.**

保证靠的**不是**那个字符串检查, 而是**事务永远回滚**. 一条溜过检查的写操作照样执行, 但它
跑在一个没人提交的事务里, 落不到磁盘.

这个保证零成本 (SQLAlchemy 2.0 不自动提交), 不需要额外依赖, 而且对所有方言都成立 —— 不像
"给数据库用户去掉写权限"那种要运维配合的做法.

代码里那句 `conn.rollback()` 是**显式写出来**的, 而不是交给 context manager 隐式回滚:
一个在代码里看不见的安全保证, 下一次重构就会有人顺手加个 commit 把它删掉.

### 两个方言级的坑

**SQLite**: pysqlite 靠嗅探语句第一个关键词来决定要不要开事务, 而它**不认识 `WITH`** ——
一条 CTE 打头的写操作会跑在 autocommit 里, 落盘, 没有东西可回滚. 所以 SQLite 引擎必须由
`new_sqlite_engine()` 打开: 关掉 `isolation_level` 让驱动别猜, 自己发 `BEGIN`.

这个函数住在 `sql_utils.py` 而不是和别的引擎放一起, 就是因为它存在的全部理由是撑住上面那
条保证. **保证在一个文件, 让保证成立的配置在另一个文件, 下一次重构删掉它不会有任何东西
报错. **

**MySQL**: DDL 隐式提交, 回滚不了. 这个仓库不用 MySQL, 但换库时要知道.

## 为什么不用关键词黑名单

`ensure_valid_select_query` 只有一条规则: 必须以 `SELECT` 或 `WITH` 开头.

黑名单 (禁 `DELETE` / `DROP` / `UPDATE` ...) 是很自然的想法, 但它把查询当字符串读, **分不
清代码和数据**:

- 它会拒绝完全合法的 `WHERE note = 'do not delete'`
- 它同时挡不住藏在一条合法 `SELECT` 里的危险东西

而每一次误拒都要烧掉一整轮模型往返, 还会把模型推向更奇怪的 SQL 去绕过它 —— 两种失败里更
糟的那种.

`WITH` 放行是因为**但凡稍微复杂的分析都是 CTE**. SQLite 确实接受 `WITH x AS (...) DELETE`,
所以这条能溜过去 —— 溜过去之后被事务丢掉, 这正是上面那条保证的用武之地.

那个字符串检查真正的作用不是安全, 是**给模型一条快而可读的错误**: 写了 `UPDATE` 的模型
立刻知道该换成什么, 而不是收到一条驱动异常.

## 失败一律返回文本, 从不抛异常

调用方是一个 LLM 工具. 抛异常会终结这一轮对话; 返回一句描述问题的话, 模型能自己改 SQL
重试.

所以三类失败都变成字符串:

```
Error: this agent is read-only, start with SELECT or WITH
Error executing query: <驱动的原话>
Error formatting result: ...
```

驱动报错用的是 `e._message()` 而不是 `str(e)`. 那是 SQLAlchemy 的**私有 API**, 但
`str(e)` 会附上完整 SQL, 绑定参数和一条 `sqlalche.me` 文档链接 —— 每次写错查询白烧几百个
token. 万一将来的 SQLAlchemy 拿掉这个方法, 退回 `str(e)` 即可, 工具会变啰嗦但不会坏.

---

## 结果为什么是 Markdown 表格

比 JSON 省大约四分之一的 token, 更贴近模型训练时见过的样子, 而且人打开日志排查时能直接读.

浮点用 `.4f` 固定宽度, 否则一列金额会变成参差不齐的 repr 噪声.
