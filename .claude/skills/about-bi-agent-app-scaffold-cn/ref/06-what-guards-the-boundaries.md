# 边界靠什么守住

模块化设计不会自己维持. 它要么被机械检查守住, 要么慢慢烂掉. 这篇是现在守着的全部东西,
以及一条决定"什么该自动检查什么不该"的判据.

---

## 三条命令, 查的东西不重叠

```bash
mise run check     # 建表顺序 / 提示词表名 / 内容文件 / kickstart 渲染配额
mise run test      # Python 单元测试
npx next build     # site.toml 的必填 key 和图标名, 只有这里查得到
```

**三条都要跑.** 最常见的漏是只跑前两条 —— 于是一个拼错的图标名安静地渲染成兜底图标, 卡片
看着好好的, 就是配错了图.

`mise run check` 的四项:

| 检查 | 拦住什么 |
| :--- | :--- |
| 建表顺序 | `tableInsertOrder` 和 SQLite 种子对不上, 两个方向都验 |
| 提示词表名 | 提示词 SQL 例子里 `FROM` / `JOIN` 了一张不存在的表 |
| 内容文件 | `data/` 下该有的文件缺失或者只是个残桩 |
| 渲染配额 | 12 条 kickstart 的 `render` 和它自己的措辞对不上, 或者四类不是各 3 条 |

`npx next build` 的两项都在 `lib/site/load.ts` 里, 都会 throw:

| 检查 | 拦住什么 |
| :--- | :--- |
| `REQUIRED_SITE_KEYS` | `site.toml` 少一个必填 key (报出 key 名) |
| `assertIconsExist` | `icon` 不在 `lib/icons.ts` 里 (报出坏名字和全部合法名字) |

---

## 机械检查盖不住的, 靠这几步人工

### 提示词里每段 SQL 对着真库跑一遍

必须走 PostgreSQL, 不能拿本地 sqlite 验. 跑不通的例子比没有例子更糟, 模型会照抄.

顺带这一步能暴露"语法对但公式写错" —— 结果数字明显不对就能看出来.

### 数据体检

对象是 SQLite 种子 (同步是逐行复制, 种子干净则线上干净, 而且 SQLite 的
`PRAGMA foreign_key_list` 拿孤儿行比写 PostgreSQL 等价查询省事). 顺序上先体检再同步, 别把
脏数据发上去再回头查.

查三样机械可判的: 空表, 孤儿外键, 日期越界 (落在 1990-2035 之外的多半是造数脚本出了问题).

剩下靠眼睛看一遍核心指标算出来的数字, 标准是**不出现一眼假的结论**: 比率落在这个行业说得
过去的区间 (不是 0% 也不是 80%), 分档之间的排序符合常识, 金额没有负数.

这个标准到此为止 —— 不需要逐行对账, 不需要和源文档统计量严格吻合.

### 12 条 kickstart 必须手点

**配额脚本只能证明问法写对了, 证明不了模型照做了.** 逐条点一遍, 确认 3 条出表格加 SQL,
3 条出流程图, 3 条出图表. 出不来最常见的原因是提示词里 `Rendering Triggers` 那节被精简过.

### 旧领域词汇扫描

换完数据集跑一次, 词表是一次性参数不提交:

```bash
mise run check -- --retired "loan,lending,borrower,default_event,risk_grade"
```

填**上一个数据集最有辨识度的名词**. 这一点要挑: 拿 `node` 这种通用词去扫, 报出来的全是
mermaid 文档里的正常用词.

## 判据: 什么该自动检查

> **判据本身机械可判吗?**

- "这 12 条里有没有恰好 3 条写了 `as a flowchart`" —— 字符串计数, 值得写成脚本
- "这 12 条问得好不好" —— 自然语言语义, 只能做成模糊匹配, 必然产出一堆需要人工判断的
  warn, 最后没人看

后一类**不加检查**, 改用**顺序**来防. 提示词先写, 下游的 kickstart 问题, 能力卡, 首页
文案, 业务说明都只从提示词改写, 不回头读原始数据集文档. 每一步只从上一步的产物推导, 漂移
就无从发生.

**顺序是零成本的, 检查是有成本且不可靠的.**

## 检查脚本自己也会误报

这件事值得单独记一笔, 因为它发生过, 而且当时的结论是错的.

`mise run check` 的"提示词表名"那一项曾经扫**整个提示词文件**找 `FROM x` / `JOIN x`. 它分
不清散文和 SQL, 于是提示词里一句正常的说明 —— "写 `EXTRACT(QUARTER FROM d)` 而不是
`strftime`" —— 被判成查了一张叫 `d` 的表, 构建失败.

当时留在文档里的对策是"换个说法". 那是错的: 那节 SQL 方言说明**必须**提到
`EXTRACT(... FROM ...)`, 绕着写等于让文档迁就工具的缺陷.

正确的修法是把扫描收紧到 ` ```sql ` 围栏块内部, 并跳过带点的名字
(`FROM l.disbursement_date` 是列不是表). 改完假阳性归零, 真错依然抓得到.

**教训**: 当一个检查逼着你把内容写歪, 先怀疑检查, 不要怀疑内容.

---

## 一条给重构的提醒

上面每一条检查都硬编码了一些路径 (`data/` 下的文件名, `lib/site/schema.ts` 的位置, 提示词
里的节标题). 重构挪文件时, **检查脚本和这些文档要在同一个 commit 里跟着改**.

一份描述着三个月前目录结构的规范, 比没有规范更糟: 它会让下一个人自信地改错地方.
