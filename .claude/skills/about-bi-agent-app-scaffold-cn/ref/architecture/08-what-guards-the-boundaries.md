# 边界靠什么守住

> 前面几篇划的边界不会自己维持, 它们要么被机械检查守住, 要么慢慢烂掉. 这篇把每条边界和
> 守它的那个东西对上, 说明哪些边界**根本没有机械检查**, 以及新增一项检查前该问什么.

## 每条边界, 谁在守

| 边界 | 出处 | 谁在守 |
| :--- | :--- | :--- |
| 生产路径不 import 教学层 | [02](02-teaching-and-production.md) | `TestNotOnTheProductionPath` (AST 扫 import) |
| 种子的外键要有插入顺序, 而且不能一张表都没有 | [03](03-the-dataset.md) | `mise run check` |
| 提示词里的 SQL 例子不能查不存在的表 | [07](07-config-and-content.md) | `mise run check` |
| `data/` 下该有的内容文件不能缺 | [07](07-config-and-content.md) | `mise run check` |
| kickstart 的 `render` 和它自己的措辞要对上 | [06](06-rendering-contract.md) | `mise run check` (双向) |
| `site.toml` 必填 key 不能少, 图标名必须存在 | [07](07-config-and-content.md) | `npx next build` |
| 后端各模块的行为 | [04](04-modular-design.md) | `mise run test` |
| **`agent_app/` 换数据集一行不改** | [04](04-modular-design.md) | **没有检查** —— 靠 review diff 的落点 |
| **模型真的照着提示词产出渲染块** | [06](06-rendering-contract.md) | **没有检查** —— 只能手点 |
| **提示词的 SQL 在真库上跑得通** | [05](05-why-postgres-everywhere.md) | **没有检查** —— 只能自己跑一遍 |

后三行是这篇真正想说的事: **最贵的三条边界都没有机械检查.** 前面那些能自动化, 是因为它们
的判据机械可判; 后面三条不是. 下面分开讲.

---

## 能自动查的: 三条命令, 都要跑

```bash
mise run check     # 建表顺序 / 提示词表名 / 内容文件 / kickstart 渲染配额
mise run test      # Python 单元测试, 含教学层边界那条 AST 检查
npx next build     # site.toml 的必填 key 和图标名, 只有这里查得到
```

**最常见的漏是只跑前两条.** 于是一个拼错的图标名安静地渲染成兜底图标 —— 卡片看着好好的,
就是配错了图, 而且没有任何东西会说一句.

`mise run check` 的四项:

| 检查 | 拦住什么 |
| :--- | :--- |
| 建表顺序 | 种子的外键成环 (没有任何插入顺序能满足), 或者种子里一张表都没有 |
| 提示词表名 | 提示词 SQL 例子里 `FROM` / `JOIN` 了一张不存在的表 |
| 内容文件 | `data/` 下该有的文件缺失或者只是个残桩 |
| 渲染配额 | 12 条 kickstart 的 `render` 和它自己的措辞对不上, 或者四类不是各 3 条 |

`npx next build` 的两项都在 `lib/site/load.ts` 里, 都会 throw:

| 检查 | 拦住什么 |
| :--- | :--- |
| `REQUIRED_SITE_KEYS` | `site.toml` 少一个必填 key (报出 key 名) |
| `assertIconsExist` | `icon` 不在 `lib/icons.ts` 里 (报出坏名字和全部合法名字) |

## 查不了的三条, 各有各的替代品

### 1. 提示词的 SQL —— 自己对着真库跑一遍

**必须走 PostgreSQL**, 不能拿本地 SQLite 验. 理由是 [05](05-why-postgres-everywhere.md)
一整篇: 一段 SQLite 方言的例子在本地永远绿, 在线上永远错, 而且**不报错, 只是答案变差**.

跑不通的例子比没有例子更糟, 因为模型会照抄然后在用户面前失败. 这一步还顺带能暴露"语法对
但公式写错" —— 结果数字明显不对就能看出来.

### 2. 模型照不照做 —— 12 条 kickstart 必须手点

**配额脚本只能证明问法写对了, 证明不了模型照做了.** 逐条点一遍, 确认 3 条出表格加 SQL 高亮,
3 条出流程图, 3 条出图表.

出不来最常见的原因是提示词里 `Rendering Triggers` 那节被精简过 —— 那是三半契约里最容易被
当成冗余删掉的一半.

### 3. 上一个数据集的残留 —— 一次性词汇扫描

换完数据集跑一次, 词表是命令行参数, **不提交**:

```bash
mise run check -- --retired "loan,lending,borrower,default_event,risk_grade"
```

填**上一个数据集最有辨识度的名词**. 挑词要挑准: 拿 `node` 这种通用词去扫, 报出来的全是
mermaid 文档里的正常用词, 你会学会忽略这个检查的输出.

数据库那边的残留是另一回事: 上一个数据集的表不会被新的同步碰到 (同步只管本 schema 里的表),
会一直占着 Neon 的配额. 见 [05](05-why-postgres-everywhere.md) 的体积预算一节.

### 还有一项在别处: 数据体检

空表, 孤儿外键, 日期越界 —— 这三样机械可判, 但它们查的是**新造出来的那份数据**, 属于换
数据集的流程而不是这个仓库的常驻检查. 脚本和判据在 `swap-dataset-cn` skill 里, 对象是
SQLite 种子而不是线上库 (同步是逐行复制, 种子干净则线上干净), 而且**先体检再同步**.

## 判据: 什么该做成自动检查

> **判据本身机械可判吗?**

- "这 12 条里有没有恰好 3 条写了 `as a flowchart`" —— 字符串计数, 值得写成脚本
- "这 12 条问得好不好" —— 自然语言语义, 只能做成模糊匹配, 必然产出一堆需要人工判断的
  warn, 最后没人看

后一类**不加检查**, 改用**顺序**来防: 提示词先写, 下游的 kickstart 问题, 能力卡, 首页文案,
业务说明都只从提示词改写, 不回头读原始数据集文档. 每一步只从上一步的产物推导, 漂移就无从
发生.

**顺序是零成本的, 检查是有成本且不可靠的.** 一个会误报的检查比没有检查更糟, 因为它会训练
人忽略输出.

## 检查脚本自己也会写错

这件事值得单独记一笔, 因为它发生过, 而且当时给出的对策是错的.

`mise run check` 的"提示词表名"那一项曾经扫**整个提示词文件**找 `FROM x` / `JOIN x`. 它
分不清散文和 SQL, 于是提示词里一句正常的说明 —— "写 `EXTRACT(QUARTER FROM d)` 而不是
`strftime`" —— 被判成查了一张叫 `d` 的表, 构建失败.

当时留在文档里的对策是"换个说法". 那是错的: 那节 SQL 方言说明**必须**提到
`EXTRACT(... FROM ...)`, 绕着写等于让内容迁就工具的缺陷.

正确的修法是把扫描收紧到 ` ```sql ` 围栏块内部, 并跳过带点的名字
(`FROM l.disbursement_date` 是列不是表). 改完假阳性归零, 真错依然抓得到.

**教训**: 当一个检查逼着你把内容写歪, 先怀疑检查, 不要怀疑内容.

## 要加一项检查的时候

先过一遍上面那条判据 —— 机械可判吗? 能不能改用顺序防住?

确定要加, 那么它属于 `mise run check` 还是 `mise run test`, 判据是**它查的是内容还是代码**:
查 `data/` 和 `dataset/` 里人写的东西, 进 `scripts/test_00_check_project_config.py`; 查
`agent_app/` 的行为, 进 `tests_python/`.

还有一条容易忘的: 上面每一项检查都**硬编码了路径** (`data/` 下的文件名, `lib/site/` 的
位置, 提示词里的节标题). 重构挪文件时, **检查脚本和这几篇文档要在同一个 commit 里跟着改**.

一份描述着三个月前目录结构的规范, 比没有规范更糟: 它会让下一个人自信地改错地方.
