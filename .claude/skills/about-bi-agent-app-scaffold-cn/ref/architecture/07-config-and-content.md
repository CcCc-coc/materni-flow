# 配置与内容: 什么进环境变量, 什么进 `data/`

> 这个仓库要人填的东西分两类, 走两条完全不同的路: **后端配置**是环境变量, 从 `.env` 和
> `.env.defaults` 一路走到 Vercel; **领域内容**是 `data/` 一个目录里的三个文件, 换领域就是
> 重写它. 这篇讲两边各自装什么, 每个字段对应屏幕上的哪块东西.

## 两条路, 别走串

| | 后端配置 | 领域内容 |
| :--- | :--- | :--- |
| 载体 | `.env` + `.env.defaults` (环境变量) | `data/` 下的 `site.toml`, `business-context.md`, `system-prompt.md` |
| 谁读 | Python (`agent_app/config.py`) | 前端 TypeScript, 和 agent 的提示词 |
| 是什么 | 连接信息, 开关, 上限, 数据集标识 | 人写的文案, 解释, 领域知识 |
| 换数据集要动吗 | **只动一行** (`SCHEMA_NAME`) | **全部重写** |
| 线上怎么到位 | Vercel 的 Environment Variables + 随部署带上去的 `.env.defaults` | 跟着代码一起部署 |

**`data/` 里没有配置.** 里面每一个字节都是人写的内容. 一个新东西该往哪放, 就问它是"设置"
还是"文案" —— 设置进 `.env.defaults`, 文案进 `data/`.

完整的执行顺序 (换数据集时先写哪个后写哪个, 为什么) 在 `swap-dataset-cn` skill, 这篇只讲
**形状**.

## 后端配置: 两个文件, 按"是不是密钥"切

| | `.env.defaults` | `.env` |
| :--- | :--- | :--- |
| 装什么 | `SCHEMA_NAME`, LLM provider 和 model, region, DB 端口, 整块配额设置 | API key, AWS 密钥, 数据库 host/user/password/name |
| 是密钥吗 | 不是 | **是** |
| 进 Git 吗 | **进** | 不进 |
| AI 能读吗 | 能 | **不能** —— `.claude/settings.json` 里 `deny` |
| AI 能改吗 | 能, 换数据集改的就是它 | **不能** |
| 加载顺序 | 后加载, 补空缺 | **先加载, 优先** |

判据就一句: **它是密钥吗?**

**另一条看着也讲得通的切法是"会不会因为换台机器而不同".** 不要用它: 按那条线切, 数据集的
身份 (一个字符串) 会被切成第三个配置文件, 于是要为它养一个格式和一个读取模块. 按密钥切的
这条线能挣回成本, 因为它决定的是**谁能打开这个文件**, 包括 AI 能不能.

所以: 轮换一个 API key 不该碰到 schema 名; 把仓库指向一个新数据集不该碰到任何人的凭据.

**没有 `.env.defaults.example`, 这是故意的.** 那个文件本身进 Git, 它**就是**模板. 搞成
"gitignore 加模板"的话, `SCHEMA_NAME` 就跑到版本控制外面去了, 每次 clone 都要重填一遍,
而且 AI 换数据集的改动不会出现在 diff 里 —— 那正好是这套设计想要的反面.

### 优先级是三层, 最上面那层在 Vercel

```
Vercel 的 Environment Variables      最高, 因为它在进程启动时就在 os.environ 里
        ↓
.env                                 本机的密钥和覆盖
        ↓
.env.defaults                        committed 的默认值, 补空缺
```

底层机制是一句话: `load_dotenv` **不覆盖已经设过的变量**. 所以先读 `.env` 再读
`.env.defaults`, 前者就自动成了覆盖层; 而 Vercel 注入的变量比两个文件都早, 于是它赢在最
上面.

**部署时只有密钥需要手填.** `.env` 不进 Git, 所以它那些值要在 Vercel 的面板里逐个录进
Environment Variables. `.env.defaults` 进 Git, **跟着部署一起上去**, 所以 `SCHEMA_NAME`
这类值不用在面板里重录一遍. 想在线上临时改一个非密钥值, 在面板里加同名变量即可, 它压过
文件.

这个覆盖是**设计**, 不是逃生舱: 它发生在同一个配置系统内部, 只有一个读取者, 而且优先级是
写死的. 真正禁止的是同一个值躺在两个**不同的**配置系统里 —— 那种情况没有谁覆盖谁的规则,
只有两个都得记得改.

### `SCHEMA_NAME` — 换数据集唯一要改的配置

```bash
SCHEMA_NAME="..."   # 小写字母/数字/下划线, 首字符不能是数字, <= 63 字符
```

它是**这个数据集唯一的标识符**, 同时干两件事: 隔离共用 Neon 实例里的表 (见
[05](05-why-postgres-everywhere.md)), 以及给 `agent_app/quota.py` 的月度花费分区当 key.
**不要为后半件事另起一个短名字**: 一个东西两个名字, 就是两个要同步维护的东西.

规则由 `Config.__post_init__` 里的 `SCHEMA_NAME_PATTERN` 在**启动时**强制执行, 写错当场
报错, 不会拖到某条查询深处才炸.

**建表顺序不用配, 它是算出来的.** `table_insert_order()` 直接读 SQLAlchemy 的
`metadata.sorted_tables`, 那本来就是按外键做的拓扑排序. 加一张表不需要改任何配置 —— 而一份
手写的顺序表是一个可能抄错的值, 还要再加一个检查去防它抄错.

## `site.toml` — 界面上说的每一句话

前端唯一的文案来源. 结构和它在屏幕上对应的位置:

| TOML 段 | 屏幕上是什么 |
| :--- | :--- |
| `[brand]` | 导航栏那个两段着色的 logo (`logoPrefix` + `logoAccent`), 页脚名字 |
| `[seo]` | `<head>` 里的 title / description / keywords, 分享出去时的预览 |
| `[[capabilities]]` × 4 | **首页四张能力卡, 和 agent 页四张洞察卡, 同一份** |
| `[home]` | 首页大标题 / 副标题 / 一段介绍 / 技术栈标签 / 数据规模那行 |
| `[home.headline]` | 大标题拆成两截, 两种颜色 |
| `[home.cta]` | 首页底部那个大按钮 |
| `[home.businessContext]` | 打开说明弹窗那个按钮的文字, 和弹窗的标题副标题 |
| `[chat]` | agent 自称的名字, 欢迎语, 输入框 placeholder, 建议提示 |
| `[chat.messages]` | 对话上方那条 banner, 限额提示, "上一条还在跑"提示 |
| `[[chat.suggestedActions]]` × 12 | 输入框上方那 12 个 kickstart 按钮 |

### 三条硬约束

**一, 必填 key 会在 build 时拦住你.** `lib/site/schema.ts` 的 `REQUIRED_SITE_KEYS` 列了每个
必须存在的 key, `lib/site/load.ts` 在解析时逐个查, 少一个就抛异常并报出 key 名. 因为 TOML
不被编译器检查, 缺一个 key 的后果是组件收到 `undefined` 然后在线上渲染成一个空标题.

**二, 图标名会在 build 时拦住你.** `icon` 必须是 `lib/icons.ts` 里注册过的名字.
`assertIconsExist` 会报出坏名字和全部合法名字. 不查的话, 拼错的图标会静默渲染成兜底图标 ——
卡片看着好好的, 就是配错了图, 没人会注意到.

**这两个检查只在 `npx next build` 时跑**, `mise run check` 查不到. 换完数据集两个都要跑.

**三, TOML 数组表的坑.** 一旦开始 `[[...]]` 数组, 后面每个裸 key 都属于该数组的最后一个
元素. 所以每一节的普通字段必须写在 `[[...]]` 之前. 写反了不报错, 只会静默错位.

### `[[capabilities]]` 只有一份

四条业务主线, 首页和 agent 页渲染的是**同一份**, 共享 `components/CapabilityCard.tsx`.

每条三段:

- `title` — 概念名. 对内行精确, 对其他所有人等于没写
- `subtitle` — 一句白话. 陌生人先读到的是这句
- `tooltip` — 两三句解释, hover / 键盘聚焦 / 手机点按时弹出

**tooltip 里不许再有黑话.** 用一个内行词去解释另一个内行词, 是这个字段存在的意义所反对的
那件事.

**不要因为两个页面尺寸不同就写两份.** 两份配置描述同一组东西迟早会各走各的 —— 同一条主线
起了不同的名字, 配了不同的图标, 只有一边有 tooltip —— 而且不会有任何测试失败, 因为两边各自
都合法. **一份数据两处渲染, 漂移在结构上就不可能发生.**

### `[[chat.suggestedActions]]` 恰好 12 条, 四类各 3 条

这是渲染契约的一半, 完整规则见 [06-rendering-contract.md](06-rendering-contract.md).
要点:

- 第 1 条固定是 Introduction / "What can you do?", `render = "free"`
- 其余 11 条逐条对着提示词的 `## Analysis Index` 改写成用户口吻
- **挑不出来说明提示词覆盖不够, 回去补提示词, 不要在这里现编**

最后这条是纪律: **提示词定义能力边界, 下游只能换措辞, 不能新增一项提示词没教的能力.**

绕开它的方式很自然 —— 12 条 kickstart 直接照着数据集的源文档写, 而不是照着提示词写. 那样
写出来的按钮里会混进几条提示词根本没覆盖的分析, 而**所有测试都会通过**: 问法合法, 配额也对,
只有用户点下去的时候模型才开始即兴发挥.

## `business-context.md` — 首页那个说明弹窗

普通 Markdown, 走的是 chat 页同一个渲染器, 所以里面写 ` ```mermaid ` 围栏会真的画成图.

**它讲的是这个 App, 不是这个数据集.** 露出去的是"一份数据加一个能查它的 agent", 但读者
真正需要知道的是这个 App 替谁解决什么问题. 标题走"the business behind the agent"这个调子,
不要写成"the business behind the data".

**两条硬要求**: 写给完全不懂这行的陌生人看, 只靠常识能读完; 讲行业不讲雇主, 讲问题不讲
项目 (不出现实习 / 公司名 / 课程 / 作业这类痕迹).

**六节结构**, 前三节讲世界, 后三节讲这个 App 在这个世界里干什么:

1. 这门生意怎么赚钱
2. 钱从哪里悄悄漏掉 —— **全篇重心**, 每条都要回答"为什么它不会自己暴露"
3. 这些事在数据里长什么样
4. agent 拿这些数据做什么
5. 你可以问什么, 以及怎么读答案
6. 只读之外 (本 App 不含)

第 6 节要同时说清三件事, 少一件就变成吹牛: 这个 App 是**故意**只读的; 同一套架构可以挂写
操作的 tool; 真上写操作的前提是**权限护栏**和**可审计轨迹**. 第三点不能省, 少了它这节读
起来就是"我们还能让 AI 乱改数据".

**两个格式约束**:

- 整份最多一张 mermaid 图, 十个节点以内. 判据很简单: 如果这张图只是把上一句话又说了一遍,
  那就删图留话. 第二张图一定是装饰
- **HTML 注释会被加载器剥掉再渲染**, 所以可以放心在文件里写批注. `react-markdown` 没装
  `rehype-raw`, 不解释 HTML —— 不剥的话 `<!-- 给下一个作者的说明 -->` 会原样打印成弹窗里
  的一段正文

## `system-prompt.md` — agent 的领域大脑

结构大致是:

| 节 | 装什么 |
| :--- | :--- |
| 身份和工具 | 你是谁, 有哪几个 tool |
| `## Core Domain Concepts` | 这个行业的基本规则, 外行会猜错的那些 |
| `## Analysis Index` | **源文档每条分析一行, 一条都不能漏** |
| `## Derived Business Concepts` | 从 Index 里挑出外行会算错的, 给精确公式和 SQL |
| `## Table Relationships` | 怎么 JOIN |
| `## Key Status Codes` | 状态码取值 |
| `## SQL Dialect` | PostgreSQL 方言清单, 见 [05](05-why-postgres-everywhere.md) |
| `## SQL Patterns` | 这个领域常用的查询骨架 |
| `## Response Guidelines` | 回答的组织方式 |
| **渲染层五节** | **逐字抄, 只换例子**, 见 [06](06-rendering-contract.md) |
| `## Safety` | 只读, 不许写 |

### 覆盖靠索引, 篇幅靠取舍

`## Analysis Index` 必须覆盖源文档里的每一条分析, 每条一行说清它回答什么问题. 但只有其中
**外行会算错的**那些才值得在 `## Derived Business Concepts` 里展开成公式和 SQL.

这两件事不要混为一谈: 索引管的是"能不能被问到", 展开管的是"会不会算错".

### 写完必须把每段 SQL 对着真库跑一遍

**而且必须走 PostgreSQL**, 不能拿本地 sqlite 验 —— 一段 SQLite 方言的例子在本地永远绿, 在
线上永远错, 而且不报错只是答案变差. 完整理由见 [05](05-why-postgres-everywhere.md).

跑不通的例子比没有例子更糟: 模型会照抄, 然后在用户面前失败. 这一步还会顺带暴露"语法对但
公式写错" —— 结果数字明显不对就能看出来.

### 一个和检查脚本打架的坑

`mise run check` 会扫提示词里 ` ```sql ` 块中 `FROM x` / `JOIN x` 的表名, 确认它们真的存在.
它扫的是围栏块内部, 所以散文里写 `EXTRACT(QUARTER FROM d)` 不会误报. 但如果你在 SQL 例子
里用了 CTE, 记得检查脚本认得 `WITH name AS (` 这种自定义名字, 不会把它当成缺失的表.

## 前端文案的写法规范

这一节管 `site.toml` 和 `business-context.md` 里每一个会显示给用户的字符串. 不管代码注释,
不管提示词.

**第一条: 不要用破折号.** 不要用 `—`, 也不要用 `--` 当停顿. 这是最容易暴露"AI 写的"的一个
特征, 因为模型极其偏爱用它来塞补充说明, 一段话里出现三四次是常态, 而人类文案很少这样写.

破折号出现的地方通常说明这句话本来就该断开. 三种改法: 断成两句; 换成逗号从句; 把补充说明
挪进另一个字段. 标题里非要分隔就用冒号.

**第二条: 叙述性语言, 简单格式.** 用完整句子把事情讲清楚, 不要写成关键词罗列. 允许的格式
只有加粗, 标题, bullet. 不要表格, 不要嵌套列表, 不要 emoji, 不要行内代码块 (那是给开发者
看的, 这里的读者不是).

**第三条: 数字要现场数出来.** `home.blurb` 里的表数和行数, 此刻从数据库数, 不要抄旧值也
不要估. 这一句恰好摆在读者判断"这 demo 有多真"的位置, 而一个差着一倍的行数比不写更糟.
