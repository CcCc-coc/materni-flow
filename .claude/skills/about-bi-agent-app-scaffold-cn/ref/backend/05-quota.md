# 月度花费上限

> 按自然月统计调用次数和 token 数, 到顶就在花钱之前拒绝新的一轮. **默认关闭**, 它是给
> 公开部署用的 —— 付钱的人和打字的人不是同一个人的那种场合.

**对应代码**: `agent_app/quota.py`

**依赖**: `config` ([02](02-config.md)), `utils` ([01](01-leaves.md)). DynamoDB client 由
调用方注入, 所以这个模块不依赖 `one`.

---

## 为什么存在

一个谁都能打开的 chat agent 是一张敞开的账单: 每条消息都在花某人云账号里的钱. 这个模块
按自然月统计调用次数和 token 数, 到顶就拒绝开始新的一轮.

**默认关闭.** 本地跑的人花的是自己的额度, 不需要上限; 而且打开它需要一张 DynamoDB 表, 那
张表在有人去建之前并不存在. 它是给**公开部署**用的 —— 付钱的人和打字的人不是同一个人的
那种场合.

---

## 什么可配, 什么不可配

**可配** (随部署变, 在 `.env` / `.env.defaults`): 开关, 表名, 三个上限.

**不可配** (写死在代码里): 那四个 DynamoDB 属性名, 以及 partition key 的形状.

partition key 是三段, 用 `:` 分隔:

```
learn-bi-agent-app-scaffold : fintech_smb_lending_pipeline_medium : 2026-08
        脚手架                          数据集                        月份
```

- **脚手架** = `SCAFFOLD_ID` 常量. 它标识**这个代码库**, 换数据集不变, 所以既不该进
  `dataset` 配置也不该进 `.env` —— 按仓库的判据 (换个业务领域要不要改?), 不改就归脚手架,
  也就是代码里的一个常量. 只有 fork 或重命名脚手架时才动它.
- **数据集** = `config.schema_name`. 那正是随数据集变的东西, 而且它本来就必须全局唯一
  (不唯一就撞别的项目的表).
- **月份** 让新的一个月自动从零开始, 不需要任何人去重置.

用 `:` 而不是 `-` 拼接, 是因为 slug 里有连字符, schema 名里有下划线, 用 `-` 粘会造出
"看不出名字在哪结束"的歧义. 现在这个 key 能 `split(":")` 拆回三段, 在控制台里能读.

**曾经有第二个标识符.** `data/dataset.toml` 里的 `[project] name = "smbll"` 也在做这件事,
那是表名前缀时代的残留 —— 前缀退役之后它唯一的工作就是当配额 key. 一个东西两个名字, 就是
两个要同步维护的东西, 所以合并到了 `schema_name`.

一张 DynamoDB 表可以装很多个部署的计数器, 理由和一个 Postgres 库可以装很多项目的表一样.

## 开关和失败策略都住在这个模块里

两个入口 (`check_quota` / `increment_usage`) **自己检查 `quota_enabled` 并提前返回**, 所以
调用方不需要包 `if`. 这一条以前不是这样: `api/index.py` 在两处各写了一遍
`if one.config.quota_enabled:`, 于是开关住在使用者那里, 而不是住在拥有这个功能的模块里 ——
第二个调用方只要忘了那个 `if`, 拿到的就是一次真实的 DynamoDB 调用.

同理, **计量出故障绝不能拒绝服务**: DynamoDB 挂了, 表不存在, 凭证过期 —— 这些都在模块内部
记一笔日志然后咽掉, 而不是让每个调用方各写一遍 `except Exception: pass`. 少记一次数, 比让
一个用户已经付过钱的回复失败要便宜.

唯一会往外抛的是 `QuotaExceededError` —— 那是**答案**, 不是故障. 它在 try 块之外抛出, 所以
永远不会被上面那层吞掉.

## 配错在启动时就报, 不等第一个用户

"打开了配额但没配表名"这件事, 检查在 `Config.__post_init__` 里. 以前它在 `quota._table`
里, 于是一个配错的公开部署**启动完全正常**, 直到有人打第一个字才炸.

## 为什么是裸 boto3 而不是 ORM

item 只有四个属性, 而且不会再多. ORM 在这里只会换来三个依赖. `boto3` 本来就是核心依赖.

每个函数都显式接收 `dynamodb_client` 和 `config`, 而不是去抓 `one` 单例. 这让这个模块可以
单独 import, 让测试能拿一个假 client 驱动它, 也避免为了读三个数字而再建一个 `Config`.

**接收的是 client 不是 session.** client 在 `one_03_boto3.py` 的 `dynamodb_client()` 里建,
所以这个模块**从头到尾看不到 session, 也就够不到任何别的 AWS 服务** —— 依赖注入注进来的是
它需要的那一个东西, 不是一把万能钥匙.

用的是低层 client API 而不是 resource API, 代价是要自己处理类型标签: 读回来的数字长成
`{"N": "42"}` (字符串, 带类型标签), 写进去也要 `{"N": str(n)}`. `_counter()` 负责把它转回
`int` —— 调用方要拿它和 int 上限比大小, 拿字符串比会抛异常.

## 测试用 moto, 不用手写的桩

`tests_python/test_quota.py` 跑在 **moto** 上 —— 一个进程内的 DynamoDB 实现 —— 而不是手写的
桩对象. 这个区别在这里是实质性的:

**手写的桩断言的是作者对 API 形状的信念.** 如果你以为写进去的是 `{":i": 1}` 而实际要
`{":i": {"N": "1"}}`, 那么代码和桩会一起错, 测试照样绿, 上线才炸. moto 跑的是真实现:
验证过, 无标签的写法会被 `ParamValidationError` 当场拒掉.

它还让两件事**第一次可以被断言**:

- **计数器真的在累加.** 桩只能记录"update_item 被调用了", moto 会真的执行 `ADD`. 三次
  increment 之后读回来是 3 —— 这正是不用 read-then-write 的理由 (并发下丢更新), 以前没有
  任何测试证明过它成立.
- **故障是真故障.** "计量出错不能拒绝服务"那几条现在指向一张**不存在的表**, botocore 抛的
  是它真正会抛的 `ResourceNotFoundException`, 而不是桩被吩咐去抛的东西.

fixture 里塞了假的 AWS 凭证, 所以配错也够不到真账号.
